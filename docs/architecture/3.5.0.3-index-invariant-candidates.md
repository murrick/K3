# KANGER 3.5.0.3 — Index invariant candidates

## Purpose

This note records behavioral and invariant risks discovered while auditing `Index.java` for dead code. None of these items is part of the `3.5.0.1` cleanup manifest. They require dedicated regression evidence before any implementation change.

Source:

```text
kanger-data-dumb/src/org/kanger/storage/Index.java
```

## I1 — `IndexOne.compareTo` narrows a `long` difference to `int`

Current implementation:

```java
@Override
public int compareTo(IndexOne indexOne) {
    return (int) (id - indexOne.getId());
}
```

The ordering relation is not valid for the full `long` ID domain. A non-zero `long` difference whose low 32 bits are zero is narrowed to `0`, and sufficiently large differences may reverse sign after truncation.

This can violate the `Comparable` contract:

```text
compareTo(a, b) == 0 while a.id != b.id
sign(compareTo(a, b)) may not equal sign(a.id - b.id)
```

No current `TreeMap` in `Index` uses `IndexOne` as its key, so immediate runtime impact is not established. The public inner type nevertheless declares `Comparable<IndexOne>`, making the behavior externally observable to implementation-level callers.

**Classification:** invariant/API defect candidate — defer to `3.5.0.3`.

**Potential correction:** `Long.compare(id, indexOne.getId())`.

**Required evidence before correction:**

1. regression over negative, positive, boundary, and >32-bit-distance IDs;
2. check for callers depending on subtraction-style overflow behavior;
3. source/binary compatibility confirmation.

## I2 — `firstKey()` calls `NavigableMap.firstKey()` before checking emptiness

Current implementation:

```java
public long firstKey() {
    if (baseIndex.firstKey() != null) {
        return baseIndex.firstKey();
    } else {
        return -1;
    }
}
```

`NavigableMap.firstKey()` does not return `null` for an empty map; it throws `NoSuchElementException`. Therefore the apparent `-1` empty-index fallback is unreachable.

The method's effective current contract is:

```text
non-empty index -> first key
empty index     -> NoSuchElementException
```

Changing this to return `-1` would alter observable behavior, even if the existing code likely intended that sentinel.

**Classification:** invariant/contract mismatch candidate — defer to `3.5.0.3`.

**Required evidence before correction:**

1. identify all direct and indirect callers;
2. capture current empty-index behavior in a regression;
3. decide whether the architectural contract is sentinel or exception;
4. update `lastKey()` and iterator behavior consistently if needed.

## I3 — empty index iteration returns `null` iterator

`IndexIterator(boolean)` initializes itself with:

```java
blockId = backward ? baseIndex.lastKey() : baseIndex.firstKey();
loadBlock(baseIndex.get(blockId), block);
```

On an empty index, construction throws. Both public iterator factories catch the exception and return `null`:

```java
@Override
public Iterator<IndexOne> iterator() {
    try {
        return new IndexIterator(false);
    } catch (Exception e) {
        return null;
    }
}
```

Consequently, `Index` implements `Iterable<IndexOne>` but does not provide a valid empty iterator for an empty collection. Enhanced-for or ordinary iterator consumers may receive a `NullPointerException` rather than an iterator whose `hasNext()` returns `false`.

The behavior is observable and may be relied upon by existing defensive callers, so it is not cleanup.

**Classification:** collection-contract/invariant candidate — defer to `3.5.0.3`.

**Required evidence before correction:**

1. regression for forward and backward iteration over an empty index;
2. inspect recovery/integrity code that explicitly checks `index.isEmpty()` before calling `iterator()`;
3. inspect external implementation-level callers;
4. define whether iterator factories may ever return `null`.

## Stage boundary

These findings must not be folded into dead-code removal commits.

```text
3.5.0.1: remove only proven unreachable code and historical debris
3.5.0.3: establish intended Index contracts, add regressions, then correct proven invariant violations
```

This separation preserves the governing rule that `3.5.0` cleanup must not hide observable semantic changes.
