# KANGER 3.5.0.3 — `User.currentMind` invariant audit

## Scope

This note resolves the `User.currentMind` candidate transferred from the
3.5.0.2 naming/lifecycle audit.

Audited surfaces:

```text
kanger/src/org/kanger/User.java
kanger/src/org/kanger/interfaces/IUser.java
kanger-console/src/org/kanger/Kanger.java
kanger-console/src/org/kanger/Console.java
kanger-console/src/org/kanger/ShutdownHook.java
```

## Implementation

`User` contains one mutable slot:

```java
private IMind currentMind = null;
```

exposed directly through:

```java
IMind getCurrentMind()
void setCurrentMind(IMind currentMind)
```

The accessors perform no validation, ownership transfer, cleanup, publication,
or synchronization.

## Lifecycle evidence

The active KANGER runtime does not use this slot as its lifecycle authority.

### Bootstrap and console session

`Kanger.main(...)` constructs a `Mind` into a local variable and passes that
reference to `Console.session(...)`.

`Console.session(...)` continues to hold and replace the active transaction/root
reference locally. Storage use, close, clear, drop, reindex, transaction commit,
and transaction rollback all return the effective `IMind`, which is assigned
back to that local variable.

The console does not publish these replacements through
`IUser.setCurrentMind(...)`.

### User storage lifecycle

`User.clear(IMind)`, `User.close(IMind)`, `User.use(IMind, String)`,
`User.remove(IMind, String)`, and `User.reindex(...)` all receive the relevant
Mind explicitly and return the effective Mind explicitly.

They do not read or update `currentMind`.

### Shutdown

`ShutdownHook` flushes and calls:

```java
user.close(null)
```

It does not consult `currentMind`.

Therefore shutdown persistence and storage cleanup do not depend on this slot.

## Reconstructed contract

The only contract demonstrated by production source is:

```text
currentMind = caller-managed public compatibility slot
```

It is not proven to be:

```text
current root Mind
current transaction level
current console-session Mind
a storage-lifecycle owner
a shutdown cleanup root
an authoritative runtime publication pointer
```

The name is broader than the implementation, but the implementation itself is
not an invariant violation.

## Retention question

Because the slot holds a strong `IMind` reference until explicitly replaced, an
external caller can retain an old or closed Mind by storing it there.

That is not currently a demonstrated internal leak:

- KANGER runtime code does not populate the slot;
- storage lifecycle does not rely on the slot;
- console replacement does not update the slot;
- shutdown ignores the slot.

Automatically clearing or replacing it during `use`, `close`, `clear`, commit,
or rollback would introduce a new coupling between an existing public mutable
property and internal lifecycle operations. Such behavior is not authorized in
3.5.0.3 without an external API contract and regression corpus.

## Invariant decision

Retain the current implementation unchanged.

The invariant is:

> `User.currentMind` is not authoritative KANGER lifecycle state. Internal
> storage, transaction, session, and shutdown code must continue to operate from
> explicit Mind references rather than infer ownership or cleanup from this
> compatibility slot.

Consequences:

1. no automatic publication into `currentMind`;
2. no automatic clearing on storage close;
3. no cleanup traversal rooted from `currentMind`;
4. no rename in 3.5.0 because the methods are public `IUser` compatibility
   surface;
5. architectural and API Javadoc must describe the slot as caller-managed unless
   a future version deliberately assigns it stronger semantics.

## Classification

```text
production defect: not demonstrated
internal lifecycle authority: no
public compatibility surface: yes
retention capability: caller-controlled
production change in 3.5.0.3: none
documentation debt: transfer to 3.5.0.5
```

```text
KangerFactory.connection ownership / close authority
```

That candidate requires checking the shared factory protocol across all factory
