# KANGER 3.5.0.2 — Data cache and diagnostic naming audit

## Scope

This audit reviews the naming/lifecycle surface already proven live in DUMB `Data` during `3.5.0.1`.

No executable change is made here.

## Established ownership

`Data` owns:

- persisted block access;
- hydration through `readOne(...)`;
- its in-memory cache and cache-weight accounting;
- read/write diagnostic counters;
- write-through, flush, and eviction interaction through `DataOne.saveBlock()`.

The cache state is owner-local implementation state. The counters are owner-local diagnostics, but their methods are public implementation-level compatibility surfaces.

## Private cache helpers

### `addToCache(...)`

Role:

- publishes one loaded or written entry into the owner-local cache;
- participates in cache lifecycle and weight accounting.

Classification:

```text
retain — name already matches effect
```

No lifecycle ambiguity is evident. `add` is appropriate because this is container insertion, not canonical registration or semantic linking.

### `cacheWeight(...)`

Role:

- computes or retrieves the cache-accounting weight used by the owner-local cache policy.

Classification:

```text
retain — no demonstrated naming defect
```

A rename would be stylistic only unless the exact return semantics prove that the method measures, estimates, or mutates weight. No N1 action is justified from current evidence.

### `clearCacheState()`

Role:

- clears owner-local cache bookkeeping/state at a lifecycle boundary;
- does not remove persisted data or destroy the `Data` owner.

Classification:

```text
retain — lifecycle verb is correct
```

`clear` is the correct vocabulary: the object remains usable, while transient cache state is emptied. Replacing it with `reset`, `release`, or `close` would be less precise.

## Public diagnostic counters

### `getReadCounter()` / `getWriteCounter()`

Role:

- expose accumulated owner-local storage diagnostics.

Classification:

```text
N3 — public compatibility-sensitive naming surface
```

The names are conventional and do not require change in `3.5.0.2`.

### `dropReadCounter()` / `dropWriteCounter()`

Observed role:

- clear/reset accumulated diagnostic counts;
- do not remove a counter object, unregister diagnostics, or drop persisted storage.

Terminological issue:

`drop` suggests destruction or structural removal. The actual lifecycle operation appears to be a reset-to-zero operation.

Preferred vocabulary, pending source verification:

```text
resetReadCounter()
resetWriteCounter()
```

Classification:

```text
N3
```

Reason:

- methods are public;
- external diagnostics or qualification code may call them;
- renaming would be source-incompatible;
- compatibility aliases would enlarge the API and are not automatically justified in a zero-behavior-change consolidation release.

Action for `3.5.0.2`:

```text
retain existing methods
record terminology debt
do not add aliases
```

A later API-versioned change may introduce `reset*` terminology and deprecate `drop*` only if external compatibility policy is explicit.

## Other public implementation surfaces

The following remain compatibility-sensitive and are not mechanical naming candidates:

```text
getUncached
getVersion
isClosed
getFile
setMaxCacheSize
iterator
DataOne accessors
```

Each requires caller and API-contract analysis before any rename. In particular, `getUncached` may describe an access mode rather than an object property, and must not be renamed without reading its exact side effects and counter behavior.

## Result

No private N1 rename is confirmed in the `Data` cache helper surface.

```text
addToCache       -> retain
cacheWeight      -> retain/U
clearCacheState  -> retain
get*Counter      -> retain/N3
 drop*Counter    -> N3 terminology debt; reset* is semantically preferable
```

The useful finding is negative but precise: the private lifecycle vocabulary is already coherent. The visible defect belongs to the public compatibility surface and must not be smuggled into mechanical cleanup.
