# Rule implementation passport review

Status: review artifact for later transfer into `org.kanger.units.Rule` type-level Javadoc.

## Architectural role

`Rule` is the concrete canonical knowledge unit used by KANGER to represent either a stored assertion or a compound logical rule. The class owns the materialized domain tree, origin reference, provenance causes and runtime projections required by inference.

The interface contract in `IRule` defines the public semantic surface. This passport records implementation-specific lifecycle and mutation rules that are not visible from the interface alone.

## Inside — stable definition state

The stable Rule definition contains:

- operational Rule ID;
- owner/materialization Mind ID;
- origin Term ID;
- rule-local variable-index boundary;
- branch/domain tree;
- assertion/compound-rule shape;
- generated/query/stored/substitutable/abstractive classification;
- provenance causes;
- referenced Predicate and Term IDs.

The logical definition is not identical to its source text, comment, debug rendering or current deletion projection.

## Outside — contextual projections

The following state is contextual to a Mind or execution pass:

- transaction-visible deletion;
- restored status;
- query and generated classification where mutation is permitted;
- current solves;
- used-rule membership;
- hydrated Domain objects;
- comments;
- native-rule discovery;
- diagnostic rendering;
- current provenance validity.

These projections may change without changing canonical Rule identity.

## Guarded direct mutation

`Rule` may be shared by parent and child Minds. Direct mutation of fields such as `query` and `generated` is permitted only when:

- no Mind is attached;
- the attached Mind is the top/root execution context; or
- the Rule belongs to the current Mind transaction.

The helper `canMutateDirectly()` enforces this boundary. A child Mind must not mutate parent-owned Rule state in place; child-specific changes belong in transactional overlays.

Invariant:

```text
parent-owned Rule definition
    !=
child-local mutable projection
```

## Tree hydration and ownership

Persistent form stores branch/domain IDs. `getTree()` lazily hydrates those IDs through the owning Mind and reconstructs the Domain graph.

Hydration may also populate derived Predicate references. It does not create a new logical Rule, and an unhydrated tree does not mean the Rule is absent.

`setMind()` propagates the selected Mind to hydrated Domains. This selects the context for visibility, lazy resolution and representation; it does not redefine Rule identity.

## Assertion versus compound rule

A Rule marked by the historical `stored` flag behaves as a single assertion and exposes statement-level operations through its first Domain:

- antecedent polarity;
- Predicate;
- arguments;
- assertion rendering.

For a compound rule these statement-only operations are invalid and raise `RuntimeErrorException`.

Historical note:

```text
stored Rule
    = assertion-shaped Rule
    != physical database I/O state
```

## Identity and structural equality

Several identities coexist:

- `equals()` / `hashCode()` use operational Rule ID;
- `getHash()` computes a structural candidate hash;
- `equalsTo(IRule)` compares branch/domain structure independent of branch ordering;
- `equalsTo(IHypothesis)` and `equalsTo(Solve)` compare context-specific statement projections.

Therefore:

```text
operational ID
    != structural equality
    != hypothesis compatibility
    != solve compatibility
```

A hash match is only a candidate filter and never proves semantic equality.

## Origin and representation

`origin` is the source-level provenance text represented by a Term. It is not canonical Rule identity.

`toString(IMind)` selects between origin and assertion-domain rendering according to Rule shape and may append debug status markers. It is diagnostic/human-readable output, not persistence or identity representation.

Comments are stored separately in the Mind comment registry and never participate in Rule equality or inference semantics.

## Provenance

`causes` records derivational provenance for generated knowledge. `packCauses()` removes causes whose donor or receiving Rule is absent/deleted in the supplied Mind.

This is provenance maintenance, not Rule deletion and not logical identity mutation.

Invariant:

```text
origin text != provenance graph
provenance cleanup != deletion of Rule identity
```

## Transaction and lifecycle semantics

- `query` marks a Rule introduced by the current query workflow.
- `generated` marks a Rule produced by inference.
- `stored` is the historical assertion-shape marker.
- `restored` is determined by Mind transaction state, not by a persistent Rule field.
- `second` is a duplicate/secondary runtime classification and not canonical identity.

These classifications must not be conflated.

## Deletion propagation

`setDeleted(on, mind)` changes transaction-visible deletion for the Rule and propagates the same projection to:

- the Rule comment, when present;
- every Domain in the hydrated rule tree.

Deletion does not physically destroy the Rule, its origin, Domain graph or operational ID. It remains available for rollback, restoration and canonical reuse according to factory contracts.

```text
deleted Rule != nonexistent Rule
```

## Variable ownership

`getTVariables()` discovers TVariables whose `ruleId` equals this Rule ID. The Rule owns the variable definitions logically, while their current TValue bindings belong to a Mind execution projection.

`varIndex` is the rule-local normalization boundary used by Function and Domain structural comparisons. It is not a global variable identity.

## Primitivization

`primitivize()` converts argument structures to base representations only when direct mutation is allowed. It is synchronized because it rewrites the materialized Domain argument graph.

The operation changes representation shape for execution compatibility; it must preserve logical Rule meaning.

## Persistence

Persistent representation contains IDs, classification flags, branch/domain IDs and packed causes. Hydration reconstructs runtime object links lazily.

Storage representation is not canonical logical identity:

```text
serialized Rule != logical Rule identity
hydrated Domain graph != creation of new Rule
```

## Caller obligations

Callers must:

- use statement-level accessors only for assertion-shaped Rules;
- provide the correct Mind for visibility and hydration;
- avoid direct parent-state mutation from child transactions;
- treat `getTree()` and collections as implementation-owned mutable structures;
- distinguish operational equality from structural and contextual comparisons;
- preserve provenance and deletion propagation invariants.

## Key invariants

```text
Rule identity != origin text
Rule identity != comment
Rule identity != diagnostic rendering

assertion shape != physical storage state
parent-owned Rule != child-local mutation

operational ID != structural equality
hash match != equality proof

hydration != creation
deleted != nonexistent
restored != generated
query != generated

origin != provenance
provenance cleanup != Rule deletion

Rule-owned TVariable definition
    !=
Mind-owned current TValue binding
```
