# Solve, Argument and ArgumentsList — architectural review

Status: review artifact for later transfer into production Javadoc.
Scope: documentation and diagnostic observations only; no runtime behavior is changed.

## 1. Architectural placement

`Solve`, `Argument` and `ArgumentsList` form the projection layer between a stable semantic atom and its current execution state.

```text
Predicate definition
        +
polarity
        +
ordered argument references
        =
Solve-shaped predicate call
```

`Domain` adds persistent identity, Rule ownership and Mind-local execution state to this base representation.

The three primitives have different responsibilities:

- `Solve` defines the shape of a predicate call;
- `Argument` is one typed reference slot inside that shape;
- `ArgumentsList` owns the ordered graph and derives current base/stamp projections.

They are not independent canonical semantic units.

---

# 2. Solve

## Architectural role

`Solve` is the non-persistent structural base of a predicate call. It binds:

- Predicate identity;
- polarity (`antc`);
- arity;
- ordered `ArgumentsList`.

It is inherited by `Domain`, which supplies persistent identity, Rule ownership and transactional lifecycle.

## Inside

Stable structural state:

```text
predicateId
range
antc
ordered argument references
```

## Outside

Context-dependent projections:

- hydrated Predicate object;
- current values of arguments;
- U-witness display names;
- operator-style rendering registered in `Parser`;
- term-closure traversal through nested Functions.

## Identity and comparison

The following relations must remain distinct:

```text
Solve structural shape
    != Domain operational identity
    != current argument values
    != textual rendering
```

`getHash(IMind)` is a current value-sensitive candidate hash. `hashCode()` uses argument reference IDs. Neither is a proof of semantic equality.

## Rendering

`toString(Mind, ArgumentsList, boolean)` is a diagnostic/source-like projection. It may:

- choose prefix, postfix or infix syntax from runtime Parser registration;
- expose current argument values;
- assign temporary display names to U-witnesses when rendering the right side.

It is not a persistence protocol and must not define canonical identity.

## Persistence

`pack()` stores Predicate ID, arity, polarity and serialized argument references. Hydration restores reference shells; it does not imply that Predicate or argument objects are loaded.

# 3. Argument

## Architectural role

`Argument` is a typed reference slot. It stores the identity of one base object and resolves its current value relative to a supplied `Mind`.

```text
Argument object reference
        !=
resolved current Term value
```

## Supported reference kinds

```text
TERM
TVARIABLE
TVALUE
FUNCTION
FVALUE
EMPTY
```

The stored `ArgumentType` determines both hydration factory and value-resolution path.

## Inside

Stable slot state:

- referenced object ID;
- `ArgumentType`;
- rule-relative `varOrder` used by structural normalization.

The hydrated object reference is a cache of that identity, not a separate semantic value.

## Outside

Context-dependent behavior:

- lazy object hydration through Mind factories;
- resolution of TVariable to current TValue/Term;
- resolution of Function to current FValue result;
- transaction-visible deletion of the referenced object;
- diagnostic rendering.

## Mutation semantics

`setValue(Mind, ITerm)` is polymorphic:

```text
EMPTY / TERM
    replace direct Term reference

TVARIABLE
    canonicalize/select TValue for the supplied Term

FUNCTION
    write transient result slot and invoke Calculator when calculable
```

Therefore `setValue()` is not a uniform field setter and may cause inference/execution side effects.

## Empty and deleted

```text
EMPTY reference != unresolved current value
unresolved current value != deleted referenced object
```

`isEmpty(Mind)` asks whether the current value resolves to `null`; it does not ask whether the slot has an object identity.

# 4. ArgumentsList

## Architectural role

`ArgumentsList` is the ordered argument graph and the projection engine used by `Domain`, `Function` and `Solve`.

Its primary responsibility is not collection storage but conversion between four views:

```text
definition references
current object projections
base Term projection
ordered substitution stamp
```

## Definition view

The list preserves argument order and reference kind. Order is semantically significant for Predicate arity, Function inputs and structural comparison.

## Current projection — `convert(Mind)`

`convert()` projects definitions to current runtime objects:

- TVariable -> current TValue;
- Function -> current FValue;
- direct/value arguments -> current Term.

This is an execution projection and may contain `null` references when no current materialization exists.

## Base projection — `convertBase(IMind)`

`convertBase()` resolves every argument to its current Term and wraps those Terms as direct arguments.

This representation is used as a Mind-local key for:

- Domain causes;
- Domain solves;
- used state;
- excluded state.

```text
base projection != original argument graph
```

It deliberately removes the distinction between a definition reference and the Term currently obtained from it.

## Stamp — `getStamp(Mind)`

A stamp is the ordered list of current Term values of all recursively contained TVariables.

It is used for produced/calculated state and FValue applicability.

`getStamp()` requires complete substitutions and throws `ParametersIncompleteException` otherwise.

```text
stamp != ArgumentsList
stamp != base projection
stamp order is significant
```

## Stamp application

`applyStamp()` selects already canonical TValue objects for the listed Terms. It does not create arbitrary values when `find()` cannot locate a compatible canonical substitution.

## Equality families

`ArgumentsList` exposes several distinct comparison modes:

```text
equals()
    current positional value compatibility plus TVariable provenance

equalsBase()
    direct value compatibility with parent/child U-witness lineage

equalsStamp()
    exact ordered current TVariable values
```

These are not interchangeable.

## Recursive discovery

The list recursively discovers:

- Functions;
- TVariables;
- U-witness Terms;
- TValues;
- referenced Terms.

The `total` flag controls whether definition metadata such as Function names and TVariable names is included in term closure.

## Ownership

`ArgumentsList` does not own canonical entities. It owns only order and references/projections. Deletion and lifecycle authority remain with the referenced units and the active `Mind`.

# 5. Cross-object invariants

```text
Solve shape != Domain identity
Argument reference != resolved value
ArgumentsList definition != base projection
base projection != ordered stamp
EMPTY != unresolved != deleted
current Function result != Function definition
current TVariable value != TVariable definition
U-witness lineage compatibility != global U-child identity
serialization != canonicalization
```

# 6. Diagnostic observations — not fixed in this documentation commit

The audit exposed three code paths that require a separate diagnostic decision before any behavioral change.

## D1 — `Solve.equals(Object)` condition

Current code enters comparison when:

```java
predicateId matches || range matches
```

This appears broader than the normal structural contract, which would usually require both Predicate and arity compatibility. It may also cast arbitrary non-null objects directly to `Solve`.

No correction is made here. Required follow-up:

1. recover intended historical semantics from callers/tests;
2. add a focused regression runner;
3. fix only in a separate semantic commit if defect is proven.

## D2 — `Solve.applyMap()` key

`createMap()` writes `range`, while `applyMap()` reads `tange`.

This appears to break map round-trip hydration. No correction is made here. Required follow-up: a round-trip regression gate covering Predicate ID, range, polarity and arguments.

## D3 — `Argument.applyMap()` switch fall-through

The type switch has no `break` statements and therefore reaches `default`, leaving `o == null` for all cases.

This appears to prevent nested object hydration from map form. No correction is made here. Required follow-up: per-`ArgumentType` map round-trip tests before a separate behavioral fix.

These observations must not be silently mixed into `3.5.0.6` documentation commits.
