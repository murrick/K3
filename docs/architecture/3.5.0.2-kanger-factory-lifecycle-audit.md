# KANGER 3.5.0.2 — KangerFactory naming and lifecycle audit

## Scope

This note records the first subsystem-level naming/lifecycle review for stage `3.5.0.2`.

The target is the `KangerFactory` object graph together with `KangerFactorySafetyRunner` and any reflection-based diagnostics that observe its private fields.

No executable rename is authorized by this document alone.

## Evidence baseline

The validated `3.4.4.2.3` regression contour includes `KangerFactorySafetyRunner` checks for:

- ownership;
- anchor reset;
- orphan cleanup;
- comment/UDF rollback and commit;
- persistent reopen;
- concurrent child query/commit.

The dead-code audit also established that the safety runner intentionally reflects on the exact private field names:

```text
top
bottom
connection
```

Those strings are therefore part of the current executable specification surface even though the fields themselves are private.

## Lifecycle role reconstructed from the regression contract

`KangerFactory` is not merely an object constructor. It owns and maintains an ordered factory sequence whose anchors and persistence connection survive across multiple creation operations and transaction outcomes.

The minimum observed state model is:

```text
connection
    persistent/storage attachment used by the factory

top
    one boundary anchor of the owned factory sequence

bottom
    the opposite boundary anchor of the owned factory sequence
```

The exact directional interpretation of `top` and `bottom` must be confirmed from source before choosing replacement names. The runner contract proves only that they are lifecycle-significant anchors, not which is logical root, tail, newest, oldest, first, or last.

## Ownership and lifetime

Provisional classification:

```text
KangerFactory instance
    owner: caller / enclosing KANGER context
    lifetime: longer than one query operation

connection
    owner: KangerFactory reference; underlying resource may have an external owner
    lifetime: factory attachment lifetime

sequence anchors
    owner: KangerFactory
    lifetime: current owned sequence state
```

The phrase `connection` is insufficiently precise until the concrete type and close authority are verified. It may mean:

- an owned persistence connection;
- a borrowed storage handle;
- a transaction-capable context;
- an attachment used only for materialization.

Renaming it before establishing ownership would risk encoding a false lifecycle contract.

## Candidate classification

### `top`

Current status:

```text
N2/U
```

Reason:

- private implementation name;
- exact name is consumed through reflection by `KangerFactorySafetyRunner`;
- semantic direction is not yet established;
- an atomic rename would have to update production source and every reflection string in the same commit.

Do not replace with `root`, `head`, `first`, `latest`, or `tail` until traversal and mutation direction are proven.

### `bottom`

Current status:

```text
N2/U
```

Reason:

- same coordinated reflection dependency as `top`;
- its relation to creation order, persistence order, and sequence traversal is not yet proven.

`top` and `bottom` must be audited as one pair. Renaming only one would make the vocabulary less coherent.

### `connection`

Current status:

```text
N2/N4
```

Reason:

- private but reflection-observed;
- the current name describes a mechanism, not ownership or lifecycle;
- the correct replacement depends on whether the resource is owned, borrowed, shared, persistent, transaction-local, or merely an adapter.

This candidate becomes N2 only after source evidence proves the role. Until then it remains N4 because a naming decision could incorrectly imply close authority.

## Required atomic rename boundary

Any accepted rename in this subsystem must update as one mechanical group:

```text
KangerFactory field declaration
all reads and writes in KangerFactory
constructor/initialization assignments
reset/clear/close paths
KangerFactorySafetyRunner reflection strings
factory-chain diagnostics
comments and Javadoc describing the anchors
```

The group must not change:

- anchor initialization values;
- statement order;
- synchronization;
- transaction publication timing;
- rollback cleanup;
- commit behavior;
- persistence bytes;
- reopen reconstruction;
- close ownership.

## Lifecycle vocabulary questions

The source audit must answer these before names are selected:

1. Which anchor is the first logical object in traversal order?
2. Which anchor is the most recently attached object?
3. Are anchors reset to `null`, a sentinel, or a canonical object?
4. Does rollback detach uncommitted objects from both anchors?
5. Does commit append, prepend, or splice a child sequence?
6. Does reopen reconstruct both anchors or only one and derive the other?
7. Is `connection` closed by `KangerFactory`, or only cleared/detached?
8. Can a factory temporarily exist without a connection while retaining an in-memory sequence?
9. Are anchor fields persistent identity, runtime navigation state, or cached derivatives?

## Acceptance regressions

A naming-only checkpoint for this subsystem must preserve all existing `KangerFactorySafetyRunner` scenarios:

```text
ownership
anchor reset
orphan cleanup
comment/UDF rollback
comment/UDF commit
persistent reopen
concurrent child query/commit
```

Reflection failures are considered product regression failures for `3.5.0.2`, not test-only maintenance noise.

## Current conclusion

No `KangerFactory` field is currently classified N1.

The known candidates require coordinated updates:

```text
top        -> N2/U
bottom     -> N2/U
connection -> N2/N4
```

The next evidence step is exact source inspection of construction, mutation, rollback, commit, reset, close, and reopen paths. Until that inspection is available, retaining the existing names is safer than selecting cosmetically attractive but architecturally false replacements.
