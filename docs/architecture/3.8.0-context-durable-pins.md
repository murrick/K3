# Durable direct pins and non-retractable initial publication

17 November 2026, stage 651. Implementation of accepted D07; H4/P1 remain open
for the supported filesystem/device profile and full persistence-fault evidence.

## Two concrete failures before the change

The [positive-revision counterexample](3.8.0-context-exported-pin-model-red-stage651.json)
uses two actual JVMs and different metadata directories. The producer is paused
only after its real CURRENT replacement, before its final barrier. The consumer
uses the unmodified packaged provider and acknowledges Consumer@2 → Producer@2.
No producer-parent barrier occurs after replacement and before consumer ACK.
Under the explicit namespace projection, losing only that unforced producer
name recovers Producer@1; the saved exact pin is unavailable. All other files
and the consumer publication remain intact. This is a persistence-model
counterexample, not an observed ext4 hardware power cut.

A second [live-filesystem counterexample](3.8.0-context-initial-pin-red-stage651.json)
needs no crash projection: a producer exposes an initial marker, then pauses
before confirmation. The consumer saves its exact pin. Injected confirmation
failure makes creation delete the marker and Context metadata. Both fresh R0
and fork R1 lose an already acknowledged consumer pin. Thus stage 650's rule
that a failed fresh-marker barrier may remove its own marker was unsafe.
This stage explicitly supersedes that rule; the original evidence is retained.

## Direct-pin confirmation before consumer publication

DurablePins processes only the exact ConnectionVector stored for the consumer's
next revision and bound by its seal. It does not use the highest staged row,
unsaved working-only connections, or the target's advisory dependencies.
For each direct reference it:

1. Opens and validates that exact target revision and checks Context identity.
2. Forces that selected target's own files, metadata and directory ancestry.
3. Forces the target CURRENT file and namespace entries.
4. Reopens the same exact identity/revision before allowing consumer publication.

Consumer frame barriers precede these checks; the consumer marker changes only
after all direct references have been stabilized. The common helper covers
append, topology/prepared publication and reindex; inherited direct fork pins
and explicit unconfirmed-publication reconciliation use the same operation.
A target barrier refusal before the consumer marker leaves that marker intact
and retains pending intent. It does not create a false uncertain-consumer fence.
Native accepted deltas remain consumed and are checkpointed without resubmission.

No foreign mutable writer lock is acquired. Legitimate writers advance markers
monotonically and retain published generation/vector history. If a writer moves
again concurrently, a stabilized marker at least as new as the selected pin is
enough: a later unforced replacement can revert to that stabilized predecessor,
not below it, under the stated model. This argument excludes explicit external
removal/replacement and requires the qualified profile to honour barriers.

Stabilization performs persistence I/O, not logical edits: target values, pins,
identity, certificates, initialization commands and trust groups do not change.
The target's B/C dependencies remain advisory for a consumer of A. The test
publishes a direct pin to A even when A's declared B is unavailable; B is neither
opened recursively nor repaired/attached. There is no hidden transitive execution.
Target barrier access is required; an inability to establish it is an explicit
refusal, not a weaker successful acknowledgement. Read-only snapshot/query
semantics are not converted into implicit stabilization operations.

## Initial marker visibility is not rollback authority

Initial marker bytes are written and forced under an owned temporary name.
A same-directory hard link installs the final name without replacing an existing
entry, then the temporary entry is removed and marker/ancestor barriers complete.
This uses optional [Java Files.createLink](https://docs.oracle.com/javase/8/docs/api/java/nio/file/Files.html#createLink-java.nio.file.Path-java.nio.file.Path-);
[Linux link(2)](https://man7.org/linux/man-pages/man2/link.2.html) specifies that
an existing destination is not overwritten. Unsupported installation is refused;
there is no nonatomic or replacing fallback. The binary marker format is unchanged.

Before a marker could be observed, owned temporary/metadata cleanup remains
possible. After visibility, confirmation failure is unconfirmed, with predecessor
-1 for an initial installation. Neither create nor fork deletes an observable
Context after that failure; cleanup requires definite marker absence. A create
preflight refuses an existing/unknown revision entry before exposing new identity.
An existing-marker create never silently overwrites it.

Opening the existing mutable Context validates and reestablishes own-frame and
marker barriers before returning ownership. Thus an error after initial/fork
visibility can leave an existing Context to reopen, rather than a nonexistent
name to recreate. A consumer may already have stabilized that same revision;
returning an error to the creator must not destroy the consumer's reference.
Read-only snapshots still select exact revisions without acquiring mutable locks.
