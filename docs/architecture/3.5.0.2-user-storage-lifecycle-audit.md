# KANGER 3.5.0.2 — User and storage lifecycle audit

## Scope

This audit reviews naming and lifecycle vocabulary at the boundary between `User`, the active `Mind`, and storage implementations.

The governing invariant remains unchanged:

> KANGER 3.5.0 must not intentionally change observable execution semantics.

No production rename is authorized by this document.

## Confirmed ownership boundary

The current implementation map establishes the following roles:

- `User` owns the selected storage implementation, registered UDF capability, open `IBase` instances, global identifier counters, and `currentMind`;
- `Mind` owns one concrete runtime/transactional inference context;
- `IData` defines the storage lifecycle through `init`, `use`, `flush`, `close`, `remove`, `reindex`, `getBase`/`connect`, `list`, and closed-state inspection;
- storage close is coordinated with cleanup of the associated `Mind` state.

This is not a flat object graph. `User` is the owner and bootstrap boundary; `Mind` is an active orchestration context; storage is a separately owned external resource with explicit close/flush semantics.

## `currentMind`

The name is generic but lifecycle-significant.

Observed role:

- identifies the active `Mind` associated with the user-level orchestration context;
- participates in ownership and cleanup coordination;
- is not merely a temporary local variable or arbitrary last-created `Mind`;
- may encode a bootstrap/root-context relation that cannot be inferred from the word `current` alone.

Potential clearer names such as `activeMind`, `rootMind`, `sessionMind`, or `attachedMind` each assert a different contract. None is proven by the available evidence.

**Classification:** N2/N4 — coordinated internal rename only after exact ownership, replacement, nested-Mind, and close/reset behavior are characterized.

## Storage lifecycle vocabulary

### `init`

`init(user)` registers or installs a storage implementation into the user bootstrap context. The name is conventional but broad. Renaming it to `register`, `attach`, or `configure` would assert a more specific ownership transition and would affect the public plugin contract.

**Classification:** N3/N4 — public compatibility and semantic-boundary sensitive; retain.

### `use`

`use(...)` selects or opens a named storage context. The verb is semantically compressed: it may include lookup, open, publication, and user-level selection.

Without proving whether repeated calls are idempotent, switching, reopening, or acquisition operations, no narrower verb is justified.

**Classification:** N3/N4 — retain.

### `connect` / `getBase`

The coexistence of `connect` and `getBase` may look terminologically uneven, but the implementation map does not prove they are synonyms:

- one may establish or recover a logical-base association;
- the other may retrieve an already open base or expose the current storage object.

Any normalization could merge different lifecycle operations.

**Classification:** N3/N4 — retain pending exact contract characterization.

### `flush`

`flush` is consistent with its resource-lifecycle role: force pending state toward the storage boundary without destroying the owner or closing the resource.

**Classification:** retain.

### `close`

`close` is the correct lifecycle verb for terminating an owned external resource while preserving the distinction from logical deletion of stored data. The fact that close also coordinates `Mind` cleanup does not justify renaming it to `clear`, `release`, or `destroy`.

**Classification:** retain.

### `remove`

At the storage boundary, `remove` refers to deletion of persisted storage, not release of an in-memory reference. The verb is compatible with the destructive data-lifecycle role, although its public contract must document scope precisely.

**Classification:** N3/documentation debt; retain in 3.5.0.2.

### `reindex`

`reindex` describes a storage maintenance operation and should not be normalized into generic terms such as `rebuild` unless the implementation contract proves that all persisted indexes are rebuilt and no other state is affected.

**Classification:** retain.

## False symmetry to avoid

The following pairs must not be normalized merely for stylistic consistency:

```text
init / close
use / release
connect / disconnect
getBase / remove
flush / clear
```

They are not proven symmetric lifecycle edges. Several operate at different ownership layers.

## Result

No N1 candidate was found in the `User`/storage boundary.

The generic names are either:

- public compatibility surface (`N3`), or
- compressed ownership/bootstrap semantics (`N4`).

A production rename here would create more semantic risk than clarity unless preceded by explicit characterization tests and API migration policy.
