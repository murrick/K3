# Native topology and legacy reindex — cold block-device qualification

18 November 2026, stage 656. Qualification only; production remains stage 652,
`fb0171fa`. Uses the [block apparatus](3.8.0-context-block-device-harness.md)
and [previous-ACK cut model](3.8.0-context-interrupted-block-device.md).
This is not default symbolic activation or general ordinary-publication acceptance.

## Required transitions

| Scenario | Acknowledged baseline | Attempted operation | Cold invariants |

| Actual reindex | Source R3 contains physical Rule-v1 and one saved Rules R1 pin | `DB.reindex(null, mind)` publishes R4 with physical Rule-v2 | Exact R3 retains Rule-v1 and its pin. CURRENT is complete R3/Rule-v1 or R4/Rule-v2; older R1/Rule-v2 and R2/Rule-v1 retain empty historical vectors |

The writer uses real DB/Mind compilation for both originals. The next-ACK
marker follows the successful API return with only an in-memory revision check;
no snapshot opening or other filesystem verification occurs between return and
that marker. Post-publication layout/vector checks belong to the cold reader. A valid historical
row is installed with the existing Rule-v1 adapter and acknowledged as R2;
the saved connection is acknowledged as R3. The reindex witness must advance
the revision and expose actual Rule-v2, so a no-op cannot pass as migration.
The cut matrix uses the existing explicit `DB.saveConnections` ingress. A
separate end-to-end control uses `saveCheckedSymbolicContextConnections()`,
which performs its additional whole-family inspection before the same save.
Neither ingress is the private-copy general publication flow, and no default
symbolic selection is activated by this qualification.

## Confirmed seed and resumed operations

Each scenario first runs its baseline preparation inside an owned guest, emits
the actual previous-publication ACK, and blocks. The host does not release the
next operation: it kills the VM and discards volatile sectors. A new kernel boot
validates that baseline using read-only snapshots. The resulting stable seed
image is hashed and retained, then copied into a fresh owned image for each
witness and cut case. No CURRENT marker is manually rolled back or reconstructed.

Each resumed writer opens that persisted baseline through the production DB,
checks the exact revision/layout/vector, recreates the working connection for
the topology case, then blocks on the previous-ready marker. Mutable open has
confirmed the previous frame; it has not acknowledged a new revision. Only
after the host arms the selected cut does it release the attempted operation.
This reuses actual confirmed bytes and their history without recompiling the
same originals for each independent failure point.

An uncut resumed witness measures the operation's FLUSH count and must
acknowledge/recover the next revision. Fresh seed clones cut before and after
every measured FLUSH ordinal, plus after the first WRITE, before replying to
the selected request. Ordinals describe actual guest block traffic and can
include transient work files or background kernel traffic; they are not Java
statement identifiers. Cases run in isolated VM/image/socket/ledger sets.

## Cold reader and evidence

Every cold reader uses exact ContextSnapshot handles before any mutable open
or application-level repair. It checks the previous and selected revision,
connection counts and exact target identity/revision/locator, the available
Rules R1 snapshot, selected physical rule layout, and equality of all original
Rule-v1 fields with their selected representation. Record id/hash/next addresses
must remain stable. Nonmigrated schema images remain byte-identical; topology
must leave all local schema images unchanged.

The reindex reader also opens Source R1 and R2, verifying their historical
layouts and empty vectors. These are persistence/physical-migration invariants,
not an exhaustive query or acceleration-index correctness proof.

The six wire controls and three finite-cut controls remain mandatory. An
acknowledged append and an interrupted append also exercise the helper's legacy
previous-marker path after the helper/guest changes. A cut
must be reached, stop subsequent requests and precede the next application ACK.
A new kernel must complete ext4 recovery and select the previous or complete
next revision. Missing/corrupt previous history, another cursor or incomplete
selected next state fails. Reports now distinguish `observed_event=block_cut`
from an application-marker observation and record whether a next ACK appeared.

Reproduce with `python3 scripts/persistence_vm/prepare.py`, then
`python3 scripts/qualify-context-native-block-device.py --workers 4`.
The prepared guest contains only the fixture class outside the unchanged JAR;
there are no provider overlays or production fault hooks. The qualification
VM uses the baseline JVM options from stage 655; production launch settings
are unchanged. An explicit `prepare.py --java-profile c1` remains available
only for the experimental diagnostic acquisition described below. Both the
prepared image and preparation script are hash-bound. Reports bind prepared
inputs, seed images, scripts, commands, ledgers and serial logs by SHA-256.

## Boundaries still open

This is a single virtual device and a serial, untorn-sector block model.
It does not interrupt inside an in-progress persistence request. The actual
observed FLUSH ordinal range is finite; it is not every possible kernel or
Java interleaving. Guest FUA is claimed only if observed.

Distinct-device producer/consumer pins, initial create/fork interruptions,
other topology operations/recipes/trust arrangements and supported deployment
review remain separate obligations. Ordinary publication/default integration
remains P2. Full operation-matrix and physical-device power-loss acceptance
are not claimed; H4/P1 remain OPEN-EVIDENCE.


## Open diagnostic observation from the experimental profile

[Archived observation and follow-ups](3.8.0-context-native-term-anomaly-stage656.json)
record one `Invalid or missing TERM field deleted` exception in
`run-_rh3p1p6/topology/f2-b`. It occurred in `DB.connectContext`, while closing a
PairQualification attached snapshot, before the previous-ready marker and
before the fault was armed. The backend ledger contains no armed/reached cut.
That acquisition stopped and is not a completed native-matrix PASS.

Eight subsequent no-fault reopen/publish/cold-read trials on identical seed
clones passed with C1, and eight passed with the interpreter. A fixed valid
Term-v1 descriptor/payload passed 20,000 decode iterations and 20,000 actual
adapter-materialization iterations on the host with C1 and in guests with C1
and the interpreter. Diagnostic sources, logs, prepared inputs and hashes are
preserved; original C1 preparation/image bytes are archived separately.

A further no-fault trial opened a copy of the actual failed image, published
R2 and passed cold reading without the TERM exception. A read-only debugfs dump
of its JAR matched the packaged JAR SHA-256. No repair or modification of the
original failed image was performed.

Sixteen additional native host JVM processes reopened extracted copies of the
same seed, connected Rules, saved R2 and closed successfully with C1. Their
record/manifest validation passed; guest uid ownership was not reproduced by
read-only debugfs extraction in the host namespace. This checks data/adapter
execution outside QEMU, not a device power-loss contract.

These follow-ups have not reproduced the exception. They neither prove a
KANGER durability defect nor establish a JVM/QEMU cause. The anomaly remains
OPEN. No production workaround or runtime fix is justified by it. Baseline
qualification is reported separately and does not silently resolve this finding.
Preliminary acquisition attempts used for apparatus tuning are not combined
with the final matrix or relabelled as completed acceptance evidence.

## Coverage mapping for private configuration and trust views

`DB.applyConnectionCommand` applies a command to a private layer and replaces
the working connection with one carrying the ordered initialization recipe.
The saved connection vector serializes that recipe together with its pin and
trust group. Cold verification needs both the saved metadata and a rebuilt
view: the recipe must change answers through Source while the exact Rules
snapshot retains its original answers. An interrupted publication must leave
the previous recipe and answers intact, or expose the complete new pair.

`DB.publishContext`, used by `ctx publish`, prepares local content in a detached
candidate and then publishes the candidate generation with the working vector
on the canonical Source. This differs from the saved-topology runner, which
calls `DB.saveConnections` and keeps local content fixed. A cold cut on the
canonical publication should change both a local original and the private
recipe so that a mixed generation and vector is distinguishable. Seed the
previous state through the ordinary entry point, verify it after reboot, and
require local content and the vector to move together. The prepared candidate
can serve as an additional pre-publication cut boundary. The canonical Source
is the recovery oracle at that boundary.

An existing trust group is represented by per-connection metadata. Use two
members to distinguish restored group execution from independent member
execution. Compare group labels and exact pins, then rebuild the commune in
a fresh runtime and check a joint inference that requires both members.
Existing private-fork and commune integration tests provide behavioral
examples. Their checks do not cover cold block-device recovery.

`ContextPrivatePublicationWitness` checks this setup on a fresh host
directory using the ordinary provider. It publishes a pending local rule
and a private Rules command together, opens Source again, and checks the
unchanged target identity and the exact old and new recipes. The witness
passed on ext4. The abrupt-cut oracle still requires a separate VM run.
