# DMZ candidate: first transaction branch probe

Status: executable characterization of existing Core capabilities. This is
not a replacement for trust and not a complete DMZ implementation.

Base: `develop/3.8.0`, `2422f7f6d9e1af7608203b1566df64b5f29fe344`.
Specification: section 20 of the live architecture specification 2.0.
Carrier: `experiment/3.8.0-dmz-transaction-probe`.

## Concrete question

Can existing transactions retain opposite external opinions, retract one
known ground support and its consequences only in an alternate branch, retain
independently supported results, and preserve the target Q?

The test uses ordinary compiler/linker/analyzer semantics throughout. No second
inference engine or production changes are introduced.

## Fixture and branch construction

Q owns these general productions:

```text
!@x a(x) -> male(x);
!@x b(x) -> ~male(x);
!@x a(x) -> shared(x);
!@x c(x) -> shared(x);
!@x male(x) -> positive(x);
!@x ~male(x) -> negative(x);
```

An ephemeral current transaction contains either `a(John)` or `b(John)`, plus
`a(Mary)`, `c(John)` and `stable(Tom)`. Trying the opposite support is rejected
with a collision witness and leaves current knowledge unchanged.

The alternate is a real child transaction over that live current transaction.
It masks the known first ground support using existing `queryDelete`, whose
production re-saturation removes unsupported consequences. It then accepts
the opposite support. Current retains the first opinion; alternate retains
the second. Neither is committed to Q.

This is a nested overlay alternative, not a sibling fork of the current state.
A separate case creates two live sibling ephemeral transactions over Q and
checks that opposite inputs and answers remain isolated. Operations are
interleaved sequentially; multi-thread execution is not tested here.

The probe recursively follows existing `ICause` links to confirm that the
generated conflict side exposes its known ground-support ancestry. The
collision witness itself still exposes diagnostic text, not a structured
rule-application conflict set.

## Qualified observations

- Both positive-first and negative-first cases succeed.
- Masking `a(John)` retracts its unsupported positive consequence; masking
  `b(John)` retracts its unsupported negative consequence.
- `shared(John)` survives through independent `c(John)` support.
- `positive(Mary)` survives: the general `a -> male` production is retained.
- Each resulting branch matches a freshly constructed transaction with the
  corresponding accepted inputs for the checked ground answers and unary
  enumeration Values.
- Original current knowledge is unchanged by alternative operations.
- Two sibling transactions retain opposite John opinions simultaneously.
- When Q itself owns `male(John)`, external `b(John)` is rejected atomically,
  while `b(Mary)` and the same general production remain applicable.
- Q's visible rules, root dictionary counts and user current-Mind slot remain
  unchanged. After disposal all branch reservations return to zero.

## Limits and next concrete step

The pair of conflicting supports is supplied explicitly by the fixture.
Deletion of one ground support is a bounded characterization technique, not
the proposed generic prohibition of a combination of rule applications.
The test does not provide automatic conflict attribution, generic symmetric
split scheduling, substitution-sensitive no-good sets, multi-source Context
attachment, branch cache/lifecycle wiring, or the final opinions API.

Next: preserve structured identities of conflicting supports before the
collision transaction is discarded; reconstruct both causal alternatives,
including substitution and source identity; represent a branch-local forbidden
combination. Only then select and qualify the production hook that can skip
that combination without deleting whole source assertions or general rules.
Full cross-context attachment remains a separate architectural question.

## Second slice: detached collision graphs

`CollisionProofCapture` is a package-private, opt-in experimental scope. The
Analyzer captures both existing cause graphs while colliding rules still
belong to the live transaction, before rejection rolls it back. Outside an
active scope the hook returns immediately. Existing collision witness text,
equality, storage and truth semantics are unchanged.

The result consists of immutable detached node/edge lists. Nodes retain
original source text, concrete domain rendering and generated status. Each
existing `ICause` pair has separate rule and donor references expressed as
graph-local indexes. Missing endpoints are `-1`, cycles are preserved without
infinite traversal, and no Mind/Rule/Term/Cause object is exported. These are
inspection graphs, not complete proof certificates or stable cross-context
application identities. Original text and domain rendering do not by
themselves constitute a no-good key.

`DmzCollisionProofCaptureRunner` verifies a two-step production chain in both
input orders, including contraposition, and inspects the captured graphs
after rejected compile rollback and complete branch disposal. It verifies
that the John conflict does not prevent the Mary substitution, immutable
graph lists, and nested capture restoration.

Clean ECJ compilation for Java 8 followed by Java 17 execution reports:

```text

DETACHED_CONFLICT_PASS reverse=true collisions=1 edges=3
DMZ_OPEN_REQUIREMENT alternative_supports_complete=false captured_a=false captured_c=true
DMZ_COLLISION_PROOF_CAPTURE_PASS checks=74
```

The prior transaction runner still reports 523 passing assertions in three
rounds with capture disabled. Full reactor qualification is not claimed.

### Blocking discovery: alternatives are not complete

For rules `a(x) -> male(x)` and `c(x) -> male(x)`, both ground supports
`a(John)` and `c(John)` are accepted. At a later conflict with `~male(John)`,
the existing stored cause graph exposes only the `c(John)` chain in this
fixture. Capturing that graph faithfully does not recover the missing
alternative. This is explicitly printed as an open DMZ requirement; it is
not counted as proof-completeness success.

Existing ordinary deletion can re-saturate surviving inputs, as the first
probe demonstrates. A generic DMZ split must also account for alternatives
that currently have no retained cause edge. Otherwise blocking the visible
support may miss or misclassify the remaining independent proof.

Next step is therefore to qualify complete operation-local support collection
or reconstruction, including grouping of multi-premise supports and query
taint, before implementing generic branch restrictions. Merely unioning
`ICause` pairs or removing a whole source rule is not accepted as a solution.


## Third slice: terminal support observation

`TerminalSupportCapture` is an opt-in, operation-local immutable journal.
The Linker observes complete terminal candidates before stored-result
suppression in its single-candidate path. Each event retains conclusion,
source rule text and a separate donor group. Outside a capture scope the
hook returns immediately; inference and stored-cause semantics are unchanged.
This hook does not cover all terminal paths and is not a proof certificate.
The scope must start before inference: it cannot recover derivations from
an already populated cache. Source text is diagnostic, not stable identity.

The qualification distinguishes two fixtures: independent `a -> male` and
`c -> male` proofs produce separate events even after canonical suppression;
`(a && c) -> male` produces one event containing both required donors in the
single-tuple fixture. Snapshots and donor groups are immutable; nested scopes
isolate events, restore the outer scope and reject out-of-order close.

Clean Java 8-target ECJ compilation and Java 17 execution report:

```text

TERMINAL_CONJUNCTION_PASS events=4
DMZ_OPEN_REQUIREMENT terminal_binding_certified=false mixed_donor_groups=true
DMZ_TERMINAL_SUPPORT_CAPTURE_PASS checks=28
```

The collision graph runner still passes 74 checks; the transaction probe
still passes 523 assertions over three rounds. Full reactor qualification
and a release workflow are not claimed.

### Blocking discovery: accumulated causes mix substitutions

With John and Mary both satisfying `(a(x) && c(x)) -> male(x)`, the raw
terminal cause group contains donors from the other tuple. This is explicitly
asserted as a characterization of the current implementation, not counted
as support-binding certification. The cause map accumulates across variable
rotations, so moving capture earlier than storage solves alternative loss
in the bounded fixture but does not solve binding attribution.

No branch restriction may use these raw groups. Filtering donors by names
in the conclusion would also be unsound: intermediate variables need not
appear in the conclusion. The next hook must retain the unification event,
its complete binding and the premise occurrence that consumed each donor,
then assemble AND supports separately from alternative proofs. Rollback,
query provenance, contraposition, cycles, source/version identity and all
terminal paths still require qualification before automatic symmetric splits.


## Fourth slice: premise-local partial bindings

The same opt-in journal now observes `markExcluded` immediately before a
new Cause is constructed. It copies the explicit substitution candidates
passed to that call, rather than reading the accumulated cause map or
assuming that current TVariable values describe the matched donor.

Each detached match contains a capture-local premise index, original rule
text, donor rendering, the native result flag and a list of partial bindings.
Each binding retains a capture-local variable index, diagnostic name and
rendering, and an immutable `SemanticTermSnapshot` of the ordinary value.
Premise and variable indexes distinguish runtime objects within the scope;
they are not durable source/version identities. The identity map holds
runtime objects only while the scope is open and is cleared on close.
Nonordinary substitutions are excluded from this observation surface.

The unary conjunction fixture keeps John and Mary bindings separate. A
second fixture uses `(a(x,y) && c(y)) -> male(x)` with `(John,One)` and
`(Mary,Two)`: the captured `c` matches preserve the hidden `y` binding even
though `y` does not appear in the conclusion. Both substitutions refer to
the same captured premise and variable, while retaining distinct values.
The snapshots are inspected after scope closure; native truth is checked.

Clean Java 8-target ECJ compilation followed by Java 17 execution reports:


This isolates bindings in the tested premise matches, but does not yet

## Fifth slice: bounded one-step application reconstruction

The single-terminal-candidate hook now reconstructs a support for a bounded
native clause: a non-query rule with one branch, at least two literals,
complete ordinary values and no functions or calculated/system literals.
It captures the entire current binding vector, including variables absent
from the conclusion. Each other literal must be excluded by native inference.

For each premise the collector resolves the opposite ground literal against
currently visible, nondeleted, non-query atomic evidence using a plain Solve
lookup (not an insert Domain, so primary promotion is not requested). It
also requires a captured premise match from the same runtime Mind, with
semantic donor equality and partial bindings compatible with the full
binding vector. Donor matching uses predicate, polarity and detached typed
argument snapshots; rendered text is diagnostic only. All premise supports
belong to one immutable application event. Separate rules produce separate
application events even when their conclusion is already stored.

The evidence/premise/rule/Mind indexes remain capture-local runtime object
indexes. They do not identify durable versions or prove Q/external origin.
Repeated native visits intentionally remain repeated events. A generated
atomic donor may serve as evidence, but its upstream proof is not expanded
by this slice. Events describe the state at their terminal observation;
there is no claim that an event survives subsequent rollback or deletion
as a valid final proof. The journal must not authorize branch restrictions.

Qualification combines two independent proofs of `male(John)`:
`(a(x,y) && c(y)) -> male(x)` and `b(x) -> male(x)`. The first event retains
exactly `{a(John,One), c(One)}` and both bindings. The alternative retains
exactly `{b(John)}`. Mary retains `{a(Mary,Two), c(Two)}`. Both rule/fact
orders are checked, with immutable snapshots inspected after scope closure.
A missing premise produces no target application. A function-bearing rule
still proves its result natively while the collector reports an explicit
unsupported-argument gap and emits no bounded target application.

Java 8-target ECJ compilation and Java 17 execution report:

## Sixth slice: detached recursive observation graph

`DmzObservedProofGraph` connects bounded application events into an immutable
AND/OR graph. Atom nodes use typed semantic ground equality within a captured
runtime Mind. One application step has all its premises (AND); different
steps concluding the same atom are alternatives (OR). Repeated visits of the
same rule, binding and premise vector are collapsed. Diagnostic rendering
is not used to join nodes. Different Mind indexes never join.

Support observations now retain typed donor snapshots and whether the
visible atomic evidence is primary according to RuleFactory, including its
existing primary-promotion view. A generated donor is not automatically a
leaf. If its producing application was unsupported or not observed, the
node stays unresolved. Primary evidence may coexist with derived alternatives.
These are observations at capture time, not durable authority labels.

Graph grounding computes a least fixed point starting with observed primary
leaves. A step becomes grounded only when every premise is grounded. A cycle
without an observed primary seed stays ungrounded. This avoids recursive
traversal overflow and preserves cyclic topology without inventing proof.
Grounded means an observed route to primary leaves exists, not that every
alternative was observed, that Q provenance is qualified, or that the graph
is valid after commit, rollback or deletion. No graph currently authorizes
a branch restriction.

The new qualification runner checks a two-step chain in both fact orders:
`(a && c) -> male`, independently `b -> male`, then `male -> good`.
Each graph has 9 nodes and 5 distinct steps, with separate John alternatives
and the Mary conjunction. Snapshot immutability, recursive links and repeat
collapse are checked. Algorithm-only transformations of captured observations
remove Mary's `c` primary leaf and move upstream events into a different
Mind namespace: the first blocks Mary's downstream graph proof while keeping
John grounded; the second cannot support the original downstream node.
These transformations do not alter native rules or execute DMZ restrictions.

A native seeded cycle is captured, then its primary observation flags are
removed only in a detached algorithm fixture. The unchanged cyclic topology
cannot ground itself. A function-bearing upstream rule demonstrates an
unresolved generated donor: native `good(2)` succeeds, but the observed graph
has no grounded proof because that upstream path is outside the bounded
collector. Numeric diagnostic rendering is `2.0`; the prior function test
was tightened to check this actual target rendering.

Java 8-target ECJ compilation and Java 17 execution report:

```text

DMZ_RECURSIVE_GRAPH_PASS reverse=true nodes=9 steps=5
DMZ_GRAPH_CYCLE_PASS
DMZ_GRAPH_UNRESOLVED_UPSTREAM_PASS
DMZ_OBSERVED_PROOF_GRAPH_PASS checks=46

DMZ_COLLISION_PROOF_CAPTURE_PASS checks=74
```

previous completeness, query-taint and production-path gaps remain open.


## Seventh slice: technical settlement lineage

The opt-in journal observes TechnicalMindTransaction opening and settlement.
Each captured technical child records its parent index and outcome: pending,
committed, rolled back or failed. Exception paths mark failure and rethrow;
automatic close still performs a single rollback through the existing
settlement guard. With no active scope these hooks retain no observations.

`settlementSnapshot()` provides an immutable accepted application list plus
pending, discarded and untracked counts. An inner commit stays pending until
all observed ancestors commit. Any ancestor rollback/failure excludes its
entire captured lineage. Raw applications remain available for diagnostics;
the graph can be built from the accepted list without rejected observations.
Earlier settlement snapshots never change when an ancestor later settles.

A missing ancestor is accepted only at the known operation boundary: either
a root Mind for the default scope or the explicit target supplied to
`begin(operationBoundary)`. A late scope inside an unknown outer transaction
reports untracked observations and excludes them from the accepted list.
An explicitly selected ephemeral branch is a valid boundary for technical
commits into that branch; this does not certify the branch's later lifecycle.
Runtime references are released on scope close, while detached indexes and
outcome records remain available for inspection.

Qualification covers normal compile acceptance, a conflicting compile that
produces raw application observations and then rolls back, inner commit with
outer commit/rollback, exception-triggered automatic rollback, immutable
snapshots, late-scope rejection and an explicit ephemeral branch boundary.
Settled graph construction excludes the rejected lineage. The existing
reservation regression also verifies direct-child accounting and underflow.

Next: bind proof observations to source/revision identity and an explicit
operation state, invalidate or revalidate them after relevant changes, and
qualify Q authority. This remains necessary before automatic no-good
construction, symmetric branch scheduling and a release workflow.


## Eighth slice: scope-local operation checkpoints

Each observed commit increments a capture-local sequence for its target
Mind. `checkpoint(target)` selects only technically accepted application
events whose ancestor committed directly into that target at the latest
sequence. Historical applications from earlier operations are excluded.
The immutable checkpoint holds the scope UUID, target index, sequence,
conservative state fingerprint and detached recursive graph.

`isCurrent` requires the original active scope, owner thread, exact target,
unchanged commit sequence and equal fingerprint. Closing or replacing the
scope invalidates use of its checkpoint. Another observed commit into the
target invalidates older checkpoints even if inputs are restored later.
Read-only native queries and rejected compiles preserve the checkpoint in
the qualified fixture. No automatic DMZ restriction consumes this surface.

The fingerprint scans currently visible nondeleted rules, their local IDs,
RuleFactory-generated status, packed rule digest and current rendering.
It is a conservative runtime state guard, not a durable semantic revision
identifier or a complete machine-state digest. If active storage provides
IContextFederation, the guard also includes source ContextId/revision and
connection target IDs, pins, current revisions, pin/qualification policy,
semantic version, initialization and trust group. Rows are sorted, and
length-prefix framing protects field boundaries. Per-rule data is hashed;
no complete database or physical transaction is copied.

The new runner verifies initial checkpoint, read-only query, rejected change,
support deletion, replacement checkpoint, support restoration, distinct
capture identity and closed-scope rejection. The deletion checkpoint cannot
reuse the older grounded good(John) observation. Separate metadata unit
fixtures verify signature changes for own revision, source pin and ContextId.
These fixtures do not constitute end-to-end revision-provider qualification.

## Ninth slice: preserve source candidates without inventing ownership

Inspection of ContextProvenance and CommuneRuntime confirms that existing
rule-source annotations are indexed by original rule text. Commune replay
adds each member's source revision and source-local rule ID under that text;
it does not bind a source handle to each concrete native application.
Identical text can therefore expose multiple candidates, and a missing
annotation cannot establish Q ownership.

`DmzSourceCandidates` preserves detached atomic source candidates:
ContextId, RevisionId, source-local rule ID and configured-by-X flag. Exact
annotation duplicates collapse; distinct contexts, revisions or source rule
IDs remain distinct. Status is unresolved, single candidate or multiple
candidates. Even a single candidate is diagnostic, never qualified ownership.
Missing-context, hypothesis and joint/commune routing annotations are counted
as unsupported rather than being reduced to one authoritative source.

Bounded application observations retain rule candidates separately from
input-evidence candidates. The conservative state fingerprint includes these
candidate records, so modifying a visible rule's attribution invalidates
its old checkpoint even without a new native commit. Captured attribution
lists remain immutable and unchanged by later annotation updates.

The fixture runner explicitly supplies provenance annotations through the
existing public Mind API; it does not simulate successful provider attachment.
It checks identical rule text annotated by two ContextIds and two revisions,
separate input attribution, exact duplicate collapse, missing authorship,
hypothesis exclusion, detached immutability and checkpoint invalidation.
Native inference results remain unchanged.

## Stage 10 — native replay source-handle transport

`DmzReplayProvenance` adds an opt-in, thread-local transport journal. Each
explicit replay input carries ContextId, revision, source-local rule ID and
explicit TARGET_Q/EXTERNAL authority. The compiler records its actual native
canonical rule ID after successful commit, or the existing canonical ID after
duplicate suppression. Thus identical Q, A and B inputs remain three distinct
source occurrences even when represented by one native rule. No source is
inferred from text or from missing annotations.

PortableSource now retains source-local primary rule IDs alongside statements.
Its new pinned replay overload forwards those handles; CommuneRuntime supplies
the actual member connection revision pin. Existing unpinned qualification
replay remains available. Without an active journal, replay uses the previous
compileLine path. Generated consequences are not imported as primary inputs.
Snapshots are immutable and detached; journal close restores nested scopes and
releases target references, with owner-thread and stack-order checks.

The standalone portable replay fixture uses synthetic revision pins. It checks
identical primary rule/fact pairs in Q, A and B, duplicate canonical IDs with
separate source-local IDs and authority, immutable snapshots, fresh insertion,
unchanged native inference, and absence of invented bindings during inference.
This qualifies the native replay/canonicalization seam, not persistent pin
acquisition or end-to-end CommuneRuntime qualification. All core and DUMB2
production sources compile for Java 8 using ECJ; Java 17 execution reports:

## Stage 12 — replay transaction ancestry settlement

The replay journal now observes TechnicalMindTransaction opening and settlement.
`settlementSnapshot()` separates historical accepted bindings from pending,
discarded and untracked replay events. A binding targets the Mind to which its
single-rule replay committed (including canonical duplicate reuse). Observed
ancestor transactions must all commit before it is accepted; ancestor rollback,
failed settlement or automatic close rollback discards its lineage. A scope
