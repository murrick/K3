# DMZ candidate: first transaction branch probe

Status: executable characterization of existing Core capabilities. This is
not a replacement for trust and not a complete DMZ implementation.

Base: `develop/3.8.0`, `2422f7f6d9e1af7608203b1566df64b5f29fe344`.
Specification: section 20 of the live architecture specification 2.0.
Carrier: `experiment/3.8.0-dmz-transaction-probe`.

## Concrete question

Can existing transactions retain opposite external opinions, retract one
known ground support and its consequences only in an alternate branch, retain
independently supported results, and preserve the target Q?

The test uses ordinary compiler/linker/analyzer semantics throughout. No second
inference engine or production changes are introduced.

## Fixture and branch construction

Q owns these general productions:

```text
!@x a(x) -> male(x);
!@x b(x) -> ~male(x);
!@x a(x) -> shared(x);
!@x c(x) -> shared(x);
!@x male(x) -> positive(x);
!@x ~male(x) -> negative(x);
```

An ephemeral current transaction contains either `a(John)` or `b(John)`, plus
`a(Mary)`, `c(John)` and `stable(Tom)`. Trying the opposite support is rejected
with a collision witness and leaves current knowledge unchanged.

The alternate is a real child transaction over that live current transaction.
It masks the known first ground support using existing `queryDelete`, whose
production re-saturation removes unsupported consequences. It then accepts
the opposite support. Current retains the first opinion; alternate retains
the second. Neither is committed to Q.

This is a nested overlay alternative, not a sibling fork of the current state.
A separate case creates two live sibling ephemeral transactions over Q and
checks that opposite inputs and answers remain isolated. Operations are
interleaved sequentially; multi-thread execution is not tested here.

The probe recursively follows existing `ICause` links to confirm that the
generated conflict side exposes its known ground-support ancestry. The
collision witness itself still exposes diagnostic text, not a structured
rule-application conflict set.

## Qualified observations

- Both positive-first and negative-first cases succeed.
- Masking `a(John)` retracts its unsupported positive consequence; masking
  `b(John)` retracts its unsupported negative consequence.
- `shared(John)` survives through independent `c(John)` support.
- `positive(Mary)` survives: the general `a -> male` production is retained.
- Each resulting branch matches a freshly constructed transaction with the
  corresponding accepted inputs for the checked ground answers and unary
  enumeration Values.
- Original current knowledge is unchanged by alternative operations.
- Two sibling transactions retain opposite John opinions simultaneously.
- When Q itself owns `male(John)`, external `b(John)` is rejected atomically,
  while `b(Mary)` and the same general production remain applicable.
- Q's visible rules, root dictionary counts and user current-Mind slot remain
  unchanged. After disposal all branch reservations return to zero.

## Run and result

Executable: `org.kanger.DmzTransactionBranchProbeRunner`, qualification source
`kanger-qualification/src/org/kanger/DmzTransactionBranchProbeRunner.java`.

Compile the exact carrier Core, Command, Bootstrap and UDF sources plus the
runner for Java 8. Put `kanger/resources` and `kanger-udf/resources` on the
runtime classpath with the compiled classes. Invoke the runner with an optional
positive round count (default 3).

Observed clean-source run used ECJ with `-8`, Java 17, and three rounds:

```text
SYMMETRIC_BRANCH_PASS first=a witnesses=1
SYMMETRIC_BRANCH_PASS first=b witnesses=1
SIBLING_BRANCHES_PASS
Q_PRIORITY_PASS
```

The four lines repeat for each round; final result:

```text
DMZ_TRANSACTION_BRANCH_PROBE_PASS rounds=3 checks=523
```

The number is the runner's assertion count, not 523 independent tests.
Maven reactor, full regression corpus and historical `set_08_02` were not run
in this probe. No production code changed.

## Limits and next concrete step

The pair of conflicting supports is supplied explicitly by the fixture.
Deletion of one ground support is a bounded characterization technique, not
the proposed generic prohibition of a combination of rule applications.
The test does not provide automatic conflict attribution, generic symmetric
split scheduling, substitution-sensitive no-good sets, multi-source Context
attachment, branch cache/lifecycle wiring, or the final opinions API.

Next: preserve structured identities of conflicting supports before the
collision transaction is discarded; reconstruct both causal alternatives,
including substitution and source identity; represent a branch-local forbidden
combination. Only then select and qualify the production hook that can skip
that combination without deleting whole source assertions or general rules.
Full cross-context attachment remains a separate architectural question.
