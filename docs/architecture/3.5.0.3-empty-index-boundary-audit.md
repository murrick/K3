# KANGER 3.5.0.3 — Empty Index boundary audit

## Scope

This note resolves the relationship between invariant candidates I2 and I3 in:

```text
kanger-data-dumb/src/org/kanger/storage/Index.java
```

The audited public surface is:

```java
long firstKey()
Iterator<IndexOne> iterator()
Iterator<IndexOne> iterator(boolean backward)
boolean isEmpty()
```

## Confirmed current behavior

For a fresh or otherwise empty `Index`:

```text
isEmpty()          -> true
firstKey()         -> NoSuchElementException
iterator()         -> null
iterator(true)     -> null
```

The `firstKey()` method contains an apparent `-1` fallback, but calls
`baseIndex.firstKey()` before the null check. `NavigableMap.firstKey()` throws
for an empty map and never returns null.

Both iterator factories construct `IndexIterator`, whose constructor also calls
`baseIndex.firstKey()` or `baseIndex.lastKey()`. The factories catch the failure
and return null.

The behavior is recorded by:

```text
IndexEmptyBoundarySafetyRunner
```

The runner is a characterization gate. It records current observability and does
not endorse the contract.

## Coupled invariant

I2 and I3 are one boundary problem:

```text
empty-key policy
        -> IndexIterator construction policy
        -> iterator factory failure policy
```

Changing only `firstKey()` does not make empty iteration valid because
`IndexIterator` directly accesses `baseIndex.firstKey()` / `lastKey()`.
Changing only the iterator factories leaves the contradictory public
`firstKey()` fallback in place.

Therefore the candidates must be resolved as one atomic contract decision.

## Candidate contracts

### Contract A — exception-based keys, collection-compliant iterators

```text
firstKey() on empty -> NoSuchElementException
iterator on empty   -> non-null empty iterator
```

This follows ordinary `NavigableMap` key behavior and the Java `Iterable`
contract. It requires the iterator constructor/factories to represent an empty
state without swallowing arbitrary exceptions.

### Contract B — sentinel-based keys and empty iterators

```text
firstKey() on empty -> -1
lastKey() on empty  -> -1
iterator on empty   -> non-null empty iterator
```

This resembles the apparent local intention and existing internal traversal
sentinels. It is safe only if `-1` is proven outside the valid persisted ID
domain for every caller.

### Contract C — preserve legacy behavior

```text
firstKey() on empty -> NoSuchElementException
iterator on empty   -> null
```

This is observable but violates normal collection expectations and converts a
specific construction failure into a later `NullPointerException` for ordinary
consumers.

## Decision status

Contract C is characterized but not accepted as the target architecture.
Contract B is not authorized because the repository-wide exclusion of `-1`
from the public ID domain has not been proven.

The conservative target candidate is Contract A:

```text
preserve the effective firstKey exception contract;
make iterator factories return a non-null empty iterator;
do not swallow unrelated construction errors.
```

This target remains pending caller analysis and a green regression gate.

## Required implementation shape

Any correction must be atomic and must include:

1. explicit empty-state support in `IndexIterator`;
2. non-null forward and backward iterators;
3. `hasNext() == false` on empty input;
4. no broad `catch (Exception) -> null` in iterator factories;
5. preservation of non-empty forward/backward order;
6. an explicit decision for `next()` exhaustion behavior;
7. no change to persistence format, block ordering, or ID allocation.

## Current classification

```text
I2 firstKey mismatch -> effective exception contract retained pending proof
I3 null iterator     -> proven collection-boundary defect candidate
I2 + I3              -> coupled implementation unit
```

No production change is authorized in this commit.
