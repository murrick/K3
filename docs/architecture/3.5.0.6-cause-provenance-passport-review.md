# 3.5.0.6 — Cause provenance passport review

## Status

Review artifact for later transfer into the type-level and method-level Javadoc of `ICause` and `Cause`.

This document is documentation-only. It does not change inference, provenance storage, equality, persistence, or telemetry behavior.

## Architectural role

`Cause` represents one directed derivation edge in the KANGER provenance graph.

It records that a receiving result was obtained by applying one Rule to one normalized donor predicate call:

```text
(rule used as inference basis, normalized donor Solve)
        -> one Cause edge
```

A `Cause` is not the complete explanation of a result. A complete explanation is reconstructed by following a set of Cause edges recursively through their donor Rules.

## Inside — architectural essence

A Cause contains:

- the operational ID of the Rule that served as the inference basis;
- a normalized donor `Solve` containing donor Predicate, polarity and base-projected arguments.

The donor is copied from the source Domain through `ArgumentsList.convertBase(mind)`. Therefore the Cause records the donor state that supported the derivation, rather than retaining the mutable live argument graph of the source Domain.

## Outside — contextual relations and projections

The following properties exist only relative to a Mind or caller workflow:

- hydration of the basis Rule from `ruleId`;
- resolution of the normalized donor Solve back to a visible donor assertion Rule;
- membership in a receiving Rule or Domain provenance set;
- recursive explanation traversal;
- telemetry emitted when the Cause is created;
- visibility changes when donor or receiving Rules are deleted or restored.

## Provenance semantics

A Cause answers two different questions:

```text
getRule(mind)
    Which Rule authorized this inference phase?

getDonor(mind)
    Which visible assertion matched the recorded donor call?
```

The basis Rule and donor Rule are not interchangeable.

```text
basis Rule != donor assertion
```

The receiving result is not stored directly inside Cause. Ownership of the Cause set belongs to the receiving Rule or Domain projection maintained by Mind.

## Donor snapshot semantics

The constructor creates the donor as:

```text
Predicate + polarity + convertBase(current arguments)
```

Consequently:

- TVariable definitions are replaced by their current Terms;
- Function definitions are replaced by their current results where resolvable;
- the donor is detached from subsequent mutation of the source Domain argument graph;
- the donor remains a structural Solve, not a persistent semantic unit.

This is a provenance snapshot of the supporting call, not a deep copy of the complete donor Rule.

## Identity and equality

The implementation equality key is:

```text
(ruleId, donor Solve equality)
```

Operationally identical Cause edges should compare equal when they refer to the same basis Rule and the same normalized donor call.

Important distinctions:

```text
Cause equality != receiving result identity
Cause equality != complete explanation equality
Cause equality != textual explanation equality
Cause equality != donor Rule operational ID alone
```

The correctness of Cause equality depends on the structural equality contract of `Solve`. In particular, donor Predicate identity and arity must both match before positional arguments can establish equality.

## Lifecycle and ownership

Cause objects are created during inference and attached to provenance structures owned by the active Mind.

They do not independently commit, roll back, delete, or publish knowledge.

Their effective lifecycle follows the receiving provenance projection:

```text
Cause creation
    -> attach to receiving result projection
    -> preserve through successful publication
    -> discard or hide with rolled-back / invalidated projection
```

Cause does not own the basis Rule or donor Rule. Hydrated references are borrowed canonical objects from the supplied Mind.

## Persistence

The binary representation stores:

- `ruleId`;
- the packed normalized donor Solve.

It does not store:

- a receiving Rule ID;
- hydrated Rule objects;
- the full recursive explanation tree;
- UI-oriented explanation text.

Therefore:

```text
serialized Cause != serialized explanation tree
```

Recursive provenance is reconstructed from multiple stored or runtime Cause relations.

## Deletion and provenance cleanup

A Cause edge is meaningful only while its basis and donor can be resolved as visible knowledge in the relevant Mind.

Cleanup of stale provenance belongs to the owning Rule/Domain provenance structures, not to Cause itself.

```text
invisible donor != malformed Cause object
stale edge cleanup != deletion of donor Rule
```

## Telemetry

Cause construction records a semantic effect through `SemanticEffectTelemetry.recordCause(this)`.

This is observability of provenance creation. It is not part of Cause identity and must not change inference semantics.

## Caller obligations

Callers must:

- supply the Mind whose current argument projection produced the derivation;
- treat `getRule()` and `getDonor()` as potentially failing hydration/lookup operations;
- not mutate the donor Solve as though it were a live Domain;
- not interpret one Cause as a complete explanation;
- retain the distinction between the basis Rule, donor assertion and receiving result.

## Key invariants

```text
Cause = one derivation edge
Cause != complete explanation

basis Rule != donor assertion
normalized donor Solve != live donor Domain

provenance != logical identity
provenance visibility != physical existence

serialized Cause != recursive provenance graph
telemetry != inference semantics
```

## Historical note

`ICause` calls the object a node of the inference tree. At implementation level, `Cause` is more precisely an edge descriptor: it connects a receiving result, held externally by the owning provenance set, to one basis Rule and one donor assertion. A tree or graph emerges only when these descriptors are traversed recursively.

## Planned Javadoc transfer

The final source documentation should:

2. document `Cause` as a normalized derivation edge;
3. describe donor snapshot and lazy resolution semantics;
4. preserve the historical inference-tree example;
