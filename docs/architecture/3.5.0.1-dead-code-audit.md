# KANGER 3.5.0.1 — Dead-code audit register

## Purpose

This register records evidence before code is removed. It distinguishes executable dead code from historical source debris, compatibility surfaces, diagnostic specification, and unresolved candidates.

The audit baseline is:

```text
fix/3.4.4.2.3-mind-lifecycle-safety
937c7d663925193cb5d37023776a95fd7751f79e
```

## Classification

| Class | Meaning | Action |
|---|---|---|
| D1 | Demonstrably unreachable or unused executable code | remove after compile/regression proof |
| D2 | Historical source debris: commented-out former implementation | remove; history belongs to Git |
| R | Intentional architectural or compatibility reserve | retain and document |
| S | Diagnostic or executable-specification support | retain unless deliberately replaced |
| U | Unresolved indirect-use risk | retain pending evidence |

## Confirmed D2 candidates

### `kanger-data-dumb/src/org/kanger/storage/Index.java`

The current source contains several complete former implementations preserved only as line comments:

1. abandoned `ReentrantReadWriteLock` / read-lock / write-lock fields;
2. abandoned `getBlockLength(Collection<IndexOne>)` helper;
3. abandoned `add(long id, long data)` wrapper whose behavior is subsumed by `set(long,long)`;
4. abandoned full-scan `size()` implementation.

These fragments are not compiled, cannot be reached through reflection, serialization, persistence hydration, scripting, CLI dispatch, or external Java linkage, and have no diagnostic effect. Their only remaining function is historical, which is already provided by Git history.

**Classification:** D2 — safe source cleanup.

**Removal boundary:** delete comments only; do not change adjacent executable statements, iteration order, synchronization, index layout, sentinel handling, or counters.

## Confirmed retained specification support

### Safety and qualification runners

The following classes may appear isolated from product call graphs but are explicit CI entry points and executable architecture specifications:

- `KangerMindSafetyRunner`;
- `KangerFactorySafetyRunner`;
- `KangerRuleRenderingRunner`;
- DUMB qualification, integrity, recovery, and concurrency runners;
- semantic telemetry and prediction runners.

**Classification:** S — retain.

A zero-reference report inside ordinary Java code is irrelevant for these classes because the workflow invokes their `main` methods by fully qualified class name.

### Reflection in safety runners

Reflective access to private fields such as factory `top`, `bottom`, `connection`, Mind transient maps, and `transactionCounter` is intentional test instrumentation. These field-name strings form part of the current regression contract.

**Classification:** S — retain during 3.5.0.1.

Any later naming change in 3.5.0.2 must update the corresponding runner atomically.

### Linker semantic notes

Documentation around `Linker.isValidFor()` and `Linker.linkDatabase()` is not obsolete commentary. It freezes observed legacy semantics until a dedicated semantic model and regression corpus permit behavioral refactoring.

**Classification:** R/S — retain.

## Initial unresolved candidates

The following patterns require whole-tree call analysis before action:

1. public methods on implementation classes not declared by interfaces;
2. no-argument constructors used by persistence hydration;
3. `createMap` / `applyMap` methods potentially used by API serialization;
4. factory `mark` / `commit` / `release` overloads that may be called only through Linker transaction choreography;
5. CLI runner classes whose entry points may be named only in shell/workflow files;
6. public getters/setters retained for source compatibility;
7. storage counters and diagnostic snapshots read indirectly by console commands.

**Classification:** U — retain until all modules, workflows, reflection strings, persistence constructors, and external API interfaces have been checked.

## Audit order

The whole-tree review proceeds in this order:

1. build/workflow entry points and runners;
2. public API and interface implementations;
3. persistence hydration and serialization constructors/methods;
4. reflection and scripting exposure;
5. private methods, fields, and imports;
6. historical commented implementations;
7. duplicate helpers and no-op wrappers.

The conservative order prevents removing apparently isolated code before its indirect contracts are known.
