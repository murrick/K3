# Stage518: actual native incoming append, rebasing and causal attribution

The owning dependent diagnostic now binds an exact incoming assertion batch to the actual native parent/child pair, checks the base and proposed families separately, and attributes proposed refutations to the incoming Sources they use. It does not create a proposed child by replaying text and treating that copy as the actual candidate. STABLE_PENDING is historical diagnostic evidence, not native product/model/write admission.

## Actual append manifest

`ContextDependentCandidateInspection` requires an immediate native parent/child relationship, the same User, local context/revision and empty initialization, plus whole primary-only views. Every parent row must remain at its exact native ID with identical origin, native rendering, packed native digest and flags. Deletions, generated/auxiliary state, missing/replaced originals and unaccounted appended rows refuse. New primary row IDs must be above the parent's maximum ID. The whole added count and native-ID order must match the exact supplied incoming assertion origins.

The request is a list of whole exact assertion origins, not a query or an arbitrary statement set. Batch order is bound to the actual native append. No Source is inferred from text alone, and foreign identical IDs/text remain separate physical occurrences. This deliberately retains the existing primary-only/empty-initialization supported profile; warm/generated/deleted or broader native states do not become eligible.

Appending a rule changes the whole-view fingerprint even for preserved originals. Therefore a preserved old X row's child-view Source differs from its parent-view Source. The manifest explicitly maps each preserved child Source back to its physical parent original, maps each new candidate Source to itself and keeps exact foreign Sources unchanged. The mapping is one-to-one. It is used for causal attribution; typed product graphs themselves retain their actual child-qualified function Sources and dependency arguments. It is not a rewrite of native Terms or a persistent Source migration.

## Base before proposed state

The method runs a fresh complete bounded dependent cycle over the actual parent and whole foreign topology first. A sourced existing refutation returns BASE_REFUTED without evaluating or blaming the proposed batch. An incomplete base returns INCOMPLETE. Only a supported-unit fixed-point base permits the proposed whole-child cycle to run.

A proposed refutation returns CANDIDATE_REFUTED with every actual original/final refutation occurrence, exact cut, incoming Source subset used by that proof and complete translated original support. Every returned proposed refutation must contain an incoming Source. A candidate-free proposed refutation after a checked fixed-point base is treated as a diagnostic disagreement and refuses INCOMPLETE, not a reason to blame the new statement.

For X(left&&right->p), A(left,p), B(right,~p), the base is checked separately, and the actual newly appended Horn rule is used in A's second-pass refutation. If an unrelated assertion is appended in the same atomic batch, it remains a candidate occurrence but is not marked as used by those proofs. A pre-existing p/~p contradiction instead returns BASE_REFUTED with parent Sources and no candidate use.

This attribution means proof participation plus the checked supported-profile base comparison. It is not a minimal-explanation or unrestricted-language necessity theorem. Distinct physical alternatives and strict support supersets remain intact; returned occurrences are not reduced to one proof.

If both whole cycles reach supported-unit fixed points, the result is STABLE_PENDING. No model audit, default acceptance, generated-native materialization or settlement permission follows. The base/proposed cycles are separate fresh executions of the existing typed engine, not a second independent proof algorithm. Stage517's independent truth/model path remains separate.

## Ownership and failure boundary

`ContextPendingProductionSnapshotSession.inspectDependentCandidate` supplies its actual saved parent/child inventories and actual complete independent/TRUST groups under the unchanged provider lock, qualified topology checks and before/after currentness/ownership guards. Callers supply only exact incoming origins and bounds, never substitute parent/child/membership snapshots on the owning route. Retained rollback ownership and all physical-member pins remain protected.

Manifest, base or proposed refusal returns INCOMPLETE without accepted fingerprints, candidate set, Source map, oppositions or checked cycles. Invalid arguments, stale whole-view/provider guards and interruption preserve their throwing behavior. Result maps/lists/sets are immutable historical data. No result can later be submitted as native write authority.

The method performs read-only qualification. It never flattens dependent functions into scalar Cvars, allocates generated product Terms/Rules, installs chosen model values, appends the incoming assertion again or settles the pending operation. Actual native incoming formulas are checked; their detached derived products are still not a native materialized final candidate.
