# KANGER 3.5.0.2 — Mind naming and lifecycle audit

## Scope

This note records the naming/lifecycle review of `Mind` runtime state and its reflection-based executable specification in `KangerMindSafetyRunner`.

No executable rename or lifecycle change is authorized by this document alone.

## Established lifecycle evidence

The stabilized lifecycle work established that child C-variables are transient runtime objects of an inference cycle rather than persistent semantic state.

The regression evidence includes symmetric relationships of the form:

```text
parent.cvarChilds[child-key] -> child
child.cvarParents[parent-key] -> parent
```

and cleanup of runtime retention through:

```text
cvarChilds
cvarParents
child-bearing TValue state
TSolve state
temporary Arguments
TValueFactory cache/top/current state
```

`KangerMindSafetyRunner` intentionally reflects on private Mind maps and `transactionCounter`. Exact private names are therefore part of the current executable specification surface.

## Architectural state classes

The audited state must be separated into at least four lifecycle classes.

### Shared semantic state

Objects that represent canonical or committed knowledge and may outlive one query or inference cycle.

These must not be renamed or cleared as though they were transient caches.

### Transaction-local state

Objects and counters associated with a transaction level, inherited child context, commit, rollback, or transaction cleanup.

### Cycle-local runtime state

Child C-variables, temporary parent/child adjacency, current solving state, and transient bindings created while evaluating one inference cycle.

### Owner-local cache/diagnostic state

Maps, current/top pointers, counters, or caches used to accelerate or observe the active runtime graph. Their lifetime is derived from the semantic object they retain and must not exceed it.

## Candidate vocabulary

### `cvarChilds`

Current status:

```text
N2
```

The name is grammatically awkward (`Childs`) but its semantic role is now known: it stores outgoing runtime child-C-variable links owned by a parent during the active inference lifecycle.

Potential replacement vocabulary:

```text
cvarChildren
childCVars
cvarChildrenByKey
```

Selection requires confirmation of key semantics. If the key is not merely an identifier, `...ById` would be false.

Any rename must be atomic with:

- all production reads/writes;
- `linkCVar` / `unlinkCVar` symmetry;
- cleanup paths;
- safety-runner reflection strings;
- diagnostics and comments.

### `cvarParents`

Current status:

```text
N2
```

This is the reverse adjacency of `cvarChilds`. It must be renamed as part of the same commit and with vocabulary that makes the pair visibly symmetric.

Preferred pair shape, pending key confirmation:

```text
cvarChildren
cvarParents
```

or

```text
childCVars
parentCVars
```

A mixed pair is rejected.

### `transactionCounter`

Current status:

```text
N2/N4
```

The name is only correct if the value counts transactions. It may instead represent:

- current transaction depth;
- next transaction identifier;
- number of active child contexts;
- monotonically increasing transaction sequence;
- ownership generation.

Because the safety runner reflects on the exact field and because the semantic distinction affects invariants, no replacement is selected before source-level read/write analysis.

Possible names must be role-specific:

```text
transactionDepth
nextTransactionId
activeTransactionCount
transactionSequence
```

Only one can be correct.

## Operation vocabulary

The stabilized lifecycle implies the following operation distinction.

### `linkCVar`

Creates or publishes a symmetric runtime relationship between parent and child C-variables.

The operation is not merely `add`: it has a reverse-link invariant.

### `unlinkCVar`

Removes the relationship from both directions and participates in lifecycle cleanup.

The operation must remain semantically symmetric with `linkCVar`.

### `clear`

May empty an owner-local container but does not by itself prove that reverse relationships or retained TValue/solve state were released.

### `release`

Would be appropriate only for an operation that makes a transient runtime object unreachable from all owners without destroying persistent semantic state.

### `remove`

Should remain reserved for semantic or collection membership removal where the removed object may continue to exist elsewhere.

## Invariants that naming must expose

The final names should make these properties visible:

1. child C-variables are transient runtime objects;
2. parent/child links are bidirectional and symmetric;
3. cleanup must remove both directions;
4. a stale cache/top/current pointer is a lifecycle violation, not harmless memoization;
5. transaction state and inference-cycle state are distinct lifetimes;
6. persistent semantic variables must not be collapsed into runtime child-variable vocabulary;
7. cleanup does not replace child identity with parent identity; it removes runtime reachability.

## Atomic rename groups

### Group M1 — C-variable adjacency

```text
cvarChilds
cvarParents
linkCVar
unlinkCVar
all reverse-map accesses
cleanup paths
reflection strings
related diagnostics/Javadoc
```

This group is N2 and must be mechanically verified as behavior-neutral.

### Group M2 — transaction counter

```text
transactionCounter
all increments/decrements/reads
constructor/reset behavior
child-context inheritance
commit/rollback assertions
reflection strings
```

This group remains N2/N4 until the value's exact meaning is proven.

## Acceptance regressions

A naming-only checkpoint must preserve:

- child creation and lookup;
- parent/child bidirectional link symmetry;
- unlink symmetry;
- repeated inference-cycle cleanup;
- no stale child in dictionary/factory lookup;
- no stale TValue cache/top/current retention;
- transaction inheritance;
- commit and rollback cleanup;
- shutdown/reopen persistence behavior where applicable.

Reflection updates are part of the same production checkpoint.

## Current conclusion

The strongest safe candidate for the first coordinated rename is the grammatical correction and symmetric alignment of:

```text
cvarChilds / cvarParents
```

Classification:

```text
N2
```

However, the exact replacement pair must wait for key/type inspection so the name does not falsely claim ID-based indexing or ownership that the map does not have.

`transactionCounter` remains:

```text
N2/N4
```

because its real numerical contract has not yet been reconstructed from all mutation sites.
