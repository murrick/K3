# 3.5.0.3 — Mind partial commit completion invariant

## Defect

`Mind.commit(child)` completes a composite factory commit sequentially after all
factory checkpoints have been acquired and the child deltas have been merged
into those frames.

If a later zero-argument factory `commit()` throws, the method has no completion
ledger and no failure cleanup path for the frames that have already been closed
or remain open.

Example:

```text
functions.commit()   succeeds
fValues.commit()     succeeds
tVars.commit()       throws
```

At that point the composite operation is structurally split:

- earlier factory checkpoints have already been committed;
- the failing and later factory checkpoints remain open;
- `finishTransactionLocked()` is not reached, so the child transaction
  reservation leaks;
- the original completion failure escapes without restoring a coherent
  checkpoint boundary.

The parent Mind is therefore left in a partially completed transaction state.
A subsequent transaction can observe stale factory frames even when the logical
child commit itself was reported as failed.

## Required invariant

Composite commit completion must have an explicit exception policy:

```text
for each acquired factory frame:
    complete the frame
    record successful completion

on completion failure:
    close every still-open acquired frame
    continue cleanup even if an individual close operation also fails
    consume the child reservation exactly once
    preserve the original completion failure
```

Cleanup failures must not replace the failure that triggered recovery. They are
attached to the original completion failure through `Throwable.addSuppressed()`.

The invariant does not claim that already committed factory state can be
silently reconstructed after an arbitrary completion failure. Its minimum
safety guarantee is narrower and mandatory: the composite transaction must not
leave open checkpoints or an outstanding child reservation. If full semantic
rollback of already completed factories cannot be guaranteed by the current
factory protocol, that limitation must remain explicit rather than being hidden
behind leaked lifecycle state.

## Regression gate

`KangerMindPartialCommitCompletionSafetyRunner` creates a parent and child Mind,
opens the normal composite checkpoint set, and replaces the `TVariableFactory`
cache with a delegating fault-injection proxy whose zero-argument `commit()`
throws.

The injected failure occurs after the preceding factory completion calls have
started. The runner requires:

- the injected completion failure to propagate;
- the child transaction reservation to be closed;
- checkpoint depth to return to zero for functions, function values,
  t-variables, t-values, domains, rules, comments, and library;
- every auxiliary factory stack to return to depth zero.

Successful output is:

```text
MIND_PARTIAL_COMMIT_COMPLETION_PASS reservation
MIND_PARTIAL_COMMIT_COMPLETION_PASS checkpoints
MIND_PARTIAL_COMMIT_COMPLETION_OK
```

## Current implementation status

The current `Mind.commit(child)` implementation performs the zero-argument
factory `commit()` calls directly and reaches `finishTransactionLocked()` only
after the entire sequence succeeds. It has neither a completion ledger nor a
`finally`/recovery path around that sequence.

The current implementation therefore violates this invariant. The regression
is intentionally a red gate until composite commit completion is made
exception-safe.
