# IMind architectural passport — review draft

Status: normative review draft for `3.5.0.6`; intended for integration into the type-level Javadoc of `org.kanger.interfaces.IMind` after contract review.

## Architectural role

`Mind` is the decision-making centre of KANGER. It owns a locally coherent world of knowledge, evaluates the applicability of visible knowledge, activates inference, and governs transitions between observable states while preserving KANGER invariants.

A Mind is not merely a container, observer, database facade, or transaction handle. It is the active subject of execution: knowledge remains potentially applicable until a Mind establishes a context in which it can be actualized.

## Inside — architectural essence

The internal essence of a Mind consists of:

- the identity of one decision context;
- one transaction level and its locally owned delta;
- the boundary within which visibility, substitution and inference decisions are made;
- ownership of runtime projections created during compilation and inference;
- ownership of query-local result surfaces;
- the fixed-point boundary for one execution context.

A child Mind is a distinct decision context. It inherits a view of its parent world, but owns its own changes and runtime projections.

## Outside — contextual relations and projections

A Mind forms external relations with:

- an `IUser`, which owns the user-visible root context and compatibility current-Mind reference;
- a parent Mind, from which visible state is inherited;
- a child Mind, whose completed delta may be committed or released;
- logical entities such as Rule, Predicate, Term and Operation;
- storage, which may materialize persistent state without defining logical identity;
- query-local projections: Solutions, Values, Hypothesis and Log;
- callers, which initiate compilation, querying and lifecycle transitions.

These relations determine how stable entities are observed and used in the current context. They do not redefine the entities' canonical identity.

## Stable properties

The following properties must remain stable across implementation evolution:

- a Mind is the unit of decision context and transaction visibility;
- local changes belong to the Mind level on which they were created;
- child commit is atomic from the parent's point of view;
- failed commit must not expose a partially published child delta;
- release must not publish child-local changes;
- canonical logical identity is preserved across overlay and persistence boundaries;
- query flood or execution failure is not a partial logical answer;
- lifecycle operations that return another Mind transfer the caller to that returned active context;
- completed or destroyed child contexts must not be reused.

## Context-dependent properties

The following properties have meaning only relative to a Mind:

- whether a Rule, Predicate, Term or Operation is visible or deleted;
- whether a previously deleted entity is restored at this level;
- the current TValue and FValue projections;
- query participation and query-local Rule state;
- materialized textual representations requiring lazy resolution;
- Solutions, Values, Hypothesis and Log of the last operation;
- storage attachment and the active storage name;
- current sorting, diagnostic and flood-control settings.

These properties describe the relation between a stable entity and one decision context; they must not be mistaken for intrinsic entity identity.

## Ownership and lifecycle

A root Mind is associated with an `IUser`. A child Mind is created from another Mind and forms an isolated transaction overlay over the visible parent chain.

The parent governs the terminal lifecycle of its direct child:

- `commit(child)` attempts to publish the complete child delta;
- `release(child)` discards the child delta;
- either operation terminates the child context;
- the caller must continue with the surviving parent or with the Mind returned by a lifecycle operation.

Storage operations may replace the active Mind and invalidate unfinished child levels. Callers must therefore use the returned Mind rather than assume object continuity.

## Decision and execution semantics

Compilation introduces potential knowledge into the current context. Query execution selects an operator, creates query-local runtime state and activates applicable knowledge until the configured fixed point or a terminal condition is reached.

The execution cycle may be understood as:

```text
visible potential knowledge
        +
current Mind state
        +
triggering query or compilation
        -> decision
        -> inference / materialization
        -> new potential state
        -> fixed point
```

The explanatory model does not change the operational contract: the actual result remains three-valued (`true`, `false`, or `null` for uncertainty), while execution failures and flood protection are errors rather than logical values.

## Transaction semantics

Visible state is composed from the current overlay and its parent chain. New objects, deletion marks, restoration marks and runtime projections remain owned by the level that created them until commit.

Commit must:

- accept only the appropriate direct child context;
- revalidate conflicts against the current parent state;
- preserve canonical identity and deduplication rules;
- publish the child delta atomically;
- leave no observable partial publication after failure.

Release discards child-owned changes without altering the parent's prior state.

## Persistence semantics

`IMind` exposes logical storage lifecycle operations but does not define the physical persistence implementation.

Storage attachment:

- does not define logical identity;
- may cause lazy materialization of entities;
- may replace the active Mind returned to the caller;
- may invalidate open child transactions during close, clear, remove or reindex operations;
- must not expose partially acquired or partially reindexed storage state after failure.

A storage address, record position or file layout must never be treated as the public identity of a KANGER entity.

## Query-local result surfaces

The following stores describe the most recent operation of this Mind:

- `Solutions` — Rules that formed the accepted solution surface;
- `Values` — externally observable substitutions of named variables;
- `Hypothesis` — unresolved alternatives produced for an uncertain result;
- `Log` — diagnostic records of execution and interpretation.

They are projections owned by the Mind, not permanent components of Rule or Term identity. A subsequent operation may replace or clear them.

## Side effects

Read accessors may trigger lazy materialization where explicitly documented. Compilation, querying, commit, release and storage lifecycle methods alter Mind-owned state.

Diagnostic settings, sorting settings, source-file metadata and log maintenance affect observation or presentation. They must not redefine canonical logical identity.

## Caller obligations

The caller must:

- serialize its own mutable workflow around a Mind;
- use only live Mind contexts;
- commit or release the correct direct child through its parent;
- stop using a child after commit or release;
- continue with the Mind returned by storage lifecycle operations;
- treat result stores as operation-local projections;
- distinguish `null` logical uncertainty from thrown execution failure;
- avoid depending on physical storage layout or diagnostic text as a stable protocol.

## Architectural invariants

```text
Mind identity != storage identity
Mind identity != current query result
child overlay != parent state before commit
failed commit != partial publication
release != rollback of parent state
uncertain result != execution failure
query-local projection != canonical entity
materialization != creation of a new logical identity
storage address != logical id
```

## Historical and compatibility notes

`Mind` is intentionally retained as a first-class KANGER term. No conventional replacement such as controller, supervisor, observer, moderator or arbiter captures its complete role.

The normative interpretation is:

> Mind is the decision-making centre of KANGER: the active context that governs a locally coherent world of knowledge, actualizes applicable knowledge and preserves the invariants of state transition.

`IUser.getCurrentMind()` remains a compatibility reference. It does not make every Mind operation an arbitrarily concurrent mutable facade, and callers must not use it as a substitute for explicit lifecycle ownership.

## Integration rule

When this passport is integrated into `IMind` Javadoc:

- retain all existing method signatures;
- retain verified method-level lifecycle and error contracts;
- replace only redundant type-level prose;
- keep philosophical development outside production Javadoc;
- keep this passport focused on developer-facing architectural obligations.
