# Stage2t: per-occurrence witness materialization correspondence

## Observed bridge

The opt-in witness journal now records each witness-valued createStored result
at the existing stored callback. ContextWitnessProjection.Materialization holds
the producer Rule ID, actual stored Rule ID, matched conclusion with its current
lineage, stored literal with its durable roots, and existing producer support
alternatives. This extends observeWitnessProjections only; default capture does
not record this metadata. Materialization occurrences consume the shared event
budget. Native matching, alpha lookup, materialization and stored identities are
unchanged. Ordinary non-witness materializations retain their existing capture.

ContextWitnessMaterializationVerifier reads one owning Session snapshot and
checks each occurrence against actual observed applications with the
same native producer, signed conclusion, semantic values, full witness lineage
and producer support alternatives. Matched and stored literals must have the
same predicate/sign/arity/ordinary values and a bijection over current witness
occurrences; repeated positions cannot split and separate positions cannot
merge. Stored witnesses must be durable roots, with compatible domini flags.
An unmatched occurrence, malformed shape, truncated event stream or work stop
returns no verified relation prefix. Existing nonordinary capture gaps remain.

The output is a list of per-occurrence Relations scoped by Session.replay, each
retaining every compatible application. It is not a derived proof, a depth
assignment, a saturation certificate or an authorization for runtime writes.
It does not assert that every observed application was materialized: purely
abstract/native-suppressed productions can remain unmaterialized.

## Concrete chain evidence

For exists w p(w,1), p->q, q->r, q's matched root is the primary p witness;
q's stored root differs. The r application uses that stored q root as a premise.
Both materialization occurrences match their actual application metadata. The
single-primary-step verifier still refuses the chain because q is not a primary
donor. Proof reconstruction must cross the verified q occurrence before using
it, carrying sources and depth instead of treating q as a new depth0 assertion.

## Why no global root union is permitted

For independent exists w left(w,1), exists v right(v,1), left->q and right->q,
the native alpha lookup reuses one stored q Rule/root for both origins. Capture
retains two distinct matched source roots leading to that one representative.
The source theory admits left(a,1), right(b,1), q(a,1), q(b,1) with a and b
different; reusing the existential q representative does not force a=b.
Consequently the two Relations are alternative per-application correspondences,
not a transitive equivalence relation between all involved witness roots.
A global union-find would erase this distinction and is not implemented.
Future proof reconstruction must retain a route-specific witness translation
and source group rather than globally rewriting both origins to the stored root.

## Controls and remaining work

The 24-check runner covers the two-step chain bridge, exact producer/lineage,
replay namespace, alpha-reused storage with independent origins, wrong predicate,
fixed value or sign, diagonal versus independent sharing, missing applications,
missing materializations, work exhaustion and event truncation. An adversarial
stored-callback injection without a native application is rejected. The prior
single-step proof, witness-scope and independent scalar controls remain active.
