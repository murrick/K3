## Architectural model

The reviewed Javadoc describes Linker as a per-Mind saturation orchestrator, not as a canonical store or transaction owner.

It separates:

```text
Mind-owned execution context;
query-local statistics and TSolve acceleration;
active Rule-set construction;
strict descending then ascending Rule traversal;
five-factory/store continuation signals;
variable rotation and partial-binding compatibility;
local TValue/FValue candidate checkpoints;
function and system-predicate evaluation;
branch classification in linkDatabase();
delayed Rule materialization in updateDatabase();
flood/error boundaries;
persistence and cleanup ownership;
concurrency and caller obligations;
frozen semantic kernels.
```

## Preserved invariants

The reviewed checkpoint preserves:

- full-range descending/ascending Rule ordering;
- candidate-index acceleration without semantic ownership;
- hydration and Mind-dependent work outside candidate metadata locks;
- query-local lifetime of TSolve acceleration;
- five-source fixed-point continuation criterion;
- existing unification direction and C-variable handling;
- retained legacy `linkDatabase()` branch-closure flow;
- delayed materialization through `updateDatabase()` and RuleFactory;
- Function/UDF binding ownership outside Linker;
- persistent storage ownership outside Linker;
- caller-side Mind reservation and serialization obligations.

## Deliberate non-changes

J8 does not rename or rewrite `isValidFor()`, decompose `linkDatabase()`, alter Rule candidate policy, introduce new convergence signals, redesign hypothesis collection, change flood semantics, or broaden exception handling. Those changes require independent equivalence evidence and are not authorized by architectural documentation.
