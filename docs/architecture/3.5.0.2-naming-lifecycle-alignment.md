# KANGER 3.5.0.2 — Naming and lifecycle alignment

## Purpose

Align source vocabulary with actual architectural role, ownership, and lifetime without changing observable execution semantics.

This stage is not a broad rename campaign. Every proposed change must resolve a demonstrated semantic ambiguity, preserve behavior, and include all reflection, scripting, persistence, runner, and documentation dependencies in one atomic boundary.

## Governing invariant

> A name may change only when the represented object, operation, ownership relation, and lifecycle remain unchanged.

No change in this stage may alter:

- logical inference;
- object identity or canonicalization;
- transaction inheritance, commit, rollback, or cleanup;
- persistence bytes or hydration;
- link topology;
- iteration order;
- storage allocation;
- exception policy;
- public behavior.

## Lifecycle vocabulary

Every reviewed field, type, and operation must be classified against one of these lifetimes:

```text
persistent
  survives storage close/reopen through serialization

shared canonical
  process-visible canonical identity owned by a factory or registry

transaction-local
  exists only within one transaction and is inherited/committed/rolled back explicitly

query-local
  exists only for one query/planning/execution context

cycle-local
  exists only for one inference cycle or iteration

transient runtime
  executable support state that must never be treated as persistent semantic state

owner-local cache/diagnostic
  derived or observational state whose lifecycle follows its owning component
```

A name that implies a stronger or longer lifetime than the implementation provides is a candidate for alignment.

## Operation vocabulary

The following verbs are not interchangeable.

```text
create
  allocate a new object or identity

register
  publish an existing object into an owner-controlled registry

bind
  associate a semantic variable/name with a value or object in a context

link
  create a graph/topology relation between semantic entities

attach
  add an owner/lifecycle relationship without implying semantic graph linkage

unlink
  remove a symmetric graph/topology relation

detach
  remove an owner/lifecycle attachment

release
  relinquish ownership or make a resource eligible for cleanup

clear
  remove contained state while retaining the owner object

close
  terminate access to an external or lifecycle-managed resource

remove
  delete an entry/entity from an owner-controlled collection or storage

destroy
  permanently invalidate an object and its owned state
```

Every rename must state which operation contract is being clarified.

## Review dimensions

For each candidate record:

1. current symbol and location;
2. actual architectural role;
3. actual owner;
4. creation/publication boundary;
5. lifetime and cleanup boundary;
6. symmetry obligations;
7. persistence/reflection/scripting/API dependencies;
8. proposed name;
9. mechanical rename boundary;
10. regressions proving behavioral neutrality.

## Initial priority slices

### A. Factory canonical-state vocabulary

Review factory fields and helpers that distinguish:

```text
top
bottom
connection
canonical instances
registered instances
factory-owned transient construction state
```

Special constraint: `KangerFactorySafetyRunner` reflects on private field names. Any accepted rename must update the runner atomically and retain the same invariant checks.

### B. Mind lifecycle vocabulary

Review fields and operations representing:

```text
persistent mind state
transaction-local state
query-local state
cycle-local child C-variable state
transient maps and counters
cleanup/unlink symmetry
```

The `3.4.4.2.3` lifecycle fix is the semantic authority. Naming must conform to that proven model rather than reinterpreting it.

### C. Linker relation vocabulary

Review verbs and fields around:

```text
link
unlink
database linkage
validation
attachment versus semantic relation
```

No behavior in `Linker.isValidFor()` or `Linker.linkDatabase()` may change during this stage. Existing semantic notes remain authoritative until `3.5.0.3` or a later dedicated semantic artifact.

### D. Storage lifecycle vocabulary

Review distinctions among:

```text
open / use / init
flush / checkpoint
close
remove / delete / clear
reindex / rebuild
cache clear versus persistent deletion
```

No persistence format or recovery behavior may change.

### E. Planning and execution lifetime vocabulary

Review semantic-estimation and telemetry symbols for accurate distinctions among:

```text
pre-execution estimate
query-local planning state
execution result
observed telemetry
shared calibration state
```

Names must not imply that an estimate is an observed result or that query-local state is shared globally.

## Candidate classification

```text
N1 — safe private mechanical rename
N2 — coordinated internal rename with runner/reflection updates
N3 — public or compatibility-sensitive rename; retain or deprecate first
N4 — lifecycle-operation mismatch requiring semantic investigation; transfer to 3.5.0.3
U  — insufficient evidence; retain
```

## First checkpoint target

The first `3.5.0.2` checkpoint will be an evidence register, not a rename commit.

Begin with:

```text
KangerFactory + KangerFactorySafetyRunner
Mind + KangerMindSafetyRunner
Linker
```

The checkpoint must identify exact rename candidates, rejected candidates, reflection dependencies, and atomic edit boundaries. Only N1/N2 items with complete evidence may proceed to executable changes.
