# Analyzer architectural passport review

## Status

Review artifact for `3.5.0.6 — public API documentation audit`.

This document records the implementation-level architectural contract of
`org.kanger.Analyzer`. It complements the existing type-level Javadoc and is the
source for later method-level Javadoc tightening without changing executable
semantics.

## Architectural role

`Analyzer` is the interpretation boundary between a saturated `Mind` and the
caller-visible logical result.

It does not derive new knowledge, execute operations, canonicalize semantic
units, or own transaction lifecycle. It reads the state produced by `Linker`
and classifies that state into:

- successful calculated or database-supported matches;
- query-local solution Rules;
- query-local TValue result sets;
- unresolved query branches;
- admissible hypotheses when no primary result exists.

```text
Linker saturation
        -> saturated Mind state
        -> Analyzer classification
        -> caller-visible result surfaces
```

## Inside

Stable per-instance state:

- owning `Mind`;
- borrowed `LogStore` of that Mind.

`Analyzer` has no independent persistent state, cache authority, canonical
identity, or transaction checkpoint.

## Outside

Context-dependent state interpreted by Analyzer:

- visible stored Rules;
- calculated Domain marks;
- query membership of Domains and TVariables;
- current TValue bindings;
- RuleFactory candidate indexes;
- `SolutionsStore`;
- `ValuesStore`;
- `HypothesisStore`;
- deleted/restored visibility;
- runtime policy `includeAbstractiveHypothesis()`.

## Result lifecycle

`analyze(Rule, boolean)` begins a fresh interpretation pass by clearing the
query-local `SolutionsStore` and `ValuesStore`.

The supplied `Rule` parameter is retained for compatibility but the current
implementation analyzes the visible database as a whole through
`checkDatabase(null, logging)`.

The returned boolean is therefore a classification of the current saturated
Mind, not the identity of one Rule and not a persistence result.

```text
analyze result != transaction commit
analyze result != durable publication
analyze result != existence of any local coincidence
```

## Primary truth classification

Analyzer recognizes two primary classes of positive evidence.

### Calculated coincidence

A Rule whose Domain is marked calculated is accepted when the Domain itself is
query-related or one of its solved TVariables is query-related.

Its solves may be published to `ValuesStore`.

### Database coincidence

For an ordinary Domain, Analyzer searches visible stored Rules with opposite
polarity and compatible base arguments.

The historical Rule-ID ordering filter prevents symmetric duplicate handling of
the same pair. Candidate indexes are accelerators only; semantic acceptance
remains based on Domain compatibility and polarity.

## Special `rule(1)` selection

The predicate form `rule(<numeric id>)` changes candidate selection from
opposite-polarity Domain lookup to full Rule iteration followed by exact `long`
ID comparison.

This path publishes the selected Rule to `SolutionsStore` and is a historical
query surface, not general Predicate matching.

```text
rule(1) selection != ordinary database coincidence
```

## Query closure and uncertainty

A query Domain that has no accepted match and is not marked used is collected
as an unresolved branch.

After all visible stored Rules are inspected:

- if at least one unresolved branch remains;
- and no calculated result closed the query;

then the overall result is forced to `false`.

This is a closure/completeness rule for the query, not proof that no local match
or partial value existed.

```text
partial coincidence != closed query
unresolved branch != execution exception
false result != proven negation in every context
```

## Values and solutions

`SolutionsStore` contains Rule-level matches selected for the current analysis.

`ValuesStore` contains TValue collections representing current query
substitutions.

They are query-local result projections:

```text
solution Rule != canonical answer identity
TValue result set != persistent knowledge
result store contents != Analyzer-owned state
```

## Hypotheses

Hypothesis admission runs only when no primary result was obtained.

A candidate Rule must be:

- stored;
- complete;
- non-query;
- visible and non-deleted;
- created in the current Mind or restored there.

When abstractive hypotheses are disabled, candidates containing U-witness
arguments are rejected.

A new `Hypothesis` is added only when neither an equivalent visible Rule nor an
existing hypothesis already represents it.

```text
hypothesis != primary result
hypothesis != persistent Rule
hypothesis admission != truth proof
```

## Provenance boundary

Analyzer consumes the effects and matches already present in Mind, but it does
not construct recursive `Cause` graphs itself.

Its responsibility is result classification and publication to result stores.
Detailed explanation remains a separate provenance reconstruction concern.

```text
result classification != provenance reconstruction
```

## Logging

Logging adds Analyzer and Timing records only.

It must not alter candidate selection, query closure, hypothesis admission, or
the returned boolean.

## Concurrency and caller obligations

`Analyzer` is bound to one mutable `Mind` and its query-local stores.

The caller must serialize the lifecycle:

```text
compile / prepare
    -> Linker saturation
    -> Analyzer interpretation
    -> consume result stores
```

Concurrent `analyze()` calls on one Mind are unsupported. Callers must not mutate
Rules, visibility markers, query flags, or result stores while analysis is in
progress.

## Key invariants

```text
Analyzer != inference engine
Analyzer != Calculator
Analyzer != provenance renderer

saturated state != interpreted answer
local match != closed query
unresolved != exception
hypothesis != result
result store != persistence
logging != semantics
```

## Method contracts to transfer into Javadoc

### `Analyzer(Mind mind)`

Creates a per-Mind interpreter borrowing the Mind and its LogStore. It does not
reserve a transaction or clear result stores.

### `boolean analyze(Rule rule, boolean logging)`

Clears current result stores, classifies the full visible saturated state, and
admits hypotheses only if no primary result exists. The `rule` argument is a
retained compatibility parameter and does not currently scope the scan.

### `boolean checkDatabase(Set<Long> list, boolean logging)`

Classifies visible stored Rules, optionally restricted by Rule IDs. Returns the
closure result after unresolved-branch control, not merely whether one Rule
matched.

## Historical and compatibility notes

- The spelling `Analyzer` is normative for the current class.
- The `rule` argument of `analyze()` is currently not used to restrict the scan.
  Removing or repurposing it requires an explicit compatibility decision.
- Rule iteration order, ID symmetry filtering, and hypothesis admission order
  are semantic kernels and must not be changed as ordinary cleanup.
