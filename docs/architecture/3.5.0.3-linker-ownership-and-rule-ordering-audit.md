# KANGER 3.5.0.3 — Linker ownership and rule-ordering audit

## Scope

This checkpoint audits the ownership and lifecycle boundary of:

```text
kanger/src/org/kanger/Linker.java
```

and records one demonstrated execution-order invariant defect without changing the frozen legacy branch-closure kernel.

## Architectural ownership

`Linker` is owned by one `Mind` and is not a persistent graph owner.

```text
Mind
  -> owns one Linker execution component

Linker
  -> observes and mutates query/phase-local Mind state
  -> invokes factories for canonical TValue/FValue/Rule operations
  -> does not serialize itself
  -> does not own storage close/reopen
  -> does not own persistent relation unlink authority
```

The private `solveIndex`, `indexedSolveCounts`, `unarySolveKeys`, and `indexedSolves` fields are acceleration-only state over transient `TSolve` objects already owned by `Mind.ruleSolves`.

Their lifecycle is explicit:

```text
start of link()
  -> mind.ruleSolves.clear()
  -> clearSolveIndex()

workspace/storage clear
  -> Mind replaces Linker instance
```

Therefore the acceleration structures must never become semantic authority and must not survive the query/workspace generation that created their referenced `TSolve` objects.

## Publication boundary

`Linker` does not directly persist a completed rule graph.

Its main publication paths are delegated:

```text
TValue creation/resurrection
  -> TValueFactory

FValue creation/invalidation
  -> FValueFactory

produced Domain materialization
  -> updateDatabase()
  -> Domain.createStored(mind)
  -> RuleFactory / related canonical factories

transient compatibility tuples
  -> Mind.addTSolve(...)
```

`linkDatabase()` remains a deferred-classification and branch-closure kernel. It marks produced state, causes, solves, and temporary hypotheses; `updateDatabase()` performs later materialization. This distinction must remain intact.

## Symmetry conclusion

No standalone `Linker.link(...) / Linker.unlink(...)` persistent relation pair exists.

The class name describes inference linkage broadly, but graph symmetry is maintained by the underlying owners:

- C-variable parent/child symmetry belongs to `Mind.linkCVar()` / `Mind.unlinkCVar()`;
- canonical TValue lifecycle belongs to `TValueFactory`;
- stored Rule/Domain lifecycle belongs to their factories and transaction protocol;
- transient solve-index cleanup belongs to the Linker/Mind query boundary.

Adding an artificial `unlink` method to `Linker` would encode false ownership.

## Demonstrated rule-ordering defect

`link()` constructs two rule traversal lists from one `Set<IRule>`:

```text
leftList  descending ID order
ruleList  ascending ID order
```

The historical comparators implement these orders through subtraction followed by narrowing:

```java
return (int) (o2.getId() - o1.getId());
return (int) (o1.getId() - o2.getId());
```

This is not a valid ordering over the full `long` identifier domain.

For IDs separated by `2^32`, a non-zero difference narrows to zero. Other large distances can reverse sign, and full-range subtraction can overflow before narrowing.

Consequences include:

```text
different Rule IDs compare as equal
ascending/descending traversal may be inconsistent
Comparator contract may be violated
TimSort may receive a non-transitive relation
Linker pass order may depend on overflow rather than Rule ID
```

Unlike the earlier `IndexOne` and `TValue` defects, this comparator is in the active Linker orchestration path. Ordering is observable because Linker deliberately performs both descending and ascending rotations.

## Intended invariant

> The first Linker rule traversal is strictly descending by the full `long` Rule ID, and the second traversal is strictly ascending by the full `long` Rule ID.

The minimal correction is:

```java
// descending
return Long.compare(o2.getId(), o1.getId());

// ascending
return Long.compare(o1.getId(), o2.getId());
```

This preserves:

- the two-pass traversal design;
- the intended direction of each pass;
- rule selection;
- set membership;
- `rotator()` behavior;
- `isValidFor()` semantics;
- `linkDatabase()` control flow;
- persistence format and canonical identity.

It changes only invalid overflow/narrowing behavior outside the safe `int` difference domain.

## Correction boundary

The production correction must be isolated from semantic refactoring.

Allowed:

1. replace the two subtraction/narrowing comparators with `Long.compare`;
2. add a focused regression over ordinary, `2^32`, `Integer.MAX_VALUE + 1`, and full-range IDs;
3. invoke the regression from `KANGER CI`.

Not allowed in the same commit:

- reorder `rotator()` calls;
- collapse the two passes;
- replace `HashSet` selection policy;
- refactor `isValidFor()`;
- decompose or reorder `linkDatabase()`;
- change publication timing or updateDatabase behavior.
