# 3.5.0.3 Mind rollback failure isolation invariant

## Scope

This note records a second-order failure in the composite transaction protocol of `Mind.commit(child)`.

The first-order decision may already be rollback: `Analyzer.checkDatabase(...)` can report a collision after child state has been merged into the parent under factory checkpoints. `Mind.commit(child)` then releases factory checkpoints sequentially.

## Defect

The release sequence is not best-effort and is not protected by a completion guard.

If any early factory throws during `release()`, execution stops immediately. Later factories retain open checkpoint frames and `finishTransactionLocked()` is never reached.

A deterministic example is:

1. open all parent factory marks;
2. merge child factory state;
3. analyzer requests rollback;
4. `functions.release()` throws;
5. `fValues`, `tVars`, `tValues`, `domains`, `rules`, `comments`, and `library` are never released;
6. the child transaction reservation remains open.

This leaves the parent in a partially rolled-back state whose frame depths no longer represent a valid transaction boundary.

## Invariant

A composite unwind must attempt every acquired frame in reverse acquisition order, regardless of individual rollback failures.

After unwind:

- every successfully acquired frame has received exactly one completion attempt;
- the child transaction reservation is consumed exactly once;
- the primary failure remains the propagated exception;
- rollback failures are attached with `Throwable.addSuppressed(...)`;
- no later rollback failure replaces or hides the original failure.

When rollback was requested by a semantic collision rather than an exception, the first rollback exception becomes the primary failure and later rollback exceptions are suppressed onto it.

## Regression gate

`KangerMindRollbackFailureIsolationSafetyRunner` injects a cache whose `release()` fails in `FunctionFactory`, the first factory released by the current implementation. A fault-injecting analyzer deterministically requests rollback.

The gate then requires:

- the release failure is propagated;
- the child reservation is closed;
- every remaining factory cache stack has depth zero;
- every auxiliary rollback stack has depth zero.

The current implementation violates the reservation and remaining-frame assertions.

## Architectural direction

The repair should use a composite guard with an acquisition ledger and a non-short-circuiting unwind routine. The ledger must be traversed in reverse order. `finishTransactionLocked()` belongs in guaranteed completion logic, not only on the normal path.
