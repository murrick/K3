## Shared per-Mind lifecycle

Both factories follow the true child-overlay pattern established in J3 and refined in J4:

```text
one concrete factory per Mind level
    -> transaction(parentFactory)
    -> child Escalera overlay
    -> child generation-local anchor reset
    -> child storage connection remains null
    -> parent Mind decides commit or release
```

Only a root factory in an open storage generation borrows the schema-specific `IBase` from `User`.

Typed `commit(childFactory)` promotes the child cache chain and rebinds promoted units to the parent `Mind`.

No-argument `mark / commit / release` methods implement nested cache/composite checkpoints. They are not interchangeable with typed child commit.

The pair is intentionally asymmetric:

```text
FunctionFactory
    comparatively direct Function overlay
    + binding metadata
    + add-time calculation side effect

FValueFactory
    canonical result registry
    + mutation/action state
    + transaction-visible invalidation set
    + nested invalidation snapshots
```

## FunctionFactory contract

### Representation

`FunctionFactory` is the per-`Mind` registry and transaction overlay for compiled `Function` occurrences.

A new Function records:

```text
schema ID
owning Mind ID
name Term
range
explicit FunctionBinding
argument structure
reserved result argument at index range
```

`add(name, arguments)` defaults to `FunctionBinding.LEGACY_AUTO`. The explicit overload stores the selected binding in the Function record.

The factory does not search for or deduplicate an equivalent Function before allocation. Structural comparison exists on the `Function` unit and is consumed elsewhere; it must not be invented as a factory canonicalization contract.

### Binding metadata

`FunctionBinding` is persistent semantic metadata for one compiled Function occurrence:

```text
LEGACY_AUTO
    backward-compatible infrastructure-first, UDF-second resolution

INFRASTRUCTURE
    immutable infrastructure registry only

UDF_DYNAMIC
    resolve the current user-defined operation by signature on each call
```

Older Function records without the binding byte hydrate as `LEGACY_AUTO`.

Binding participates in Function hashing and structural comparison. Javadoc must not describe it as a transient calculator preference.

### Add-time side effect

After creating and caching a Function, `FunctionFactory.add` calls the Calculator when `Function.isCalculable()` returns false.

The class contract must state this as an add-time execution side effect without renaming or reinterpreting the historical `isCalculable` predicate. In the current source that predicate is derived from whether the argument structure contains TVariables.

Callers therefore cannot assume that `add` is only an inert registry insertion.

### Transaction, persistence, and cleanup

The class has a direct `Escalera` checkpoint protocol and no independent auxiliary journal.

Typed child commit promotes Function units and rebinds their runtime owner.

Root cache misses may hydrate Function records through the borrowed `IBase`; root `update()` persists cache changes.

`pack()` physically removes Functions still marked logically deleted. Function-unit deletion may also mark the currently resolved FValue deleted through the active `Mind`; that unit-level cascade must be acknowledged without overstating `FunctionFactory.pack` as general result invalidation.

### Concurrency boundary

`add` is synchronized locally. Function arguments, Calculator execution, cache iteration, related FValues, and the complete Mind transaction protocol are not thereby independently thread-safe.

## FValueFactory contract

### Representation

`FValueFactory` is the per-`Mind` canonical registry and transaction overlay for materialized function results.

An `FValue` stores:

```text
schema ID
owning Mind ID
Function identity
result Term identity
captured substitution stamp
```

The substitution stamp contains the current value Term IDs of the Function's TVariables in argument traversal order; an empty variable contributes `0` during construction.

The result is persistent semantic state, while the runtime references to Function, Term, and Mind may hydrate lazily from stored IDs.

### Completeness and canonical lookup

`add(Function)` creates a new FValue only when the Function is complete. Otherwise it returns `null`.

Before allocation it calls `find(Function)`.

Lookup uses the Function's current hash base and then verifies the existing FValue against:

```text
same Function ID
same captured substitution stamp for current TVariable bindings
not present in the transaction-visible invalidated set
```

The stored result Term participates in the FValue record and hash. Javadoc must describe the operational lookup accurately and must not simplify it into an unsupported universal mathematical key.

If a matching non-invalidated FValue exists, add clears its logical deletion mark and reuses it. Physical removal remains a `pack()` boundary.

### Action state

Creating a new FValue sets the factory `action` flag.

Typed child commit propagates the child action state according to the current source contract. No-argument checkpoint release must restore factory action through the Mind composite protocol where protected by the established action rollback gate.

The class currently owns no dedicated `actionStack`; documentation must not copy the TValueFactory delta model into FValueFactory. Any action rollback guarantee must be stated only to the extent established by the actual checkpoint/transaction coordination.

### Dynamic UDF invalidation

`invalidated` is transaction-visible auxiliary semantic state, not persistent FValue bytes and not merely a performance cache.

`LibraryFactory.add` invokes `FValueFactory.invalidateUdf(name, range)` when replacing an operation whose old or incoming mode is a function.

The invalidation scan marks existing FValue IDs whose Function uses the affected UDF under the binding contract:

```text
UDF_DYNAMIC
    invalidated for matching name/range

INFRASTRUCTURE
    not invalidated by UDF replacement

LEGACY_AUTO
    invalidated only when no matching infrastructure operation exists,
    preserving historical fallback semantics
```

A requested range of zero acts as the source-defined broad range condition in `usesUdf`; documentation must state the implemented condition rather than invent a new wildcard API promise.

Invalidated values are excluded from `find`, so subsequent calculation may create a fresh result while the obsolete canonical record remains transaction-visible only as invalidated metadata until physical pack.

### Transaction propagation and checkpoint rollback

Child initialization copies the visible parent invalidation set.

Typed child commit merges child invalidations into the parent and publishes the child action state.

No-argument `mark()` pairs an `Escalera` checkpoint with a complete snapshot of the invalidated ID set.

```text
mark
    mark cache
    snapshot invalidated IDs

commit
    commit cache
    discard snapshot

release
    release cache
    restore invalidated IDs from snapshot
```

This is category-specific auxiliary rollback. It is deliberately different from TValueFactory's additions delta journal and from CommentFactory's override/dirty-update journal.

### Packing and persistence

`pack()` physically removes FValues that are:

```text
still logically deleted
or
present in the invalidated set
```

After deletion it clears the invalidation set.

Only root factories borrow the FValue `IBase`; child overlays remain memory-only transaction layers. Root update persists cache changes. Invalidation metadata itself is not stored as an independent persistent record.

### Concurrency boundary

The invalidation set is copy-on-write and `add` is synchronized, but mutable Function/FValue objects, lazy hydration, Calculator interaction, iterators, and the composite transaction protocol are not independently thread-safe.

## Pair comparison

| Dimension | `FunctionFactory` | `FValueFactory` |
| --- | --- | --- |
| Represented unit | Compiled Function occurrence and binding contract | Materialized result for Function/substitution state |
| Allocation | Always allocates a new Function | Find/reuse or allocate only when complete |
| Binding role | Stores `FunctionBinding` | Uses Function binding to decide UDF invalidation |
| Add side effect | May invoke Calculator immediately | Sets action when a new result is created |
| Auxiliary state | No separate checkpoint metadata | `invalidated` set + snapshot stack + action |
| Typed commit | Promote/rebind Functions | Promote/rebind, merge invalidations, publish child action |
| Checkpoint journal | Escalera only | Escalera + full invalidation snapshots |
| Persistence | Root Function schema base | Root FValue schema base; invalidation set is memory metadata |
| Pack | Remove logically deleted Functions | Remove logically deleted or invalidated results |

## J5 acceptance criteria

J5 closes only when:

1. both class-level comments explain exact per-Mind ownership, child initialization, parent completion, and root-only storage attachment;
2. Function allocation is not misdescribed as factory-level canonical deduplication;
3. `FunctionBinding` modes, persistence, backward-compatible hydration, and structural role are explicit;
4. the add-time Calculator side effect is explicit without redefining `isCalculable`;
5. FValue completeness, stored result, substitution stamp, and operational lookup are accurately separated;
6. logical reuse, invalidation exclusion, and physical pack boundaries are explicit;
7. UDF invalidation differs correctly for `UDF_DYNAMIC`, `INFRASTRUCTURE`, and `LEGACY_AUTO`;
8. invalidation propagation and nested snapshot rollback are explicit;
9. FValue auxiliary state is not generalized from TValueFactory or CommentFactory;
10. persistence, cleanup, action, and concurrency claims remain evidence-bounded;
11. Java 8/21 rendered pages contain both introductions with resolved links;
12. factory lifecycle, action rollback, dynamic-UDF replacement, persistence, and the complete qualification contour remain green on one final HEAD;
13. paired review confirms no wording implies that invalidation metadata is durable, that Function add is inert, or that FValue identity is simpler than the implemented lookup.
