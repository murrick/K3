## Representation

`LibraryFactory` is the per-`Mind` registry and transaction overlay for user-defined or dynamically supplied `Operation` units.

An Operation stores:

```text
schema ID
owning Mind ID
LibMode
name
range
runtime reactor/procedure reference
source scripts
parameter names
logical deletion state
```

The source-defined operation signature is:

```text
name + "(" + range + ")"
```

`Operation.toString()`, `getHash()`, and `LibraryFactory.find(title)` use this signature. The factory therefore reuses and replaces one existing operation for the same title rather than allocating a second active canonical identity before physical pack.

This signature identity is separate from the mutable implementation payload: mode, procedure, scripts, and parameters can be replaced while the operation ID remains stable.

## Per-Mind ownership and effective view

Each `Mind` owns a concrete `LibraryFactory` instance.

Child initialization:

```text
transaction(parentFactory)
    -> child Escalera cache overlay
    -> parentView points to the visible parent factory
    -> local overrides, dirtyUpdates, and overlayStack cleared
    -> generation-local top and storage connection reset
    -> child connection remains null
```

The effective read order is:

```text
local override
    -> parent effective view
    -> raw local/cache value or root storage hydration
```

Existing inherited Operations are never mutated directly by a child. `writable(existing)` creates a child-owned copy containing the same operation ID, mode, name, range, procedure, scripts, and parameters.

The iterator traverses raw cache identities but resolves each returned ID through the effective view, so callers observe child overrides rather than stale parent payload.

## Add, replacement, resurrection, and deletion

`add(IOperation)` first searches by the incoming signature.

### New signature

For an absent title:

```text
bind incoming Operation to current Mind
allocate a new library schema ID
set owning Mind ID
add to local Escalera cache
establish generation-local top anchor
```

### Existing signature

For an existing title:

```text
obtain writable local object
clear logical deletion
replace mode and procedure
replace scripts and parameters
retain canonical operation ID
mark direct root mutation dirty when applicable
```

The factory therefore supports pre-pack logical resurrection of a previously deleted Operation with the same signature.

### Empty implementation

After add/replacement, an Operation with no scripts is marked logically deleted.

Javadoc must state the implemented condition without claiming that an empty script list is the only possible public deletion API.

## Cross-factory FValue invalidation

Operation replacement has a semantic side effect outside the Library cache.

Before mutating an existing operation, `LibraryFactory.add` invokes:

```text
mind.getFValues().invalidateUdf(existing.name, existing.range)
```

when either the existing or incoming mode is `LibMode.FUNCTION`.

`Operation.setDeleted(true, mind)` also invalidates matching function results when the operation's current mode is `FUNCTION`.

This side effect is intentionally delegated to `FValueFactory`, whose binding-sensitive rules distinguish `UDF_DYNAMIC`, `INFRASTRUCTURE`, and `LEGACY_AUTO` Functions.

The Library class comment must not duplicate or redefine those binding rules; it should state that replacement/deletion invalidates affected materialized results through the active `Mind`.

### Composite rollback boundary

A Library replacement can mutate two factory-local semantic views:

```text
LibraryFactory
    operation override / dirty metadata

FValueFactory
    invalidated result IDs
```

`LibraryFactory.mark/release` journals only Library overrides and dirty IDs. Correct rollback of the cross-factory invalidation side effect requires the enclosing `Mind` composite checkpoint, where `FValueFactory` is marked and released alongside LibraryFactory.

This is a caller/lifecycle obligation, not evidence for a universal cross-factory journal inside LibraryFactory.

## Typed child completion

`commit(childFactory)` publishes child state into the parent factory:

```text
promote child Escalera chain
rebind child-created Operations to parent Mind
copy child overrides into parent-owned override objects
merge child dirtyUpdates
```

Typed commit does not directly persist existing-record overrides. Parent/root persistence occurs later through root pack/update lifecycle.

The parent `Mind` remains responsible for choosing commit or release and sequencing Library completion with FValue invalidation completion.

## Nested Library checkpoints

No-argument `mark / commit / release` implement Library-local nested checkpoints.

`mark()`:

```text
mark Escalera cache
snapshot deep copies of overrides
snapshot dirty update IDs
```

`commit()`:

```text
commit Escalera cache
pop current overlay snapshot
```

`release()`:

```text
release Escalera cache
restore override copies
restore dirty update IDs
```

The snapshot owns copied Operation payloads so a later mutation of the active writable object cannot alter the saved rollback state.

This journal is category-specific and intentionally analogous to, but not shared with, CommentFactory's copy-on-write overlay journal.

## Persistence and root materialization

Only a root factory in an open storage generation borrows the library `IBase` from `User`.

New Operations flow through normal cache update.

Existing-record replacement uses two paths:

```text
direct root mutation
    -> dirtyUpdates records the existing ID

child replacement committed to root
    -> root overrides contain the effective replacement
    -> root pack applies override payload to raw canonical Operation
    -> dirtyUpdates records the existing ID
```

`update()` first persists cache changes, then rewrites dirty existing steps through `persistExisting(id)`, and finally clears `dirtyUpdates`.

Override metadata itself is memory-only; the materialized Operation record is the persistent state.

Child factories do not own the storage connection, generation, flush, or close authority.

## Physical cleanup

Root `pack()` first applies accumulated overrides to raw canonical Operations.

It then physically deletes Operations that remain logically deleted and removes their IDs from overrides and dirtyUpdates.

Before pack, signature lookup can find a logically deleted Operation and add can restore/reuse it. Pack is therefore the physical canonical removal boundary.

`clear()` discards generation/checkpoint metadata and reconstructs either a child overlay over the current parent or a new root cache generation.

## Concurrency boundary

The implementation uses:

```text
ConcurrentHashMap for overrides
CopyOnWriteArraySet for dirtyUpdates
synchronized add for one replacement/allocation path
```

These guards protect specific metadata operations. They do not make mutable Operation payloads, effective-view iteration, reactors, FValue invalidation, persistent updates, or the full `Mind` transaction protocol independently thread-safe.

J6 closes only when:

1. class-level Javadoc explains exact per-Mind ownership and child overlay initialization;
2. operation signature identity remains distinct from mutable implementation payload;
3. effective-view order and child copy-on-write behavior are explicit;
4. new allocation, existing replacement, logical resurrection, and empty-script deletion are separated;
5. cross-factory FValue invalidation is explicit without duplicating binding rules;
6. the need for composite Mind rollback across Library/FValue state is explicit;
7. typed child commit remains distinct from local checkpoint commit;
8. override/dirty snapshots and deep-copy requirement are explicit;
9. direct-root and child-committed persistence paths are explained;
10. pack remains the physical removal/materialization boundary;
11. concurrency claims remain evidence-bounded;
12. rendered Java 8/21 LibraryFactory Javadoc contains the architectural opening with resolved links;
13. factory overlay, persistent reopen, FValue rollback, and the complete qualification contour remain green on one exact review HEAD;
14. review confirms no wording implies that operation reactors are persisted, that Library-local release alone restores FValue invalidation, or that all operation payload fields define canonical signature identity.
