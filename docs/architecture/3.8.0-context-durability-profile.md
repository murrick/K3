# Durability eligibility profile and device boundary

17 November 2026, stage 652. D07 remains ACCEPTED / IMPLEMENTATION_OPEN.
The runtime now enforces a necessary storage eligibility profile. This is not
certification of a particular device or full power-loss acceptance; H4/P1 stay open.

## Concrete gap

The [stage-651 runtime observation](3.8.0-context-volatile-profile-red-stage652.json)
records an actual acknowledged R1 on tmpfs: file and directory barriers returned
without error. No reboot or destructive mount operation was performed. The
[kernel tmpfs contract](https://docs.kernel.org/filesystems/tmpfs.html) states that
the filesystem keeps temporary data in memory and loses it on unmount. Successful
barrier calls alone therefore cannot establish D07's reboot/power-loss guarantee.
The test used and removed only its own disposable directory.

## Necessary profile: linux-ext4-ordered-barriers-v1

This first profile admits the Linux default OpenJDK file provider and ext4 paths
with verified active ordered-journal settings and barriers. It is intentionally
narrow; rejection of other filesystems means they are outside this profile, not
that every other filesystem is intrinsically unsafe or permanently out of scope.

The checks use current `/proc/self/mountinfo`, resolve the actual path or nearest
existing ancestor, and select the deepest matching mount by path components.
Escaped mount names are decoded once. Missing/malformed evidence or an ambiguous
effective mount is refused rather than guessed. Each selected ext4 device is
resolved through `/sys/dev/block/<major:minor>`; active settings come from its
`/proc/fs/ext4/<device>/options`, not an assumption about default mount options.
Only a short inspection-local settings cache is used, never an indefinite global
certificate. Fresh inspection runs after marker barriers before acknowledgement.

The active settings must positively identify `barrier` / `barrier=1` and
`data=ordered`. Disabled or unverified barriers, writeback/journal alternatives,
no-recovery modes, asynchronous journal commit and DAX are outside v1. The
[kernel ext4 documentation](https://docs.kernel.org/admin-guide/ext4.html) describes
the ordering role of barriers and the different data/journal modes. Those are
profile conditions, not a claim that settings alone certify the underlying media.

Context metadata and data paths need a writable effective mount view. Existing
ancestor directories may be read-only views while a deeper bind view is writable.
FileStore.isReadOnly can describe the backing mount instead of that effective
bind view, so the guard uses per-path mountinfo flags. Unit and actual sandbox
controls cover a read-only root with writable ext4 bind paths. Every selected
frame file/directory is checked, including nested or file bind mounts; checking
only the Context's parent would miss a different storage domain below it.

Other media, non-default providers and unavailable kernel evidence yield
`STORAGE_DURABILITY_UNSUPPORTED`, action `SELECT_SUPPORTED_DURABILITY_STORAGE`.
There is no configuration switch or silent fallback to process-only durability.
Existing barrier/hard-link capability errors are still failures.

## Publication boundaries and unchanged read scope

Create and fork check eligibility before exposing new metadata. Mutable open
checks before taking ownership. Own-frame stabilization checks the metadata,
selected generation tree and ancestor domains, including each persisted direct
pin's selected frame. It does not inspect or acquire that target's advisory
connections recursively. Missing legacy history is not manufactured (D09).

The final marker confirmation repeats fresh eligibility checks after file and
parent barriers. A failure at this post-visibility boundary is converted to the
existing unconfirmed publication outcome; rereading CURRENT cannot clear the
fence. Reconciliation repeats the checks and barriers before adopting the result.
The focused native/save/reindex matrix tests this exact late refusal, including
blocked checkpoint, retained consumed native deltas and exactly-once recovery.

A rejected create leaves no Context metadata. A refused target pin leaves the
consumer marker and selected published vector unchanged. Valid legacy snapshots
on unsupported media remain readable without acquiring mutable ownership.
A self-contained explicit fork/import to eligible storage is allowed; it copies
and stabilizes its own data instead of persisting a reference to the volatile
locator. No automatic relocation or weaker persistent pin is introduced.

## Device contract and finite remaining qualification

[Actual environment evidence](3.8.0-context-durability-profile-stage652.json)
records ext4 `data=ordered`, barriers and the kernel's `write back` cache report
for the observed device. These are observations, not a power-loss attestation.
The runtime cannot prove that a controller, drive, virtual disk or backing store
really preserves acknowledged flushes. The deployment contract still requires
persistent backing, an I/O stack that honours flush/FUA, stable mount topology
and no external deletion/replacement during publication. Kernel-visible settings
do not replace that device requirement; hidden volatile backing is not certified.

Remaining H4 work is finite: build an isolated block-device persistence harness
that can discard unflushed writes and cold-recover ext4; exercise creation,
append, topology, reindex, fork and cross-module pins at the specified failure
boundaries; bind the supported deployment profile to that evidence and review
its assumptions. The current tests used only owned files and read-only observations. No host
reboot, raw-device write, mount reconfiguration or kernel/device setting change
was performed.
The session did not find qemu-system-x86_64, qemu-system-aarch64 or guestfish
on PATH. The next harness will use an isolated tool bundle and owned images.

unit tests pass, full native recovery passes 32/32 / 2485 checks, and a separate
focused marker-policy run passes 3/3 / 413 checks. The focused run overlaps the
