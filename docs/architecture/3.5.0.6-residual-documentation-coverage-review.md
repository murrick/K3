# KANGER 3.5.0.6 — residual documentation coverage review

## Purpose

This review defines what remains after the public API documentation audit and the architectural passport pass. It deliberately separates:

1. machine-detectable method-contract debt;
2. architectural concepts that deserve a passport;
3. implementation surfaces that need only proportional Javadoc;
4. explicitly excluded noise.

The completion criterion for `3.5.0.6` is not a zero count across every public Java method. It is complete, accurate coverage of KANGER-owned architectural and caller-visible contracts without manufacturing formal comments for implementation detail.

## Audit model

`tools/audit_public_api_javadoc.py` classifies members into:

- `public_api` — public interface contracts owned by KANGER;
- `internal_spi` — `IBase`, `IData`, `ICache`, `IStep`, `IUnit` and interfaces under `interfaces.internal`;
- `public_implementation` — public/protected methods on concrete classes;
- `protected_helper` — protected implementation helpers.

Only `public_api` and `internal_spi` contribute to `actionable_owned_debt`.

The audit also excludes:

- vendored `org.mozilla.*`;
- tests and diagnostic packages;
- runners, qualification, safety, telemetry, benchmark and performance classes;
- all field initializers, because candidate detection rejects declarations with `=` before the first parenthesis;
- interface implementations carrying an explicit `@Override`, which are classified as inherited when no local Javadoc exists.

The script is therefore a method-contract inventory, not a complete architectural-documentation oracle.

## Remaining architectural concepts

Only a small number of areas still justify a concept-level passport.

### 1. Factory ecosystem — required

Factories are the missing connective tissue of the object model. A family-level passport should define:

- provisional creation versus canonical lookup;
- operational ID allocation;
- hydration through storage records;
- child-Mind overlay visibility;
- commit/release propagation;
- deletion and restoration;
- resurrection and canonical reuse;
- continuation/action signals;
- pack/update publication.

This should be a family document, not one passport per factory. Individual factories need extra text only where they introduce a distinct invariant, such as Rule-scoped U-child recovery, `TValue` pair canonicalization or `FValue` stamp applicability.

### 2. Bootstrap and outer lifecycle — required

A compact lifecycle document should describe:

```
IUser / User
    -> IData plugin and storage generation
    -> root Mind
    -> factories and runtime stores
    -> Parser / Compiller
    -> Linker
    -> Analyzer
    -> root pack / update / flush / close
```

This is the remaining caller-facing map needed to use the architecture safely without reading constructors and console code.

### 3. Library / UDF boundary — required

The `Library`, `Operation`, UDF prototype and `LibMode` family needs one boundary contract covering:

- infrastructure operations versus user-defined operations;
- signature and arity lookup;
- copy-on-write or per-Mind visibility;
- `FunctionBinding` interaction;
- callback ownership and side effects;
- publication and replacement semantics;
- absence of canonical semantic identity for executable callbacks.

### 4. Console/bootstrap implementation — proportional only

Console commands and launch classes should be documented only where they expose lifecycle operations such as:

- opening and closing storage;
- creating/releasing child Minds;
- commit versus rollback commands;
- query compilation/link/analyze sequence;
- output surfaces.

Command parsing, help text, formatting and terminal mechanics do not warrant architectural passports.

## Remaining method-level work

After the concept-level documents above, method-level work should be driven by normalized audit output under these rules.

### Public API

Every remaining `missing`, `placeholder`, `brief` or `incomplete` member must be reviewed. It may be closed by one of three outcomes:

1. add a real caller contract;
2. rely on an inherited interface contract and make that inheritance explicit;
3. reclassify the type as internal implementation if it was never intended as public API.

No public API item may be suppressed merely to reduce the counter.

### Internal SPI

All actionable debt is real. SPI methods must state ownership, lifecycle, errors, persistence effects and caller obligations.

### Public implementation surface

This surface is informational, not a release gate by count. Priorities are:

1. constructors or methods that establish ownership;
2. lifecycle transitions;
3. destructive operations;
4. canonicalization/hydration/publication methods;
5. methods whose historical names misdescribe their current role;
6. methods with non-obvious side effects or compatibility behavior.

Simple getters, setters, collection adapters and inherited interface implementations do not require duplicated prose.

### Protected helpers

Document only semantic kernels and extension hooks. Ordinary decomposition helpers are excluded from completion criteria.

## Explicit exclusions

The following do not belong to the owned public documentation surface:

- vendored Rhino;
- regression, diagnostic, safety, profile, performance and qualification runners;
- test-only utilities;
- exceptions whose meaning is already fully specified by the throwing contract;
- simple diagnostic/presentation enums;
- DTO-like holders without independent lifecycle or identity;
- generated build metadata;
- trivial adapters and collection plumbing.

## Known semantic observations outside documentation scope

Documentation review found behavioral questions that must remain separate from `3.5.0.6` unless handled by an isolated diagnostic decision and regression gate:

- `Solve.equals()` conjunction defect — already isolated in bugfix PR `#40`;
- `Solve.applyMap()` writes/reads `range` versus `tange`;
- `Argument.applyMap()` switch fall-through.

The latter two must not be silently repaired inside a Javadoc package.

## Proposed completion sequence

1. Confirm all workflows for the current documentation HEAD.
2. Produce the factory-ecosystem passport.
3. Produce the bootstrap/outer-lifecycle passport.
4. Produce the Library/UDF boundary passport.
5. Run the normalized method-level audit and capture its exact summary.
6. Review every remaining `public_api` and `internal_spi` debt item.
7. Perform a targeted pass over high-risk `public_implementation` methods.
8. Run Java 8 compile, Maven corpus, Java 8/21 Javadoc, rendered semantic checks and full KANGER CI.
9. Verify integration of PR `#40` without mixing any other behavioral fix.
10. Create a closure document for `3.5.0.6` and only then promote `develop/3.5.0`.

## Completion definition

`3.5.0.6` is complete when:

- every KANGER-owned public interface and internal SPI contract is documented or explicitly inherited;
- all central architectural concepts have stable passports;
- caller-visible lifecycle, transaction, persistence and execution boundaries are documented;
- public implementation methods with dangerous or surprising behavior have local contracts;
- excluded implementation noise is classified rather than cosmetically documented;
- all qualification workflows are green;
- behavioral fixes are isolated behind their own regression gates and PRs.
