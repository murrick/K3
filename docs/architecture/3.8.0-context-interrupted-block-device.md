# Previous ACK across interrupted next publication — block-device qualification

18 November 2026, stage 655. Production baseline remains stage 652, `fb0171fa`.
This qualification extends the [cold block-device apparatus](3.8.0-context-block-device-harness.md).
It does not introduce a production fault hook or a weaker persistence mode.

## Invariant and acquisition

An unmodified packaged provider creates Source, appends row 42, waits for actual
`flush()` R1 success, and emits the previous-ACK marker. It then blocks on its
console input. Only after the host records this marker and arms a finite block
cut does it release the guest to append row 84 and attempt R2.

A separate witness run permits R2 to return successfully. Its actual number of
FLUSH requests after the previous-ACK marker defines the finite ordinal range.
For each ordinal, a fresh image repeats the operation with a cut immediately
before that FLUSH's persistence effect or immediately after it, before replying
to the guest. An additional cut follows the first cacheable WRITE's effect,
also before its reply. Two independent cases may run concurrently; their VM,
socket, backing image and event ledger are separate.

At a selected boundary the backend stops accepting requests and disconnects.
The host kills QEMU, waits for termination, and discards volatile sectors. No
shutdown, context close, host mount or global synchronization repairs the image.
The next kernel boot performs ext4 recovery, then read-only snapshot operations
run before any mutable reopen or explicit reconciliation:

- Exact R1 must open and contain 42.
- CURRENT must be R1 or R2; R0, missing/corrupt metadata and other outcomes fail.
- CURRENT must contain 42, and if it is R2 it must also contain 84.
- A cut case fails if the application emitted the R2 ACK before termination.
- The no-cut witness must recover R2 and both values.

Initial R1 durability is therefore an observed application acknowledgement,
not an assumption inferred from a directory listing. Unacknowledged R2 may
survive or disappear, but it cannot revoke R1 or leave an incomplete selected R2.

## Independent controls and reproducibility

The six existing wire controls remain mandatory. Three added controls verify
cut placement: before FLUSH drops the dirty write; after FLUSH retains it; after
a cacheable WRITE drops it. Each selected cut request receives no reply and
its exact ordinal/edge is recorded. A cut that was armed but never reached fails.
In cut-case reports, `write.observed` means the configured NBD fault was reached;
`expected_marker` retains the no-cut completion marker and is not an R2 ACK
witness. `cut_reached`, the ledger and absence of the R2 ACK in serial output
are the cut-case evidence.

Prepare the owned guest with `python3 scripts/persistence_vm/prepare.py`, then
run `python3 scripts/qualify-context-interrupted-block-device.py`. The manifest
binds the fixture source, original JAR and guest image. Run reports bind scripts,
serial logs, NBD ledgers and QEMU commands by SHA-256. The fixture alone is added
to the guest classpath; no provider classes are overridden.

## Limits

These are ordinal boundaries in actual guest block traffic after release, not
one-to-one labels for Java calls. Background kernel traffic can affect ordinal
counts, and the witness range is remeasured each run. A case that reaches an R2
ACK before its selected cut is rejected rather than called an interrupted PASS.
The apparatus has serial requests and untorn sectors; it does not cut inside a
FLUSH/FUA stable-image write. Guest FUA must not be claimed without observing it.

This is one same-device append with primitive Long records. Topology changes,
actual Rule-v1 reindex, initial create/fork interruptions, historical connection
vectors and distinct-device exported pins require their own cases. Device and
deployment assumptions still need review. H4/P1 remain OPEN-EVIDENCE; full
operation-matrix and physical-device power-loss acceptance are not claimed.


## Recorded stage-655 result

[Observation](3.8.0-context-interrupted-block-device-stage655.json),
`run-asmdvsog`: all six wire controls, all three added cut controls and 21 cut
cases passed. The witness measured ten R2 FLUSH requests after the actual R1
ACK (22 already completed FLUSH requests before release). The matrix cuts before
and after each ordinal 1–10, plus after WRITE 1: 44 VM boots including the
no-cut witness. Every VM exits by SIGKILL; every cold read observes journal
recovery. Guest FUA count is zero.

Twenty cut cases select R1. Only after FLUSH 10 does a cut recover selected R2;
that request was persisted but not replied to, and the application never emitted
R2 ACK. Exact R1 remains readable in all 21 cases, including this R2 outcome.
The no-cut witness acknowledges and recovers R2. No runtime defect is proved.

Independent post-run checks validate one previous application ACK, no next
application ACK, exact fault ordinal/edge, no requests after the reached fault,
observed FLUSH counters, process exit, recovery results and all artifact/input
hashes. The original 175 provider classes match built bytes and the prior-stage
JAR; the guest classpath contains only the fixture outside that JAR.
Python AST, documentation gate and diff checks pass. Full runtime unit/native
gates were not rerun, because production code is unchanged; older results are
not relabelled as stage-655 evidence.
