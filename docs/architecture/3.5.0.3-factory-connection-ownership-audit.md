# KANGER 3.5.0.3 — Factory storage-connection ownership audit

## Scope

This audit resolves the lifecycle meaning of the repeated factory field:

```java
private IBase connection;
```

across the core factories.

The question is not lexical. It is whether a factory owns the storage resource, merely borrows a logical-base handle, or has authority to terminate the shared storage lifecycle.

## Authoritative lifecycle

The storage lifecycle is coordinated by `User` and `IData`.

```text
User.use(mind, name)
    -> IData.use(name)
    -> IData.getBase(schema)
    -> publish one IBase handle into each root factory through transaction(null)

User.close(mind)
    -> clear base caches
    -> IData.close()
    -> clearMind() for every Mind level
    -> factory clear()/transaction(...) resets generation-local anchors
```

`Mind.useStorage`, `Mind.closeStorage`, and `Mind.clearWorkspace` delegate to `User`; they do not close individual factory handles.

Therefore the factory field is a borrowed attachment to one schema-specific logical base. The factory does not create the `IBase`, does not register it in the storage map, and does not own the enclosing `IData` lifecycle.

## Publication and reset

For a root Mind with open storage, `transaction(...)` assigns:

```text
connection = user.getStorage(SCHEMA)
```

For child transactions or a closed/in-memory generation, the connection is reset to `null` before transaction initialization. The 3.4.4.2.3 factory-safety gate already verifies all core factories:

```text
open storage   -> connection != null
close storage  -> connection == null after lifecycle reset
reopen storage -> connection refers to the new generation
```

The field must never retain a base from a previous storage generation.

## Close-authority anomaly

Several factories expose a public method shaped as:

```java
public void closeConnection() throws Exception {
    if (connection != null) {
        connection.close();
    }
}
```

This method is stronger than the ownership model. It allows a factory to close a borrowed `IBase` directly even though normal orchestration closes storage through `User` / `IData`.

No active lifecycle path inspected here invokes `closeConnection()`. The method is therefore not evidence that factories own their bases; it is a legacy implementation-level compatibility surface with potentially excessive authority.

Removing it, making it private, converting it to detach-only behavior, or changing it to clear the field would all be observable API/behavior changes. None is authorized in 3.5.0 without repository-wide caller and compatibility proof.

## Invariant

> `User` / `IData` own storage termination. Factory `connection` fields are borrowed generation-local attachments and must be reset when that generation closes or is replaced.

Consequences:

1. factories must not independently decide when shared storage closes;
2. `transaction(...)` must clear old `connection` before publishing a new generation;
3. close/reopen must leave no factory pointing at a closed prior-generation `IBase`;
4. factory code may use the handle for schema-local reads, writes, and updates only while the enclosing storage is open;
5. `closeConnection()` must not be treated as the authoritative lifecycle path.

## Classification

```text
factory connection ownership     borrowed attachment
storage close authority          User / IData
stale-generation retention       already guarded by factory safety regression
active production defect         not demonstrated
closeConnection()                public compatibility / authority debt
production change in 3.5.0.3     none
follow-up                         public API audit in 3.5.0.5
```
