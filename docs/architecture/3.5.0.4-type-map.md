# KANGER 3.5.0.4 — Architectural Javadoc type map

## Purpose

This document defines the documentation order and evidence boundary for significant KANGER III implementation types.

It describes the architecture that exists at the `3.5.0.3` baseline. It does not prescribe the package structure or decomposition of a future implementation.

## Map dimensions

Every mapped type is classified by the following dimensions:

| Dimension | Meaning |
| --- | --- |
| Representation | What an instance represents in the KANGER model |
| Architectural role | Why the type exists and which responsibility boundary it implements |
| Owner | Component or caller responsible for retaining and completing its lifecycle |
| Publication boundary | How other components obtain or observe the instance |
| Lifetime | Persistent, user/session-scoped, transaction-scoped, query-scoped, cycle-scoped, or helper-local |
| Transaction role | Inheritance, overlay, commit, rollback, checkpoint, result projection, or none |
| Persistence role | Durable record, storage adapter, hydration boundary, durability coordinator, or memory-only |
| Cleanup authority | Component and operation responsible for making the state inactive or unreachable |
| Principal invariants | Non-local properties maintained by the type |
| Evidence | Production source, closure document, resolution note, regression, or trace |
| Priority | Order for architectural Javadoc work |

## Detailed P0 map

### `User`

| Dimension | Current contract |
| --- | --- |
| Representation | User-scoped bootstrap and resource context for one KANGER runtime environment |
| Architectural role | Owns user settings, selected storage implementation reference, open logical bases, UDF capability, and identifier allocation domains; coordinates storage lifecycle with explicit `IMind` references |
| Owner | Application or delivery shell that constructs the `User` |
| Publication boundary | Passed explicitly as `IUser`/`User`; `Mind` retains the owning `User` reference |
| Lifetime | Normally session- or application-scoped; longer than an individual query or child transaction |
| Transaction role | Not a transaction; supplies shared services and storage bases to root/child `Mind` contexts |
| Persistence role | Owns the attached `IData` reference and open `IBase` registry; delegates physical persistence to the storage implementation |
| Cleanup authority | Caller invokes `clear`, `close`, `remove`, or `reindex` with the effective `IMind`; storage and Mind cleanup are coordinated through those explicit parameters |
| Principal invariants | Internal lifecycle uses explicit `IMind` references; in-memory and persistent ID allocation remain distinct; storage close does not turn `currentMind` into an authority; storage associations are not destroyed by transaction-local factory cleanup |
| Compatibility boundary | `currentMind` is a caller-managed public slot only; it is not the current transaction publication pointer, storage owner, shutdown root, or internal cleanup root |
| Evidence | `User.java`; `3.5.0.2-user-storage-lifecycle-audit.md`; `3.5.0.3-user-current-mind-invariant-audit.md`; `3.5.0.3-closure.md` |
| Priority | P0 / J1 pilot |

#### Required class-level explanation

The `User` Javadoc must make these distinctions explicit:

1. `User` is a resource/bootstrap boundary, not a logical transaction.
2. `IData`, open `IBase` instances, settings, UDF capability, and ID allocators have different ownership and lifetime contracts.
3. Storage operations receive and return the effective `IMind` explicitly.
4. `flush`, `clear`, `close`, `remove`, and `reindex` are different lifecycle operations and are not stylistic synonyms.
5. The `currentMind` property has no automatic publication, validation, cleanup, or synchronization semantics.
6. A closed storage resource does not imply destruction of the `User` object.

#### Questions reserved for `3.5.0.5`

- exact external guarantees of each public storage method;
- checked-exception and partial-failure contracts;
- persistence timing visible to API callers;
- final public wording for `getCurrentMind` and `setCurrentMind`.

### `Mind`

| Dimension | Current contract |
| --- | --- |
| Representation | One concrete version of the KANGER information state and its transaction/inference execution context |
| Architectural role | Composition root for factories, query-result stores, compiler, analyzer, calculator, and Linker; coordinates query workflow and parent/child transaction completion |
| Owner | Root is created and retained by the application; a child is created against an explicit parent, whose transaction slot is reserved during construction |
| Publication boundary | Passed and replaced through explicit `IMind` references; not automatically published through `User.currentMind` |
| Lifetime | Root may span a user/storage session; child lifetime ends through parent `commit` or `release`; query- and cycle-local state is cleared or replaced within the owning Mind |
| Transaction role | Represents the transaction level; child factories inherit or overlay visible parent state; parent validates and applies or rejects child completion |
| Persistence role | Root factories may attach to `IBase` storage through `User`; only state reaching the root/open storage boundary becomes durable |
| Cleanup authority | Parent completes child reservation through commit/release and failure paths; `clearMind`, factory cleanup, and query-component replacement remove transient state without redefining persistent ownership |
| Principal invariants | Transaction-slot reservation precedes child publication; commit is exception-atomic across factory checkpoints; rollback failures are isolated; partial mark and commit completion are cleaned up; C-variable links are released symmetrically; `Mind.locker` must not participate in a reverse lock order with Rule candidate metadata work |
| Compatibility boundary | The implementation is broader than a simple transaction DTO: it is an intentional orchestration boundary. Documentation must explain this without presenting the current concentration of responsibilities as a mandatory future design |
| Evidence | `Mind.java`; `3.5.0.2-mind-lifecycle-audit.md`; Mind invariant documents under `3.5.0.3`; Rule candidate lock-order resolution; `3.5.0.3-closure.md` |
| Priority | P0 / J1 pilot |

#### Required class-level explanation

The `Mind` Javadoc must explain:

1. the difference between root and child construction;
2. explicit parent linkage and transaction-slot reservation;
3. ownership of factories, stores, compiler, analyzer, calculator, and Linker;
4. the difference between shared canonical state, transaction-local overlays, query-local projections, and cycle-local runtime state;
5. parent authority over child commit and rollback;
6. the memory-to-persistence boundary at root storage attachment;
7. cleanup and failure atomicity across multiple factory checkpoints;
8. why C-variable adjacency is transient runtime state rather than durable knowledge;
9. why active-Mind publication remains the caller's explicit-reference responsibility;
10. the documented lock-order boundary around Rule candidate resolution.

#### Questions reserved for `3.5.0.5`

- complete external semantics of `IMind.commit`, `release`, `query`, and `compile`;
- postconditions for a child reference after completion;
- API exception taxonomy and concurrency guarantees;
- external lifetime of Values, Solutions, Hypothesis, and Log projections.

## P3 semantic/runtime distinction

Before documenting principal units, classify each field and relationship as one of:

```text
canonical semantic identity;
persistent representation;
transaction-local view or overlay;
query-result projection;
cycle-local solving state;
diagnostic provenance;
acceleration metadata.
```

A type may span more than one category, but its Javadoc must identify the boundary rather than call all retained state “data” or “cache”.

Particular documentation risks:

- `Rule.origin` is source provenance, not the authoritative rendering of hydrated parameters;
- generated/primary status participates in transaction-local promotion;
- `TVariable` runtime context and owner/default context have different publication semantics;
- child C-variable `Term` objects and their `TValue` links are transient matching state;
- `Function` binding mode and `FValue` invalidation have persistence and dynamic-UDF consequences;
- IDs are operational descriptors within their supported generation/lifetime, not universal semantic identity.

## P4 projection boundary

Query-result stores must be documented as projections of the most recent operation owned by a `Mind`, not as independent durable knowledge repositories.

The map must later resolve for each store:

- creation and reset boundary;
- whether returned iterators or maps are snapshots or live views;
- relationship to query result and provenance;
- effect of the next query, clear, commit, release, and storage close;
- whether public access belongs in implementation Javadoc or the `3.5.0.5` API audit.

## J1 decision record

The first implementation edit is limited to class-level Javadoc in:

```text
User.java
Mind.java
```

No interface Javadoc is changed in J1.

The pilot is reviewed against this map in two forms:

1. source readability adjacent to the implementation;
2. generated Javadoc readability without relying on the architecture Markdown corpus.

Only after both forms adequately explain the ownership and lifecycle model may the template be propagated to P1.

## Map maintenance rule

When source inspection disproves a map statement:

1. correct the map explicitly;
2. cite the stronger production evidence;
3. do not rewrite historical audit documents to fabricate a linear investigation;
4. update already-written Javadoc in the same checkpoint if it encoded the superseded claim;
5. add a regression only when an executable invariant, not merely wording, requires protection.
