## Requirement reconciliation

[SMART 2.0](https://docs.google.com/document/d/1PXSMOt-mbwa30-WathSMc0kLX0tbtjlUpfiRUTKOx7s/edit)
§§11.5–11.7 require complete sealed candidates, atomic generation/CURRENT
publication, no authoritative adoption of an orphan, retained exact pins and
unambiguous recovery. They describe the logical pipeline and crash recovery,
but do not specify a filesystem/device crash model or a complete flush ordering.
The earlier lifecycle discussion in
[architecture 0.1 §22](https://docs.google.com/document/d/11fiuj47V9gX8xzY_5PaXqe-TyW05xT6B9R6wjoPg-GE/edit)
explicitly left physical journal/fsync design open. That historical discussion
does not override the later accepted logical invariants or waive their acceptance.

The existing tests establish bounded process-termination and injected-I/O
behavior on a running filesystem. That evidence cannot be promoted into a
power-cut guarantee from the words “durable”, “atomic” or “cold reopen”.

## Platform API boundaries and proof limits

The [Java 8 FileChannel.force contract](https://docs.oracle.com/javase/8/docs/api/java/nio/channels/FileChannel.html#force-boolean-)
provides a file-channel durability operation with local-device and implementation
conditions. It is not an atomic transaction over every file and directory in a
revision. The [Files.move contract](https://docs.oracle.com/javase/8/docs/api/java/nio/file/Files.html#move-java.nio.file.Path-java.nio.file.Path-java.nio.file.CopyOption...-)
provides atomic namespace movement when supported; it does not promise a complete
power-loss commit protocol. The Linux
[fsync documentation](https://man7.org/linux/man-pages/man2/fsync.2.html)
separately identifies directory-entry persistence as requiring directory syncing.

Therefore the trace does not establish a generic power-loss guarantee. A protocol
argument that allows unsynchronized namespace changes to be lost can retain the
old CURRENT name after an acknowledged rename, even when temporary marker bytes
were forced. An unforced manifest/copy is another missing dependency in such an
argument. These are model-level counterhistories showing why the API calls are
insufficient evidence, not observed power-cut failures of this ext4 installation.
No physical device corruption, VM reset or machine restart was executed.

The existing 31-driver recovery profile remains evidence for its named process
cuts and injected failures, not every filesystem fault or fresh-create/fork cut.
The 13-control trace fixture adds successful create/fork observations, not a
complete termination matrix for those paths. Java 8, Windows, network providers,
filesystem mount variants and storage-device flush behavior were not independently
qualified by this Java 21 Linux measurement.

## D07: decision needed before changing runtime guarantees

The author has been asked whether an acknowledged DUMB2 publication must survive
power loss/reboot on a supported local filesystem, with explicit refusal where
that guarantee is unavailable, or whether the current delivery's required model
is process termination only. No reply is treated as acceptance of either option.

Until answered: keep D07 OPEN, do not claim or enable a stronger profile, do not
waive power-loss acceptance, and do not introduce a breaking unsupported-filesystem
policy. No runtime flush/rename/fencing code is changed by stage 648.

If the stronger guarantee is required, its implementation/acceptance must cover
all publication dependencies and initial/fork creation, persist-before-ack order,
errors before and after visible marker replacement, unconfirmed-outcome fencing,
retry, supported-platform assumptions and an appropriately separate crash model.
This is a finite next design obligation; adding one manifest force alone would
not establish that full guarantee. If a process-only delivery is explicitly chosen,
record that boundary and its separate future scope without relabeling existing
process tests as power-loss evidence.

## Reproduction and artifact boundaries

Build the production Console package using the selected profile recorded in the
current checkpoint, then run:

```sh
python3 scripts/audit-context-durability.py
```

Requires a repository checkout, git, JDK/java/javac, Linux strace and permission
to trace its own child. Restricted runners may deny ptrace; that is an acquisition
failure, not a durability verdict. Each invocation owns a unique run directory
under target/context-durability-audit. Existing directories are never used as the
fixture database. Raw syscalls, compiler output, fixture output and detailed JSON
are retained there; the small committed JSON preserves the observation's provenance.

No production source changed, no fresh full runtime/DMZ gate or package rebuild
is claimed, and no release/default activation follows from this audit. Documentation
qualification, source/link/provenance checks and the traced fixture are the
appropriate stage-648 validation. Next: resolve D07; P1 remains open meanwhile.
