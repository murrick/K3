# KANGER 3.5.0.3 — TValue canonical resurrection audit

## Scope

This audit resolves the registered question around:

```java
TValueFactory.find(TVariable, ITerm)
```

and its deliberate lack of a logical-deletion filter.

## Observed path

`TValueFactory.add(tv, value)` first performs canonical lookup:

```java
TValue t = find(tv, value);
```

It allocates a new `TValue` identity only when lookup returns `null`. When an equal value already exists, the factory executes:

```java
t.setDeleted(false, mind);
```

The lookup therefore participates directly in resurrection. It is not merely a query over currently visible live values.

## Identity invariant

The canonical key is the semantic pair:

```text
(TVariable identity, ITerm value identity)
```

For one canonical pair, the factory must not allocate a second `TValue` merely because the existing canonical object is transactionally marked deleted.

Logical deletion is visibility state attached to an existing identity. It is not proof that the identity has ceased to exist or may be duplicated.

The intended transition is:

```text
canonical TValue exists and is live
    -> transaction marks it deleted
    -> same (TVariable, ITerm) pair is added again
    -> find returns the same canonical TValue
    -> add clears the deletion mark in the current Mind
```

Filtering deleted values inside `find()` would change that transition into duplicate allocation and would split canonical identity.

## Distinction from ordinary lookup

`find()` has a broader contract than a visibility-filtered read:

```text
find()  canonical identity lookup, including logically deleted candidates
get()   identity retrieval by ID
current active runtime binding lookup through current map
```

The name is broad, but the behavior is coherent with its use by `add()`. A future API may separate `findCanonical(...)` from visible-value lookup, but that would be naming/API work rather than an invariant correction.

## Physical deletion boundary

`pack()` removes values that remain logically deleted at the packing boundary. Before that boundary, the object remains available for canonical resurrection.

Therefore:

```text
logical deletion   reversible transaction/lifecycle state
pack deletion      physical canonical removal boundary
```

A value physically removed by `pack()` may later receive a new identity if the same semantic pair is added again. That is a different lifecycle generation and does not contradict the pre-pack resurrection rule.

## Invariant

> Before physical packing removes a TValue, re-adding the same TVariable/value pair must reuse the existing canonical TValue identity and clear its logical deletion in the active Mind.

Consequences:

1. `find()` must not exclude a candidate solely because it is logically deleted;
2. `add()` must restore the matching canonical object instead of allocating a duplicate;
3. the secondary variable index must continue to identify the canonical object while it remains physically present;
4. transaction rollback/commit semantics remain authoritative for whether deletion or restoration is visible;
5. physical removal belongs to `pack()`, not `find()`.

## Classification

```text
missing deleted filter       intentional canonicalization behavior
production defect            not demonstrated
identity invariant           confirmed
production change            none
naming clarity               3.5.0.4 / 3.5.0.5 documentation debt
focused regression gap       explicit resurrection identity test desirable
```

## Verification boundary

The source transition `find -> add -> setDeleted(false)` and the physical deletion boundary in `pack()` were inspected. No new execution is claimed in this checkpoint.
