# KANGER 3.7.0 Core / Feature Boundary

Status: architectural invariant for 3.7.0 refactoring.

## Purpose

Define the minimum stable platform boundary for KANGER as an embeddable inference engine and keep optional runtime capabilities outside that boundary.

The governing rule is:

> `kanger-core` contains the necessary and sufficient functionality for using the KANGER inference engine as a library.

A consumer that needs only the inference engine must be able to depend on `kanger-core` without acquiring command processing, persistence providers, UDF providers, runtime discovery, Console, Server or Browser infrastructure.

## Core

`kanger-core` owns KANGER inference/runtime semantics and the contracts required to use them directly, including the `Mind` / `User` model, compiler/analyzer/linker pipeline, inference state, transactions and the lifecycle API needed by the runtime itself.

Core is independently usable and must not depend on optional features.

## Optional features

The following capabilities are peers around Core rather than parts of Core or children of one another:

```text
                 CORE

     +------------+------------+------------+
     |            |            |            |
  COMMAND       STORAGE       UDF       BOOTSTRAP
```

### Command

`kanger-command` is the canonical KANGER infrastructure-control feature. It owns the command vocabulary, grammar, parser, invocation model, formatting/help facilities and command execution/dispatch over the Core API.

For 3.7.0 grammar and execution remain one module. A grammar-only consumer is possible in principle, but no current deployment topology requires a separate artifact. If a real independent use case appears later, the existing internal boundary provides material for a future split.

Target dependency:

```text
kanger-command -> kanger-core
kanger-core    -X-> kanger-command
```

Command names, intents and dispatch are not Core semantics. Core exposes operations; the command feature maps canonical commands onto those operations.

### Storage

Storage providers are optional persistence features. Core defines only the contracts and lifecycle semantics required to cooperate with an attached persistence capability. A Core-only runtime remains valid without a storage provider.

### UDF

UDF providers are optional extension features. A Core-only runtime remains valid without a UDF provider.

### Bootstrap

`kanger-bootstrap` is an optional feature-composition mechanism. It discovers and attaches available runtime features; it does not own those features and is not a parent layer for Storage or UDF.

Removing Bootstrap must not make Storage or UDF impossible to attach explicitly. Removing Storage or UDF must not make Core invalid; Bootstrap simply has fewer capabilities available to discover.

## Delivery adapters

Console, Server, Browser and future delivery adapters sit above the feature boundary. They may depend on `kanger-command` and on whatever optional runtime features they require, but their presentation, transport, authentication and interaction concerns must not leak into Core.

Core-language input remains a Core concern only at the language/runtime API boundary (`compile`, `query`, and related semantic operations). Infrastructure commands are handled above that boundary.

## Refactoring rule for 3.7.0

The 3.7.0 change is structural refactoring, not a semantic redesign. Existing observable command and runtime behavior should remain unchanged while dependencies are corrected.

In particular:

- remove the `kanger-core -> kanger-command` dependency;
- move command-aware processing and command-oriented status projection out of Core;
- retain transaction, storage-lifecycle and inference semantics in Core;
- expose only the narrow Core API required by optional features instead of making command concepts part of Core;
- keep Storage, UDF, Bootstrap and Command independently optional with respect to Core.

## Acceptance criterion

After the refactoring, a developer must be able to use `kanger-core` alone as the complete KANGER inference-engine library. Adding any other KANGER module must correspond to an explicitly chosen feature or delivery adapter, not to an accidental transitive dependency of Core.
