## Ownership and primary-declaration guard

Only two production call sites opt in: qualifyCurrentContext's existing technical
transaction uses commitRefresh, and User.checkpoint delegates creation/commit of
its empty child to Mind.checkpointStorageState. Generic TechnicalMindTransaction
commit, public Mind.commit and explicit user commits stay ordinary authoring.
The package-private entry points and public observation method are final.

During the exact provider validateCommit call, proposed-child isOperationalCommit
is true only on the owning thread. The flag is private, set by Core inside the
commit frame, cleared in finally before native settlement, and never read from a
user statement, a public commit argument or a historical receipt. An ordinary
empty child has no such permission. Other providers keep the existing interface;
production DB has not yet been switched to the new admission policy.

Before exposing this frame Core captures the parent's active primary declarations
and checks the child against them. After provider return it checks both parent
and child against that same immutable entry snapshot. The native primary Rule
packet and referenced Domain packets retain rule/domain/argument identities,
slot kinds/order and origin; generated/deleted rows are excluded. Rule.setMind
selects the owning view before capture. There is no new language/row-count limit.
This guard accompanies trusted, narrowly selected Core call sites; it is not a
general semantic equivalence proof over arbitrary mutable native factories.

The initial probe mistakenly included Rule.toString's presentation status:
unchanged !p(1) renders B in parent and BU in the empty child while the packets
are identical. /tmp/k3-stage3ef-state-probe.log records this distinction. Final
comparison uses actual declaration packets/origin, not display execution flags.
It also compares Domain packets, not just rule IDs. No logical qualification
or supported language bound is weakened to accommodate that display difference.

A changed-primary entry refuses before provider validation; a provider changing
primary declarations during validation refuses before settlement. Existing native
technical release behavior consumes the child once on refusal. An explicit user
rejection retains its child as before, since it is never an operational frame.

OperationalCommitScopeRunner checks ordinary writes/unchanged children have no
frame; only owning refresh/checkpoint receive it; another thread cannot observe
permission; success/refusal clear it. It rejects new primary and primary deletion
before the provider and a provider-injected primary after the entry guard, with
exact reservation cleanup/no fact leakage and subsequent ordinary usability.
Final observation cannot be overridden by a caller's Mind subtype.

The isolated --ordinary-integration-candidate now chooses strict whole-family
admission only for non-operational writes without an explicit attempt. Operational
frames keep existing operational validation; explicit attempts keep their engines,
limits and owning lease. This is operation-based routing, not an unsupported-row
catch/fallback. The candidate remains an isolated compiled DB copy, never a default
provider switch in production.

user transactions/rollback, witness dispatch, unsupported foreign write refusal,
unchanged function-source close, and explicit smaller round-bound preservation.
The stage3ee trust session close and COMMITTED publication-finalization regressions

member-origin distinction; a new communal inference engine is not missing.
