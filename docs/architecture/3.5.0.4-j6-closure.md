## Established architecture

`LibraryFactory` is documented as the per-`Mind` copy-on-write registry and transaction overlay for `Operation` units.

### Canonical identity and mutable payload

The canonical operation title is:

```text
name + "(" + range + ")"
```

That signature drives `Operation.toString()`, hashing, and factory lookup.

The following remain mutable implementation payload:

```text
LibMode
runtime reactor/procedure
scripts
parameter names
```

Replacing or logically restoring an operation with the same title preserves its canonical operation ID before physical pack.

### Effective view and child copy-on-write

The child effective-view order is:

```text
local override
    -> parent effective view
    -> raw cache or root storage hydration
```

Inherited Operations are not mutated directly. Child writable state is a deep copy preserving ID and implementation payload, while the parent retains its previous view until typed completion.

Iterator identity traversal is resolved through the effective view, so child iteration observes local overrides rather than stale parent payload.

### Replacement and deletion

The class contract separates:

```text
new signature
    allocate a new library ID and cache record

existing signature
    preserve ID, clear logical deletion, replace payload

empty scripts after add
    mark the effective Operation logically deleted
```

Before physical pack, a deleted Operation remains discoverable by signature and can be restored with the same canonical ID.

### Cross-factory FValue invalidation

Replacing an Operation invalidates affected materialized function results through the active `FValueFactory` when the existing or incoming mode is `FUNCTION`.

Function-operation deletion delegates the same side effect.

Binding-sensitive invalidation selection remains owned by the closed J5 `FValueFactory` contract and is not duplicated or redefined by Library documentation.

### Composite rollback boundary

A replacement can modify two semantic views:

```text
LibraryFactory
    cache / overrides / dirty existing IDs

FValueFactory
    transaction-visible invalidated result IDs
```

Library-local no-argument checkpoints restore only Library state. Complete rollback of the cross-factory effect requires the enclosing `Mind` composite checkpoint, which coordinates both factories.

No universal cross-factory journal is introduced.

### Typed completion and local checkpoints

Typed `commit(childFactory)`:

- promotes the child Escalera chain;
- rebinds child-created Operations to the parent Mind;
- copies child overrides into parent-owned objects;
- merges dirty existing-record IDs.

No-argument `mark / commit / release` implement nested Library-local checkpoints using deep override copies plus dirty-ID snapshots.

Typed child completion remains distinct from local checkpoint completion and from persistent update.

### Persistence

The class contract separates three paths:

```text
new Operation
    ordinary root cache update

direct root replacement
    existing ID recorded dirty and rewritten during update

child replacement committed to root
    root override materialized during pack
    existing ID recorded dirty
    existing storage step rewritten during update
```

Only root factories borrow the library `IBase`. Child overlays remain memory-only and do not own storage generation, flush, or close.

Overlay metadata is not persistent state. Runtime reactor references are not described as durable object references; persistence is bounded by the existing `Operation` record serialization.

### Physical cleanup

Root pack first materializes overrides into raw canonical Operations and then physically removes records that remain logically deleted, clearing corresponding override and dirty metadata.

Pack is therefore both the root override-materialization boundary and the physical canonical-removal boundary.
