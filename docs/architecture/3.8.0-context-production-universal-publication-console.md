# Stage3ba — explicit Console publication

Console now distinguishes the two invocations:

```
ctx candidate "!@x p(x)->q(x);"
ctx candidate write "!@x p(x)->q(x);"
```

The first remains read-only. The second is an explicit new write attempt through
the existing stage3ay provider bridge. It always acquires, stages, qualifies and
audits afresh; no saved diagnostic/artifact/certificate/audit is an input authority.
Ordinary `!` input and the default authoring path are unchanged.

## Shared grammar and operation

CTX_CANDIDATE_WRITE is a separate shared intent. The exact case-insensitive word
write selects publication; it is not an abbreviation or a boolean limit. A valid
assertion such as !write(1) remains an ordinary diagnostic candidate. Both modes
use the same immutable statement/bounds request and canonical limit round trips.
Malformed/missing statements and invalid limits refuse without Core fallback.
Shared help marks the operations as Console bindings.

IContextFederation has an optional publication method with unsupported default.
DUMB2 forwards it to its explicit fresh writer, preserving the owning provider
monitor, exact snapshots, independent audit, current recheck and pre-settlement
lease consumption. Native logging is disabled for this adapter so Console owns
result rendering. Exceptions are not converted into fabricated normal reports.

The transport-neutral ContextUniversalCandidatePublication is an immutable report:
PUBLISHED/COLLISION/INCOMPLETE/NATIVE_REJECTED, exact historical trial/audit and
actual physical before/after revisions. It is not an authorization token and no
writer accepts a report as input. The shared processor's isSuccess is true only
for PUBLISHED; declined operations still have their typed report for presentation.
Server runtime retains its existing explicit allowlist and does not bind the new
intent. This stage supplies no server publication route or automatic migration.

## Truthful rendering at settlement

Console shows the actual writer status and physical revision transition, followed
by the scoped evidence. Audited collisions retain all whole-proof attribution.
Normal declines explicitly state no assertion was published. Repeating a successful
command reacquires and rechecks, so the existing duplicate-staging rule refuses
rather than publishing the same primary twice.

TransactionSettlementException remains unchanged through the shared processor.
Console catches this specific type separately and displays its actual COMMITTED
or REJECTED outcome, finalization failure/cause and reservation-consumed flag.
A COMMITTED failure is neither displayed as a clean PUBLISHED success nor as a
refused/no-write claim. Other operational errors use the neutral write failed
label; they do not fabricate an unchanged physical state. There is no automatic
retry. Current Mind recovery remains the existing Console loop behavior.

## Controls and continuation

Disposable actual-provider tests cover exact grammar/all-limit round trips,
separate diagnostic/write modes, malformed requests, audited masked collision,
incomplete inference/audit refusal with unchanged physical/presentation state,
historical diagnostic success followed by actual opposite source knowledge,
real Console publish-once/duplicate refusal, durable primary contents with no
foreign-produced primary, and ordinary native consequences after publication.

Separate FailOnceUser controls exercise both shared dispatch and actual Console:
a real durable flush throws once, the original COMMITTED/cause/reservation outcome
is retained, no hidden retry occurs and the universal assertion survives reopen
for unmentioned values. Console output must not claim refusal or clean success
for that committed finalization failure. Existing stage3ay writer tests still
cover direct authority consumption and other lifecycle boundaries.

Main checkpoint records authoritative validation/report and journal recovery.
Manifest counts are registrations, not a new full DMZ/reactor test run. Default
last contract remains stage3r RED56/2; native residual/witness/function scope and
question3 remain open.
