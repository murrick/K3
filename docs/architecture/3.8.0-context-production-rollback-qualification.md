# Owning rollback-target qualification (stage 3bj)

Stage3bi proved that blanket pending qualification prevents rollback of a refused
user transaction: target qualification temporarily creates a technical child beside
the retained user child, whereas ordinary publication requires exactly one child.
This stage represents that exact Core operation explicitly. It does not skip
inspection, audit or legacy validation, and does not enable the default strict hook.

Canonical rollback calls `Mind.qualifyRollbackTarget(retained)` instead of the
generic current-context qualifier. Under the parent monitor it requires the exact
current live direct child without grandchildren. Local link/analyze semantics,
regeneration of generated rules, native refresh commit and ordinary rollback
rejection handling are preserved. Only for the synchronous `tx.commit()` call on
the successfully locally qualified technical child, private Core fields designate
the retained sibling and owning thread; finally clears both on every exit.

`requirePendingPhysicalChild` remains unchanged. The new read-only
`requirePendingValidationChild` uses that original contract unless a private live
rollback-refresh scope is present. In the latter case it checks physical root,
exactly two reservations, both distinct actual direct children of the same owner,
current retained sibling, no grandchildren, live original reservations and owning
thread. Its returned sibling identifies inventory to guard, not knowledge to merge.
There is no caller-provided boolean, statement or detached proof that enables this
scope. Calling the ordinary check on this pair still fails.

The provider pending lease captures and rechecks the returned sibling identity and
its bounded complete native rule inventory, in addition to its existing parent,
proposed-X, initialized foreign views, Context/revision, exact connection identities,
current Mind and thread checks. The retained child's inventory is not bound as X,
not added to the foreign cuts, and not fed to inspection or audit. Thus a conflicting
pending rule in the retained child cannot prevent rollback to a consistent parent.
A conflicting parent itself still fails the same synchronous whole-family audit.
The extra sibling has its own row bound; no aggregate CPU/memory bound is claimed.

The actual native hook policy runner now exercises strict rollback without
restoring the old route. It proves retained-child exclusion, no physical revision
publication for the fixture, one hook invocation, incomplete-budget refusal keeping
the exact live child, retry after that refusal, and audited barrier2 rejection of a
legacy masked inconsistent parent while keeping the user child/current revision.
Additional controls reject cross-thread use and ordinary ownership of the pair,
prove a retained-child mutation invalidates an already acquired lease, and invalidate
the freshly reacquired refresh lease/scope after settlement. Existing pending
lease controls continue rejecting arbitrary sibling reservations/grandchildren.

Stage3bi's rollback counterexample is resolved for this bounded strict flat-family
path; its witness-writer counterexample remains. Unsupported parent language still
produces INCOMPLETE rather than silently succeeding. The next integration task is
a fresh owned handoff from already-qualified writers, before deciding default scope.
No detached historical result can authorize that handoff. General native
residual/witness/function coverage and question3 remain open.
