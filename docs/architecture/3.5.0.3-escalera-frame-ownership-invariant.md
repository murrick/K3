# KANGER 3.5.0.3 — Escalera frame ownership invariant

## Scope

This checkpoint audits stack discipline for:

```text
Escalera.mark()
Escalera.commit()
Escalera.release()
```

It is independent of the already proven empty-root checkpoint defect.

## Corrected protocol boundary

The current API has the following shape:

```text
mark()    -> long
commit()  -> long
release() -> long
```

`commit()` and `release()` receive no frame token. Consequently, after an inner frame has been completed, a second parameterless completion call is indistinguishable from a legitimate completion of the outer frame.

Therefore the earlier proposed requirement:

```text
duplicate inner release must be rejected while outer frame remains open
```

cannot be implemented by `Escalera` without changing the completion API to carry frame identity. Any production workaround based on hidden one-shot state would reject valid nested completion sequences and would not establish real ownership.

## Enforceable invariant

With the current API, `Escalera` can and must guarantee:

> Every `commit()` or `release()` consumes exactly one currently open frame in LIFO order. Completion at depth zero is an invariant violation and must be rejected.

Consequences:

1. every `mark()` increases checkpoint depth by one, including when `root == null`;
2. every successful `commit()` decreases depth by one;
3. every successful `release()` decreases depth by one and restores that frame's root snapshot;
4. `commit()` at depth zero throws `IllegalStateException`;
5. `release()` at depth zero throws `IllegalStateException`;
6. auxiliary factory stacks must follow the same successful-completion boundary as the canonical Escalera stack.

## Nested LIFO example

```text
mark outer
add A

mark inner
add B

release
commit
```

Required result:

```text
release -> consumes inner frame and removes B
commit  -> consumes outer frame and retains A
```

A further `commit()` or `release()` must fail because checkpoint depth is zero.

## Strong ownership extension

Detecting a duplicated completion from a specific lexical scope requires an explicit frame identity, for example:

```text
CheckpointToken token = mark();
release(token);
commit(token);
```

Such an API change is outside the current minimal correction boundary because it would require coordinated changes across `ICache`, every factory, `Mind`, `Linker`, and all transaction runners.

This remains a possible future hardening direction, not a property of the current parameterless API.

## Regression gate

```text
kanger-console/src/org/kanger/KangerEscaleraFrameOwnershipSafetyRunner.java
```

The corrected runner verifies:

```text
nested inner release restores the outer snapshot
outer commit retains the outer mutation
commit underflow is rejected
release underflow is rejected
```

It deliberately does not claim that lexical frame ownership can be inferred without a token.

## Relationship to empty-root defect

The two proven defects remain distinct:

```text
empty-root mark defect
    mark failed to create a frame when root was null

stack-discipline defect
    completion at depth zero was silently accepted
```

Both are corrected by the nullable checkpoint frame plus strict underflow guards.

## Classification

```text
nullable frame creation: corrected
LIFO depth discipline: corrected
underflow rejection: corrected
lexical frame identity: unsupported by current API
explicit token redesign: deferred
```
