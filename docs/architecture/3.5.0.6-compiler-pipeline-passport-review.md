# KANGER 3.5.0.6 — compiler pipeline architectural passport review

## Scope

This document describes the single internal workflow formed by:

```text
source text
    -> Parser
    -> Token cursor
    -> mutable Leaf AST
    -> Compiller
    -> canonical KANGER units in one Mind
```

`Parser` and `Compiller` are documented together because `Token` and `Leaf` form a private intermediate language used only between these two stages. They are not independent public semantic subsystems.

## Architectural role

The compiler pipeline is the boundary between external source syntax and the canonical semantic object model of KANGER.

```text
external syntax space
    -> parser-owned transient representation
    -> compiler-owned semantic construction
    -> Mind factory canonicalization
```

The pipeline does not execute inference, determine truth, publish a transaction, or replace factory identity rules.

## Pipeline ownership

### Parser ownership

`Parser` owns no `Mind` and no semantic units. It owns only one parse operation's mutable lexical cursor and AST construction state.

### Token ownership

`Token` is a mutable source cursor containing only:

```text
source position
source length
```

The token text is a projection obtained from the original source string. A `Token` does not own a copied lexeme.

### Leaf ownership

`Leaf` is a parser-private mutable AST node containing:

```text
normalized value
left/right child references
parser priority
calculated range
source position
```

It belongs to one parse/compile workflow and has no canonical identity, persistence lifecycle, transaction visibility or independent ownership.

### Compiller ownership

`Compiller` is bound to exactly one `Mind`. It consumes the parser AST and uses that Mind's factories to construct and canonicalize semantic units.

## Stage 1 — lexical scanning

`Parser.nextToken(source, cursor)` advances a reusable `Token` over the original source.

It recognizes:

- delimiters;
- longest matching operators;
- block and line comments;
- quoted literals;
- nested brace blocks;
- identifiers;
- numeric forms;
- punctuation and grouping syntax.

The lexical cursor preserves source positions for diagnostics. Unclosed comments, quotes or brackets fail with `ParseErrorException` carrying the original position.

```text
Token position != semantic identity
Token text != canonical Term
```

## Stage 2 — AST construction

Parser converts the token stream into a mutable `Leaf` tree according to the frozen operator table.

The operator table defines:

- external aliases;
- internal operation names;
- precedence;
- arity;
- direction;
- postfix behaviour;
- replacement semantics.

The tree is normalized for the exact traversal expected by `Compiller`:

- grouping nodes may be removed;
- functional names are moved into operation nodes;
- actual range is calculated;
- comma trees encode ordered arguments;
- quantifiers retain their variable and body positions;
- conjunction, disjunction and implication preserve historical ordering.

```text
Leaf != Rule
Leaf != Domain
Leaf range != persistent arity object
Leaf value != canonical Term
```

The numerical priorities and resulting tree shape are compatibility semantics, not formatting details.

## Stage 3 — semantic compilation

`Compiller.compileLine(...)` creates a new provisional Rule in the target Mind, stores the source origin Term, recursively translates the Leaf tree and finally delegates canonicalization to `RuleFactory`.

The compiler may construct:

- Rule;
- Domain;
- Predicate;
- Term;
- TVariable;
- U-witness;
- Function;
- ArgumentsList and Argument references.

These objects become canonical only through their owning factories.

```text
compiled provisional object != canonical published object
compiler construction != factory canonicalization
compile success != transaction commit
```

## Logical transformation

`Compiller.construct(...)` translates parser operators into the historical Rule domain-tree model.

Negation, conjunction, disjunction and implication do not map to a generic Boolean AST. They clone, append and invert Rule branches according to antecedent/consequent polarity.

The ordering of those operations is a semantic kernel. Refactoring it requires an equivalence proof and permanent regression gate.

## Quantifier compilation

Quantifiers create different semantic objects depending on operator and current polarity:

```text
matching quantifier/polarity
    -> Rule-owned TVariable

opposite quantifier/polarity
    -> Rule-owned U-witness
```

The compiler:

- rejects duplicate variable names;
- records Rule substitutable/abstractive state;
- marks an earlier U-witness as dominant where required;
- resolves later argument references through the Rule-local replacement map.

```text
source variable name != TVariable identity
source quantifier node != canonical variable
```

## Function and predicate resolution

During compilation, a function signature is resolved against:

1. Calculator infrastructure operations;
2. the current Mind Library.

The resulting `FunctionBinding` is explicit:

```text
built-in operation -> INFRASTRUCTURE
Library operation  -> UDF_DYNAMIC
```

Compiler resolution determines binding metadata but does not execute the operation.

Predicate and Domain identity are delegated to their factories.

## Arguments and external parameters

Comma trees are flattened left-to-right.

Argument compilation supports:

- nested Function definitions;
- `_set` construction into a canonical set Term;
- Rule-local variable references;
- literal Term canonicalization;
- external `?...` placeholders consumed from the provided Queue in source order.

Insufficient external values, duplicate variables, empty terms and undefined functions are compilation errors, not unresolved runtime results.

## Source origin and provenance

The original source string is stored as the Rule origin Term before semantic construction.

```text
source origin != canonical Rule identity
source origin != derivation provenance
```

Origin explains where a Rule was compiled from. `Cause` explains how a later result was derived.

## Failure boundary

Parser failure leaves no semantic units because no Mind is involved.

Compiler failure may occur after provisional units have been registered in the current Mind. `Compiller` itself creates no checkpoint and owns no rollback.

Therefore caller obligations are:

- compile inside an appropriate child Mind or explicit transaction boundary when failure isolation is required;
- release that context on parse/compile failure;
- never treat a partially constructed Rule as published merely because an operational ID was allocated.

```text
parse success != compile success
compile success != commit
allocated ID != durable publication
```

## Concurrency

Parser static routines are reentrant only when each call owns its own mutable Token and Leaf graph.

`Compiller` is bound to one mutable Mind and is not independently thread-safe. Concurrent compilation through one Mind requires external serialization or separate child Minds.

## Public-surface classification

### Architectural API

- `Parser` entry points used by callers to parse source;
- `Compiller.compileLine(...)` as the semantic compilation boundary.

### Internal pipeline SPI

- `Token`;
- `Leaf`;
- parser operator metadata and AST normalization helpers;
- recursive construction helpers inside `Compiller`.

`Token` and `Leaf` are public Java classes for historical accessibility, but they are not public semantic API and should be documented as internal compiler structures.

## Core invariants

```text
Token identity != semantic identity
Leaf identity != Rule identity
Parser owns no Mind
Compiller owns no transaction
parse success != compilation success
compilation success != transaction commit
source origin != canonical identity
factory canonicalization remains authoritative
```

## Historical note

The spelling `Compiller` is historical compatibility surface. Renaming it is not part of documentation consolidation and would require a separate API migration decision.
