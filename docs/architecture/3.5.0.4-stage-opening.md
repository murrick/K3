## Purpose

This stage makes the established architecture understandable from the source itself.

Architectural Javadoc must explain the semantic and lifecycle meaning of significant implementation types rather than restate their names, signatures, fields, or obvious control flow.

For each documented component, the relevant questions are:

```text
what the component represents in KANGER;
why it exists;
which architectural boundary it implements;
who creates and owns it;
through which reference or interface it is published;
how long it lives;
where cleanup authority resides;
how it participates in transactions;
how it relates to persistence;
which invariants it maintains;
which side effects and obligations apply to callers.
```

## Governing invariant

> `3.5.0.4` must not intentionally change executable behavior.

The stage does not authorize:

- source-language or inference-semantic changes;
- persistence-format or storage-policy changes;
- performance-policy changes;
- signature, visibility, synchronization, or statement-order changes;
- speculative lifecycle coupling introduced only to make documentation simpler;
- public API migration hidden inside implementation documentation.

Any executable defect discovered while reconstructing a contract must be recorded separately and requires its own invariant proof and regression package.

## Evidence and authority

Architectural statements must be supported by one or more of:

1. current production code at the working HEAD;
2. a late closure or subsystem resolution document;
3. a focused regression or qualification gate;
4. a directly observed lifecycle trace.

The authority order for conflicting documents is:

```text
current production code
    > stage closure documents
      > subsystem resolution documents
        > candidate and audit-opening documents
          > historical comments and early recovery notes
```

A historical `pending`, `candidate`, or `unresolved` label does not reopen an issue that a later closure explicitly resolved.

## Documentation layers

### `3.5.0.4` — implementation architecture

This stage documents concrete implementation roles and internal lifecycle boundaries.

It may describe that an implementation method backs an existing public compatibility slot, but it must not silently redefine the external API contract.

### `3.5.0.5` — public API contract

The following work is deliberately deferred to the next stage:

- full review of `IUser`, `IMind`, `IFactory`, units, and other public interfaces;
- compatibility-sensitive terminology;
- completeness and accuracy of method-level public API contracts;
- historical API slots such as `User.currentMind`;
- error, exception, and externally observable side-effect documentation.

The two layers may cite the same evidence, but they have different audiences and acceptance criteria.

## Class-level semantic template

A significant implementation type should document the applicable dimensions in this order:

1. **Representation** — what the object is in the KANGER model.
2. **Architectural role** — why it exists and which responsibility boundary it implements.
3. **Ownership and publication** — who creates it, who retains it, and how other components obtain it.
4. **Lifecycle** — creation, active lifetime, replacement, completion, and cleanup authority.
5. **Transaction participation** — inheritance, local overlays, commit, rollback, checkpoints, or query-local state.
6. **Persistence relationship** — whether the object is durable, hydrates durable state, coordinates a storage boundary, or is memory-only.
7. **Maintained invariants** — properties that every valid operation must preserve.
8. **Caller obligations and side effects** — preconditions, state transitions, invalidated references, and effects outside the returned value.
9. **Compatibility boundary** — retained historical surfaces whose implementation role is narrower than their names suggest.

A dimension with no architectural content is omitted. It must not be filled with boilerplate such as “not applicable”.

## Method-level documentation rule

Method Javadoc is required where a method crosses an architectural boundary or performs a non-obvious state transition.

Useful method documentation explains some combination of:

```text
semantic effect;
state transition;
ownership or publication effect;
transaction consequence;
cleanup and failure boundary;
persistence consequence;
caller postcondition.
```

It must not merely translate the signature into prose.

Private helper documentation is justified only when the helper encodes a lifecycle protocol, lock-order rule, checkpoint boundary, canonicalization rule, or other non-local invariant.

## Language policy

Repository architecture evidence remains in English, consistent with the existing `docs/architecture` corpus.

The first implementation Javadoc pilot is written in Russian, consistent with the existing generated public documentation and avoiding an uncontrolled language mixture within the same generated package documentation.

A future bilingual publication layer is outside this stage.

## Type-map-first workflow

No mass Javadoc editing is authorized before the type map identifies:

- the significant type;
- its architectural category;
- owner and publication boundary;
- lifecycle class;
- transaction and persistence role;
- cleanup authority;
- authoritative evidence;
- documentation priority.

The map describes the current implementation. It is not a target decomposition proposal and must not make current package boundaries normative for a future KANGER architecture.

## First checkpoint: J1

Working name:

```text
J1 — Architectural Javadoc framework and User–Mind pilot
```

`J1` is a checkpoint label, not a fifth version component.

### J1 scope

Documentation artifacts:

```text
docs/architecture/3.5.0.4-stage-opening.md
docs/architecture/3.5.0.4-type-map.md
```

Implementation pilot:

```text
kanger/src/org/kanger/User.java
kanger/src/org/kanger/Mind.java
```

The pilot initially changes class-level Javadoc only. Method-level additions are limited to lifecycle boundaries whose meaning cannot be understood from the class contract alone.

### J1 exclusions

The pilot does not edit:

```text
IUser.java
IMind.java
factory implementations
Linker
storage implementations
units
query-result stores
```

Those surfaces remain in the type map and are documented only after the pilot template has been reviewed in generated output.

### Why `User` and `Mind`

The pair exercises nearly every documentation dimension without requiring broad source edits:

- user-scoped resource ownership;
- explicit publication of runtime references;
- root and child transaction lifecycles;
- storage attachment and durability boundary;
- commit, rollback, cleanup, and failure isolation;
- compatibility-sensitive `currentMind` semantics;
- factory, store, compiler, analyzer, calculator, and Linker composition.

## J1 acceptance criteria

J1 is acceptable only when:

1. changes are documentation-only;
2. no executable token, signature, visibility, annotation, synchronization, or statement order changes;
3. `User` and `Mind` class documentation answers the applicable ownership, publication, lifecycle, transaction, persistence, invariant, and caller-obligation questions;
4. every non-obvious claim is traceable to production code or authoritative evidence;
5. `User.currentMind` is described according to the final `3.5.0.3` contract and not as internal lifecycle authority;
6. implementation Javadoc does not duplicate or pre-empt the complete public API audit;
7. Javadoc generation succeeds on Java 8 and Java 21;
8. the full existing CI and qualification contour remains green;
9. PR `#31` remains draft;
10. the pilot is reviewed in rendered form before the template is propagated.

## Stage progression after J1

After the pilot is accepted, documentation proceeds by architecture rather than by package order:

1. concrete factory subsystem;
2. `Linker`;
3. `Escalera`, `Index`, and the storage boundary;
4. principal units and internal interfaces;
5. query-result stores and compiler/analyzer/calculator support types.

Each expansion checkpoint may refine the template, but it must preserve terminology already validated by the pilot unless new evidence requires an explicit correction.

## Artifact policy

PR `#31` remains draft throughout `3.5.0.4` and `3.5.0.5`.

The branch `develop/3.5.0.4` is created only after the complete architectural Javadoc stage is closed and qualified. The J1 pilot alone is not a stage artifact.
