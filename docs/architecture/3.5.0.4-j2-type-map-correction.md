# KANGER 3.5.0.4 — J2 type-map correction

## Status

This note corrects the P1 factory grouping in `3.5.0.4-type-map.md` using stronger production-source evidence discovered during J2.

The correction is authoritative for subsequent `3.5.0.4` work. The historical wording remains useful as a record of the initial map, but must not be used to describe all concrete factories as child overlays.

## Superseded generalization

The initial P1 row grouped all concrete factories as:

```text
canonical registries plus transaction overlays
root and child factories have different attachment and inheritance paths
```

That statement is valid for several factory categories but not for `DictionaryFactory` and `PredicateFactory` in the standard `Mind` lifecycle.

## Stronger source evidence

Child `Mind` construction explicitly reuses the parent's instances:

```java
terms = (DictionaryFactory) root.getTerms();
predicates = (PredicateFactory) root.getPredicates();
```

The remaining principal factories initialize child transaction state through their own `transaction(parentFactory)` paths.

## Corrected P1 split

### P1a — chain-shared canonical registries

```text
DictionaryFactory
PredicateFactory
```

Contract:

- constructed and retained by the root `Mind`;
- published by exact reference throughout the child Mind chain;
- canonical cache, counters, and storage attachment are shared through that instance;
- not normal child transaction overlays;
- not promoted by the standard `Mind.commit` composite;
- category-specific packing occurs at root transaction quiescence.

### P1b — explicit child transaction factories

```text
DomainFactory
RuleFactory
CommentFactory
TVariableFactory
TValueFactory
FunctionFactory
FValueFactory
LibraryFactory
```

Contract:

- each `Mind` initializes a category-specific factory instance;
- child construction calls `transaction(parentFactory)`;
- parent commit/release coordinates overlay completion;
- several participate in composite cache checkpoints and action-state rollback;
- persistence attachment and cleanup still follow category-specific ownership rules.

### P1c — inference/index owners

```text
RuleCandidateIndex
Linker
```

Contract remains unchanged: these types own acceleration/query metadata and must be documented against their precise generation, hydration, cleanup, and lock-order boundaries.

## Consequences for existing map text

Read the P1 subsystem table as follows:

```text
"Concrete factories" row
    applies directly to P1b
    applies to P1a only for canonical registry, IBase attachment,
    persistence and cleanup concepts
    does not imply child overlays for P1a
```

The detailed `User` and `Mind` P0 maps remain valid. The `Mind` composition-root wording means that a Mind exposes and coordinates the factories visible at that level; it does not imply that every factory reference is a distinct child-owned instance.

## Documentation consequence

J2 class-level Javadoc must state exact-instance sharing explicitly. Later P1 checkpoints must not copy that wording to transactional factories, and must instead document their child overlay and parent completion protocols.

This correction satisfies the map-maintenance rule: production source overrules the initial abstraction, while the investigation history is retained rather than rewritten.
