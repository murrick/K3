## The actual call paths

`Mind.commit` calls provider `validateCommit(child)` at the physical root before
native settlement. A rejected technical child is released; a rejected user-visible
transaction retains its exact child for amendment/rollback. However this hook is
not exclusive to user authoring:

- ordinary assertion/rule query settles its proposed child through it;
- `qualifyCurrentContext` refreshes generated rules in a TechnicalMindTransaction
  and commits the refreshed view, including from queryCheck;
- `User.checkpoint` creates an empty child and commits it when closing/checkpointing;
- `DB.publishContext` publishes a generation, marks it accepted and calls
  `User.reloadAfterContextPublication`; opening/qualifying that storage can reach
  the same hook after physical publication has already succeeded.

The old default uses pair/composition validation. Explicit native attempts have
owning leases, engines and limits; their pre/post checks are separate. The existing
`validatePendingProductionCommit` can classify/bind the complete proposed X and
private cuts, choose ground/universal/witness, and refuse incomplete or unaudited
results. Its lease currently requires distinct ordinary cuts: a trust-group
member is not a supported separate family cut. `ContextProductionSnapshotSession`
likewise explicitly refuses TRUST views. Removing that guard would incorrectly
model commune members as independent siblings; it is not a proved solution.

## Concrete blockers, before proposing a repair

1. A standalone legal function rule `!@x fun(x)->next(x+1);` can be attached to
   ordinary X. An unrelated or conflicting write must correctly return INCOMPLETE
   if the whole native binding is unsupported. But *closing/checkpointing the
   unchanged source* then invokes the same strict authoring qualifier and fails
   with Unsupported native clause argument. Scope refusal of a new write has
   spread into the lifecycle of existing legal knowledge.
2. Rules `!@x p(x)->q(x);`, Facts `!p(1);`, X `!anchor(1);`, connect both as
   `trust own`. A read-only session's close/checkpoint now refuses with
   `Distinct ordinary initialized pending cuts required`, although no primary
   assertion is being introduced. The maintained compatibility control requires
   the native joint answer and a usable unchanged-source close.
3. The same trusted setup, followed by `ctx publish ordinary-compatibility`,
   reaches reload after physical publication. Candidate qualification refuses
   that technical commit, and DB reports TransactionSettlementException with
   outcome COMMITTED. Refusal is too late to undo that publication. The desired
   contract requires successful configuration publication and usable physical
   state, not acceptance of this exception as normal behavior.

The two new runners retain their intended behavior. Candidate failures are not
weakened to PASS. Ordinary production keeps the old route while the boundary is
unresolved; no catch-and-legacy-fallback is added for unsupported authoring.
