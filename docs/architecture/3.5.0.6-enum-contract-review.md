# KANGER 3.5.0.6 — enum contract review

## Purpose

Enums are documented only when they encode a stable semantic, execution, or persistence contract. Plain diagnostic flags and local control constants do not require standalone architectural passports.

## Semantic enums

### DataType

`DataType` defines the typed value domain of canonical `Term` objects. It is part of term identity, comparison, serialization, expansion, and operation dispatch.

Key distinctions:

- `VOID` represents an undefined/empty typed state, not Java `null` identity;
- `TERM` represents a nested canonical term reference;
- `NUMERIC` uses the historical unified numeric representation;
- `INTERVAL` and `SET` are structured term-valued containers;
- `BLOB` is raw binary payload and has value semantics distinct from strings;
- enum order must not be treated as semantic ordering unless explicitly encoded by persistence.

`DataType` therefore belongs to the public semantic contract.

### ArgumentType

`ArgumentType` identifies what an `Argument` references, not the current resolved value of that reference.

The stable distinction is:

```
TERM / TVARIABLE / TVALUE / FUNCTION / FVALUE / EMPTY
    = reference kind

current Term value
    = contextual projection in a Mind
```

It participates in hydration, serialization, polymorphic `setValue`, and runtime projection. It belongs to the public semantic contract.

### FunctionBinding

`FunctionBinding` is an execution-resolution contract captured by each compiled `Function` occurrence.

- `INFRASTRUCTURE` resolves only through the built-in registry;
- `UDF_DYNAMIC` resolves through the current user Library on each call;
- `LEGACY_AUTO` preserves the historical compatibility order.

`fromCode(int)` deliberately falls back to `LEGACY_AUTO` for unknown legacy codes. Enum declaration order is therefore persistence-visible and must not be reordered casually.

This enum is both semantic and compatibility-critical.

## Persistence/wire discriminator

### UnitType

`UnitType` identifies serialized or operational unit categories used by pack/unpack and internal dispatch.

It does not define canonical identity or object ownership. Names such as `HYPOTHESE` and generic categories such as `LONG`, `LONGS`, `ARGLIST`, and `ARGUMENT` are historical wire vocabulary.

Rules:

- values are persistence/wire discriminators, not a semantic class hierarchy;
- declaration order or numeric encoding must be treated as compatibility-sensitive until proven otherwise;
- historical spelling must not be corrected as a documentation-only change;
- adding, removing, or reordering constants requires storage compatibility analysis.

`UnitType` needs concise compatibility documentation, not a philosophical passport.

## Operational enums

Enums used only for logging modes, UI presentation, debug flags, or local execution control should be documented at the owning class or method. They need standalone documentation only when their values cross persistence, plugin, or public API boundaries.

## Audit rule

Classify each enum into exactly one category:

1. semantic contract;
2. execution/binding contract;
3. persistence/wire discriminator;
4. diagnostic/presentation control.

Only categories 1–3 require durable architectural documentation. Category 4 is adequately covered where consumed.
