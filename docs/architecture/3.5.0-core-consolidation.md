# KANGER 3.5.0 — Core consolidation and architectural documentation

## Purpose

KANGER 3.5.0 is a single finishing artifact built on the verified 3.4.4.2.3 stabilization baseline.

It does not introduce new logical semantics, storage features, or performance work. Its purpose is to make the established implementation smaller, terminologically coherent, explicitly invariant-safe, and understandable from the source itself.

## Governing invariant

> KANGER 3.5.0 must not intentionally change observable execution semantics.

Permitted work includes:

- removal of code proven unreachable or unused;
- naming and lifecycle alignment whose behavioral neutrality is mechanically or regressively verified;
- focused correction of demonstrated invariant violations;
- assertions, diagnostics, and regressions that expose existing contracts;
- architectural Javadoc describing role, usage, ownership, lifecycle, contracts, side effects, and semantic boundaries;
- revision of public API Javadoc against actual current behavior.

A newly discovered behavior change that cannot be justified as an invariant correction must be recorded separately rather than hidden inside cleanup.

## Artifact stages

### 3.5.0.1 — Dead-code audit and cleanup

Classify every candidate before removal:

1. **Demonstrably dead** — no supported construction, invocation, persistence, reflection, scripting, CLI, test, or API path reaches it.
2. **Architectural reserve** — an intentional extension point or compatibility surface; retain and document it.
3. **Diagnostic/specification support** — code used by regression runners, observability, migration, or executable specification; retain unless replaced deliberately.
4. **Uncertain** — insufficient evidence; retain until static and runtime evidence resolves it.

An IDE or search result reporting zero direct Java references is not sufficient evidence by itself. The audit must exclude indirect use through reflection, serialization, JavaScript/UDF exposure, persistence hydration, command entry points, external API compatibility, and test discovery.

### 3.5.0.2 — Naming and lifecycle alignment

Align names with architectural role and lifetime, especially across persistent, transaction-local, query-local, transient runtime, and shared canonical state.

Verify operation vocabulary and symmetry, including create/register/link/bind/attach and unlink/detach/release/clear/close/destroy.

### 3.5.0.3 — Invariant audit and hardening

For each critical subsystem, make explicit:

- ownership;
- creation and publication boundary;
- reachability and canonical identity;
- mutation authority;
- transaction inheritance, commit, rollback, and cleanup;
- persistence and reopen behavior;
- symmetric relationships;
- impossible states and failure policy.

Use focused regressions for every corrected violation.

### 3.5.0.4 — Architectural Javadoc

Document what each significant type represents in KANGER, where it participates, who owns it, how long it lives, what invariants it maintains, and what callers must guarantee.

Method documentation must explain semantic effect and lifecycle consequences rather than restating the signature.

### 3.5.0.5 — Public API documentation audit

Review existing API Javadoc as an external contract:

- current architectural accuracy;
- distinction between source provenance and materialized state;
- transaction and lifecycle semantics;
- error and side-effect contracts;
- practical usability without reading implementation sources.

## Working model

All five stages remain on one branch and in one draft pull request. Each fourth-component stage is represented by a validated checkpoint commit or commit group, while 3.5.0 is the complete three-component artifact.
