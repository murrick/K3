# KANGER III 3.5.0.3 — Mind composite commit exception atomicity

## Scope

Audit of the parent/child `Mind.commit(IMind)` protocol and its interaction with factory `mark / commit / release` frames.

## Current protocol

When the child rule sequence is not already sequenced by the parent, `Mind.commit(child)` opens marks independently on the parent factories:

```text
functions
fValues
tVars
tValues
domains
rules
comments
library
```

It then merges child factories, merges deleted/restored metadata, runs `analyzer.checkDatabase(...)`, and finally either commits or releases those marks.

## Defect

The complete composite operation is not protected by `try / catch / finally`.

Any exception after the first successful `mark()` and before the normal completion block can leave:

- a prefix of parent factories marked while later factories are unmarked;
- all parent factory frames still open;
- merged child state partially published;
- `deleted` / `restored` metadata partially merged;
- the child transaction reservation still active because `finishTransactionLocked()` is not reached;
- the parent `transactionCounter` permanently elevated;
- a later unrelated `commit()` or `release()` consuming stale frames.

The problem is independent of the already documented empty-root and underflow defects. Even with a correct cache frame implementation, a composite transaction requires exception-safe orchestration.

## Required invariant

```text
begin parent composite commit
    acquire every required frame
    perform merge and validation

normal success
    consume every acquired frame exactly once
    finish child transaction exactly once

validation rejection
    restore every acquired frame exactly once
    restore metadata snapshots
    finish child transaction exactly once

exception
    restore every acquired frame in reverse acquisition order
    restore metadata snapshots
    finish or abort child transaction reservation exactly once
    rethrow original exception with rollback failures suppressed
```

A factory mark must be recorded as acquired only after that individual mark succeeds. Rollback must therefore operate over an explicit acquisition ledger rather than assuming all factories reached the same depth.

## Related persistence barrier

`Escalera.update()` clears its internal mark stack after a storage flush. Consequently, persistence update must be prohibited while any speculative frame is open, or explicitly defined as a transaction commit barrier. Silently clearing open checkpoints is not a valid rollback protocol.

## Remediation direction

Introduce one parent-level composite frame/guard that owns:

- the ordered list of successfully marked factories;
- snapshots of parent metadata (`deleted`, `restored`, and other mutable control state);
- child reservation completion state;
- reverse-order rollback;
- strict single completion.

`Mind.commit(child)` should delegate all completion paths to this guard.
