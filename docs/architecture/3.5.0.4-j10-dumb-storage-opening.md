## Physical ownership model under audit

```text
DB
  owns the selected storage name and logical Base registry
  coordinates use / close / flush / remove / reindex generation lifecycle

Base
  owns one logical baseCode subset of the shared physical files
  coordinates Index, Data, RecoveryLog and IntegrityManifest
  owns schema-local IDs, endpoint reconstruction and hydrated-record cache

Data
  owns the .store block format and physical-offset LRU
  appends or relocates packed Sapato records and tombstones removed blocks

Index
  maps (baseCode, semantic ID) to physical store offsets

RecoveryLog
  retains first before-images until a completed flush checkpoint

IntegrityManifest
  protects committed index/store subsets with snapshot and delta checksums
```

## Governing distinctions

1. Semantic chain order is persisted through `Sapato.next`, not numeric ID order.
2. `baseCode` is physical addressing metadata assigned by canonical base-acquisition order.
3. The Base hydrated-record cache and Data offset cache are physical accelerators, not semantic identity owners.
4. WAL rollback restores the pre-flush state; integrity snapshot/delta validates the committed state.
5. `DB` owns generation publication and must not leave a registry that mixes closed, failed and still-open bases.
6. Reindex is a generation replacement operation, not an in-place semantic rewrite.

## Existing evidence to preserve

- strict DUMB Q1–Q3 qualification;
- crash recovery at the existing fault-injection points;
- integrity bootstrap and corruption rejection;
- full-range signed semantic IDs except reserved traversal sentinel `-1`;
- linked endpoint reconstruction independent of ID allocation/commit order;
- bounded Base and Data cache telemetry;
- storage traversal and persistent lifecycle diagnostics.

## Focused hypotheses

### H1 — DB close failure isolation

`DB.close()` currently iterates all registered bases and clears the registry only
after every `IBase.close()` succeeds. A failure after earlier bases have already
closed may leave a mixed registry. A retry would then revisit already-closed
bases before reaching still-open bases.

Required evidence:

- inject one deterministic close failure among several registered bases;
- prove whether later bases are attempted;
- inspect the registry after failure;
- prove whether a clean retry can close the remaining generation.

### H2 — reindex generation swap publication

`DB.reindex()` deletes the old files before invoking unchecked `File.renameTo()`
operations for the temporary generation. This is a serious candidate, but it
must be reproduced at the actual filesystem boundary before any correction.

Required evidence:

- distinguish a copy/build failure from a swap/publication failure;
- demonstrate the exact surviving old/temporary files;
- avoid relying on platform-specific rename assumptions;
- preserve file format and baseCode assignment if correction is required.
