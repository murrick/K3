# KANGER 3.5.0.6 — DUMB storage implementation passport review

## Status

This document records the implementation-level architectural contract of the
current DUMB persistence family. It complements the already documented
`IData`, `IBase`, `ICache`, and `IStep` SPI contracts and does not redefine
those interfaces.

The document is normative for architecture review and a source for later
method-level Javadoc patches. It does not authorize behavioral changes.

## Architectural role

The DUMB module is the concrete persistence adapter of the current KANGER
runtime. It translates the logical storage SPI into a physical generation of
linked records, cached steps, durable roots and tops, and reversible maintenance
operations.

It is intentionally simple storage. It is not a semantic database, a query
engine, a transaction manager for Mind overlays, or an owner of canonical
knowledge identity.

```text
semantic units and factories
        -> IBase / IData SPI
        -> DUMB Data / Base / Cache / Step family
        -> physical generation and record chain
```

## Core separation

The implementation must preserve four distinct layers:

1. **semantic unit** — canonical KANGER object;
2. **serialized packet** — physical representation of that object;
3. **step** — node in a persistent linked chain;
4. **generation** — the currently published collection of bases and files.

These layers are related but not interchangeable.

```text
semantic identity != step identity
step identity != traversal position
serialized bytes != canonical object identity
generation identity != Mind transaction identity
```

## Data implementation

The concrete `Data` implementation owns one opened physical storage generation
for one user-level storage namespace.

Its responsibilities include:

- resolving/opening the requested generation;
- creating and publishing named bases;
- tracking opened bases;
- coordinating flush and close;
- removing a generation only through explicit destructive API;
- exposing generation and namespace observability;
- performing reversible reindex publication.

`Data` does not own the `Mind` transaction chain. A child Mind is not a child
storage generation, and commit/release of Mind overlays must not be mapped to
open/close of Data.

### Acquisition and publication

Opening or constructing a candidate base is not equivalent to publishing it in
the active base registry.

```text
acquire physical resource
        -> validate/open
        -> publish into Data registry
```

If acquisition fails, no partially acquired base may remain visible through the
registry. This is the storage acquisition atomicity invariant recovered during
3.5.0 stabilization.

### Close failure isolation

Closing several bases is a best-effort aggregate operation. Failure of one base
must not prevent close attempts for the remaining bases.

The implementation may report an aggregate/first failure after all owned bases
have received a close attempt, but it must not abandon the rest of the ownership
set at the first exception.

```text
one close failure != unattempted close of sibling bases
```

### Reindex publication

Reindex is a migration workflow, not in-place mutation of the active generation.

The required shape is:

```text
active generation
        -> build candidate generation
        -> validate candidate
        -> atomically publish candidate
        -> retire old generation
```

Before successful publication, failure must leave the original generation
usable and authoritative.

```text
failed reindex != partially published generation
```

## Base implementation

A concrete `Base` owns one physical chain of records belonging to one schema or
unit family.

Its responsibilities include:

- allocation of persistent record IDs;
- append/update/delete of records;
- root/top management;
- hydration of semantic units from packets;
- cache coordination;
- flush and close;
- clear and reindex support;
- telemetry of physical and cached state.

A Base is not a set of canonical semantic units. It is the physical authority
for records and chain metadata used by a factory.

### Root and top

`root` and `top` are physical chain endpoints.

They are not:

- minimum and maximum semantic IDs;
- query result bounds;
- transaction checkpoints;
- proof of canonical ordering.

```text
root/top != semantic ordering
```

### Add and update

`add()` publishes a new physical record and links it into the current chain.
`update()` replaces the physical representation of an existing persistent
record.

Neither operation by itself defines semantic canonicalization. The calling
factory must already have resolved the semantic identity contract.

### Delete and clear

Physical delete removes or invalidates one record according to the DUMB chain
contract. `clear()` destroys the contents of one physical base.

These operations are different from transaction-visible deletion markers in
Mind:

```text
Mind deletion marker != physical Base.delete
Mind rollback != Base.clear
```

The default multi-record `deleteAll()` loop does not promise group atomicity.
Callers must not interpret partial failure as an automatic rollback of earlier
physical deletions.

### Flush, cache clear, and close

These lifecycle operations are intentionally distinct:

- `flush()` establishes the implementation's durability boundary for pending
  physical changes;
- `clearCache()` discards hydrated/cached projections while preserving durable
  records;
- `close()` terminates ownership of opened physical resources;
- `clear()` destroys data.

```text
flush != close
clearCache != clear
close != remove
```

## Step implementation

A concrete `Step` is one physical linked-record node.

Its durable coordinates include:

- persistent ID;
- hash/candidate metadata;
- physical size;
- next-node link;
- serialized packet.

An optionally hydrated semantic object is a runtime attachment and must not be
confused with the durable identity of the Step.

```text
Step != semantic unit
hydrated data == null does not imply missing record
```

Hydration through a Mind may resolve or canonicalize the semantic object using
the relevant factory. Hydration is therefore context-aware, while the packet
and persistent ID remain physical coordinates.

## Cache implementation

The concrete cache accelerates access to Steps and hydrated units and provides
local mark/commit/release support required by storage operations.

It is not:

- the Mind transaction overlay;
- the canonical object registry;
- the durable record authority;
- a semantic equality index.

A hash lookup produces candidates only. Final record or semantic validation
remains mandatory.

```text
cache hit != semantic identity proof
cache checkpoint != Mind transaction checkpoint
```

## Persistence and transaction boundary

The DUMB module persists the root Mind's factory state after the caller has
completed the logical transaction protocol.

It must not infer transaction completion from incidental calls to `flush()`,
`close()`, or base acquisition.

```text
Mind commit/release
        -> root publication protocol
        -> factory pack/update
        -> Base/Data durability
```

A storage failure may prevent durable publication, but it must not silently
reinterpret a failed write as a successful logical commit.

## Ownership

- `IData`/`Data` owns opened bases and generation-level resources.
- `IBase`/`Base` owns physical records, chain endpoints, and its cache.
- `IStep`/`Step` owns one persistent node representation.
- factories own semantic canonicalization.
- `Mind` owns transaction-visible overlays and runtime projections.
- `User` supplies the external storage namespace/configuration.

Borrowed objects returned from these layers must not be closed, removed, or
mutated outside the documented owner.

## Error model

Storage errors are operational failures, not logical false results.

The caller must distinguish:

- record absent;
- hydration failure;
- physical I/O failure;
- schema/generation mismatch;
- destructive-operation failure;
- close failure after partial cleanup.

```text
storage exception != false logical answer
physical absence != unresolved inference
```

## Concurrency

The current DUMB implementation is an owned mutable storage adapter. Concurrent
access requires the synchronization guarantees of the owning Data/Base and the
higher-level Mind reservation protocol.

No caller may assume that independent Java references to the same Data or Base
represent independent physical sessions.

## Recovered permanent invariants

The following implementation properties are permanent qualification targets:

1. storage acquisition is atomic with respect to registry publication;
2. one close failure does not prevent sibling cleanup attempts;
3. reindex publication is reversible until successful swap;
4. cache clearing does not destroy durable records;
5. physical record identity does not replace semantic canonical identity;
6. Mind transaction lifecycle remains separate from storage lifecycle.

## Historical name

`DUMB` identifies the intentionally direct physical storage implementation. It
does not mean that the module may ignore lifecycle, durability, recovery, or
observability contracts.

## Documentation placement

The final production documentation should be distributed as follows:

- module/package overview: full persistence-family model;
- `Data`: generation ownership, acquisition, close isolation, reindex;
- `Base`: record chain, durability, destructive operations;
- `Step`: physical node and hydration;
- cache implementation: acceleration and local checkpoint semantics;
- methods: exact I/O effects, errors, caller obligations, and return states.

No method-level comment should claim semantic canonicalization unless the code
explicitly delegates that decision to the owning KANGER factory.
