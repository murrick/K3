# Rule-relative variable identity in canonical comparison

Stage2i counterexample discovered while investigating multi-variable production
coverage. This is a Core rule-comparison defect, independent of the accepted
X/A versus X/B epistemic-context semantics.

## Concrete counterexample

```text
!@x edge(x,1) -> out(2,x);
!@x @y edge(x,1) -> out(2,y);
!edge(3,1);
!~out(2,4);
```

The second rule implies out(2,4) from edge(3,1): its head variable y is
independent of the premise variable x. The first rule alone implies out(2,3),
but not out(2,4). Thus the complete family is inconsistent.

Before the fix, ordinary Mind.compile accepts this family. The second rule is
mistakenly identified as a duplicate of the first and discarded. With the
independent rule first, the query out(2,4) instead succeeds. A standalone
independent-rule control also succeeds. Native source capture confirms that
the supposed duplicate has the original rule ID and only one declared variable.

Raw probes, pre-fix observations and ordinary compile red/green controls are
retained in `target/context-production-rounds/evidence-stage2i/`.
The committed RuleVariableIdentityRunner independently exercises both orders,
the actual query, the ordinary conflicting assertion and the shared-only case.

A second fixture uses the same number of variables in both rules:

```text
@x @y edge(x,1) && tag(y) -> out(2,x)
@x @y edge(x,1) && tag(y) -> out(2,y)
```

With edge(3,1) and tag(4), both out(2,3) and out(2,4) must be available.
Counting variables alone would not correct this case.

## Cause and bounded correction

Rule.equalsTo delegates literal comparisons to Domain.equalsToStruct. Direct
TVariable positions previously compared only Domain.getVarOrder, an atom-local
normalization. A variable appearing alone in one predicate has the same local
role whether it is x or y elsewhere in the rule. Consequently the canonical
lookup loses sharing across literals and can attach a source occurrence to a
different, stronger or weaker rule.

The TVariable comparison now additionally compares its Rule-relative binder
position, TVariable.index minus Rule.varIndex. Recursive Function structural
comparison already uses this convention. The check uses declared variable
identity rather than current TValue bindings. The old local-shape condition
and all other argument-kind checks remain in force.

Structural hashes are deliberately unchanged. They are coarse candidate
selectors and may collide; definitive comparison now refuses the demonstrated
non-equivalent candidates. This avoids changing persisted hash/index formats.
Actual aliases retain their existing behavior: same binder roles with renamed
symbols and reordered literals still share a canonical rule, even after
unrelated variable allocations. Their source occurrence labels remain separate.

This is the existing positional binder convention made consistent between
plain arguments and recursive functions. It is not a new general alpha-
equivalence, implication, subsumption or arbitrary formula equivalence solver.
C-variable and richer-term comparison are not newly certified. Previously
discarded source assertions are not reconstructed by this correction.

## Relation to production rounds

The preceding multi-variable probe used X: forall x,y edge(x,y), and a target
containing edge(1,2) and forall x,y,z edge(x,y) && edge(y,z) -> out(z,x).
Before the fix, replay of a proved two-variable residual encountered a
one-variable canonical twin and stopped with derived-clause-transport-mismatch.
The existing roundtrip guard correctly prevented a false saturation claim.

After the fix, those residuals replay with their original sharing and the
specific mismatch disappears. The cut still returns INCOMPLETE/Coverage.NONE
because arbitrary multi-variable observation coverage and TSolve filtering
remain unproved. No TSolve inference/filter logic is changed and no wider
coverage certificate is issued by stage2i.

The new rule-identity regression is included in both the focused production
qualification and the full DMZ manifest, so canonical comparison cannot silently
regress in either workflow. Runtime write/publication/topology gates remain
unconnected to the reference; question3 query/hypothesis/orphans remains open.
