## Invariant discovered during documentation

J3 source analysis showed that `DomainFactory` owns semantic state outside `Escalera`:

```text
waiters: deferred Domains consumed by Linker
```

The original checkpoint protocol restored only Escalera. A typed child commit performed under a composite mark could merge child waiters into the parent; a later no-argument release restored the cache but retained those waiters.

Focused red gate:

```text

```

Observed failure:

```text

```

Minimal correction:

```text

Restore Domain waiters on checkpoint release
```

Permanent record:

```text

```

The fix adds a nested waiter snapshot stack parallel to Escalera checkpoints. It changes no Domain identity, Rule expansion criterion, Linker matching rule, persistent format, or public method signature.

## Paired role model

| Dimension | `DomainFactory` | `CommentFactory` | Shared overlay boundary |
| --- | --- | --- | --- |
| Representation | Canonical Domain registry plus transaction-local inference metadata | Rule-ID keyed provenance registry plus effective-view metadata | One concrete factory instance per Mind level |
| Child initialization | Escalera overlay plus copy of parent waiters | Escalera overlay, parent effective view, empty COW overrides | `transaction(parentFactory)` establishes child visibility |
| Existing parent state | Child cache can add/find Domains; waiter set starts as copied state | Inherited Comment is read through parent view and copied before write | Parent state must not be mutated before commit |
| Typed commit | Promotes child units and merges waiters | Promotes child units, copies overrides, merges dirty IDs | Parent factory performs category-specific publication |
| Release | Child factory discarded; composite cache/waiter checkpoint restores parent snapshot | Child factory discarded; COW overrides disappear | Logical rejection must not leak auxiliary state |
| Auxiliary checkpoint | Stack of waiter snapshots | Stack of override/dirty snapshots | Escalera alone is not complete transaction state |
| Persistence | Root-only borrowed Domain `IBase`; cache update | Root-only borrowed Comment `IBase`; cache update plus in-place dirty record update | `User` / `IData` own storage generation and close |
| Packing | Remove deleted Domains and matching waiters | Apply root overrides, then remove deleted Comments and metadata | Packing is category-specific root cleanup |

## Common lifecycle findings

The paired comments agree on these invariants:

1. Each `Mind` owns a distinct factory instance for these categories.
2. A child factory receives visible parent state through `transaction(parentFactory)` without receiving storage close authority.
3. Typed `commit(childFactory)` and no-argument checkpoint `commit()` are different protocols.
4. Parent `Mind` owns the decision and sequencing of child completion.
5. The canonical cache is only one component of factory transaction state when category-specific metadata exists.
6. Root storage attachment is borrowed from `User`; child factories remain memory overlays.
7. A local concurrent collection or synchronized add method does not imply independent thread safety of mutable units or the full transaction protocol.
8. Child clear resets the overlay from the parent view; root clear resets the current storage generation.

## DomainFactory-specific findings

`DomainFactory` Javadoc now describes:

- compound Domain identity and canonicalization;
- per-Mind cache overlay ownership;
- substitutable/abstractive classification during creation;
- deferred-domain waiter publication by `RuleFactory`;
- Linker consumption of waiter metadata;
- copy/merge/checkpoint lifecycle of waiters;
- root-only storage hydration;
- deletion-only packing and waiter cleanup.

The documentation explicitly states that `waiters` is semantic inference state. It is not diagnostic metadata and cannot be omitted from rollback reasoning.

## CommentFactory-specific findings

`CommentFactory` Javadoc now describes:

- Rule-ID, header, and footer identity;
- effective lookup order;
- copy-on-write of inherited Comments;
- parent isolation before commit;
- typed commit of child overrides;
- dirty tracking for already persistent IDs;
- auxiliary checkpoint snapshots;
- effective iterator behavior;
- root-only application of accumulated overrides;
- persistent override survival across close/reopen.

The production safety runner already verifies parent isolation, release, commit, and persistent reopen postconditions. J3 does not reinterpret those postconditions as implementation detail; they define the actual lifecycle contract.

## Important asymmetry

The pair must not be flattened into one generic factory description.

```text
DomainFactory auxiliary state
    copied waiter set
    merge-on-typed-commit
    whole-set rollback snapshot

CommentFactory auxiliary state
    parent effective view
    copy-on-write map
    dirty persistent IDs
    copy-preserving nested journal
```

Both require auxiliary rollback, but for different semantic reasons and through different structures.

## Compatibility surfaces

The classes retain public methods whose exact external contract is deferred:

