# KANGER 3.5.0.4 — J9 storage acquisition atomicity invariant

## Defect

`User.use(IMind, String)` opened the selected `IData` generation and published each schema-specific `IBase` directly into `User.storage` as it was acquired.

If `IData.getBase()` failed after some schemas had been opened, the operation returned by exception with a half-open generation:

```text
IData remained open;
User.isClosed() reported false;
User.storage contained a partial schema set;
no complete factory generation had been attached;
the next lifecycle operation observed ambiguous ownership.
```

## Focused red evidence

Permanent runner:

```text

```

Permanent CI step:

```text
Storage acquisition atomicity invariant
```

The fixture fails on the fourth `getBase()` call. The isolated red run reached the exact state:

```text
storageUsed=true
closeCalls=0
publishedBases=3
```

All Maven tests and all preceding permanent invariant gates passed before the new step failed.

## Governing invariant

> A storage generation is published to KANGER factories only after `IData.use()` and acquisition of the complete canonical schema set succeed. Failure before publication closes the partially opened `IData`, publishes no partial base set, and does not destroy the caller's existing in-memory Mind.

## Correction

Commit:

```text
b358c8785994133ccf774983cc6cef53870c2b9c
Make storage acquisition exception-atomic
```

`User.use()` now performs two phases:

```text
1. acquire IData and all ten IBase handles into a method-local map;
2. replace User.storage only after the complete set exists.
```

If acquisition fails:

- an open `IData` is closed;
- a close failure is attached as suppressed to the original exception;
- the original exception is rethrown;
- the published storage map is not partially mutated;
- factory transaction initialization is not entered.

## Preserved behavior

The correction does not change:

- the canonical ten-schema order;
- `IData`, `IBase`, factory, or public API signatures;
- DUMB file formats, base codes, WAL, recovery, reindex, or cache policy;
- successful factory attachment order;
- persistent ID allocation;
- `Mind` transaction semantics.
