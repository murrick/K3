## Reviewed ownership model

| Dimension | `User` | `Mind` | Boundary established by the pair |
| --- | --- | --- | --- |
| Representation | User-scoped bootstrap and external-resource context | Active logical state, transaction level, and inference workspace | Resource context is not logical transaction state |
| Owner | Application or embedding shell | Caller that creates the root or child level | The application owns `User`; transaction code completes child `Mind` levels |
| Publication | Explicit constructor/lifecycle references; optional external compatibility slot | Explicit `IMind` references and the `next` chain | Internal lifecycle does not discover an active context through hidden global state |
| Lifetime | Usually longer than a query or child transaction | Root is user/session scoped; child is transaction/query scoped | Closing storage does not destroy `User`; completing a child does not replace resource ownership |
| Transaction role | None; coordinates resources used by the transaction system | Root state plus child overlays, commit/release, reservation accounting | `User` must not be described as a transaction or version of knowledge |
| Persistence role | Owns the `IData` attachment, bases, configuration, and flush boundary | Reaches durability only through root factory update and `User.flush()` | A child `Mind` is not an independently durable version |
| Cleanup authority | Coordinates storage close/clear/reindex and chain cleanup | Clears factory/runtime state belonging to its level | Persistent state and query-local references have distinct cleanup paths |
| Compatibility | `currentMind` is caller-managed only | Creation does not publish into `currentMind` | The slot is not internal lifecycle authority |

## Contract consistency findings

The two class contracts agree on the following non-local invariants:

1. The active runtime context is passed explicitly as `IMind`.
2. Every level in one `Mind` chain retains the same `User` reference.
3. A child transaction reserves one unfinished operation in its parent and must complete exactly once.
4. Commit and release have different semantic effects but both discharge the transaction reservation.
5. Root persistence occurs only after transaction quiescence; a child does not write an independent durable snapshot.
6. Storage lifecycle operations may invalidate or replace the effective runtime chain, so callers must use their returned `IMind` value.
7. Query-local C-variable links, inference maps, stores, and Linker indexes are not persistent factory state.
8. `User.currentMind` is not used as storage owner, transaction publication, shutdown root, or active-context discovery.

No contradiction was found between the paired class contracts, current production code, or the final `3.5.0.3` lifecycle resolutions.

## Template findings

The J1 pilot validates the class-level template with four refinements for later checkpoints:

- Open with a direct representation statement before subsystem detail.
- Separate ownership from publication; a component can own a resource without being the mechanism through which the active runtime reference is published.
- State transaction and persistence roles independently; in KANGER an object may coordinate both without itself being durable.
- Document concurrency only as a proven invariant boundary. Do not infer general thread safety from a local lock.

Compatibility language belongs in implementation Javadoc only where it prevents a false architectural interpretation. Complete external method contracts remain reserved for `3.5.0.5`.

## Propagation decision

After qualification, the template may be propagated by architecture rather than package order.

The next checkpoint begins with the concrete factory subsystem because it consumes the ownership, transaction-overlay, persistence, cleanup, and lock-boundary vocabulary established by `User` and `Mind`.

The recommended first factory sequence is:

```text
KangerFactory
    -> DictionaryFactory / PredicateFactory
    -> transactional factories
    -> RuleFactory
```

`RuleFactory` remains last in that sequence because its candidate metadata, hydration boundary, generation checks, and lock-order constraints require the vocabulary established by the simpler factory roles first.
