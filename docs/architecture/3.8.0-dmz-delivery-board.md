# DMZ 3.8.0 — актуальный план завершения

Актуализация: 18.11.2026, этап 658. Это рабочая приёмочная матрица и порядок
разработки. Архитектурные решения задаются SMART и подтверждениями автора;
этот документ не меняет семантику и не принимает открытые предложения.

## Рабочая точка и маршрут чтения

- Runtime baseline: `fix/context-production-rounds`, этап 652, `fb0171fa3ed2fdc520ca26f86089b1a88cc612dc`. Этапы 653–658 добавляют qualification harness и документы без production-изменений; текущий commit указан в Drive checkpoint.
- Цель: реализовать задуманный DMZ и предоставить воспроизводимую ручную приёмку
  всех обязательных операций. Включение по умолчанию, интеграция, замена trust
  и выпуск — отдельные решения с собственными условиями.
- Постоянный вход: [00A](https://docs.google.com/document/d/13ST2WbRRss4gWdhOLm6dv9H9oRQy2qET3sx96HvRKS0/edit).
  Текущая точка восстановления: [checkpoint](3.8.0-dmz-recovery-checkpoint-2026-11-17.md).
- Требования: [SMART 2.0](https://docs.google.com/document/d/1PXSMOt-mbwa30-WathSMc0kLX0tbtjlUpfiRUTKOx7s/edit)
  §20 — кандидат DMZ, §21 — принятые синхронные раунды;
  [операторские расширения](https://docs.google.com/document/d/11fiuj47V9gX8xzY_5PaXqe-TyW05xT6B9R6wjoPg-GE/edit)
  §§49–53 сохраняют свой принятый смысл.
- Затем читать только пакет текущей работы и его evidence. Старые этапные
  протоколы нужны для конкретного доказательства, а не для выбора очередной задачи.

Этот файл ведёт текущий статус. Октябрьские планы и накопленные этапы сохраняются
как история требований и испытаний. Их старые NEXT, NOT IMPLEMENTED, RED,
ограничения арности и описания интерфейсов не заменяют эту сверку с кодом.

## Как читать статус

**QUALIFIED-SCOPE** — есть реализация и записанное доказательство в указанной
области. **CANDIDATE** — доказательство относится к отдельному экспериментальному
маршруту, а не к обычному runtime. **OPEN-IMPLEMENTATION** — обязательная операция
или форма ещё не доведена до нужной поверхности. **OPEN-EVIDENCE** — полнота
приёмки не доказана; это само по себе не дефект. **OPEN-DECISION** — вопрос
семантики/границы требует явного решения. У строки могут быть несколько статусов.
Ни один частный PASS не закрывает строку целиком автоматически.

## Конечные пакеты и критерии завершения

### P1 — история и границы хранения (первый в очереди)

- **H1 — QUALIFIED-SCOPE, этап 646:** [матрица и контрпример](3.8.0-context-pinned-revision-visibility.md). Проверены new root / fork от R0 / fork от положительной revision;
  exact current / retained history / R0 / unpublished future. Сопоставлены
  exists, version history, pinned open и фактическое чтение связей.
- **H2 — классификация завершена, этап 647:** [матрица восстановления](3.8.0-context-history-recovery-boundaries.md), sealed / codec-v1 / unsealed legacy.
  Разделены доказуемое восстановление, отказ и необходимость исходного
  recovery-артефакта. Пропущенные строки не заполняются догадкой; прежний контракт
  полностью отсутствующего legacy-файла не удостоверяет потерянную историю (D09).
- **H3 — аудит завершён, этап 647:** [конечная матрица артефактов](3.8.0-context-history-recovery-boundaries.md). Зафиксированы классы распознанных interrupted artifacts,
  правила их удаления/удержания и повторного checkpoint. Не расширять cleanup лишь
  ради удаления каждого неизвестного файла: неизвестный артефакт — не доказанная ошибка.
- **H4 — D07 ACCEPTED / QUALIFIED-SCOPE:** [контракт и фактические барьеры](3.8.0-context-durability-contract-audit.md). Подтверждённая модель отказов и требование
  durability. Process death на живой FS уже проверен; power loss / directory
  durability этим не доказаны и не исключаются из требований молча (D07).

Выход: H1–H4 классифицированы, доказанные нарушения исправлены, непроверенные
гарантии названы, профиль E08 зелёный. Новый storage-цикл после этого оправдан
конкретным контрпримером или незакрытым требованием, а не новой вариацией фикстуры.

### P2 — общая интеграция операций и совместимость

Свести конечную матрицу write / commit / connect / disconnect / repin /
private edit / publish / reopen × ground / universal / witness / arithmetic /
symbolic cache × independent / trust-group / private initialized views.
Каждая ячейка получает supported+gate либо явный обязательный пробел/вопрос.
Не требуется декартово размножать тождественные фикстуры: каждой проверке нужен
отдельный инвариант, ingress или неохваченный способ отказа.

Выход: R01/R08/R09 закрыты для принятого обязательного scope; owning authority
и settlement общие, операционные commits безопасны, fallback не скрывает
INCOMPLETE. Кандидат и production явно различаются до отдельного решения
о включении. Интеграция с develop учитывает его собственные изменения.

### P3 — публичный язык, ветви и результаты

Сначала инвентаризация требуемых форм: terms/tuples/functions, свободные и
связанные переменные, quantifier scope/polarity, witness dependencies, составные
запросы, точные application restrictions. Общие внутренние механизмы переиспользуются;
старые ограничения публичного replay не повышаются заменой одной константы.
Затем по конечным группам соединить их с публичной branch/query surface.

Выход: R02–R06/R12 проверены на принятом каталоге; A–G, перестановки и
монолитные контроли имеют одинаковые нормализованные результаты. D01–D04
разрешаются только когда конкретная обязательная операция зависит от решения.
Безусловный агрегированный ответ и полнота всех теорий не вводятся по умолчанию.

### P4 — основание, ресурсная модель и практическая стоимость

Проверить §20.4 на реальном маршруте; определить небольшой фиксированный корпус:
размер source/history, число cuts/branches, повторные запросы, bounds/refusal,
close/reopen и injected failures. Зафиксировать JVM, cold/warm, повторы,
разброс, allocation/retained memory, объём shared и branch-local состояния.
Включить O(R) первую запись connection history и повторную проверку missing-row
sealed proof. Оптимизация допускается только с parity результатов/происхождения.

Выход: R07/R11 имеют измерения и воспроизводимую приёмку, ресурсы освобождаются,
гарантии завершения/отказа точны. Физический parallelism и необязательный
межоперационный cache сами по себе не обязательные новые функции (D06).

### P5 — пользовательская приёмка и review кандидата

Один exact candidate и manifest; единый walkthrough A–G, SDK examples,
обязательные transports (D05), читаемые имена, результаты/ветви/proof,
исправленные повторы и восстановление. Запустить требуемые gates из E01–E10
для соответствующего scope, затем ручную приёмку. Сверить документацию и пакет.

Выход: R13/R14/R15 закрыты либо исключения явно приняты автором; нет
неразмеченных mandatory gaps. Результат — reviewable candidate. Merge, trust
migration, tag/release/deployment требуют своих решений и не следуют из PASS.

The native acceptance test now distinguishes equality of sets from equality
of substitutions. The standalone family query finds twelve permutations
across two sets. Joining the same pattern with `father(x,z)` and
`mother(y,z)` yields exactly two ordered assignments with the original
father, mother and child positions. Both this test and the binding boundary
test pass. This supplies an acceptance oracle for the new representation.
Existing scalar clause slots cannot express references from the set to the
variables of the other literals. A structured implementation must carry
those references into substitution, proof comparison and model audit.

The bounded flat set capture stores ordinary constants and variable positions
relative to the owning rule. It excludes the native constructor's result slot.
The qualification runner supplies assignments using the corresponding body
positions, verifies the resulting set against a native closed value, checks
equality under swapping assignments and rejects a missing variable. The
ordinary binder still returns INCOMPLETE for a set pattern. Family-level
substitution, occurrence provenance and model audit remain required before
these declarations can authorize a write.
