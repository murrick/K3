# 3.5.0.6 — Public API documentation audit closure

## Status

`3.5.0.6` closes the public API documentation audit for the KANGER `3.5.0` core-consolidation artifact.

The goal of the stage was not exhaustive comment density. The goal was to make the owned KANGER architecture understandable through stable contracts: architectural role, ownership, lifecycle, transaction semantics, canonicalization, persistence boundaries, side effects, failure obligations and historical naming where the implementation name no longer expresses the current meaning.

## Owned documentation surface

The qualified owned surface is divided into:

- public API — caller-facing interfaces and entry points;
- internal SPI — contracts intentionally implemented by storage and runtime modules;
- high-risk public implementation surface — public classes whose lifecycle, canonicalization or destructive semantics cannot be inferred safely from an interface alone.

The normalized method audit intentionally reports public implementation and protected helper methods separately. Only public API and internal SPI debt is release-blocking by default. Public implementations are reviewed by architectural risk rather than by raw method count.

## Covered architectural systems

The documentation package covers the following systems and boundaries:

- `IUser` / `User` and `IMind` / `Mind` ownership and transaction lifecycle;
- semantic units: `Rule`, `Domain`, `Predicate`, `Term`, `TVariable`, `TValue`, `Function`, `FValue`;
- projection primitives: `Argument`, `ArgumentsList`, `Solve`;
- provenance through `Cause`;
- fixed-point execution through `Linker`;
- operation dispatch through `Calculator`;
- result interpretation through `Analyzer`;
- compiler workflow `Parser -> Token / Leaf -> construct -> Compiller`;
- storage SPI `IData`, `IBase`, `ICache`, `IStep`, `IUnit`;
- concrete DUMB persistence family;
- runtime result stores;
- semantic, binding and persistence enum contracts;
- factory-owned canonicalization, hydration, transactional visibility and durable publication through the contracts of the documented units, Mind and SPI.

The more general ontological interpretation of factories, spaces, object birth and canonical existence is intentionally reserved for the separate Architectural Object Model. It is not duplicated in Javadoc.

## Permanent audit and rendered gates

The method-level audit is implemented by:

```text
tools/audit_public_api_javadoc.py
```

It excludes:

- vendored Mozilla Rhino;
- test, diagnostic, safety, qualification, performance and telemetry runners;
- field initializers and control statements misread as declarations;
- inherited implementation methods carrying an interface contract.

It classifies:

```text
public_api
internal_spi
public_implementation
protected_helper
```

Rendered architectural Javadoc is qualified on Java 8 and Java 21. Permanent semantic phrase checks protect the first caller-facing package from regression into placeholder documentation.

## Conscious exclusions

The following are outside independent architectural-passport scope:

- exceptions whose meaning is fully defined by the throwing contract;
- presentation and debug enums;
- DTOs and collection adapters without independent identity or lifecycle;
- trivial accessors whose semantics are exhausted by the containing passport;
- generated metadata;
- vendored code;
- test and diagnostic runners.

These exclusions are deliberate ownership decisions, not missing work.

## Documentation-only rule and demonstrated defects

The stage remained documentation/tooling-only except where review exposed a demonstrated semantic defect.

The `Solve.equals(Object)` predicate-call identity defect was corrected separately in the live artifact:

```text
predicate identity matches
    AND
arity matches
    AND
positional argument identities match
```

The correction is isolated in commit:

```text
19b795b32230321f63d7a34370640e6e53a2329c
3.5.0.6: require predicate and arity in Solve equality
```

The stale diagnostic PR #40 was closed unmerged after the one-line correction was reapplied to the current documentation HEAD.

Two additional map-hydration observations remain outside this documentation closure until they receive focused diagnostic gates:

- `Solve.applyMap()` reads `tange` while `createMap()` writes `range`;
- `Argument.applyMap()` appears to fall through its type switch.

They are not silently mixed into the Javadoc artifact.
