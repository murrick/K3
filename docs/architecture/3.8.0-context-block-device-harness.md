# Flush-aware block-device harness — first cold ext4 recovery

18 November 2026, stage 653. Qualification only; production remains stage 652
`fb0171fa3ed2fdc520ca26f86089b1a88cc612dc`. H4/P1 remain open for the complete
operation/failure matrix and deployment-profile review.

## What now runs

The harness boots an actual Linux kernel with an owned ext4 root image in QEMU
TCG. Inside that guest, an unmodified packaged DUMB2 provider creates a Context,
publishes R1 with index value 42 and emits its ACK. The host kills QEMU with
SIGKILL, discards the export's volatile sectors, then boots a new VM on the
remaining stable image. Ext4 replays its journal; an exact read-only snapshot
verifies R1 and value 42 without rewriting the Context first.

This replaces neither the existing namespace models nor process-death gates.
It supplies a lower-level persistence model in which the real kernel performs
filesystem recovery. It is not a power cut of the host or a physical-device test.

## Independent model controls

The single-connection test NBD export keeps ordinary writes in a sector map.
Reads see that map, but the stable backing file changes only for a completed
FLUSH or the sectors of an FUA write. FUA does not accidentally persist unrelated
pending writes. Disconnect/close does not flush the map, and cut freezes new
commands before dropping it. [The NBD protocol](https://github.com/NetworkBlockDevice/nbd/blob/master/doc/proto.md)
defines the completed-write prefix covered by FLUSH and per-request FUA semantics.
The export advertises only the implemented basic features and uses the oldstyle
handshake supported by the pinned QEMU client; it is not a production NBD server.

Six socket-level controls pass: acknowledged unflushed data is visible then lost;
FUA retains only its own request; FLUSH retains the completed prefix; later writes
are lost; out-of-range access is rejected; a post-cut FLUSH is not acknowledged.
The VM must send cacheable writes as well as actual persistence barriers, so a
write-through configuration cannot silently trivialize the positive experiment.

## Positive and deliberately broken devices

[Recorded observation](3.8.0-context-block-device-observation-stage653.json),
`run-e77b_lo6`: positive write issued 28 block writes and 22 FLUSH commands;
all acknowledged Context data was already stable at cut, so no dirty sectors
remained to drop. A separate kernel boot logged ext4 recovery complete and the
exact snapshot returned value 42 at R1. Both VM processes exited by SIGKILL.
The current guest path used FLUSH, not FUA; FUA is covered by the independent
wire control, not falsely claimed as observed guest behaviour.

The negative device advertises FLUSH but deliberately ignores persistence. The
same application/eligible ext4 environment ACKed R1; 808 volatile sectors were
dropped and a fresh boot returned STORAGE_NOT_FOUND for that exact revision.
This expected failure is a sensitivity control for the apparatus and the device
assumption. It is not a new KANGER defect under the supported flush-honouring
contract, nor evidence that the runtime can detect a lying controller itself.
The weaker behaviour exists only in the qualification backend, never as a
production durability option.

## Isolation and reproducibility

The guest has no NIC, host filesystem share or physical-device passthrough.
Only owned regular image files are exported. No host mount, kernel/device option,
system package installation or reboot is performed. QEMU, firmware and a kernel
were downloaded as official distribution debs and extracted under target.
[QEMU invocation documentation](https://www.qemu.org/docs/master/system/invocation.html)
is the reference for the explicit machine/device command lines preserved in the
run artifacts. The only guest class outside the packaged provider is the test
entry point; image construction rejects an unexpected provider override.

The tool lock records 12 exact package versions, architectures and SHA-256 hashes.
The generated manifest records QEMU version, kernel/image/JAR/fixture hashes and
prepared inputs. Host prerequisites are Linux amd64, the configured Ubuntu noble
APT sources for the locked packages, static BusyBox, OpenJDK 21, ldd, dpkg-deb and
mkfs.ext4. The image includes the selected JDK and required libraries; this is
an observed toolchain, not a claim of a hermetic cross-platform build.

```sh
python3 scripts/persistence_vm/fetch_tools.py
python3 scripts/persistence_vm/prepare.py
python3 scripts/qualify-context-block-device.py
```

Fetch downloads but never installs. Prepare creates ext4 with mkfs.ext4 -d,
without mounting it. Run needs local Unix sockets and execution of QEMU; the
managed filesystem sandbox denies socket creation, so this session used approved
unsandboxed execution for its owned VM files. Initial missing-module/BIOS paths
were setup failures, corrected to local bundle paths; they were not classified
as product counterexamples or passing recovery observations.

## Exact remaining scope

The model uses aligned 512-byte sectors, one connection and serial request
processing. An already processing persistence operation may finish before cut;
there is no torn-sector or exhaustive mid-FLUSH failure model. The positive case
has one Context and one append. It does not yet cover initial publication cut
points, multiple schemas, topology/reindex/fork failures, retained historical
vectors, or cross-module pins on distinct devices. No full operation matrix or
physical device power-loss acceptance is claimed.

Next apply the apparatus to the finite create/append/topology/reindex/fork matrix,
including previous ACK versus interrupted next publication. Then use separate
producer/consumer devices for the pin invariant. Finally bind the supported
software/deployment profile to that evidence and its explicit flush/FUA assumptions.
Other DMZ integration, language/results, D09 authenticity and P4 performance
requirements remain separate; no symbolic default or trust migration follows.

## Follow-up — stage 657 — exact marker-visible windows and separate data devices

[Dedicated protocol](3.8.0-context-device-pins.md) separates OS, Producer and
Consumer ext4 devices and pauses only Producer after marker visibility, before
its own confirmation. The positive Consumer provider is unchanged. Native
append/reindex/create/fork exports and no-export windows have separate receipts;
negative controls omit Consumer stabilization or lie about Producer barriers.
The interrupted initial namespace can be partial and explicitly refused before
any ACK. Do not interpret that as an empty valid Context, acknowledged-pin loss,
or permission to repair/delete unknown files. Strict initial absent-or-complete
acceptance and aggregate qualification are reported separately from positive
pin survival. H4/P1 remain open; no physical-device acceptance is claimed.
