# P1/H1 — exact revision visibility and historical preflight

Stage 646, 2026-11-17. Requirement R10, bounded checklist H1 of the
[delivery board](3.8.0-dmz-delivery-board.md). This records current root/fork
behavior and an executed metadata-selection defect, not a new R0 semantics.

## Counterexamples before repair

`PinnedRevisionVisibilityTest` reproduces four failures in
`/tmp/k3-646-before.log` (4 failures, no fixture errors):

- A positive-revision fork inheriting a nonempty connection vector starts at
  R1 with a sidecar bound to R1. `DB.exists("PinnedFork@0")` returned true,
  while `DB.use("PinnedFork@0")` failed with a missing exact connection binding.
- The same switch from an already open BareFork closed that active storage
  before failing, despite a preliminary `validateStorageOpen` call.
- A retained R1 with a valid codec-v1 manifest but a missing sidecar entry was
  likewise advertised as available. Switching to it lost the active selection.
- The root/fork availability matrix therefore disagreed at PinnedFork@0.

`ContextSnapshot.validatePublishedGeneration` returned at R0 before reading the
connection vector. For positive revisions it read the vector only when the
manifest contained a dependency digest. Header/data validation alone consequently
passed the exact-revision existence/preflight checks. Actual DB activation then
attempted the missing vector after closing the previous storage.

## Repair boundary

Published ContextSnapshot validation now selects the exact source revision's
ConnectionVector before the R0 return or generation checks. Where a dependency
digest exists it is compared against that same selected vector. Unpublished
candidate snapshots continue using their explicitly supplied candidate vector;
they do not acquire publication permission from a future sidecar row.

Both DB.exists(X@N) and validateStorageOpen already use ContextSnapshot, so they
share this complete local metadata boundary without a second special-case
existence policy or a rollback-after-close workaround. Missing/inconsistent
bindings fail before storage switching. The missing-vector diagnostic renders
`PinnedFork@0` and its path rather than the Context UUID; its typed error code
remains STORAGE_CONTEXT_CONFLICT.

There is no new empty-vector inference, sidecar write, generation write,
publication, R0 deletion or change to the history catalog.

## Observed finite matrix

The four origin fixtures are checked at creation and after one local publication.
Each checks current selection, previous retained selection, R0 and unpublished
future, plus the generation catalog and exact connection selection.

| New root, no connections | 0 | [0] | Available under the existing absent-sidecar empty contract | Current 1, catalog [1], previous R0 remains available |

Future revisions are unavailable in each origin, before and after advancing
CURRENT. Existing recovery matrices separately exercise physically installed
unpublished candidates and marker boundaries. The fixture does not grant
future generations visibility based on their files alone.

## Catalog and availability are distinct

`versionHistory` is the retained-generation catalog. Once CURRENT is positive,
it enumerates positive generations; an initial empty view is not added back as
a positive physical generation. It may list an old generation whose topology
metadata is no longer sufficient to open that exact Context. Silently removing
such an entry would conceal retained history and is not part of this fix.

Unversioned `DB.exists(X)` retains namespace/artifact existence semantics.
Versioned `DB.exists(X@N)` checks the selected snapshot's own metadata. It is not
a lease guaranteeing later target hydration, permissions, external-pin availability
or successful inference. Those runtime/lifecycle gates remain separate. No new
universal statement about the authenticity of arbitrary fork R0 views is made.
