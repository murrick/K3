# Calculator method-contract review

## Status

Review artifact for `3.5.0.6 — public API documentation audit`.

This document records the caller-visible method contracts that must remain aligned with the already qualified type-level Javadoc of `org.kanger.calculator.Calculator`. It is documentation-only and does not authorize behavioral changes.

## Architectural role

`Calculator` is the per-`Mind` execution facade between semantic `Function` / `Domain` objects and executable built-in or user-defined `Operation` implementations.

It does not own fixed-point orchestration, transaction lifecycle, canonical `Function` identity, canonical `FValue` identity, or persistent Library state.

```text
Function / Domain definition
        +
current argument projection
        +
operation binding
        ->
Operation execution
        ->
transient result / canonical FValue effect
```

## `Calculator(Mind)`

Creates one calculator bound to the supplied mutable `Mind` and creates matching built-in `Functions` and `Predicates` catalogs.

The calculator borrows the `Mind`; it does not reserve, commit, release, or close it.

Caller obligations:

- do not reuse the instance with another `Mind`;
- externally serialize concurrent use of the same mutable `Mind`;
- treat catalog objects as dispatch metadata, not persistent knowledge.

## `boolean calculate(Function function, boolean logging)`

Recursively calculates unresolved nested function arguments, resolves and executes the current function, and publishes a canonical `FValue` only when execution produced an applicable result that is not already represented by the current value.

Return value:

- `true` — a new canonical function-result effect was added;
- `false` — no new result was added, including already-known, unresolved, incompatible, or unavailable-operation cases.

Important distinctions:

```text
operation executed != new FValue added
existing result != calculation failure
unresolved input != exception by definition
transient result slot != canonical FValue
```

Side effects may include:

- recursive nested-function calculation;
- mutation of transient function result slots;
- operation-specific changes in the active `Mind`;
- canonical `FValue` creation;
- Linker continuation signalling through `FValueFactory`;
- analyzer log entries when `logging` is enabled.

The method does not start or finish a `Mind` transaction and does not independently roll back operation side effects.

## `int execute(Domain domain)`

Resolves an executable predicate operation by exact `name(arity)` signature, first in the built-in predicate catalog and then in the active `Mind` Library, and invokes the operation with the supplied `Domain`.

Historical return convention is forwarded unchanged:

- `1` or `2` — successful/affirmative operation-specific outcome;
- `0` — negative or incompatible outcome;
- `-1` — no matching operation.

The method does not interpret the result as a final logical answer. Branch selection, calculated marks, solve publication, and fixed-point continuation remain responsibilities of `Linker`.

## Function operation resolution

Function dispatch is selected by `FunctionBinding`:

```text
INFRASTRUCTURE
    built-in Functions catalog only

UDF_DYNAMIC
    active Mind Library only

LEGACY_AUTO
    built-in exact -> Library exact -> built-in name(0) -> Library name(0)
```

The `name(0)` fallback is a compatibility contract, not normal overload resolution.

```text
FunctionBinding != display metadata
exact arity miss != unconditional operation absence
Library operation != built-in operation identity
```

## `int execute(Function function)`

Resolves the function operation according to its `FunctionBinding`, rejects execution while any non-empty argument resolves to a U-witness, and invokes the operation otherwise.

Return convention:

- operation-specific integer result when an operation runs;
- `-1` when no operation is found or the function remains unresolved because of a U-witness argument.

The method may mutate the function's transient result slot or active `Mind` through the invoked operation. It does not itself create the canonical `FValue`; that publication belongs to `calculate(...)` and `FValueFactory`.

## `boolean exists(IPredicate predicate)`

Returns whether an exact `name(arity)` operation exists in the built-in predicate catalog or active Library and is explicitly classified as `LibMode.PREDICATE`.

```text
operation exists != predicate operation exists
Predicate definition exists != executable predicate implementation exists
```

This is runtime dispatch observability, not canonical `Predicate` existence and not persistence existence.

## `Functions getFunctions()`

Returns the built-in function catalog owned by this calculator instance.

The returned object is mutable runtime dispatch infrastructure bound to the same `Mind`; callers must not treat it as a detached snapshot, persistent Library, or semantic-unit store.

## `Predicates getPredicates()`

Returns the built-in predicate catalog owned by this calculator instance.

The same ownership and concurrency restrictions as `getFunctions()` apply.

## `List<ITerm> expand(ITerm source, ITerm step, boolean expandString)`

Expands one source term into canonical terms of the active `Mind` according to its `DataType`.

### Interval

- includes the starting endpoint;
- advances toward the final endpoint using explicit `step`, or implicit increment/decrement;
- stops before overshooting the final endpoint;
- includes the final endpoint when reached exactly;
- returns an empty result for numeric zero step;
- clears the result when an advance produces the same canonical Term ID and therefore makes no progress.

### Set

Recursively expands nested sets and intervals; ordinary members are retained.

### String

- without `step`: either returns the original string term or expands it into one-character canonical terms according to `expandString`;
- with `step`: treats `step.value` as a regular expression and emits canonical terms for matched capture groups.

The entire match is not emitted unless it is explicitly captured.

### Blob

- without `step`: either returns the original blob or expands it into single-byte terms according to `expandString`;
- with `step`: partitions the blob into positive-size chunks and canonicalizes each chunk as a Term.

### Other types

Returns the source as a single-element result.

Important distinctions:

```text
expanded list != source identity
canonical output Terms != newly unique logical values
regex pattern != delimiter
zero/no-progress expansion != execution failure
```

The method may create or recover canonical Terms through the active `Mind` term factory. It does not publish Rules, commit transactions, or preserve a reversible expansion object.

## Errors and obligations

Operation callbacks, regex compilation, hydration, canonicalization, or type conversion may throw exceptions. The caller owns the surrounding transaction/checkpoint policy.

The caller must provide type-compatible `step` values:

- numeric for interval advancement;
- string-compatible regex for string capture expansion;
- positive numeric chunk size for blob partitioning.

Current implementation behavior for invalid values is not strengthened by this documentation and should only be changed behind focused regression gates.

## Core invariants

```text
Calculator != Linker
Calculator != Library
Calculator != transaction owner

Function definition != transient result slot
transient result slot != canonical FValue
operation lookup != semantic identity

unresolved U-witness != false logical answer
operation return code != final query result
expansion != persistence publication
```
