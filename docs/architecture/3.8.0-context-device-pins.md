# Marker-visible producer and distinct-device direct pins

18 November 2026, stage 657. Qualification only; production remains stage 652,
`fb0171fa`. Extends the [native block matrix](3.8.0-context-native-block-device.md)
and the [direct-pin contract](3.8.0-context-durable-pins.md).

## Apparatus and exact publication window

An owned QEMU guest has three independent NBD exports: ext4 OS/root on vda,
Producer data on vdb and Consumer data on vdc. The data templates have distinct
filesystem UUIDs, stable backing files and volatile sector maps. Guest code
asserts different unix device identities for `/producer` and `/consumer`.
A Consumer filesystem barrier cannot write Producer's in-memory NBD cache.
No host mount, raw device, network, system installation or host reboot is used.

The Producer runs in a separate JVM with one qualification-only RevisionStore
copy. Exactly two calls are inserted: after a successful real marker replacement,
and after the initial final-name link is visible/temp name removed, before its
confirmation. The pause applies only to `/producer/Producer.revision`, not other
contexts. It signals through the OS disk and stays paused until the VM is killed.
The original provider JAR is unchanged. Positive Consumer and all cold readers
load its original provider, with no override. Separate JVMs prevent the paused
producer's static marker monitor from blocking Consumer's own publication.

Before releasing Consumer, the coordinator reads the exact Producer marker and
prints `PIN_VISIBLE`; the host records all three device counters. Producer has
not returned its publication ACK. Consumer compiles a local original, connects
to that exact visible Producer revision, calls ordinary `DB.saveConnections`,
and prints its R2 ACK immediately after return. There is no graceful close or
extra filesystem verification after this ACK. The host kills QEMU and drops
volatile sectors on all three exports.

## Scenario invariants

| Producer operation | Visible target without its own ACK | Exported pin cold check | No-export window cold check |
| --- | --- | --- | --- |
| Append | R2, two native originals | Consumer R2 pins exact Producer R2; predecessor R1 still opens | R1 or complete R2, exact R1 retained |
| Reindex | R4 / Rule-v2; R3 / Rule-v1 had saved Support R1 | Consumer R2 pins R4; Producer R3 remains Rule-v1 with a one-entry saved vector | R3 or complete R4, exact R3 retained, saved vector still has one entry |
| Initial create | R0 | Consumer R2 pins the same initial identity/revision | Absent or complete R0; creator had no ACK |
| Initial fork | New identity R1 from Template R1 | Consumer R2 pins the fork; Template R1 remains; fork identity differs | Absent or complete fork R1; Template R1 remains |

The initial no-export expectations above are strict qualification oracles, not
a newly accepted promise of atomic multi-file creation before ACK. A refused
partial initial namespace must be recorded separately; it is not silently
counted as absence or complete recovery.

No-export cases cut at `PIN_VISIBLE` without releasing Consumer at all. They
close the specific marker-visible window left unobserved by some ordinal
reindex cuts. Initial publication is not promised to survive without an ACK or
export; once Consumer acknowledges a pin, that exact target must survive.

New kernel boots mount both data filesystems and perform read-only snapshots
before any mutable reopen/repair. Consumer must retain R2, its local original
and exactly one direct pin with the expected location, identity and revision.
Producer must retain the target and its native original count/layout; reindex
also retains R3/Rule-v1 and checks the one-entry cardinality of its advisory
vector. Exact Producer-to-Support target identity is not independently compared
in this slice; Consumer-to-Producer target identity/revision is compared. This is not a proof of automatic
advisory recursion or a new trust/default integration contract.

## Sensitivity and incidental journal commits

Only guest data mounts use `data=ordered,barrier=1,commit=3600`, within the
accepted ext4 barrier profile. The long commit interval keeps a background
periodic journal commit from quietly stabilizing the paused Producer during
Consumer's qualification. Positive exports must issue actual Producer barriers
after visibility. The no-export and omitted-stabilizer controls check this
assumption; it is not inferred solely from elapsed time.

Two append controls preserve all other logic:

- A Consumer-only test DurablePins override omits stabilization. Its saved pin
  must be lost/unreadable after cut, despite Consumer's own R2 survival; Producer
  must receive no post-visible FLUSH/FUA. This is a regression sensitivity control,
  not the production Consumer or a newly proved production defect.
- A test backend advertises but ignores Producer FLUSH/FUA. The original Consumer
  may ACK, but a subsequent honest cold reader must find its exact target missing.
  This demonstrates the device-honesty assumption; software does not acquire a
  capability to certify a lying controller.

The six existing wire controls remain mandatory. Positive consumers use no
negative overlay. Device ledgers, commands, exact visibility/ACK markers,
SIGKILL exits, recovery and prepared/source hashes are retained separately.

## Reproduction and remaining boundary

Run `python3 scripts/persistence_vm/prepare_pins.py`, then
`python3 scripts/qualify-context-device-pins.py`. The preparation reuses the
verified local tool/rootfs bundle; it never mounts an image on the host. It
checks exact source pause points and classpath allowlists and records both
pause and negative overlay sources/bytes. Baseline JVM options are unchanged.

The sector model is serial and untorn; an already processing persistence request
may complete before cut. There is no exhaustive mid-FLUSH/torn-sector or physical
hardware power-loss acceptance. Other topology/private/trust arrangements and
deployment/device review remain separate. The stage-656 experimental TERM
observation remains OPEN; this work neither repeats blind probes nor claims a
runtime fix. H4/P1 status must follow the recorded scope, not the existence of a
new apparatus or a positive subset alone.

## Initial acquisition and explicit refusal

The [first acquisition](3.8.0-context-device-pins-initial-stage657.json),
`run-yy673pi4`, recovered all four acknowledged cross-device exports and both
append/reindex no-export windows. The create-window cold reader refused
incomplete metadata: only one of `.context` / `.revision` survived. This was
before any producer or Consumer publication ACK. The stronger initial
absent-or-complete oracle did not pass. No acknowledged-target loss is proved,
and no production fix or automatic cleanup is justified by that result alone.
The original serial logs, including the failed cold boot, are preserved.

The coordinator now retains a failed cold-reader receipt and continues collecting
other cases, while preserving an INCOMPLETE aggregate and nonzero exit status.
It does not widen the cold-reader acceptance criterion. Read-only `debugfs`
inspection of both first-run initial images found `Producer.context` and the
owned temporary revision name, but no final `Producer.revision`; this matches
the explicit refusal and does not authorize adopting a temporary marker. Before closing H4,
classify interrupted, unacknowledged initial creation separately from an
acknowledged create or externally acknowledged pin. Do not treat a partial
namespace as an empty valid Context or infer lost identity/history from it.
