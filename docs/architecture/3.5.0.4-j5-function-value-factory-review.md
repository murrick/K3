## Pair rationale

The pair documents the boundary between a compiled Function occurrence and a materialized result produced for one Function/substitution state.

```text
FunctionFactory
    Function allocation and binding metadata
    + per-Mind cache overlay
    + add-time Calculator side effect

FValueFactory
    canonical materialized results
    + transaction-visible UDF invalidation
    + Linker continuation action
    + nested invalidation/action checkpoint journals
```

They are related but not symmetrical. Function allocation does not canonicalize structural duplicates; FValue allocation performs operational canonical lookup and reuse.

## Shared lifecycle review

Both introductions correctly establish:

- one concrete factory instance per exact `Mind` level;
- child initialization through `transaction(parentFactory)` and an `Escalera` overlay;
- child-created units remaining unpublished until typed parent completion;
- root-only borrowed schema `IBase` attachment;
- child factories remaining memory-only overlays without storage close authority;
- parent `Mind` authority over commit/release sequencing and reservation;
- typed `commit(childFactory)` remaining distinct from no-argument checkpoint `commit()`.

Neither class claims that synchronized add or copy-on-write metadata makes the complete transaction/inference protocol thread-safe.

## FunctionFactory review

### Identity and allocation

The documentation states that each add allocates a separate Function occurrence containing:

```text
schema ID
owning Mind ID
name Term
range
FunctionBinding
argument structure
reserved result slot at index range
```

It does not convert Function unit comparison into a nonexistent factory-level deduplication contract.

### Binding contract

The class introduction preserves the three source-defined modes:

```text
LEGACY_AUTO
    infrastructure-first, UDF-second compatibility dispatch

INFRASTRUCTURE
    infrastructure registry only

UDF_DYNAMIC
    current user-defined operation resolved by signature
```

Binding is described as persistent semantic metadata participating in Function hashing and structural comparison. The default overload and older records without a binding byte remain `LEGACY_AUTO`.

The documentation does not present binding as a transient Calculator preference.

### Add-time execution

The class comment explicitly records that add is not inert: after cache publication it calls Calculator when `Function.isCalculable()` is false.

The wording intentionally preserves the historical predicate rather than redefining it. Current source derives the predicate from TVariable presence in the argument structure.

### Transaction, persistence, and cleanup

The direct `Escalera` checkpoint model, typed promotion/rebinding, root-only hydration/update, and physical removal of logically deleted Functions are bounded correctly.

The unit-level cascade from Function deletion to a currently resolved FValue is acknowledged without misdescribing `FunctionFactory.pack()` as a general invalidation engine.

## FValueFactory review

### Stored result and operational canonical lookup

The documentation distinguishes the stored dimensions of one FValue:

```text
schema ID
owning Mind ID
Function identity
result Term identity
captured substitution stamp
```

Add returns `null` for an incomplete Function. For a complete Function it first searches the Function hash-base bucket, excludes transaction-visible invalidated IDs, and verifies `FValue.equalsTo(Function)` against Function ID and current substitution stamp.

This is described as an operational lookup contract, not reduced to an unsupported mathematical key.

A logically deleted matching FValue remains reusable before pack and has its deletion mark cleared. An invalidated result is excluded from lookup and therefore cannot be resurrected through ordinary add.

### Binding-sensitive UDF invalidation

The class comment accurately states the source behavior:

```text
UDF_DYNAMIC
    matching Function results invalidated

INFRASTRUCTURE
    unaffected by UDF replacement

LEGACY_AUTO
    invalidated only when no exact or zero-range infrastructure fallback exists
```

The implemented `range == 0` broad condition is acknowledged without turning it into a new public wildcard promise.

Invalidation IDs are described as transaction-visible memory metadata, not durable independent records.

### Action rollback invariant

J5 documentation analysis proved an additional production invariant defect.

Red gate:

```text
7c6ab082af9498742b6c50d5387a835214ece6a4
Gate FValue action rollback
```

Minimal correction:

```text
3a749b7ca08f8ada4a1f67c3b745c58034ae5ad5
Restore FValue action on checkpoint release
```

Before correction, release restored the cache and invalidated IDs but retained `action=true` from a speculative FValue that no longer existed. `Linker.link()` directly includes `FValueFactory.isAction()` in its pass-continuation condition, so this was semantic continuation state rather than diagnostics.

The correction adds a dedicated action snapshot stack paired with the existing full invalidation snapshots. It changes no result identity, invalidation selection, binding mode, storage layout, typed commit, or public signature.

Authoritative record:

```text

```

### Category-specific checkpoint journal

The class contract now correctly distinguishes:

```text
invalidatedStack
    complete snapshots of transaction-visible invalidated IDs

actionStack
    saved Linker continuation state
```

No-argument mark snapshots both after marking the cache; commit discards both saved states; release restores both alongside the cache.

This is not copied from the `TValueFactory` additions-delta implementation and is not generalized into a universal factory journal.

### Persistence and physical cleanup

Only root FValue factories borrow the schema base. Cache records are persisted through root update; invalidation/action metadata is not stored independently.

Pack physically removes records that remain logically deleted or invalidated and then clears invalidation metadata. This remains separate from pre-pack logical reuse.

## Review conclusion

J5 establishes the function/result rule:

> Function binding and compiled structure define how evaluation is dispatched; a materialized FValue is a canonical result for implemented Function/substitution state, while UDF invalidation and Linker continuation are separate transaction-visible metadata that must be published and rolled back explicitly.

J5 may close only when the complete qualification contour is green on one exact review HEAD.

The next checkpoint should document `LibraryFactory` as the copy-on-write operation registry and then isolate `RuleFactory` in its own high-risk checkpoint because candidate metadata, hydration, generation publication, and lock ordering form a distinct evidence boundary.
