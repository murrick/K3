# KANGER 3.5.0.6 — Runtime stores architectural passport

Status: review source for production Javadoc.

## 1. Architectural role

The runtime stores attached to one `Mind` expose four distinct projections of an execution:

- `SolutionsStore` — Rule-level matches selected for the caller;
- `ValuesStore` — query-variable substitution rows;
- `HypothesisStore` — admissible assumptions and their continuation signal;
- `LogStore` — ordered diagnostic observations.

They are not persistent databases, canonical unit factories, or interchangeable result containers.

```text
runtime store state != canonical knowledge
runtime store commit != Mind transaction commit
clear runtime store != delete semantic units
```

Each store borrows semantic objects owned by Mind factories. Clearing or replacing a store changes only the current result/diagnostic projection.

## 2. Common ownership and lifecycle

Each store is created for exactly one `Mind` and resolves borrowed objects in that context.

Child-to-parent transfer is explicit through store-specific `commit(...)` methods. These methods copy or merge projection state; they do not publish storage, canonicalize units, or independently close a Mind transaction.

```text
store commit = projection transfer
store commit != durable publication
```

Concurrent mutation of one Mind's stores is not supported except where a concrete collection provides incidental iteration safety. The link/analyze/caller workflow must serialize semantic access.

## 3. SolutionsStore

### Role

`SolutionsStore` is the ordered query-local collection of `IRule` matches exposed by Analyzer.

It stores borrowed Rule references. It does not own Rule lifecycle or define equality.

### Identity and deduplication

`add(IRule)` deduplicates using the Rule object's Java equality semantics (`List.contains`). This is operational object equality, not structural Domain compatibility.

`contains(Domain)` is a different operation: it scans visible, non-deleted Rules and checks base compatibility and equal polarity.

```text
add deduplication != contains(Domain) compatibility
```

### Commit

`commit(base)` replaces the receiving projection with the source store contents. It is snapshot-style transfer, not additive union with the previous receiving state.

### Null-root lifecycle

`clear()` sets the internal list to `null`. Empty iteration lazily creates an empty list, while `size()` and `isEmpty()` treat `null` as empty.

### Historical IFactory surface

`get(long)` returns `null`; SolutionsStore is not an ID-addressable canonical factory despite implementing `IFactory<IRule>`.

## 4. ValuesStore

### Role

`ValuesStore` exposes rows of current query substitutions. Internally each row is an ordered `ArgumentsList` of canonical `TValue` references; externally iteration projects it to a sorted map:

```text
variable name -> donor Term
```

```text
internal TValue row != external Map row
```

### Row identity

Rows are held in a `LinkedHashSet` when unsorted and a `TreeSet` when an order variable is configured.

`add(Collection<TValue>)` ignores empty rows and suppresses duplicate `ComparableArgumentsList` rows according to the collection's equality/ordering behavior.

The row is a projection of canonical TValue objects; it is not a new semantic entity and has no persistent identity.

### Ordering

`setOrder(name)` and `setAscending(...)` configure presentation order. `getRoot()` can convert the backing set between insertion-order and sorted forms.

Sorting compares the donor Terms for the named TVariable. Missing values are ordered explicitly; if the named variable is absent from both rows, the first value is used as a historical fallback.

```text
presentation order != semantic identity
```

### External projection

`ValuesIterator` creates a new `TreeMap<String, ITerm>` per row. Map keys are variable names; values are resolved donor Terms in the owning Mind.

`get(long)` treats the argument as a zero-based row position, not as a persistent or operational ID.

### Commit

`commit(base)` replaces current rows with the source rows. Ordering configuration belongs to the receiving store and is not itself a semantic result.

## 5. HypothesisStore

### Role

`HypothesisStore` holds runtime assumptions admitted by Linker/Analyzer. A hypothesis is not a persistent Rule and not a primary answer.

### Canonicalization inside the store

`add(...)` and `find(...)` define store-local canonical reuse by:

```text
Predicate id
+ polarity
+ base-compatible arguments
```

When an existing hypothesis is found, a new query marker may be promoted onto it rather than creating a duplicate.

For one comparison path, two U-witness arguments are treated as base-compatible. This is hypothesis matching semantics only; it does not redefine global Term identity or the Rule-scoped U-child invariant.

### Action signal

`action` is a continuation signal indicating that the store admitted new hypothesis state. It is not itself a hypothesis or truth result.

```text
action signal != hypothesis identity
```

`dropAction()` resets only this signal.

### Commit

`commit(base)` merges hypotheses through `add(...)`, preserving store-local deduplication, and copies the source action state when source content exists.

Unlike SolutionsStore and ValuesStore, this is additive merge behavior rather than full replacement.

### optimize()

`optimize()` validates each candidate in a fresh child `Mind`:

1. render hypothesis to source form;
2. compile it as a Rule;
3. link and analyze it;
4. release the child Mind;
5. retain only candidates that do not already produce a successful answer.

This is semantic filtering, not sorting or storage compaction.

```text
optimized hypothesis set != persistent publication
```

The method mutates the runtime store and marks it optimized; callers must not run it concurrently with link/analyze mutation.

## 6. LogStore

### Role

`LogStore` is the ordered diagnostic stream of one Mind. Log records are observations and timing/debug messages, not provenance edges and not semantic results.

```text
LogEntry != Cause
LogStore != explanation graph
```

### Initialization and append

The list is created lazily. The first append adds a timing start marker. Rule logging formats the Rule tree into one or more textual rows before appending entries.

When runtime logging is enabled through debug flags, newly appended records are also printed to standard output. Console output is a side effect of logging configuration, not semantic execution.

### Commit

`commit(base)` appends child log entries to the receiving stream and adds a commit timing marker. It does not replace existing parent logs and does not imply semantic commit by itself.

### Lookup

`find(LogMode, String)` performs exact type/record lookup. `getCurrent(mode)` returns the latest entry overall or the latest entry of one mode.

The generic `find(Object...)` exposes the backing list index and is a historical compatibility surface, not semantic search.

### Concurrency

The concrete list is `CopyOnWriteArrayList` after initialization, which protects iteration mechanics during append. This does not make the owning Mind or the semantic pipeline thread-safe.

### Historical IFactory surface

`get(long)` returns `null`; log entries are positionally observed, not canonical ID-addressable units.

## 7. Cross-store invariants

```text
SolutionsStore Rule match != ValuesStore substitution row
ValuesStore row != Hypothesis
Hypothesis != primary result
LogEntry != semantic effect
```

Analyzer clears SolutionsStore and ValuesStore at the beginning of a new analysis. Hypothesis and Log lifecycle are governed separately because they may accumulate across specific execution/transaction paths.

A caller must not infer truth solely from store non-emptiness without the boolean classification returned by Analyzer.

```text
non-empty store != closed successful query
```

## 8. Javadoc integration guidance

Production Javadoc should classify these classes as runtime projection stores, not general factories.

Method-level contracts should explicitly document:

- replacement versus merge semantics of `commit(...)`;
- borrowed-object ownership;
- positional versus identity-based `get(...)` behavior;
- sorting as representation-only state;
- hypothesis action signaling;
- diagnostic side effects;
- null-root/empty lifecycle.

No behavior changes are authorized by this review document.
