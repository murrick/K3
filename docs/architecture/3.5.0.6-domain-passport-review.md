# Domain architectural passport review

Status: review artifact for `3.5.0.6 — public API documentation audit`.

Target production type:

```text
kanger/src/org/kanger/units/Domain.java
```

This document records the implementation-level architectural contract to be transferred into type-level and method-level Javadoc without changing executable semantics.

## Architectural role

`Domain` is the materialized atomic proposition inside a `Rule` branch. It binds one `Predicate`, polarity (`antc`) and an ordered recursive argument graph to the owning `Rule`.

It is simultaneously:

- a persistent semantic unit;
- an atomic member of a Rule tree;
- an execution key for one current argument projection;
- a carrier of query-local causes, solves and lifecycle markers.

`Domain` is not merely a predicate call DTO and is not itself the set of current substitutions produced while evaluating that predicate call.

## Inside — architectural essence

The stable definition contains:

- operational Domain ID;
- owner/materialization Mind ID;
- owning Rule ID;
- Predicate ID;
- polarity (`antc`);
- arity;
- ordered `ArgumentsList` structure;
- `substitutable` marker;
- `abstractive` marker.

This state defines the Domain as one atomic element of the Rule graph.

## Outside — contextual projections

The following state belongs to a particular `Mind` and current argument projection rather than to Domain identity:

- hydrated Predicate and Rule references;
- current TVariable/TValue/Function values;
- causes selected for the current base argument list;
- solves associated with the current base argument list;
- used/excluded markers;
- produced/calculated stamps;
- query membership;
- stored assertion lookup result;
- system-operation execution state;
- transaction-visible deletion;
- debug rendering suffixes.

## Ownership

A Domain belongs structurally to one Rule through `ruleId`.

Its argument definitions are part of the Rule graph, while current bindings of those arguments are projections owned by the active Mind.

```text
Rule-owned Domain definition
    !=
Mind-owned current argument state
```

`setMind(Mind)` selects the context used for hydration and execution projections. It also propagates that active context to contained TVariables. It must not redefine Rule ownership or canonical identity.

## Identity and canonicalization

Several identities coexist and must not be conflated.

### Operational identity

`equals(Object)` and `hashCode()` use the persistent/operational Domain ID.

### Rule-local candidate identity

`getHash()` combines base predicate-call state with `ruleId`.

### Predicate-call base identity

`getHashBase(Mind)` describes polarity, Predicate ID and current argument base independently of owning Rule identity.

### Structural Rule identity

`getHashStruct()` and `equalsToStruct(Domain)` compare Domain structures across Rule-local variable spaces. TVariable and U-witness positions are normalized by variable order rather than absolute IDs.

### Current projection equality

`equalsTo(Domain)` compares the current concrete argument/object projection, optionally constrained by `ruleId`.

### Base-value compatibility

`equalsBase(Domain)` compares resolved base values and recognizes direct parent/child U-witness adjacency as compatible where required by inference.

```text
operational ID
    != Rule-local lookup key
    != structural equality
    != current projection equality
    != base-value compatibility
```

Hashes are candidate selectors and never identity proofs.

## Argument graph

The ordered `ArgumentsList` may contain:

- Term;
- TVariable;
- TValue;
- Function/FValue projections;
- U-witness Terms.

`substitutable` means the Domain contains T-variable-dependent structure.

`abstractive` means the Domain contains U-witness/C-variable-dependent structure.

These flags describe execution requirements; they are not query-result markers.

## Execution-state keying

A Domain definition can participate in multiple runtime states. KANGER stores those states in Mind-owned registries keyed by the Domain plus a normalized argument representation.

Two principal key forms exist:

### Base argument projection

`ArgumentsList.convertBase(Mind)` is used for:

- causes;
- solves;
- used markers;
- excluded markers.

### Ordered value stamp

`ArgumentsList.getStamp(Mind)` is used for:

- produced markers;
- calculated markers.

Therefore:

```text
Domain definition
    + normalized base/stamp
    -> one contextual execution state
```

The registries do not become part of Domain identity.

## Causes and provenance

`setCauses(...)` stores provenance for the current normalized base argument projection.

Only causes whose donor arguments overlap the Domain are retained. `getCauses(...)` may rank candidates by argument overlap and remove the weakest weight group when stronger alternatives exist.

This is query-local provenance selection, not canonical Rule provenance and not persistent Domain identity.

```text
Domain causes != Domain identity
selected causes != all historical causes
```

## Solves

`setSolves(...)` and `getSolves(...)` associate a set of `TValue` substitutions with one normalized base argument projection.

The returned set is contextual execution state. It must not be confused with Predicate-level assertion Rules returned by `Predicate.getSolves(IMind)`.

## Used and excluded state

`setUsed(...)` records that one normalized argument projection has participated in the current inference process.

`setExcluded(...)` records that one normalized projection is excluded from further consideration.

Both are Mind-local markers and can coexist for different projections of the same Domain definition.

```text
used Domain projection != globally used Domain
excluded projection != deleted Domain
```

## Produced and calculated state

`setProduced(...)` records a complete ordered argument stamp that has already produced an outcome.

`setCalculated(...)` records a complete ordered argument stamp that has already been evaluated.

Incomplete parameter sets are not published as stamps. The current implementation silently declines publication when stamp creation reports incomplete parameters or buffer failure.

`unCalculated(...)` removes the matching calculated projection; it must not remove the Domain definition itself.

```text
produced != calculated
calculated != stored
stamp rollback != Domain deletion
```

## Stored semantics

Historical `isStored(...)` does not inspect physical database records. It asks `RuleFactory` whether an equivalent visible assertion Rule exists for the Domain projection.

`setStored(Mind)` stores/canonicalizes an assertion through the Rule factory.

`createStored(Mind)` adds an assertion Rule through the Rule factory.

Thus:

```text
stored Domain projection
    = visible equivalent assertion Rule exists

stored
    != physical database I/O
```

## Query semantics

A Domain projection is query-related when:

- its owning Rule is a query Rule; or
- one of its TVariables currently exposes a query TValue; or
- a TValue argument belongs to the Mind query-value projection.

Query membership belongs to the current projection and is not part of Domain identity.

## System-operation semantics

`isSystem(Mind)` delegates classification to the Predicate/runtime operation registry.

`execSystem(Mind)` invokes `Mind.executeSystem(this)` only for a registered system Domain and returns `-1` otherwise.

System classification depends on runtime registration and is not persistent Domain identity.

## Completeness

`isComplete()` means every argument currently resolves to a value in the owning Mind.

```text
incomplete projection != invalid Domain definition
```

A structurally valid Domain may be incomplete during inference.

## U-witness semantics

Structural comparison treats Rule-local TVariables and U-witness Terms by normalized variable order.

`equalsBase(Domain)` additionally recognizes parent/child U-witness adjacency where the current inference projection represents the same existential lineage.

This does not weaken the Rule-scoped child invariant:

```text
(parent U-witness, target Rule id) -> canonical U-child
```

Compatibility during comparison must never reintroduce global one-child aliasing.

## Deletion lifecycle

`setDeleted(on, mind)` changes transaction-visible deletion for the Domain and propagates the same visibility to execution-owned children:

- contained TVariables;
- contained Functions;
- contained TValues created by the same Mind.

TValues owned by another Mind are not blindly deleted.

Deletion does not destroy:

- Domain operational identity;
- Rule ownership;
- Predicate identity;
- persistent serialized form;
- rollback/restoration capability.

```text
deleted Domain != nonexistent Domain
excluded Domain projection != deleted Domain
```

## Persistence and hydration

The serialized form stores:

- Domain ID;
- owner Mind ID;
- deletion marker;
- Rule ID;
- substitutable/abstractive flags;
- inherited `Solve` state: Predicate, polarity, arity and arguments.

`apply(ByteBuffer)` restores an unresolved shell and nested Solve state.

`isLoaded()` only confirms that the Predicate reference is hydrated consistently. It does not prove that the Rule or every nested argument object is hydrated.

```text
partially hydrated != absent
serialization != canonical identity
```

## Ordering

`compareTo(Domain)` orders primarily by Rule ID and secondarily by Domain ID.

This is an operational deterministic order, not semantic or structural equality.

## Representation

`toString(ArgumentsList)` renders the inherited predicate call and may append debug-only flags:

- `Q` query;
- `U` used;
- `X` excluded;
- `B` stored assertion exists;
- `S` calculated.

This output is context-sensitive diagnostic text and is not a stable persistence or interchange protocol.

## Caller obligations

Callers must:

- use the correct Mind for hydration and visibility;
- distinguish Domain definition from its current argument projection;
- use structural comparison only for Rule-structure identity;
- use base/stamp registries only as query-local lifecycle state;
- avoid interpreting `isStored()` as physical storage I/O;
- avoid interpreting `isComplete()` failure as malformed definition;
- preserve Rule-scoped U-child identity;
- balance any surrounding DomainFactory/Mind checkpoints that own waiter and rollback state.

## Historical notes

`Domain` historically means a “variant of solving a predicate.” In the modern architecture it is more precisely the atomic predicate-call unit inside a Rule, plus the key through which Mind addresses contextual execution projections.

The inherited name `Solve` denotes the common predicate/polarity/argument structure; a `Domain` is the persistent Rule-owned specialization of that structure.

## Key invariants

```text
Domain definition != current argument projection
Rule ownership != Mind execution state
Predicate definition != Domain assertion
base projection != ordered stamp
causes != solves
used != excluded
produced != calculated
calculated != stored
stored != physical database I/O
operational ID != structural equality
hash != identity proof
incomplete != invalid
deleted != nonexistent
diagnostic rendering != persistence protocol
```
