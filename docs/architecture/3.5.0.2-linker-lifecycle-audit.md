# KANGER 3.5.0.2 — Linker naming and lifecycle audit

## Scope

This audit classifies Linker naming/lifecycle candidates without changing execution semantics.

Linker is not treated as a generic utility. It participates in query-local and phase-local semantic work: variable linking, transient solve compatibility, database/branch materialization, and construction of concrete linked instances.

## Governing boundary

Two historically suspicious methods are not equivalent cleanup candidates:

```text
isValidFor()
linkDatabase()
```

They belong to different risk classes and must not be grouped in one rename/refactor commit.

## isValidFor()

Current architectural understanding:

```text
runtime hidden join over transient TSolve state
```

The method checks whether a candidate is compatible with a transient solve context. Its behavior depends on solve-local runtime objects rather than only on persistent or structural identity.

`solveIndex` is an acceleration structure. It must not be promoted into the semantic source of truth.

Consequences:

- a local rename is not automatically safe;
- callers, temporary solve ownership, compatibility rules, and duplicate-elimination behavior must be preserved;
- any rewrite must prove equivalence when the acceleration structure is present, absent, rebuilt, or reordered;
- the method may eventually receive a name that expresses compatibility or join admissibility, but only after its exact input/output contract is captured by regressions.

Classification:

```text
isValidFor() -> N4, potentially N2 after contract proof
solveIndex   -> N4/U
```

No executable change is authorized in the first 3.5.0.2 pass.

## linkDatabase()

Current architectural understanding:

```text
frozen legacy branch-closure / deferred-materialization kernel
```

The method is not merely a poorly named helper. It captures an established legacy semantic path whose local control flow may mix traversal, closure, compatibility filtering, and materialization boundaries.

A cosmetically attractive decomposition could change:

- traversal order;
- duplicate suppression;
- branch visibility;
- transaction/query-local publication timing;
- deferred versus immediate materialization;
- interaction with transient variables and solve state.

Classification:

```text
linkDatabase() -> N4 / retained legacy semantic kernel
```

Action in 3.5.0.2:

```text
retain name
retain control flow
retain explanatory legacy-contract notes
```

Do not perform local semantic refactoring. Any later redesign belongs to a dedicated global semantic stage with a complete regression corpus.

## Operation vocabulary

The name `link` is valid only when the operation establishes a semantic relation between already existing runtime or logical objects.

Before renaming any Linker method, determine whether it actually performs one or more of these operations:

```text
match          structural candidate comparison
bind           assign a variable/substitution value
join           combine compatible solve fragments
instantiate    produce a concrete linked expression
materialize    publish a concrete rule/assertion into a database scope
traverse       inspect branch/database content
link           establish a maintained relation
```

Methods that perform several of these roles are N4 until their semantic boundaries are proven. A narrower name must not hide remaining side effects.

## Lifecycle model

Linker-owned or Linker-observed state must be classified as one of:

```text
query-local
phase-local
solve-local transient runtime
transaction-visible
persistent/materialized
acceleration-only
```

For every field or helper, record:

1. creator;
2. owner;
3. publication boundary;
4. reset/cleanup boundary;
5. whether identity survives query phase, transaction, commit, or reopen;
6. whether ordering is semantic or incidental;
7. whether reflection, diagnostics, or runners depend on its exact name.

## Initial classification summary

```text
isValidFor()   N4 -> N2 only after compatibility-contract proof
solveIndex     N4/U; acceleration only, not semantic authority
linkDatabase() N4; frozen legacy contract, no 3.5.0.2 refactor
Linker type    retain; class name still matches its broad architectural role
```

## Required regressions before any rename

For `isValidFor()` and adjacent helpers:

- equivalent acceptance/rejection with and without populated solveIndex;
- stable results under candidate iteration reordering;
- no leakage of transient TSolve objects across phase/query cleanup;
- no change in duplicate solutions or Values projection;
- preserved positive/negative phase behavior;
- preserved child/parent C-variable compatibility.

For `linkDatabase()`:

- no local rename/refactor is currently authorized;
- future work requires branch-closure, deferred-materialization, duplicate, transaction, and persistence regressions as one semantic package.

## Decision

The Linker audit produces no N1 candidate.

The apparent naming problems are semantic-boundary problems:

```text
isValidFor()   may later be clarified under proof
linkDatabase() must remain frozen in 3.5.0
```

This prevents aesthetic cleanup from silently rewriting the inference kernel.
