# KANGER 3.5.0.3 — Closure checkpoint

## Status

The invariant audit and hardening stage is complete.

`3.5.0.3` converted transferred audit candidates into one of four explicit outcomes:

```text
proven defect        -> minimal production correction + focused regression
historical contract  -> retained and documented
compatibility slot   -> retained without new lifecycle coupling
unproven concern     -> not converted into speculative production behavior
```

No known demonstrated invariant defect remains open within the audited scope.

The stage did not introduce new logical semantics, persistence formats, query language behavior, storage features, or performance policy.

## Resolved invariant areas

### Index

Resolved:

- `IndexOne.compareTo` narrowing/overflow over the `long` domain;
- null iterator factories on an empty index;
- empty iterator construction crossing the `firstKey()` exception boundary.

Retained contract:

```text
empty Index.firstKey() -> NoSuchElementException
```

The apparent `-1` fallback was not promoted into a new public sentinel contract.

Regression gates:

```text

IndexEmptyBoundarySafetyRunner
```

### TValue canonical state

Resolved and documented:

### Escalera checkpoint ownership

Resolved:

- an empty root now has an explicit reversible checkpoint frame;
- nested frames are completed exactly once and in LIFO order;
- release restores nullable root state;
- commit/release underflow is rejected;
- rollback invalidates acceleration metadata consistently.

Regression gates:


### Factory rollback and ownership

Resolved:

- `TValueFactory.action` is journaled per mark frame and restored on release;
- committed action remains visible after commit;
- factory connection ownership and close authority are characterized;
- storage associations are not destroyed by transaction-local cleanup.

Regression gate:

```text
KangerFactoryActionRollbackSafetyRunner
```

### Rule candidate concurrency

A nondeterministic factory timeout was proven to be a real deadlock:

```text
Mind.locker -> Rule candidate metadata lock
Rule candidate metadata lock -> Mind.locker
```

The resolved-candidate path no longer holds `RuleFactory.metadataLock` while entering `RuleCandidateIndex.collectResolvedLocal(...)`.

`RuleCandidateIndex` now:

- snapshots and filters candidate IDs under its guard;
- hydrates Rules and applies semantic effects outside the guard;
- versions candidate/memo mutation state;
- publishes a computed memo only when the observed version remains current.

Regression gates:

```text
KangerFactorySafetyRunner.testConcurrentMetadata
KangerFactoryConcurrencyDiagnosticRunner   (8 isolated attempts)
DUMB RuleCandidateIndex concurrency stress
```

Authoritative record:

```text

```
