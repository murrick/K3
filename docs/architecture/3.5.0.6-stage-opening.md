# KANGER III 3.5.0.6 — public API documentation audit

## Purpose

Close the final documentation stage of the consolidated `3.5.0` artifact by documenting the contracts that callers see, rather than repeating implementation signatures.

The stage starts from the qualified checkpoint:

```text
branch: arch/3.5.0-core-consolidation
shelf:  develop/3.5.0.5
HEAD:   3db35ae7d0139f021950059843d3baef4dc10407
```

`develop/3.5.0.5` remains a frozen shelf. Work continues only on the architectural branch until the final `develop/3.5.0` promotion.

## Documentation contract

A public member is complete when its Javadoc records the caller-relevant parts that are actually material for that member:

- semantic purpose and the distinction from adjacent operations;
- parameter meaning, accepted null/empty values and ordering constraints;
- return-value meaning, including tri-state or snapshot semantics;
- ownership and object lifetime;
- transaction, checkpoint, commit/release and persistence participation;
- side effects on Mind state, factories, result stores, logging or storage;
- error and partial-result behaviour;
- concurrency and caller obligations;
- a small example where the contract is otherwise ambiguous.

Not every member needs every item. Boilerplate tags without a semantic contract do not satisfy the stage.

## Scope

Owned KANGER surfaces:

1. caller entry points and interfaces (`IUser`, `IMind`, factories and public semantic interfaces);
2. public methods of core execution classes where callers or extensions can invoke them;
3. semantic units, primitives and stores;
4. enums and exceptions;
5. `Leaf`, `Token` and compiler-facing leaf structures;
6. console/bootstrap classes;
7. built-in function and predicate registries;
8. DUMB public implementation surfaces where the implementation contract is externally visible;
9. the KANGER-owned UDF adapter.

Explicitly outside documentation ownership:

- vendored Mozilla Rhino sources;
- regression, diagnostic, profiling and qualification runners;
- generated Javadoc output and build artifacts.

## Priority semantic kernels

The first package documents the external Mind/User entry point and the Linker methods whose names do not reveal their real semantic role.

### `Linker.isValidFor(...)`

This method is a query-local compatibility join between the current partial TVariable binding and already registered `TSolve` tuples. It neither creates a substitution nor proves a Rule. Absence of a relevant tuple constraint permits continuation; presence of a relevant constraint requires at least one compatible tuple.

### `Linker.linkDatabase(...)`

Despite its historical name, this method is not a physical database call. It classifies a terminal branch after system-predicate evaluation, records produced-domain candidates or hypotheses, and defers canonical Rule materialization to `updateDatabase(...)` after branch traversal.

These methods remain behaviourally frozen. Documentation does not authorize renaming or refactoring without an equivalence proof and a focused regression gate.

## Execution order

Packages may be split into smaller commits, but each checkpoint must remain documentation-only unless the audit produces a separately demonstrated invariant defect.

## Qualification

Every checkpoint must pass:

- Java 8 and Java 21 Javadoc generation;
- method-level public API inventory;
- rendered semantic checkpoint assertions;
- KANGER CI and the complete historical corpus;
- semantic-planning, storage-optimization and DUMB reliability workflows when production sources are touched.

The final stage closes only after the owned public surface has no unexplained missing/placeholder contracts, all temporary tooling is removed or promoted to a permanent audit, and the exact final HEAD is promoted to `develop/3.5.0`.
