# KANGER 3.5.0.3 — Rule candidate lock-order invariant

## Scope

This checkpoint resolves a concurrent child-query deadlock spanning:

```text
Mind
RuleFactory
RuleCandidateIndex
```

The defect was exposed by the existing factory concurrency qualification and characterized by:

```text
kanger-console/src/org/kanger/KangerFactoryConcurrencyDiagnosticRunner.java
```

## Historical symptom

`KangerFactorySafetyRunner.testConcurrentMetadata()` starts sixteen child Minds that query and commit into one parent Mind.

The gate was nondeterministic:

- some JVM/platform runs completed;
- other runs exceeded the 90-second timeout;
- the failing platform varied between Java 8, Ubuntu/Java 21, and macOS/Java 21;
- retrying could turn the same configuration green.

This initially resembled a timing-sensitive qualification flake.

The diagnostic runner repeated the exact private regression in isolated user homes and captured thread snapshots at 30 and 75 seconds. A failing attempt produced identical snapshots at both boundaries: eight workers had completed and eight remained permanently blocked.

## Proven lock cycle

The snapshots and source inspection reconstructed this cycle:

```text
worker A
  holds parent Mind.locker
    Mind.commit(child)
      RuleFactory.commit(childRules)
        waits for RuleFactory metadata/candidate lock

worker B
  holds RuleFactory metadataLock or RuleCandidateIndex write lock
    collectResolvedLocal(...)
      hydrate candidate Rule
        RuleFactory.get(...)
          Rule.isDeleted(...)
            Mind.isUnitDeleted(...)
              waits for parent Mind.locker
```

Equivalent lock ordering:

```text
A: Mind.locker -> Rule candidate metadata lock
B: Rule candidate metadata lock -> Mind.locker
```

This is a genuine lock-order inversion, not a slow Linker pass or an insufficient timeout.

## Ownership boundary

The candidate index owns only acceleration metadata:

```text
predicate/polarity/arity signatures
position-to-term candidate IDs
fallback candidate IDs
per-Mind batch-summary memo
```

It does not own:

```text
Rule hydration
Rule deletion state
Mind transaction state
semantic used-state publication
```

Therefore no candidate-index lock may be held while hydrating a Rule or invoking an operation that can enter a Mind lifecycle lock.

## Invariant

> Rule candidate metadata locks protect only coherent metadata snapshots and memo publication. Rule hydration, deletion checks, and all other Mind-dependent semantic work must execute outside those locks.

Required properties:

1. `RuleFactory.metadataLock` does not wrap `RuleCandidateIndex.collectResolvedLocal(...)`;
2. candidate IDs and memo state are copied or filtered while the candidate guard is held;
3. `activeMind.getRules().get(id)` is executed after releasing the guard;
4. semantic `setUsed(...)` effects are executed after releasing the guard;
5. a computed memo is published only if the candidate-index version has not changed;
6. index mutation and rollback invalidate the memo generation;
7. returned candidate IDs remain a coherent snapshot even when a concurrent commit advances the index generation.

## Production correction

### `RuleFactory`

The resolved-candidate path now calls:

```java
ensureDomainIndex();
candidateIndex.collectResolvedLocal(source, candidateAntc, mind, result);
```

without an enclosing `synchronized (metadataLock)` block.

`ensureDomainIndex()` retains its own narrow initialization critical section.

### `RuleCandidateIndex`

The index now maintains a mutation generation:

```java
private long version = 0L;
```

Operations that invalidate candidate or memo state advance this version, including:

```text
clear
release
mergeFrom
indexRule
unindexRule
```

`collectResolvedLocal(...)` is split into three phases:

```text
1. outside lock
   resolve source arguments and active Mind

2. under candidate write lock
   copy/filter candidate IDs
   read an existing memo
   record index version

3. outside lock
   hydrate Rules
   evaluate generated non-substitutable batches
   apply semantic used-state effects

4. under candidate write lock
   publish the computed memo only when version is unchanged
```

Thus no path from the candidate guard reaches `Mind.isUnitDeleted()`.

## Semantic preservation

The correction does not change:

- candidate signature construction;
- positional/wildcard filtering;
- Rule IDs selected from one coherent index generation;
- generated/non-substitutable batch eligibility;
- semantic used-state effects;
- transaction commit order;
- persistence format;
- Rule identity or hydration ownership.

A concurrent mutation may prevent a newly computed batch summary from being cached, but it does not invalidate the current call's coherent candidate snapshot. A later call recomputes against the newer generation.

## Regression gate

`KangerFactoryConcurrencyDiagnosticRunner` invokes the existing factory concurrency regression eight times, each in an isolated temporary user home.

For each attempt it:

- preserves the original pass/fail semantics;
- emits worker thread snapshots after 30 and 75 seconds if progress stops;
- rejects attempts that exceed the diagnostic window;
- verifies all original metadata isolation and commit expectations through the wrapped regression.

The runner is executed by the read-only `KANGER CI` workflow as:

```text
Factory concurrency lock-order invariant
```

The historical one-run factory safety gate remains in the DUMB qualification matrix.
