# KANGER 3.5.0.2 — TValueFactory lifecycle and naming audit

## Scope

This audit classifies the visible `TValueFactory` naming surface without changing executable code.

The governing rule remains:

> 3.5.0 must not intentionally change observable execution semantics.

## Established architectural role

`TValueFactory` owns canonical `TValue` identity and participates in the transaction-overlay factory model.

The implementation map distinguishes two kinds of state associated with this factory:

- `current` — the currently selected/evaluated `TValue` context used while processing a `TVariable`;
- `top` — the Escalera/overlay anchor used by the factory lifecycle and transaction snapshot model.

These fields are therefore not a semantic pair and must not be renamed merely to look symmetrical.

## Lifecycle evidence

The B7.1 stabilization work demonstrated that stale `top` retention could keep a deleted transient child C-variable reachable through:

```text
TValueFactory.top -> Step -> TValue.value -> child C-variable
```

The fix required coordinated cleanup of:

```text
Mind.cvarChilds
Mind.cvarParents
TValueFactory.current
TValueFactory.top
factory cache state
```

This proves that `top` is lifecycle-significant infrastructure, not an incidental cursor.

`current` is also runtime-significant: it represents the active value context for a `TVariable` and must be reset consistently between cycles and transaction boundaries.

## Candidate classification

### `top`

Observed role:

- transaction-overlay / Escalera anchor;
- participates in snapshot, release, commit, and cleanup;
- referenced by lifecycle diagnostics and safety runners.

Classification:

```text
N2/U
```

A rename is potentially useful because `top` does not expose the ownership or anchor role, but it is not N1. Any rename must update production code, transaction lifecycle paths, reflection strings, diagnostics, and architectural documentation atomically.

No target name is approved until the exact direction of the Escalera chain and the distinction from factory root/bottom anchors are re-read from source.

### `current`

Observed role:

- active runtime `TValue` context for the currently processed `TVariable`;
- transient and cycle/query-local rather than persistent;
- reset/cleanup-sensitive.

Classification:

```text
N2/U
```

The name is generic, but a replacement such as `currentValue`, `activeValue`, or `currentTValue` cannot be selected without verifying whether the field stores a `TValue`, a `Step`, or another carrier.

The important constraint is semantic: `current` must not be conflated with the factory overlay anchor.

### `find(...)`

The implementation map records an unresolved observation that `TValueFactory.find` does not filter logically deleted `TValue` instances.

Classification:

```text
N4
```

This is not a naming-only candidate. The method name may be broad, but changing filtering behavior or narrowing the name would require a semantic decision about resurrection, canonical identity, and deleted-value visibility. Defer to `3.5.0.3` or a later semantic stage.

## Prohibited false symmetry

Do not introduce paired names such as:

```text
current / previous
top / current
active / root
```

unless the source proves those relationships.

`current` and `top` belong to different lifecycle dimensions:

```text
current -> runtime evaluation context
top     -> transaction-overlay anchor
```

## Atomic rename boundary

Any approved N2 rename must include all of:

1. the production field declaration;
2. every read and write;
3. reset, release, commit, rollback, pack, and cleanup paths;
4. safety-runner reflection strings;
5. diagnostics that print factory chain state;
6. Javadoc and invariant documentation.

No partial compatibility alias should be introduced for private fields unless an external reflective contract is explicitly retained.

## Result

No N1 candidate is confirmed in `TValueFactory`.

```text
top     -> N2/U
current -> N2/U
find    -> N4
```

The subsystem is naming-sensitive because its generic names encode two independent lifecycle axes. The next step is to inspect narrower owner-local helpers whose names do not participate in transaction anchors, runtime evaluation state, reflection contracts, or canonical identity semantics.
