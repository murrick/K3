# 3.5.0.6 — Architectural Object Passport

## Purpose

This document defines the documentation standard for the public architecture of KANGER.

The goal is not to maximize comment coverage or to restate Java signatures. The goal is to make the architectural meaning of the system explicit: what an object is, who owns it, what makes it identical to itself, how it participates in transactions and persistence, which projections depend on a concrete `Mind`, and which invariants must remain stable while implementations evolve.

A passport is therefore a compact architectural specification attached to a public or architecturally significant object.

## Core principle: inside and outside

Every fundamental KANGER object is documented through two complementary views.

### Inside

The inside view describes the object's architectural essence:

- logical meaning;
- canonical identity;
- stable structure;
- properties that belong to the object itself;
- invariants that must not depend on a caller, transaction, storage generation or textual projection.

### Outside

The outside view describes relationships and projections that appear only in a concrete context:

- transaction visibility;
- deletion or restoration relative to a `Mind`;
- storage attachment and lazy materialization;
- provenance and explanation links;
- query participation;
- text rendered for a concrete transaction;
- parent/child transaction projection.

The distinction is mandatory for level-I passports because it prevents contextual state from being mistaken for intrinsic identity.

A recurring KANGER invariant is:

```text
stable entity
    + contextual relationships
    = observable state in a Mind
```

## Mind as decision context

`Mind` is not merely a container. It is the active, self-reproducing decision context of KANGER.

A `Mind` owns the current transactional world, holds potentially applicable knowledge, and repeatedly actualizes that potential through inference until a fixed point is reached.

The explanatory model is:

```text
potential knowledge
        +
current Mind state
        +
triggering conditions
        ↓
decision
        ↓
inference / materialization
        ↓
new potential knowledge
```

The process terminates when the current `Mind` contains no new admissible transitions for the selected inference mode.

This metaphor is explanatory, not normative. The normative contracts remain the concrete identity, lifecycle, transaction and fixed-point invariants documented in the relevant types.

## Passport depth

Documentation depth is proportional to architectural significance.

### Level I — full architectural passport

Use for entities without which the KANGER model cannot be understood.

Required sections:

1. Purpose
2. Architectural essence
   - Inside
   - Outside
   - Stable
   - Context-dependent
3. Ownership
4. Identity and canonicalization
5. Lifecycle
6. Transaction semantics
7. Persistence and materialization
8. Provenance
9. Decision or execution role
10. Side effects
11. Caller obligations
12. Architectural invariants
13. Historical notes

Level-I objects currently include:

- `Mind` / `IMind`;
- `User` / `IUser`;
- `Rule` / `IRule`;
- `Predicate` / `IPredicate`;
- `Term` / `ITerm`;
- `Operation` / `IOperation`;
- `TVariable` and `TValue` as one conceptual pair;
- `Function` and `FValue` as one conceptual pair;
- `Linker`.

### Level II — reduced architectural passport

Use for important architectural boundaries and services.

Required sections:

1. Purpose
2. Ownership
3. Identity
4. Lifecycle
5. Transaction and persistence semantics
6. Key invariants
7. Historical notes where names or responsibilities are misleading

Typical level-II objects:

- canonical factories and registries;
- `Calculator`;
- `Analyzer`;
- `Parser` and `Compiller`;
- `Escalera`;
- `IBase` and `IData`;
- `Base`, `Data` and `DB`.

### Level III — caller-oriented method contract

Use for leaf structures, enums, exceptions, console/bootstrap surfaces, built-in operations and implementation classes that do not express an independent architectural concept.

Required content:

- what the object or method represents;
- where it is used;
- what the caller must provide;
- what is returned or changed;
- side effects and errors;
- historical naming only where it could cause misuse.

A level-III object must not receive artificial philosophical depth merely to reduce an audit counter.

## Significance scale

Each object may be scored from 0 to 2 on five dimensions:

- semantic centrality;
- transaction significance;
- identity/canonicalization significance;
- persistence significance;
- historical ambiguity.

The score guides documentation depth:

```text
8–10  Level I
5–7   Level II
0–4   Level III
```

The score is a planning aid, not a quality metric or release gate.

## Architectural invariants

A passport must state the few invariants whose violation would change the meaning of the system.

Good invariants distinguish concepts that are easy to conflate:

```text
identity != representation
origin != materialization
deleted != nonexistent
generated != temporary
comment not-in logical identity
storage address != logical id
```

Invariants should be concise, testable where possible, and stable across implementation changes.

## Method documentation

Method Javadoc belongs under the passport and should describe the projection or operation represented by the method.

A useful method contract answers:

- whether the result is intrinsic or `Mind`-dependent;
- whether it is canonical, materialized, copied or live;
- whether deleted objects remain visible;
- whether storage access or lazy hydration may occur;
- whether the method mutates logical state, transaction state or metadata;
- what preconditions the caller must satisfy;
- which failures are part of the contract.

Restating a method name or return type is insufficient.

## Historical names

Historical terminology is preserved where changing it would harm API compatibility or obscure the evolution of the system.

Every misleading historical name must document:

- the historical name;
- the current architectural meaning;
- what it does not mean;
- why the name remains.

Examples:

```text
isStored()
current meaning: Rule is an assertion
not: Rule currently has a physical storage record
```

```text
linkDatabase()
current meaning: query-local join/filter over materialized domains and T-values
not: physical database I/O
```

```text
C-variable
current meaning: canonical unknown witness and Rule-scoped projection source
not: a concrete substitution value
```

## Ownership boundary

The passport standard applies to KANGER-owned architecture.

Outside the owned documentation surface:

- vendored `org.mozilla.*` sources;
- diagnostic, safety, qualification, performance and telemetry runners;
- test-only implementation details.

These may have operational comments, but they are not counted as public architectural passports.

## Examples of proportional depth

### Rule — Level I

A Rule requires a full passport because it combines logical identity, assertion/compound structure, transaction visibility, origin/materialization, provenance and historical terminology.

### ILogEntry — Level III

A log entry requires a caller-oriented contract explaining that it is diagnostic metadata, not logical knowledge, transaction state, canonical identity or a stable persistence protocol. It does not require a full ontology of inference.

## Completion criteria for 3.5.0.6

The public API documentation stage is complete when:

- actionable `public_api` debt is zero;
- owned `internal_spi` contracts are documented;
- every level-I object has a coherent architectural passport;
- level-II and level-III objects are documented proportionally;
- Java 8 and Java 21 Javadoc generation succeeds;
- rendered semantic checks succeed;
- Maven regression corpus and KANGER CI succeed;
- changes remain documentation/tooling-only unless a separately diagnosed semantic defect is protected by a permanent regression gate.
