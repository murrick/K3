# Предложение по интеграции диагностики TValue

**Рекомендация: следующий шаг — ограниченное подключение в диагностический модуль. Для включения в рабочее ядро проверки пока недостаточны.** У нас есть воспроизводимый журнал с автоматическими уведомлениями, полным сравнением и обязательным отказом потребителя на известных неподдерживаемых границах. Выигрыш сериализации измерен локально; ускорение машины вывода этим экспериментом не доказано.

Это предложение собирает результаты параллельной оптимизации. Оно не выполняет интеграцию, не меняет defaults, не сливает develop и не заменяет основной план разработки: гигиена исходников, устойчивость длительных сессий, глобальное согласование гипотез и M5 остаются отдельной работой.

## Что именно предлагается перенести

| Компонент | Назначение | Проверенная граница |
| --- | --- | --- |
| [StreamAuthorityJournal](tvalue-authority-stream/StreamAuthorityJournal.java) | Выбранный диагностический журнал; свежая потоковая сериализация полного представления | Поддерживаемые resident-состояния; полный контроль остаётся включён |
| [StreamAuthorityRead](tvalue-authority-stream/StreamAuthorityRead.java) и [ResidentTValueRead](tvalue-persistent-lookup/ResidentTValueRead.java) | Свежая полная проверка и чтение resident-бакетов без изменения native-состояния | Точные поддерживаемые классы и quiescent-чтение; общие raw-примитивы требуют отдельного native-контроля |
| [BeforeAuthorityJournal](tvalue-authority-stream/BeforeAuthorityJournal.java) | Контрольный вариант для парной квалификации | Сохраняется на этапе интеграции; его удаление не входит в это предложение |
| [ConsumerHooks](tvalue-consumer-gate/ConsumerHooks.java) | Автоматические callbacks, учёт активных контекстов, очистки и коллизий идентичности | Однопоточная диагностическая сессия на проверенном core |
| [QualifiedJournalConsumer](tvalue-consumer-gate/QualifiedJournalConsumer.java) | Выдаёт неизменяемую трассу только после обеих проверок; иначе typed refusal | Проверены коллизия ID, пропущенное событие, ошибка адаптера, отсутствие сессии и восстановление после отказа |

Текущие классы — диагностические прототипы в `docs`, а не готовый production API. Отражение, статический реестр адаптера и жёсткие ограничения raw-reader нельзя незаметно превратить в общий контракт ядра. Перенос должен сохранить независимое перечисление native-значений как отдельный контроль, а не ограничиться согласием двух представлений на общих примитивах.

Числа относятся к финальным сериям соответствующих этапов. Архивные прототипы, неудачные предварительные fixture-ожидания и повторные измерения исключены. Эти серии проверяют перекрывающиеся контракты; сумма JVM не является числом независимых сценариев или доказательством полной корректности.

Последние memory-этапы привязаны к точному native commit `5d5f6aff271f1abf371fbde55d637744c53f0bc3`. Восстановление исходных тел удалением записанных callbacks совпадает побайтно; instrumented native bytecode отличается в четырёх классах. Это доказательство ограниченной структуры изменения, а не гарантия поведения произвольных callback-реализаций. Сдвиг develop требует проверки новых исходников и затронутых контрактов.

## Предлагаемая последовательность

1. **Изолировать диагностический модуль.** Перенести выбранные классы и воспроизводимые fixtures в `kanger-qualification` или отдельный диагностический source set. Дать одному потребителю владение сессией; вернуть checked immutable trace только после полного finish. Сохранить парный контроль и выключенное по умолчанию подключение. Не добавлять runtime-зависимость core от классов `docs`.
2. **Определить контракт observer-подключения.** Уведомления должны покрывать конструирование, мутации, clear-фанout, checkpoints, promotion, settlement и retirement. Ошибки диагностического захвата должны запрещать экспорт, сохраняя результат/исключение исходной native-операции. Показать конкретный patch и подтвердить clean/diagnostic parity на текущем выбранном HEAD. Interface и политика отключённого observer ещё не реализованы и не измерены.
3. **Принять отдельное решение о native `clear()`.** Пока коллизия означает обязательный отказ диагностического потребителя. Исправление политики ID или снимков — отдельный patch ядра с собственными regression-сценариями; оно не следует автоматически из переноса журнала.
4. **Закрыть границы корректности и хранения.** Проверить полный inference corpus с заранее определённым критерием семантической эквивалентности, сохраняющим допустимые альтернативные порядки публикаций. Для SMART отдельно проверить открытие, загрузку, lazy/resident переходы, ревизии, rollback/publication/fork и долгую сессию. Memory-успех не заменяет эти проверки.
5. **Измерить рабочую стоимость.** На точном интеграционном patch измерить отключённые hooks, включённую диагностику, allocation и end-to-end inference. Только после корректности можно выбирать production-путь и обсуждать отключение парного контрольного журнала. Полный oracle в текущем диагностическом контракте сохраняется.

Каждый шаг имеет конкретный результат для ревью. Подготовка предложения и публикация evidence не разрешают автоматически merge или включение production defaults.

## Что решить для `clear()`

| Вариант | Что предотвращает | Цена и обязательные проверки |
| --- | --- | --- |
| Монотонные TValue ID в пределах живого User/schema, без сброса при обычном clear | Повторный ID не связывает новый маршрут со старым captured объектом | Разделить очистку значений и явный reset идентификаторов; проверить остальные пользователи schema counters, повторное открытие storage и тестовые ожидания |
| Поколение фабрики как часть идентичности | Различает объекты с одинаковым числовым ID между поколениями | Более широкий контракт: cache keys, маршруты, storage, сериализация и API должны понимать поколение |
| Запрет clear при зависимых живых контекстах | Исключает конкретную опасную комбинацию | Ограничивает допустимые операции и требует точного учёта зависимостей; ID-семантика после закрытия контекстов остаётся отдельным вопросом |

Для первого отдельного core-прототипа предлагаю исследовать монотонные TValue ID: это прямо устраняет найденную причину без переопределения captured membership. Это инженерная рекомендация по ограниченному memory-контрпримеру, а не принятое изменение общей storage-политики. Сначала нужно проверить, где сброс счётчиков является намеренным контрактом, и согласовать работу с основным strand, чтобы не дублировать уже начатый fix.

## Условия готовности

| Подключение | Текущий статус | Что ещё обязательно |
| --- | --- | --- |
| Повторить опубликованные bounded memory fixtures | Воспроизводимо на точной базе | Совпадение source/class hashes и сохранение native-контролей |
| Изолированный диагностический модуль | Можно готовить patch | Чистая зависимость от core, единый owner сессии, безопасные callbacks, regression parity |
| Авторитетный production-потребитель | Не готов | Полный corpus, поддерживаемая storage-граница, политика идентичности, поведение конкурирующих сессий |
| Обещание ускорения вывода | Не подтверждено этой серией | Новое end-to-end измерение конкретного интегрированного решения |

Известные исключения: SMART persistence; concurrent sessions; произвольные классы/расширения; зарегистрированные изменения ID/переменной; all-factory payload atomicity; полный frozen corpus. Ранние попытки полного corpus не дали frozen-equivalence, и поздние memory-тесты этот результат не отменяют. `JOURNAL_DISAGREEMENT` в consumer — защитная ветка, отдельно не fault-injected. Исправление коллизии ID в ядре ещё не выполнено.

## Проверка источников предложения

[audit.json](tvalue-integration-proposal/audit.json) фиксирует SHA summaries и manifests, commit каждого отчёта и результат проверки всех файлов десяти evidence manifests. [audit.py](tvalue-integration-proposal/audit.py) воспроизводит эту сверку и проверяет внутренние ссылки. Новых runtime-прогонов и performance-замеров здесь нет: этот этап собирает уже опубликованные доказательства и формулирует условия следующего patch.
