# Resident inference: проверка стабильности и отдельных запросов

Дата: 2026-10-22. Ветка: `experiment/3.8.0-tvalue-resident-stability`.
Родитель: `303be970c719cea70991791a4286cda9460b9802`.
Native pin: `2422f7f6d9e1af7608203b1566df64b5f29fe344`.

## Результат

**28 JVM, 50 176 запросов; все проверки корректности прошли.**
Ни одна из шести пар baseline/candidate не подтвердила стабильность по
заранее зафиксированному протоколу. Поэтому итоговое отношение скорости
не вычисляется. Это результат проверки конкретного критерия на ограниченном
запуске, а не доказательство отсутствия любого плато или дефекта кандидата.

В одной паре предварительное условие выполнилось после 176 циклов, но
последующая проверка обнаружила дальнейшее ускорение baseline на 7.9%.
Фиксация одного удачного окна дала бы ложную уверенность в стабильности.

Изменён только qualification fixture и добавлены скрипты/данные.
Код ядра, оба диагностических модуля, production defaults и develop не менялись.
Кандидат остаётся отдельным; inference speedup не заявляется.

## Протокол, зафиксированный до запуска

`plan.json` записан до исполнения матрицы; его SHA256 совпадает в build,
environment, summary и manifest. Предел — 256 циклов на JVM. Режим только `off`,
где первоначально появился вопрос о замедлении. Профили default и `-Xbatch`,
по три повторения, четыре режима clean/disabled/baseline/candidate:
24 timing JVM. Порядок модулей и профилей обращается в среднем повторе.
Ещё четыре отдельные JVM baseline/candidate × default/batch собирают полный
LogCompilation и **не входят** в timing comparisons. Параллельные benchmark
процессы этим исследованием не запускались.

Условие для каждого cutoff 64, 80, …, 208:

- взять четыре предыдущих неперекрывающихся окна по 16 циклов;
- во всех трёх последовательных сравнениях отношение медиан суммы query
  intervals должно лежать в `[1/1.05, 1.05]`;
- отношение медиан каждого из семи запросов должно лежать в `[1/1.10, 1.10]`;
- baseline и candidate должны одновременно выполнить условия на одном cutoff.

Выбирается **первый** совместно подходящий cutoff без просмотра последующих
timings. Следующие 48 циклов — контроль: сравниваются первые и последние
16 циклов с теми же пределами. Если контроль не прошёл, пара получает
`holdout_unstable`; более позднее удобное окно не ищется. Если исходное условие
не выполнилось, статус `no_joint_gate`. Агрегированное отношение скорости
разрешено только при успешных трёх парах внутри профиля.

Это инженерный критерий локальной устойчивости, не статистический тест,
не доверительный интервал и не гарантия неизменности производительности.
Допуски не расширялись после просмотра результатов.

## Решения по парам

| Профиль | Повтор | Cutoff | Результат |
|---|---:|---:|---|
| default | 0 | 176 | holdout_unstable |
| default | 1 | — | no_joint_gate |
| default | 2 | — | no_joint_gate |
| batch | 0 | — | no_joint_gate |
| batch | 1 | — | no_joint_gate |
| batch | 2 | — | no_joint_gate |

В default/0 отношение query-медиан последнего к первому окну контрольных
48 циклов: baseline **0.921**, candidate **0.972**. Baseline выходит за предел
суммарного времени. Именно поэтому пара отвергнута, несмотря на первоначальный
проход. Остальные пары не прошли совместное условие к последнему допустимому
cutoff 208. Последние 48 циклов нужны для контроля: предел не переносился
задним числом на 256 без доступного последующего окна.

В batch исходное условие не прошли также все clean/disabled JVM. Поэтому
наблюдаемая нестабильность не локализована исключительно в подключённом
диагностическом кандидате. Это не устанавливает её причину.

## Отдельные запросы

Семь запросов и ожидаемые результаты сохранены из родительского fixture:
три положительных ground, отрицательный ground, UNKNOWN и два запроса
подстановок. Для каждого Mind.query записаны wall time и thread allocations.
Два массива на цикл создаются до outer timer. Запись отдельных CSV строк идёт
после outer timer; внутри query interval нет форматирования CSV или записи
на диск. Сумма семи отдельных wall/allocation интервалов точно сверяется
с cycle query totals для каждого цикла. Проверки ответов, root authority,
наблюдения и finish остаются вне query timers. Full-cycle данные сохраняются,
но не смешиваются с прежним fixture как неизменённая измерительная нагрузка.

Описательно, в последних 48 циклах два variable запроса занимают около
56.0% времени query intervals с default JIT и 55.3% с batch: медиана долей
внутри JVM, затем медиана шести attached JVM профиля. Это распределение работы
в данном сценарии, без квалифицированного сравнения скорости модулей.
Исходные per-query данные доступны для всех циклов.

## Корректность и журналы

Все 28 JVM завершились успешно, stderr пуст. Все 50 176 native строк совпали
с соответствующими clean контролями, включая точные `[{x=Tom}]`, освобождение
транзакций и authority. Проверены 14 336 variable rows.
Все **4096** attached trace проходят authority replay; **2048** пар
baseline/candidate совпадают побайтно, как и callback counts. Observer и
context references освобождаются после каждого цикла.

Trace и event evidence упакованы в отдельный tar.gz на JVM. Analyzer читает
каждый элемент, сверяет полный ожидаемый набор и исполняет прежний replay;
архивирование не заменяет проверки содержимого. Сборка сверяет неизменность
clean/hooked runtime и обоих модулей с родительскими class hashes. Сохранено
ограничение Java 21 из родителя: класс Rhino NativeArray отличается от сборки
Java 17, классы Kanger и диагностических модулей совпадают с frozen manifests.

## Отдельные компиляционные пробы

Используется тот же новый fixture с корреляцией JVM uptime и monotonic clock
до seed. Погрешность привязки — интервал выборки плюс 1 мс. В последние
48 циклов отдельных logging JVM установлены следующие Kanger nmethod:

| Профиль | Baseline | Candidate |
|---|---:|---:|
| default | 69 | 55 |
| batch | 35 | 32 |

Это завершения компиляций, включая повторные уровни/OSR, а не число уникальных
методов. Полные XML, method/level/timestamp и invalidation records сохранены.
Компиляция продолжается поздно в этих logging запусках; это не доказывает,
что она одна объясняет timing variation в отдельных unlogged JVM. Нагрузка
общего хоста, GC, частота CPU и состояние native caches отдельно не изолированы.

## Воспроизведение

Java Temurin 21.0.6, macOS aarch64, общий хост без pinning/exclusivity.
Восстановить frozen артефакты по предыдущему отчёту; запускать из корня:

```sh
python3 docs/tvalue-resident-stability/build.py
python3 docs/tvalue-resident-stability/run.py
PYTHONDONTWRITEBYTECODE=1 python3 docs/tvalue-resident-stability/analyze.py
python3 docs/tvalue-resident-stability/compilation.py
python3 docs/tvalue-resident-stability/manifest.py
```

run.py требует свежий evidence namespace. Сохраняются исходники, план,
команды, environment, CSV, native строки, stdout/stderr, архивы полных traces,
LogCompilation XML, результаты решений и SHA256 manifest. Synthetic gate
проверки покрывают константные данные, непрерывный дрейф, поздний срыв и
разнонаправленные per-query изменения при неизменной общей сумме.

## Границы и дальнейшая работа

Квалифицирован только ограниченный resident API сценарий на прежней native
базе. SMART persistence, полный inference corpus, concurrent sessions и
root-clear recycled-ID repair не квалифицированы. Failure/wiring серию заново
не запускали: исполняемые runtime/module классы Kanger не менялись.

Не увеличивать число циклов бесконечно и не продвигать кандидат по allocations.
Следующий содержательный шаг — сопоставить актуальный develop с pinned native,
затем локализовать состояние и стоимость двух variable запросов на согласованной
базе. При повторном измерении сохранить заранее заданные ограничения и
возможность результата «стабильность не подтверждена».
