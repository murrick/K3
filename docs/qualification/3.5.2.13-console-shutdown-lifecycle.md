# KANGER 3.5.2.13 — Console shutdown lifecycle

## Scope

This stage repairs the interactive Console JVM shutdown path after the explicit storage lifecycle contract made an active `IMind` mandatory for physical close.

The defect was observed manually as:

```text
java.lang.IllegalStateException: Cannot close an open database without an active Mind
    at org.kanger.User.close(User.java:237)
    at org.kanger.ShutdownHook.run(ShutdownHook.java:48)
```

## Root cause

The legacy Console `ShutdownHook` retained only `User` and executed:

```text
flush -> close(null)
```

The corrected Core lifecycle intentionally rejects `close(null)`. The Console bootstrap and session did not publish the actually active `IMind` to the JVM shutdown path.

## Correction

The Console shutdown adapter now retains the active Console-owned `IMind`.

On JVM shutdown it:

1. rolls back unfinished child transaction levels until the root is reached;
2. delegates root physical shutdown to the ordinary `IMind.closeStorage()` path;
3. never performs `close(null)` or a direct low-level storage close.

`Console.session` publishes every lifecycle transition that can replace the active Mind, including transaction start/commit/rollback and storage/workspace operations. The historical public `Console.session(IMind)` entrypoint remains intact.

## Qualification

The existing `KangerConsoleLifecycleBindingRunner` is extended rather than adding a new qualification runner. It proves:

- the shutdown hook receives an active level-1 Mind;
- uncommitted child content is rolled back during shutdown;
- committed root content survives the ordinary checkpoint/close path;
- the closed database reopens cleanly;
- shutdown on an already closed root is idempotent.

Expected new markers:

```text
CONSOLE_LIFECYCLE_BINDING_PASS shutdown-active-rollback
CONSOLE_LIFECYCLE_BINDING_PASS shutdown-root-close
CONSOLE_LIFECYCLE_BINDING_PASS shutdown-idempotent-closed
```

## Artifact boundary

The KANGER Server Maven build does not consume `kanger-console/src`; therefore this is a Console/root-aggregate correction and does not change the `server-0.18` production code or require a new Server identity.

Any VPS operations package must nevertheless be regenerated or requalified from the post-fix canonical shelf so its source ancestry remains exact.

No release merge, release publication, VPS deployment, or production cutover is authorized by this stage.
