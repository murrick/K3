# 3.5.2.15 — storage baseline insertion boundary

## Problem

Manual Console transaction torture testing exposed a lifecycle defect that predates 3.5.2.

Opening a database while the active `IMind` was already at transaction level 1+ caused `User.use(...)` to rebind the factories of a child Mind with `transaction(null)`. The Mind retained its runtime parent chain while its factories became rooted directly in physical storage.

That hybrid topology violated the child-overlay invariant. Later commit/rollback could splice storage-rooted caches back into runtime parent overlays, producing duplicated logical rules and eventually malformed DUMB linked-chain endpoints.

The observed `DUMB storage corruption: invalid chain endpoints ...` failures are therefore treated as detection of already-invalid persisted topology, not as the root cause.

A related lifecycle gap was also identified: `mind.getTransactionLevel() == 0` is not sufficient proof of transaction quiescence. A caller can retain a direct reference to the root Mind while a child reservation is still open. Storage lifecycle must reject that hidden-reservation state as well.

## Accepted lifecycle contract

`use` has one supported workspace-preserving transformation:

```text
offline workspace L0
        |
        | open database
        v
workspace overlay L1
persistent database L0
```

The previous level-0 workspace remains provisional. Console recompiles its logical source in the context of the opened database so identifiers, canonical terms/predicates/rules, generated consequences, and contradiction checks are rebuilt against the new persistent baseline.

Generated rules are intentionally not replayed as source. They are derived state and are recalculated in the database context.

The workspace reaches the database only after an explicit transaction commit. Rollback discards it without modifying the database.

Generalized multi-level transaction-stack rebase is deliberately out of scope for 3.5.2.15. A `use` attempt while a normal L1+ stack is active is rejected.

## Transaction quiescence

Storage lifecycle now defines quiescence as both:

```text
active Mind transaction level == 0
AND
root Mind has no pending child reservations
```

`Mind.hasPendingTransactions()` is a package-private lifecycle probe used only by the owning Core `User`; it does not widen the public `IMind` API.

`User` applies this invariant to:

- `use`;
- `checkpoint`;
- `close`.

The rejection uses the existing stable lifecycle contract:

```text
ACTIVE_TRANSACTION
TRANSACTION_RESOLUTION_REQUIRED
```

Rejected operations occur before storage acquisition, physical close/checkpoint, or factory rebinding. They must not change active Mind topology, storage identity, workspace source, or physical generation.

## Workspace baseline insertion

Console routes database opening through one baseline-insertion path.

For a non-empty offline L0 workspace:

1. Core opens the selected database as the persistent L0 baseline.
2. Console creates a child Mind above that root.
3. The old logical workspace source is recompiled in the child context.
4. Canonical identities and generated consequences are therefore rebuilt against the database.
5. A successful non-empty import remains active at L1 for explicit commit/rollback.
6. An empty import releases the child and leaves the database root active.

Source replay is intentional here: carrying the old object graph directly across the storage boundary would preserve offline IDs and canonical references that are not authoritative in the opened database namespace.

## Failed import recovery

A rejected or failed workspace import must not leave a hidden child reservation underneath a root pointer.

Recovery ordering is now:

```text
release imported child reservation
        -> close newly opened storage
        -> restore original offline workspace source
```

The imported diagnostic log is preserved for the normal Console explanation path.

Exception recovery tracks whether the import reservation is still open so cleanup is not attempted twice. Recovery failures are attached to the primary failure rather than replacing it.

## Qualification

`KangerConsoleLifecycleBindingRunner` verifies:

- a root pointer at visible L0 with a live child reservation cannot open storage;
- active level-2 `use` is rejected before storage acquisition;
- rejected `use` preserves transaction depth and visible source;
- ordinary rollback/commit still works after rejected `use`;
- an offline level-0 workspace becomes level 1 above a newly opened database;
- rollback of the imported workspace leaves the database unchanged;
- a pre-existing database baseline remains on level 0;
- explicit commit publishes the imported workspace exactly once;
- close/reopen preserves baseline plus committed workspace without multiplicative duplicates;
- a root pointer with a live child reservation cannot checkpoint or close storage;
- existing root checkpoint, active-close, semantic-presentation, diagnostic and shutdown lifecycle qualifications remain green.

Required markers:

```text
CONSOLE_LIFECYCLE_BINDING_PASS hidden-reservation-use
CONSOLE_LIFECYCLE_BINDING_PASS active-use-rejected
CONSOLE_LIFECYCLE_BINDING_PASS baseline-insertion-rollback
CONSOLE_LIFECYCLE_BINDING_PASS baseline-insertion-commit
CONSOLE_LIFECYCLE_BINDING_PASS baseline-insertion-reopen
CONSOLE_LIFECYCLE_BINDING_PASS hidden-reservation-storage
CONSOLE_LIFECYCLE_BINDING_OK
```
