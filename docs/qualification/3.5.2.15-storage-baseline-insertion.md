# 3.5.2.15 — storage baseline insertion boundary

## Problem

Manual Console qualification exposed an old lifecycle defect that existed before 3.5.2: opening a database while the active `IMind` was already at transaction level 1+ caused `User.use(...)` to rebind the factories of a child Mind with `transaction(null)`. This created an invalid hybrid topology in which the Mind still had a parent transaction chain while its factories were already rooted directly in physical storage.

Subsequent commit/rollback operations could then splice storage-rooted caches back into runtime parent overlays, producing duplicated logical rules and eventually malformed DUMB linked-chain endpoints.

The DUMB `Base.resolveEndpoints()` failure is therefore treated as detection of already-invalid persisted topology, not as the root cause.

## Accepted lifecycle contract

`use` has one supported workspace-preserving transformation:

```text
offline workspace L0
        |
        | open database
        v
workspace overlay L1
persistent database L0
```

The previous level-0 workspace remains provisional. Console recompiles its logical source in the context of the opened database so identifiers, canonical terms/predicates/rules, generated consequences, and contradiction checks are rebuilt against the new persistent baseline. The workspace reaches the database only after an explicit transaction commit.

Generalized multi-level transaction-stack rebase is deliberately out of scope.

## Correction

`User.use(IMind, String)` now rejects any non-null Mind with `transactionLevel > 0` before `data.use(...)`, storage acquisition, or factory rebinding.

The rejection uses the existing lifecycle contract:

```text
ACTIVE_TRANSACTION
TRANSACTION_RESOLUTION_REQUIRED
```

No storage identity, Mind topology, factory topology, or workspace source may change on rejection.

## Qualification

`KangerConsoleLifecycleBindingRunner` now verifies:

- active level-2 `use` is rejected before storage acquisition;
- the rejected operation preserves transaction depth and visible source;
- ordinary rollback/commit still works after the rejection;
- an offline level-0 workspace becomes level 1 above a newly opened database;
- rollback of that imported workspace leaves the database unchanged;
- a pre-existing database baseline remains on level 0;
- explicit commit publishes the imported workspace exactly once;
- close/reopen preserves both baseline and committed workspace without multiplicative duplicates.

Expected markers:

```text
CONSOLE_LIFECYCLE_BINDING_PASS active-use-rejected
CONSOLE_LIFECYCLE_BINDING_PASS baseline-insertion-rollback
CONSOLE_LIFECYCLE_BINDING_PASS baseline-insertion-commit
CONSOLE_LIFECYCLE_BINDING_PASS baseline-insertion-reopen
CONSOLE_LIFECYCLE_BINDING_OK
```
