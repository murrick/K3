# Повтор option keys: allocations и время с JFR и без него

2026-10-22. Родитель `2a082580b7f00c211b376047fa617f615897da1b`.
Native pin `60fdc34736c51fa4e5659982630347fb1d1b59fc`.
Кандидат и все product исходники не изменялись.

## Результат

26 inference JVM: два smoke, 16 измерительных без JFR, восемь с JFR.
Все 86 044 запроса, 24 584 точные строки `[{x=Tom}]`, 6 148 replay traces
и 6 148 побайтных сравнений trace/event файлов с frozen контролями прошли.
Оба журнала и callback counts сохранены. Прежние evidence не изменены.

Снижение allocations воспроизвелось во всех 12 измерительных парах, но прежние
23% attached экономии не воспроизвелись. Ниже отношения keys/current для медианы
суммы семи Mind.query в циклах 128–511: медиана отношений и диапазон по парам.

| Режим | Пар JVM | Allocated bytes: медиана (диапазон) | Wall time: медиана (диапазон) |
|---|---:|---:|---:|
| clean, без JFR | 4 | 0.8900 (0.8889–0.9033) | 0.9711 (0.8649–1.0673) |
| attached, без JFR | 4 | 0.9357 (0.9342–0.9415) | 0.9908 (0.9131–1.0401) |
| clean, с JFR | 2 | 0.8985 (0.8844–0.9126) | 0.9300 (0.8968–0.9631) |
| attached, с JFR | 2 | 0.9538 (0.9476–0.9599) | 1.0057 (1.0047–1.0067) |

Без JFR экономия clean составляет 401–468 тыс. байт на семь запросов,
attached — 440–495 тыс. байт. В новых профильных attached JVM baseline выделяет
8.97–9.11 МБ, keys — 8.61–8.63 МБ. Это отличается от 9.11/7.01 МБ первого
облачного этапа при тех же проверенных class hashes. Первоначальная цифра
23% остаётся результатом отдельной пробы и не является свойством патча.
Размер экономии и абсолютный уровень allocations зависят от исполнения;
конкретный механизм различий JIT этим этапом не локализован. Всю разницу
нельзя приписывать только устранённой конкатенации.

В обеих непрофильных группах временные отношения пересекают 1. Профильные
attached пары немного медленнее, clean быстрее. Малое число JVM, общий хост,
фиксированный корпус и чувствительность к профилированию не позволяют заявить
устойчивый inference speedup или статистическую значимость. Циклы внутри JVM
не используются как тысячи независимых повторений.

Решение: кандидат остаётся небольшим способом снизить allocations с сохранённым
контрактом. Оснований переносить обещание ускорения или прежние 23% экономии
в production нет. Следующий содержательный шаг — расширение семантической
квалификации перед отдельной интеграцией; очередное увеличение фиксированного
прогрева не снимает текущих ограничений. Develop, defaults и production не менялись.

## Постановка

Первый облачный этап дал одну профильную JVM на конфигурацию. Этот этап
проверяет повторяемость на том же ограниченном resident сценарии, отдельно
без JFR и с JFR, с обращением порядка запуска. Он не расширяет квалификацию
на полный inference corpus, SMART или production.

Перед запуском preflight проверил все source/class hashes из прежнего
build-validation, содержимое обоих диагностических JAR, compiler hash, runtime
version и все файлы прежнего manifest. Существующие артефакты относятся к той же
облачной среде и совпали побайтно; заново собирать неизменённый код не потребовалось.
Если sibling builds отсутствуют в новой среде, их следует восстановить по
предыдущему отчёту, а не заменять произвольными сборками.

Два smoke запуска current/keys, OFF, attached TOUCH journal, по два цикла.
Они побайтно совпали с прежними native rows и обоими журналами до основной серии.
План измерений записан в environment.json до первого длинного запуска:

- Без JFR: четыре пары current/keys для clean и четыре для attached TOUCH journal,
  всего 16 JVM. Чётные повторы: keys → current; нечётные: current → keys.
- С JFR: по две пары для каждого режима, всего восемь JVM, тот же принцип порядка.
- Каждый измерительный процесс выполняет 512 циклов семи запросов. Все восемь
  опций остаются OFF через JVM properties; session overrides не используются.

Пары запускаются соседними JVM, последовательно. Порядок режимов также обращён
между повторами. Измерительная единица повторения — отдельная JVM/пара JVM,
а не каждый из коррелированных циклов внутри процесса.

## Метод анализа

`analyze.py` сверяет все native строки с frozen current контролем первого
облачного этапа, точные variable rows, query CSV accounting и оба журнала.
Для каждой attached трассы выполняется authority replay, а затем побайтное
сравнение trace и callback event counts с frozen attached контролем того же
диагностического модуля. Изменение product кода здесь отсутствует; сравнение
с прежним context-snapshots журналом остаётся результатом предыдущего этапа.

Per-JVM медианы вычислены отдельно для 0–127, 128–511 и трёх окон по 128 циклов
внутри поздней части. Поздняя часть не объявляется steady state. Для каждой
соседней пары отношение keys/current рассчитано из двух per-JVM медиан, затем
показаны медиана и диапазон этих отношений. Все 28 672 query events восьми JFR JVM точно соответствуют query CSV; интервалы
не пересекаются. Sample attribution использует thread ID, timestamp внутри query
и стек с Mind.query. Профильные и непрофильные данные
не объединяются. Полные per-query и per-window результаты — metrics.json.
Allocations — точные ThreadMXBean bytes; выборочные JFR weights их не заменяют.

## Воспроизведение и evidence

Из корня K3, при неизменённых артефактах `../build/option-keys` и exact native
trees предыдущего этапа:

```sh
export JAVA_HOME=/workspace/tooling/jdk-21.0.2
python3 docs/tvalue-option-keys-repeat/preflight.py
python3 docs/tvalue-option-keys-repeat/run.py --smoke
python3 docs/tvalue-option-keys-repeat/run.py
python3 docs/tvalue-option-keys-repeat/export.py
python3 docs/tvalue-option-keys-repeat/analyze.py
python3 docs/tvalue-option-keys-repeat/profile.py
python3 docs/tvalue-option-keys-repeat/manifest.py
```

Запуски отказываются перезаписывать result файлы. Для нового повторения нужен
новый каталог evidence/checkout без опубликованных result файлов; прежние данные
следует сохранить. Java runtime OpenJDK 21.0.12.1 Debian amd64, jfr из Oracle JDK
21.0.2, ECJ 3.33.0. Полные версии, URL и hashes — в toolchain.json предыдущего этапа;
здесь environment.json и preflight.json проверяют связь с этим build.

export.py сохраняет только org.kanger.ResidentQuery, jdk.ExecutionSample,
jdk.ObjectAllocationSample в JSON.gz с выбранными полными стеками; raw JFR
уходят в непубликуемый `../build/option-keys-repeat/private-recordings`, их hashes
остаются в result JSON. Прежние CSV, manifests и скрипты не редактируются.
Linux времена не смешиваются с прежними macOS данными. Хост общий, CPU pinning нет.
