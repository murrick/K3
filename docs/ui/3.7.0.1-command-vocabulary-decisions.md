# KANGER 3.7.0.1 — Accepted command vocabulary decisions

Status: ACCEPTED DESIGN BASELINE / NO RUNTIME AUTHORITY YET

Reference runtime: `release/3.5.2` at `9c8b7dd2c9ef347cea6af6a6faef9cfa48030306`

## Purpose

Record vocabulary decisions accepted while deriving the unified Console/Browser/future-UI command dialogue from the semantic structure of KANGER and the original `Практикум`, rather than from accidental historical dispatcher spellings.

## Accepted vocabulary

### Base

The command group for the statement base remains:

```text
base
```

Although the underlying semantic projection is effectively the Statements/base-of-statements view, `statements` is not adopted as the canonical operator word. `base` is concise, historical, semantically stable in KANGER, and has lower abbreviation ambiguity.

Bare form is a read-only view/status command:

```text
base
```

Selectors remain to be normalized separately.

### Hypothesis operator group: WHEN

The operator-facing command group for the hypothesis set is:

```text
when
```

Rationale:

- `hypothesis` is an internal semantic/domain name but is unnecessarily long for interactive command dialogue;
- historical `list` is too generic and does not identify the semantic object;
- `if` is too high-entropy and too broadly overloaded in programming/logical language;
- `when` expresses the operator meaning of the projection: conditions/assumptions under which the current undefined query can be brought to determination;
- the internal object remains Hypothesis/HypothesisStore. The command-language word does not rename the Core entity.

Bare form is a read-only projection:

```text
when
```

It shows the hypotheses/conditions produced for the current query context.

### Accepting a hypothesis

Historical Console vocabulary:

```text
append [n]
```

is retired from the canonical language. It reflects an old implementation/storage action rather than the semantic user action.

Canonical form:

```text
when accept <n>
```

Meaning: accept the selected hypothesis as persistent/authoritative knowledge according to the existing qualified KANGER semantics.

`accept` describes the semantic operator action; it does not expose the historical container operation.

Canonical IDs should therefore evolve toward concepts equivalent to:

```text
WHEN_STATUS
WHEN_ACCEPT
```

while implementation mapping may continue to use current hypothesis APIs internally during migration.

### Transaction creation

Canonical transaction vocabulary is confirmed as:

```text
transaction
transaction start
transaction commit
transaction rollback
```

`start` is normative. `transaction create` is not the canonical long form.

This matches both the semantic meaning — starting a new transactional Mind level — and the historical KANGER/Practicum vocabulary.

Any compatibility spelling `create` may exist only as an explicit usability/migration alias if later judged necessary. It must never define a separate execution path.

## Vocabulary principle

Command-group names are operator-facing semantic vocabulary. They are not required to mirror implementation class/store names.

Examples:

```text
base  -> statement/predicate projection internally
when  -> hypothesis projection internally
```

The naming criterion is:

```text
what the semantic object/action means to the KANGER operator
```

not:

```text
what the implementation container/class happens to be called
```

## Current accepted fragment

```text
base

when
when accept <n>

transaction
transaction start
transaction commit
transaction rollback
```

All command words remain case-insensitive and subject to the accepted minimum-unique-prefix abbreviation rule. Canonical documentation and canonical echo use the full forms above.

## Historical compatibility

The following historical spellings are no longer candidates for canonical documentation:

```text
list          # old hypothesis-list command
append [n]    # old accept-hypothesis implementation vocabulary
```

Whether either is temporarily accepted as a compatibility alias during implementation is a migration decision, not a semantic-design decision.

## Boundary

This document changes no runtime behavior. It refines the accepted vocabulary for the future unified command parser/registry and UI command dialogue.
