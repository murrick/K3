# KANGER 3.7.0.1 — Command processor ownership and module boundary

Status: **ACCEPTED DESIGN DECISION / DOCUMENTATION ONLY**

Reference runtime: accepted `release/3.5.2`.

No runtime behavior is changed by this document.

## 1. Decision

The canonical KANGER command language is no longer owned by the Java Console.

A separate sibling module is the single owner of command-language parsing and canonical command metadata:

```text
kanger-command/
    src/org/kanger/command/...
```

Working module name: **`kanger-command`**.

This module is the common command processor for Console, Server-backed Browser/UI, and future clients that need the same command model.

## 2. Why ownership changes

When Console was the only interactive client, keeping command parsing inside Console was natural.

With Browser/UI and possible future clients, retaining command parsing in Console would force either:

- duplicated command grammars/parsers;
- Server depending on Console;
- or transport-specific command semantics.

All three are rejected.

The command language is now a shared interface contract and therefore requires one neutral owner.

## 3. Owned responsibilities

`kanger-command` owns only command-language concerns:

```text
CommandRegistry
CommandParser
CommandIntent
ParsedCommand / CommandArguments
CommandParseException / parse result
canonical keyword metadata
minimum-unique-prefix resolution
lexical/quoting rules
canonical form / canonical echo metadata
```

Exact class names may vary during implementation, but the responsibility boundary is normative.

The module transforms command text into a canonical intent plus arguments.

Example:

```text
sto u close
    -> STORAGE_USE { name = "close" }
```

After producing that result, the command processor is finished.

## 4. Explicit non-responsibilities

`kanger-command` must not own or depend on:

- `IMind` execution semantics;
- KANGER Core inference/runtime implementation;
- Console UI/readline behavior;
- HTTP/WebSocket/session transport;
- JSON protocol encoding;
- Browser DOM/UI behavior;
- concrete storage implementation;
- source repository filesystem operations;
- transaction execution;
- confirmation dialogs/prompts;
- runtime logging/presentation.

It must not become a generic application/service layer.

## 5. Consumer model

```text
                    kanger-command
                 parser + registry + intents
                      /             \
                     /               \
          kanger-console          kanger-server
          presentation +          session/transport +
          local dispatch          server dispatch
                 \                   /
                  \                 /
                     KANGER runtime
```

Browser/UI sends or composes canonical command text through the Server-owned interaction path; the Server uses the same `kanger-command` processor rather than maintaining a second grammar.

A future Java/native/local client may consume `kanger-command` directly.

## 6. Core dependency invariant

The existing architecture invariant remains:

```text
kanger Core
    MUST NOT depend on kanger-command
    MUST NOT depend on kanger-console
    MUST NOT depend on kanger-server
```

The dependency direction is outward:

```text
kanger-console  -> kanger-command
kanger-server   -> kanger-command
future clients  -> kanger-command
```

`kanger-command` itself should depend only on the JDK unless a later concrete requirement proves otherwise.

In particular, command parsing must not require `IMind` or any runtime context merely to identify a command.

## 7. Physical build model

The repository currently uses sibling production source roots rather than a strict Maven multi-module reactor.

Therefore the accepted implementation target is a sibling source module:

```text
kanger-command/src
```

and later build integration should add that source root to:

- the aggregate/root production build;
- the standalone Server build.

This preserves architectural modularity without introducing Maven restructuring merely for packaging symmetry.

A separate published Maven artifact is not required by this decision.

## 8. Dispatcher boundary

The shared command processor stops at canonical intent resolution.

Execution adapters remain client/runtime specific where necessary:

```text
raw command text
    -> kanger-command parser
    -> canonical intent + arguments
    -> Console dispatcher OR Server dispatcher
    -> existing KANGER/runtime operation
```

There must be no second keyword parser inside either dispatcher.

The dispatchers may differ in presentation behavior, session ownership and transport, but the same textual command must resolve to the same canonical intent and arguments.

## 9. Console-local extensions

Console-local behavior already accepted remains possible without contaminating the Browser/UI registry:

```text
xplain ...

bare get / put / delete
    -> read-only source listing convenience
```

Such behavior must be expressed as an explicit Console extension/adaptor over the shared command processor, not by forking the canonical grammar implementation.

## 10. Consequence for implementation sequence

The design sequence is now:

```text
canonical registry          CLOSED
lexical/quoting contract    CLOSED
parser conformance matrix   CLOSED
processor ownership         CLOSED
        ↓
transport/intent mapping
        ↓
dedicated implementation artifact
        ↓
Console flash-back/convergence
        ↓
Browser/future-UI adoption through the same processor
```

No Java runtime implementation is introduced by this 3.7.0.1 decision.
