# KANGER 3.7.0.1 — `when` command decisions

Status: **ACCEPTED DESIGN DECISION / DOCUMENTATION ONLY**

Reference runtime: accepted `release/3.5.2`.

No runtime behavior is changed by this document.

## 1. Semantic object

`when` presents the current hypothesis rowset produced by the latest informational inference context.

Hypotheses do not expose a stable semantic/runtime ID comparable to Rule or Solution IDs. They are therefore addressed by their current row position in the displayed hypothesis list.

## 2. Accepted canonical syntax

```text
when
when accept <index>
```

`when` shows the current optimized hypothesis list.

`when accept <index>` accepts one hypothesis from that current list.

## 3. Addressing rule

Hypothesis addressing is **zero-based**:

```text
first row   -> 0
second row  -> 1
third row   -> 2
...
```

The canonical row projection should expose that index explicitly so every client presents and sends the same address.

Example:

```text
when

0  ...first hypothesis...
1  ...second hypothesis...
2  ...third hypothesis...

when accept 2
```

accepts the third row of the current hypothesis rowset.

This is deliberately different from `solution <id>`:

```text
solution <id>
    addresses a concrete Solution/IRule runtime identity

when accept <index>
    addresses a row in the current hypothesis result list
```

No artificial persistent ID is introduced for hypotheses.

## 4. Historical Console compatibility

The historical Console displayed hypothesis choices one-based and decremented the entered number before selection.

That presentation convention is not carried into the canonical command dialogue. Console convergence must display and accept the canonical zero-based row index.

Any temporary migration compatibility must normalize before execution and must not change the canonical grammar.

## 5. Runtime binding

Core already owns hypothesis acceptance through the existing hypothesis-selection / `Mind.queryAccept(...)` path.

The future Server binding must:

1. operate on the current hypothesis rowset;
2. validate `0 <= index < size`;
3. select exactly that row;
4. delegate acceptance to existing Core semantics;
5. avoid inventing transport-side inference behavior.

## 6. Design principle

- use object IDs only where the object actually owns an identity;
- use row indexes where the object exists only as a current result-list item;
- expose the same address the command accepts;
- do not manufacture identity merely for UI symmetry.
