# KANGER 3.7.0.1 — Command lexical and quoting decisions

Status: **ACCEPTED DESIGN DECISION / DOCUMENTATION ONLY**

Reference runtime: accepted `release/3.5.2`.

No runtime behavior is changed by this document.

## 1. Scope

This document closes the lexical/quoting rules for the 3.7.0.1 command dialogue.

The goal is deliberately small: enough syntax to express the accepted command registry without importing shell grammar or creating a second language beside KANGER.

## 2. Tokenization

Ordinary command words and arguments are separated by whitespace.

```text
storage use demo
rule show 123
values order x desc
```

Repeated separating whitespace has no semantic meaning.

## 3. Keywords versus arguments

Keyword positions are grammar-defined.

Keywords are:

- case-insensitive;
- resolved by the accepted minimum-unique-prefix rule.

Arguments are data and are not keyword-resolved merely because their spelling matches a command word.

For example, after `storage use` the grammar expects a storage name, so:

```text
storage use close
```

means a storage whose name is `close`.

Likewise:

```text
get delete
get 123
```

use `delete` and `123` as source names.

The parser must not infer command identity from the lexical appearance of an argument.

## 4. Argument case/content

Command keywords are case-insensitive, but argument content is preserved as entered and passed to the relevant namespace/semantic validator.

The lexer does not silently lowercase source names, storage names, predicate names, file names, free text or other arguments.

Any domain-specific canonicalization belongs below the lexer.

## 5. Quoted argument

A single argument that contains whitespace may be enclosed in double quotes:

```text
get "my source.k"
storage use "test base"
```

Inside a double-quoted argument, only these escapes are special:

```text
\"   literal double quote
\\   literal backslash
```

No general shell-style escape language is introduced.

Outside quoted arguments, backslash has no command-language escape role.

Single quotes are not command-language quoting syntax.

Therefore the command dialogue does not introduce forms such as:

```text
'my source.k'
my\ source.k
--name
/name
```

## 6. Free-text tail for rule comments

The accepted rule-comment forms remain:

```text
rule comment <id>
rule comment <id> <text...>
```

After `<id>`, if no text remains, the command is the read form.

If text remains, the remainder of the command line is the comment body. Internal spaces do not require quoting:

```text
rule comment 123 This is an arbitrary comment
```

An explicitly empty comment body is written as:

```text
rule comment 123 ""
```

and means set the comment to the empty string / remove the existing comment.

Apart from this explicit empty-string notation, the free-text tail is not treated as a sequence of command keywords.

## 7. Names are namespace objects, not paths

The command lexer treats source and storage names as argument values, not as filesystem path syntax.

Characters such as `/`, `\\`, `.`, `..`, drive-letter-like text or reserved-looking words receive no special command meaning from the lexer.

Whether a particular spelling is legal is decided by the corresponding source/storage namespace validation and containment rules.

The command parser must not implement filesystem navigation semantics.

## 8. UI versus Console source-name convenience

The canonical source operations are:

```text
get <source>
put <source>
delete <source>
```

For Browser/UI command execution, the source argument is required. The UI already has a visible/selectable source namespace and can compose the explicit command with the chosen name.

The deferred Java Console convergence may additionally preserve a terminal-only convenience:

```text
get
put
delete
```

with no source argument performs a **read-only listing of available source names** and no mutation.

This is Console presentation convenience, not an additional canonical source intent and not part of Browser/UI grammar. It exists so a minimal terminal remains self-sufficient even without a richer source browser.

The user must still issue an explicit named command to perform the source operation after seeing the list.

## 9. Deliberate omissions

The 3.7.0.1 command language does not add:

- shell-style flags;
- single-quoted strings;
- shell backslash escaping outside quoted arguments;
- environment-variable expansion;
- pathname expansion/globbing;
- command substitution;
- parser heuristics based on whether an argument looks numeric or textual.

## 10. Closed lexical contract

At this baseline, command lexing is intentionally reducible to:

```text
keyword/argument tokens separated by whitespace
+ double-quoted argument when one argument contains whitespace
+ minimum-unique-prefix resolution only in keyword positions
+ free-text remainder for rule comment bodies
```

No additional lexical machinery is required by the accepted command registry.
