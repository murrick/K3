# KANGER 3.7.0.1 — accepted `rule` command family

Status: ACCEPTED DESIGN DECISION / DOCUMENTATION ONLY

Reference runtime: `release/3.5.2` at `9c8b7dd2c9ef347cea6af6a6faef9cfa48030306`

## Canonical family

The canonical operator-facing `rule` family is:

```text
rule
rule <id>
rule all
rule produced
rule level <n>
rule tree <id>
rule comment <id>
rule comment <id> <text...>
```

## Semantics

- bare `rule` is a read-only projection of the current rule context;
- `rule <id>` displays one rule by runtime id;
- `rule all` selects all rules;
- `rule produced` selects produced/generated rules;
- `rule level <n>` selects rules at a transaction/context level;
- `rule tree <id>` displays the compiled/structural tree associated with one rule;
- `rule comment <id>` reads the current comment;
- `rule comment <id> <text...>` updates the comment.

## Grammar decision

The second position belongs to one RULE-family grammar:

```text
rule [<id> | all | produced | level <n> | tree <id> | comment <id> [<text...>]]
```

`rule <id>` is intentionally the direct object-address form, matching the accepted `function <id>` and `solution <id>` forms.

The historical/intermediate design form:

```text
rule show <id>
```

is rejected as redundant. `show` carries no semantic information once the family and object id are already explicit.

## Why direct `<id>` is not the rejected lexical heuristic

This does not recreate the old `put <numeric-rule-id>` ambiguity.

In the historical `put` overload, argument spelling selected between two unrelated operations: source persistence and rule-comment editing. That was rejected because a numeric-looking token could also be a valid source name.

Inside the RULE family, however, `<id>` is an explicit grammar production of the same semantic family. Reserved selector/action words (`all`, `produced`, `level`, `tree`, `comment`) are recognized in keyword position; the remaining valid object-address production is the rule id.

The parser therefore follows the grammar rather than guessing unrelated command identity from argument shape.

## Implementation principle

Prefer the shortest command phrase that remains semantically unambiguous.

The resulting family is compatible with a small transparent dispatcher:

```text
rule
  -> empty                 : RULE_STATUS
  -> id                    : RULE_SHOW
  -> all                   : RULE_ALL
  -> produced              : RULE_PRODUCED
  -> level <n>             : RULE_LEVEL
  -> tree <id>             : RULE_TREE
  -> comment <id> [...]    : RULE_COMMENT_GET / RULE_COMMENT_SET
```

No heavy parser architecture is required.
