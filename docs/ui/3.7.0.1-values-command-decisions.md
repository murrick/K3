# KANGER 3.7.0.1 — `values` command decisions

Status: **ACCEPTED DESIGN DECISION / DOCUMENTATION ONLY**

Reference runtime: accepted `release/3.5.2`.

No runtime behavior is changed by this document.

## 1. Semantic object

`Values` is the resulting rowset of the last informational query: the exported values of the query's existential/t-variables.

It is a result projection, distinct from `Solutions`:

- `Solutions` represents proof-producing statements / solutions;
- `Values` represents the resulting rows of exported variable bindings;
- several proofs may correspond to one Values row.

Therefore a Values row number is not a semantic object identity and is not exposed as a command address.

## 2. Accepted canonical syntax

```text
values
values order <variable> [asc|desc]
```

Semantics:

```text
values
```

shows the current Values rowset in its natural order.

```text
values order x
values order x asc
values order x desc
```

show the same current rowset ordered by exported variable `x`; omitted direction means ascending.

## 3. Deliberately rejected syntax

The canonical language does not add:

```text
value <n>
values <n>
values where ...
values filter ...
values select ...
values order natural
values order reset
```

Rationale:

- row numbers are presentation positions, not semantic IDs;
- filtering/selecting belongs to the KANGER informational query itself, including existential quantification and query conditions;
- a no-argument `values` invocation already means the natural-order projection, so `natural` / `reset` are redundant.

## 4. Ordering is a projection, not Mind state

Accepted architectural interpretation:

```text
informational query
        ↓
raw Values rowset
        ↓
optional per-invocation order projection
        ↓
output
```

`order` and `ascending` are not logical properties of `Mind`, not query semantics, and not persistent workspace options.

Each command invocation is self-contained:

```text
values
values order x
values order y desc
values
```

The final `values` again shows the rowset in natural order. A prior ordered display must not change later display semantics.

## 5. Required Core projection cleanup

When the accepted command model reaches runtime implementation, the historical ordering shortcut must be projected out of Core/Mind state.

Current implementation evidence includes:

- `ValuesStore` owns mutable `order` and `ascending` fields;
- its collection representation can change between insertion-preserving and sorted sets according to that state;
- `Mind(IMind root)` copies `root.getOrder()` and `root.isAscending()` into the child `ValuesStore`, making presentation state part of transaction inheritance;
- Console exposes the same concern through general `options order ...` handling.

Required direction:

1. Preserve the query-produced Values rowset independently of display ordering.
2. Do not inherit display ordering between parent and child Mind transactions.
3. Remove Values ordering from general Mind/workspace option semantics and from the public logical-context contract where it exists solely for presentation.
4. Implement `values order <variable> [asc|desc]` as a temporary ordered view/projection of the current rowset.
5. Plain `values` must not depend on any previously executed ordering command.

Exact class/module placement of the projection helper is intentionally left to the later implementation stage; the semantic boundary above is normative.

## 6. Design principle

Apply Occam's razor to the command dialogue:

- do not reproduce query semantics in result-view commands;
- do not turn presentation positions into object identities;
- do not promote presentation preferences into logical-context state;
- add syntax only where it expresses a distinct operator intention.
