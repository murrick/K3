# KANGER 3.7.0.1 — `values` command decisions

Status: **ACCEPTED DESIGN DECISION / DOCUMENTATION ONLY**

Reference runtime: accepted `release/3.5.2`.

No runtime behavior is changed by this document.

## 1. Semantic object

`Values` is the resulting rowset of the last informational query: the exported values of the query's existential/t-variables.

It is a result projection, distinct from `Solutions`:

- `Solutions` represents proof-producing statements / solutions;
- `Values` represents the resulting rows of exported variable bindings;
- several proofs may correspond to one Values row.

Therefore a Values row number is not a semantic object identity and is not exposed as a command address.

## 2. Accepted canonical syntax

```text
values
values order <field> [asc|desc] [, <field> [asc|desc]]...
```

Examples:

```text
values
values order x
values order x desc
values order x desc, y asc
values order surname, name, age desc
```

Within one `values order` invocation, each sort key is a pair:

```text
(field, direction)
```

Direction is optional for each field and defaults to `asc`.

A comma separates sort-key pairs. This avoids lexical ambiguity between a following field name and the `asc` / `desc` direction keyword.

The comma is structural punctuation of the `values order` production only. It does not become general shell-style command punctuation.

## 3. Default ordering and invocation-local override

Values presentation has two layers:

```text
configured DefaultSortSpec
        ↓
plain `values`

explicit SortSpec from `values order ...`
        ↓
that invocation only
```

`values` shows the current Values rowset using the configured default ordering. If no default sort is configured, natural rowset order is used.

`values order ...` shows the same current rowset using the explicitly supplied ordered list of sort keys for that invocation only.

For example:

```text
values order x desc, y asc, name
```

means:

```text
1. x    DESC
2. y    ASC
3. name ASC
```

Executing an explicit `values order ...` command must not alter the configured default ordering.

## 4. System/default sorting remains supported

Historical KANGER already carries a default Values ordering preference. That capability is not rejected by the canonical command model.

The accepted distinction is:

```text
default sort configuration
    persistent/operator presentation preference

explicit `values order ...`
    invocation-local result projection
```

Both may use the same conceptual `SortSpec` model, preferably an ordered list of:

```text
SortKey(field, direction)
```

The exact command or configuration surface used to edit the default sort policy is not added to the 3.7.0.1 canonical command registry. Historical `options` remains retired as a general command namespace; later settings/UI work may expose the default policy through an appropriate settings surface.

## 5. Required Values projection evolution

Current implementation evidence includes:

- `ValuesStore` owns one mutable `order` field and one `ascending` flag;
- its collection representation can change between insertion-preserving and sorted sets according to that state;
- `Mind(IMind root)` copies the current order/ascending state into a child;
- historical Console `options order ...` edits that state.

The accepted implementation direction is more precise than simply deleting ordering state:

1. Preserve the query-produced Values rows independently of physical/presentation sort order.
2. Represent ordering as an explicit ordered `SortSpec`, capable of more than one field.
3. Allow a configured default `SortSpec` to be inherited where the settings model requires it.
4. Apply `values order ...` through a temporary invocation-local `SortSpec` without mutating the default.
5. Do not rebuild or mutate the authoritative Values rowset merely to display it in a different order.
6. Plain `values` uses the configured default; if no default exists, it uses natural order.

The old single-field `order` / `ascending` mechanism may inform migration of the default policy, but it is insufficient as the final projection model because it conflates row storage with presentation and cannot express ordered multi-key sorting.

## 6. Deliberately rejected syntax

The canonical language does not add:

```text
value <n>
values <n>
values where ...
values filter ...
values select ...
values order natural
values order reset
```

Rationale:

- row numbers are presentation positions, not semantic IDs;
- filtering/selecting belongs to the KANGER informational query itself;
- default ordering belongs to settings/presentation policy, not to an ad-hoc reset verb in the result command.

## 7. Design principle

Apply Occam's razor to the command dialogue:

- do not reproduce query semantics in result-view commands;
- do not turn presentation positions into object identities;
- distinguish durable/default presentation policy from one-shot projection;
- use one explicit ordered sort-key model for both;
- add syntax only where it expresses a distinct operator intention.
