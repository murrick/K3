# KANGER 3.7.0.1 — Language-derived command taxonomy

Status: DESIGN BASELINE / NO RUNTIME AUTHORITY YET  
Accepted runtime base: `release/3.5.2` at `9c8b7dd2c9ef347cea6af6a6faef9cfa48030306`

## 1. Decision

The command taxonomy for the 3.7.0 UI/Console line is not to be invented independently from the KANGER language model.

Its normative derivation order is:

```text
KANGER Core language semantics
        ->
authorial structural model expressed in the language document / Practicum
        ->
canonical command dialogue
        ->
Console / Browser / future UI presentation
```

The current Java Console `showCommonHelp()` is therefore treated as an executable historical projection and completeness checklist, not as the sole source of semantic taxonomy.

## 2. Core-language boundary

Symbols and forms belonging to the KANGER language/compiler remain outside the UI command namespace.

In particular, `?`, `=`, and other logical-language syntax are not repurposed as UI command markers or option punctuation.

The command parser must preserve the existing routing boundary between KANGER language expressions and command dialogue.

## 3. Structural principle

Canonical command syntax follows semantic hierarchy:

```text
<group> [<verb>] [<arguments...>]

WHERE -> WHAT TO DO -> WITH WHAT
```

Examples:

```text
transaction start
transaction commit
storage use demo
source put foo.k
rule comment 123
```

A bare group is an official read-only context/status request where such a context exists:

```text
transaction
storage
source
```

## 4. Historical Console help as projection

The accepted 3.5.2 Console help currently exposes these semantic areas:

```text
INFORMATION
    rules
    base
    functions

QUERY RESULTS / EXPLANATION
    values
    solutions
    list (hypotheses)
    append
    xplain
    transaction

SOURCE FILES
    get
    put

DATABASE / STORAGE
    use
    close
    drop
    index/reindex

SYSTEM / WORKSPACE
    options
    erase
    quit
```

These areas are evidence for required capability coverage, but their historical top-level spellings and overloads are not automatically canonical.

Examples:

- `put <numeric-rule-id>` comment editing is rejected as a canonical overload; `put 123` must remain a source operation if `123` is a valid source name;
- rule comment editing belongs under `rule comment <id>`;
- `index`/implementation `pack` is normalized toward the storage `reindex` operation;
- transaction creation uses the authorial/historical word `start`, not `create`, as canonical syntax.

## 5. Practicum as semantic organization

The language document's Practicum organizes interaction by the actual reasoning/workspace model: constructing and inspecting the program, queries and results, hypotheses, grouped data operations, transaction levels, and persistent source/storage work.

The 3.7.0 registry should preserve those conceptual boundaries instead of mirroring accidental `switch` branches or transport endpoint names.

This yields the working distinction:

```text
CORE LANGUAGE
    logical program / query syntax

SEMANTIC VIEWS
    rules
    base/statements
    functions
    values
    solutions
    hypotheses
    explanation

WORKSPACE LIFECYCLE
    transaction
    source
    storage

SESSION / SYSTEM
    help
    options/preferences
    diagnostics/admin
    erase
    quit
```

The exact final nouns for semantic-view groups remain subject to comparison with the authorial Practicum terminology; no Browser transport name should override the language document merely because it is newer implementation vocabulary.

## 6. Aliases

Aliases exist only for usability.

They must:

1. resolve one-to-one to a canonical command before argument interpretation;
2. never own separate execution semantics;
3. never depend on whether an argument looks numeric, textual, a filename, or another lexical form;
4. remain unambiguous under minimum-unique-prefix parsing.

Examples:

```text
put foo.k
    -> source put foo.k

put 123
    -> source put 123

commit
    -> transaction commit
```

There is no rule-comment interpretation of `put 123`.

## 7. Command dialogue, not shell syntax

KANGER command interaction is a command dialogue, not a Unix-style shell.

Therefore the canonical grammar does not introduce `--flags`, option dashes, or punctuation that does not express KANGER semantics.

Selectors and modifiers remain ordinary words in semantic order.

## 8. Design consequence for UI

The UI does not invent a second interaction model.

Live textual links and semantic objects compose the same canonical command text or KANGER-language fragments into the command editor. They do not execute automatically.

```text
screen object/link
    -> command composition at caret
    -> optional human editing
    -> explicit execution
    -> canonical parser
```

## 9. Next analysis

Before freezing the complete registry, perform an explicit pass over the Practicum and current Console help to produce a table:

```text
Practicum concept/domain
    -> historical Console command/help
    -> current Browser/Server capability
    -> canonical group/verb
    -> compatibility alias, if justified
```

The purpose of that pass is recovery and normalization of the authorial model, not redesign for its own sake.
