## 1. Purpose

3.7.0.4 removed command-language authority from the historical Browser and converged operator input on exact raw `context=dialogue` transport to the shared `kanger-command` processor on Server.

3.7.0.5 uses that stable boundary to introduce the first actual KANGER presentation model:

```text
LEFT       semantic KANGER structure
CENTER     Dialogue / Source editor
RIGHT      collapsible technical/admin context
BOTTOM     Results / Solutions / Hypothesis / Log
```

This is deliberately not a generic IDE/dashboard shell. Presentation follows the semantic structure of KANGER and composes the same command language that can be typed manually.

## 2. Presentation authority

The new capability consists of:

```text
html/presentation.js
html/presentation.css
```

It is loaded after the previously qualified Browser authorities:

```text
trusted rendering
    -> operation / coherent snapshot
    -> workspace projection
    -> error boundary
    -> raw dialogue
    -> presentation
```

The presentation layer owns only:

- screen geometry;
- labels and presentation state;
- semantic click-to-compose behavior;
- read-only technical status projection.

It explicitly does not own:

- command parsing;
- command abbreviation or normalization;
- command execution;
- raw dialogue transport;
- bearer/session authority;
- operation serialization;
- workspace canonicalization;
- trusted-rendering policy;
- containment/network authority.

`presentation.js` therefore contains no `window.command`, `window.query`, `window.post`, `window.token`, `document.cookie`, `innerHTML`, `eval` or `new Function` execution path.

## 3. Historical DOM as migration substrate

3.7.0.5 does not rewrite the 2000+ line historical `console.html`.

The existing DOM remains a fallback/evidence substrate and the new capability projects KANGER geometry over stable element IDs. This minimizes migration risk and preserves the already-qualified rendering, snapshot, workspace and containment layers.

The historical left/right and bottom splitters remain active. `presentation.js` wraps the historical layout function, lets it perform its existing state/cookie calculations, and then reapplies the KANGER grid/flex presentation.

Historical raw command parsing in `console.html` was already made dormant by 3.7.0.4 and remains dormant here. Its physical removal is separate source-hygiene work.

## 4. KANGER geometry

The presentation projects the authenticated Browser into four semantic regions.

### LEFT — semantic structure

The existing Base/Statements and Functions projections occupy the left semantic column.

The left column remains resizable through the historical horizontal splitter.

### CENTER — Dialogue / Source

The center region is the principal working surface.

Normal mode is labelled `Dialogue`. The existing source editor is retained as a mode of the same center region and labelled `Source` when opened.

The command line remains the single execution entry. Presentation never invokes the shared dispatcher itself.

### RIGHT — TECH

A narrow right-side `TECH` rail is collapsed by default.

When expanded it exposes read-only technical context derived from already-qualified authorities:

```text
Dialogue
  parser: kanger-command / server
  session: parent-owned
  generation
  active operation
  snapshot

Workspace
  source
  storage
  physical generation / WAL summary

Authority
  trusted rendering
  parent containment
```

No bearer token is read or displayed by the presentation layer.

### BOTTOM — query/runtime evidence

The existing Results, Solutions, Hypothesis and Log projections occupy the bottom region.

The historical vertical splitter continues to control its height.

## 5. Mouse semantics: compose, never execute

The central invariant of 3.7.0.5 is:

> The mouse helps write the command; the decision to execute it remains with the operator.

All semantic click actions insert text into `#query-input` at the current caret. If text is selected, the click replaces exactly that selection. The command line is focused afterward.

No semantic click submits the line.

Explicit Enter therefore remains the execution boundary for both manually typed and mouse-composed commands.

## 6. Direct semantic text composition

Current semantic projections are:

```text
predicate row      -> <predicate-name>(
statement row      -> <statement-origin>
function row       -> <function-name>(
solution row       -> <solution-origin>
hypothesis row     -> historical Core assertion form
result value       -> exact displayed value
```

For a hypothesis whose origin begins with `?`, the historical assertion transformation remains:

```text
?x  ->  !~x
```

The predicate expansion sign remains an ordinary expansion control and is deliberately not captured as a command-composition click.

## 7. Explicit command projections

Small textual action projections provide canonical command forms without executing them:

```text
predicate  view    -> base predicate <id>
statement  tree    -> base tree <id>
function   source  -> function source <id>
solution   tree    -> solution tree <id>
hypothesis accept  -> when accept <index>
```

Workspace/status projections also compose canonical text:

```text
current source      -> get <source>
current storage     -> storage use <name>
no active storage   -> storage
transaction status  -> transaction
```

Arguments containing whitespace, quotes or backslashes are quoted according to the accepted command lexical contract.

These projections are presentation metadata only. They do not bypass the shared `kanger-command` parser and they do not call Server directly.

## 8. Existing automatic clicks are contained

Historical semantic renderers attached automatic actions to several rows, for example inference-tree display or source-editor opening.

3.7.0.5 installs one capture-phase presentation boundary before those handlers. Semantic clicks that now mean command composition are stopped before the historical automatic handler can execute.

This converts the existing screen from action-by-click to command-composition-by-click without rewriting the trusted renderers themselves.

Expansion controls that remain purely presentational are allowed through.

## 9. Technical state comes from existing authorities

The TECH panel does not invent a new state model.

It reads only public snapshots already exposed by:

```text
KANGER_OPERATION_PROTOCOL
KANGER_WORKSPACE_STATE
```

and fixed capability presence for the other qualified boundaries.

The panel therefore observes the same generation, operation, snapshot, source and storage state used by the existing Browser protocol rather than maintaining shadow state.

## 14. Result

3.7.0.5 establishes the first working KANGER Browser interaction model in which:

```text
semantic screen object
      |
      v
compose canonical/core text at caret
      |
      v
operator reviews/edits line
      |
   explicit Enter
      |
      v
raw Browser dialogue
      |
      v
shared kanger-command / Core path
```

The UI is therefore no longer a second command surface. It is a semantic editor for the same dialogue.
