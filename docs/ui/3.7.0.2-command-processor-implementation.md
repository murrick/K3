## 1. Result

The accepted 3.7.0.1 command-language contract now has one executable shared implementation.

```text
raw operator input
        |
        v
kanger-command
  parser / registry / formatter / help metadata
        |
        +--> CORE_LANGUAGE
        |
        +--> CommandIntent + normalized arguments
```

The module contains no KANGER runtime execution code.

Server execution is attached through a separate adapter boundary.

## 4. Values SortSpec

Accepted runtime representation:

```text
SortKey(field, ASC|DESC)
```

Accepted syntax:

```text
values order <field> [asc|desc] [, <field> [asc|desc]]...
```

A comma is structural only inside this grammar production.

Explicit ordering is an invocation-local projection. It sorts a copy of the current Values rows and does not modify the configured default ordering stored by the existing runtime.

If no explicit command ordering is supplied, ordinary `values` continues to use configured default ordering, falling back to natural order when no default is configured.

## 6. Server raw-dialogue ingress

New authenticated remote-client input form:

```json
{
  "context": "dialogue",
  "parameters": {
    "token": "...",
    "line": "raw operator input"
  }
}
```

`CanonicalCommandIngressReactor` parses the raw line with `kanger-command`.

For Core language:

```text
dialogue line
  -> CORE_LANGUAGE
  -> existing query/request path
```

For canonical commands already represented faithfully by Server 0.18:

```text
dialogue line
  -> CommandIntent
  -> strict projection onto existing qualified legacy operation
```

Canonical-only intents are never approximated through broader legacy operations. They are passed to `CanonicalCommandRuntimeReactor`.

## 7. Qualified Server chain

The new boundaries are inserted without bypassing the accepted Server 0.18 protections:

```text
SessionSerializingReactor
  -> MailBoundaryReactor
    -> CanonicalCommandIngressReactor
      -> WorkspaceStateReactor
        -> CanonicalCommandRuntimeReactor
          -> ExplicitStorageLifecycleReactor
            -> DestructiveStopLossReactor
              -> MindLifecycleReactor
                -> QueryProcessor
```

Consequences:

- raw parsing runs under the existing per-session serialization boundary;
- translated source/storage operations still pass the existing filesystem input policy;
- WorkspaceState sees the translated command/query context and remains the authoritative response projection;
- lifecycle, stop-loss and transaction ownership remain below the adapter;
- old legacy JSON requests remain accepted unchanged.

## 8. Input-policy preservation

`SessionSerializingReactor` validates the original request parameters before canonical translation. Therefore raw `dialogue` input by itself does not expose translated `get/put/delete/use/drop/reindex` parameters to that first check.

`CanonicalCommandIngressReactor` explicitly reuses:

```text
ApiInputPolicy.violation(translatedParameters)
```

after canonical-to-legacy projection and before delegation.

The policy implementation is not copied or weakened.

The raw dialogue envelope additionally rejects extra operation parameters. Only `token` and `line` are accepted, preventing a packet from combining canonical text with injected legacy operation keys.

## 9. Canonical-only runtime bindings

`CanonicalCommandRuntimeReactor` implements the accepted intents which cannot be represented faithfully through historical `QueryProcessor` endpoints:

```text
RULE_COMMENT_GET
RULE_COMMENT_SET
BASE_STATUS
BASE_TREE
VALUES_ORDER
SOLUTION_SHOW
SOLUTION_TREE
WHEN_ACCEPT
HELP
```

### Rule comments

Uses the active rule/comment factory through existing `IRule.getComment()` / `setComment()` semantics.

### Base

`BASE_STATUS` projects current non-system, non-empty base predicates with their stored statements.

`BASE_TREE` searches only the current Base rule set and exposes its cause/provenance tree. It deliberately does not inherit the historical `getStatements(id)` fallback into Solutions.

### Solutions

`solution <id>` and `solution tree <id>` iterate the current Solutions set and match the concrete `IRule.getId()`.

Presentation row ordinals are never accepted as Solution identity.

### Hypotheses

`when accept <index>` optimizes the current hypothesis rowset, then addresses it by zero-based row index and delegates acceptance to existing `Mind.queryAccept(...)` semantics.

No artificial hypothesis ID is introduced.

### Values

`VALUES_ORDER` copies the current Values rowset, applies ordered multi-key comparison and serializes the projected rows without modifying `Mind`/`ValuesStore` default ordering.

### Help

HELP is rendered directly from `CommandRegistry` metadata.
