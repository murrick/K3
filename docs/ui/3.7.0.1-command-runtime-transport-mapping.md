# KANGER 3.7.0.1 — Canonical command runtime / transport mapping

Status: **DERIVED DESIGN MAPPING / DOCUMENTATION ONLY / REVIEW BEFORE CLOSURE**

Reference runtime: accepted `release/3.5.2` / `server-0.18`.

This document maps the accepted canonical command intents onto the currently qualified Server/Core execution surface. It changes no runtime behavior.

The purpose is not to preserve the historical Browser protocol as a second command language. The purpose is to identify which accepted intents already have a qualified execution path, which need only a strict adapter, and which require a narrow new Server binding over an existing Core capability.

## 1. Mapping classes

```text
DIRECT
    Current Server 0.18 already exposes the required runtime operation.
    The canonical adapter may rename/repackage the request, but no new
    semantic/runtime capability is required.

STRICT_ADAPTER
    The required runtime data/capability already exists, but the legacy
    transport is broader, overloaded, or shaped differently from the
    accepted canonical intent. The adapter must narrow/project it.

NEW_BINDING
    Core/Console already has the required semantic capability, but Server 0.18
    has no exact transport operation for it. A narrow Server binding is needed;
    this is not a new Core semantic feature.

COMMAND_LAYER
    No runtime operation is required. The command processor/registry owns the
    result or metadata.

CORE_PRESENTATION_FIX
    The accepted command semantics intentionally reject an existing stateful
    presentation mechanism. Core/result projection must be cleaned before the
    canonical intent can be implemented correctly.
```

These classes describe implementation work only. They do not create aliases or additional command syntax.

## 2. Current qualified Server execution chain

Server 0.18 currently executes authenticated application requests through:

```text
SessionSerializingReactor
  -> MailBoundaryReactor
    -> WorkspaceStateReactor
      -> ExplicitStorageLifecycleReactor
        -> DestructiveStopLossReactor
          -> MindLifecycleReactor
            -> QueryProcessor
```

The canonical command adapter must preserve these qualified lifecycle, stop-loss, workspace-projection and session-serialization boundaries. Introducing the shared command processor is not permission to bypass them.

## 3. Core-language boundary

Accepted KANGER language prefixes remain outside ordinary command grammar:

```text
! ? + - =
```

For Browser/future remote clients, raw console input should reach the Server command ingress before the current Browser-side command/query split. The Server-side shared processor then decides:

```text
raw line
    -> CORE_LANGUAGE
        -> existing query/request execution path

    -> COMMAND
        -> canonical CommandIntent + arguments
        -> runtime mapping below
```

For the Java Console the same `kanger-command` parser is invoked locally.

The exact future JSON/wire field carrying raw command text is intentionally not frozen by this design mapping.

## 4. RULE family

| Intent | Canonical syntax | Mapping | Current/runtime path |
|---|---|---|---|
| `RULE_STATUS` | `rule` | DIRECT | query `rules=""` -> `QueryProcessor.getRules()` |
| `RULE_SHOW` | `rule <id>` | DIRECT | query `rules=""`, `id=<id>` |
| `RULE_ALL` | `rule all` | DIRECT | query `rules="all"` |
| `RULE_PRODUCED` | `rule produced` | DIRECT | query `rules="produced"` |
| `RULE_LEVEL` | `rule level <n>` | DIRECT | query `rules=""`, `level=<n>` |
| `RULE_TREE` | `rule tree <id>` | DIRECT | query `rules=""`, `id=<id>`, `tree=true` |
| `RULE_COMMENT_GET` | `rule comment <id>` | NEW_BINDING | Core `IRule.getComment()` already exists; no Server operation |
| `RULE_COMMENT_SET` | `rule comment <id> <text...>` | NEW_BINDING | Core `IRule.setComment()` already exists; no Server operation |

`Rule.createMap()` does not currently include comments, so comment GET must not be faked by ordinary `rule <id>` response parsing.

The new comment binding must operate on the active Mind/Rule context so existing transactional comment-factory semantics remain authoritative.

## 5. FUNCTION family

| Intent | Canonical syntax | Mapping | Current/runtime path |
|---|---|---|---|
| `FUNCTIONS` | `functions` | DIRECT | query `functions=""` |
| `FUNCTION_SHOW` | `function <id>` | DIRECT | query `functions=""`, `id=<id>` |
| `FUNCTION_SOURCE` | `function source <id>` | DIRECT | query `functions=""`, `id=<id>`, `sources=true` |

`QueryProcessor.getFunctions()` already provides all three projections through one runtime path.

## 6. BASE family

| Intent | Canonical syntax | Mapping | Current/runtime path |
|---|---|---|---|
| `BASE_STATUS` | `base` | STRICT_ADAPTER | existing predicate + statement/solve projection, filtered to current non-empty/unambiguous statement groups |
| `BASE_PREDICATES` | `base predicates` | DIRECT | query `predicates=""` |
| `BASE_PREDICATE` | `base predicate <id|name>` | DIRECT | query `statements=""`, `predicate=<ref>` |
| `BASE_TREE` | `base tree <statement-id>` | STRICT_ADAPTER | existing statement `id` + `causes=true` mechanism, but must forbid legacy fallback into Solutions |

Important semantic boundary:

- `base` means current unambiguous semantic-base statements/domains;
- `base predicates` means predicates known in the semantic context independently of whether they currently own unambiguous domains;
- `base tree` is provenance of a base statement, not a solution tree.

The historical `getStatements(id)` fallback into `mind.getSolutions()` is therefore too permissive for canonical `BASE_TREE` and must not be inherited by the new adapter.

## 7. VALUES family

| Intent | Canonical syntax | Mapping | Current/runtime path |
|---|---|---|---|
| `VALUES` | `values` | DIRECT | query `results=""` -> `QueryProcessor.getValues()` |
| `VALUES_ORDER` | `values order <variable> [asc|desc]` | CORE_PRESENTATION_FIX | current `ValuesStore.order` / `Mind.setOrder()` is persistent/inherited presentation state and is explicitly not canonical |

Accepted 3.7 behavior is a per-invocation projection:

```text
current raw Values rowset
    -> copy/project
    -> sort copy for this response only
    -> do not mutate Mind / ValuesStore ordering state
```

The old Console `options order` mechanism must not be reused. `Mind(IMind root)` currently inherits Values order/ascending state, and `ValuesStore` can change its backing set between insertion-order and sorted representations. That is precisely the presentation leakage already identified for later Core cleanup.

## 8. SOLUTION family

| Intent | Canonical syntax | Mapping | Current/runtime path |
|---|---|---|---|
| `SOLUTIONS` | `solutions` | DIRECT | query `solutions=""` -> all current solutions |
| `SOLUTION_SHOW` | `solution <id>` | NEW_BINDING | Core solutions are iterable with logical Rule IDs; Server `getSolutions()` ignores selectors |
| `SOLUTION_TREE` | `solution tree <id>` | NEW_BINDING | Core solution Rule causes exist; Server `getSolutions()` exposes neither id selection nor cause tree |

Do not implement `solution <id>` by abusing `getStatements(id)` fallback. That would reintroduce the semantic collision between Base statements and Solutions that the canonical taxonomy deliberately separates.

`SolutionsStore.get(long id)` currently returns `null`; the first implementation may select by iterating current solutions and comparing `IRule.getId()`. Whether `SolutionsStore.get(long)` is later completed is Core cleanup, not a command-language concern.

## 9. WHEN family

| Intent | Canonical syntax | Mapping | Current/runtime path |
|---|---|---|---|
| `WHEN_STATUS` | `when` | DIRECT | query `hypothesis=""` -> current optimized hypotheses |
| `WHEN_ACCEPT` | `when accept <n>` | NEW_BINDING | Console/Core already performs hypothesis selection then `Mind.queryAccept(...)`; Server has no accept operation |

The accepted index semantics remain the existing hypothesis-selection semantics. The Server binding should call the same Core operation rather than reproduce inference logic in transport code.

## 10. TRANSACTION family

| Intent | Canonical syntax | Mapping | Current/runtime path |
|---|---|---|---|
| `TX_STATUS` | `transaction` | DIRECT | query `transaction=""` -> level/id/empty status |
| `TX_START` | `transaction start` | DIRECT | canonical `start` maps internally to legacy transport action `create`; `MindLifecycleReactor` owns lifecycle |
| `TX_COMMIT` | `transaction commit` | DIRECT | current transaction `commit`; root commit/checkpoint protected by `ExplicitStorageLifecycleReactor` |
| `TX_ROLLBACK` | `transaction rollback` | DIRECT | current transaction `rollback`; `MindLifecycleReactor` owns publication |

The word `create` remains a legacy transport spelling only. It is not restored as canonical command vocabulary.

## 11. SOURCE operations

| Intent | Canonical syntax | Mapping | Current/runtime path |
|---|---|---|---|
| `SOURCE_GET` | `get <source>` | DIRECT | command `get=<source>` -> qualified safe source load/compile path |
| `SOURCE_PUT` | `put <source>` | DIRECT | command `put=<source>` -> atomic UTF-8 publication path |
| `SOURCE_DELETE` | `delete <source>` | DIRECT | command `delete=<source>` -> truthful delete path |

The accepted Browser/UI grammar requires the source name explicitly. This deliberately prevents current legacy empty-argument fallbacks from becoming executable canonical forms.

Console-only bare `get` / `put` / `delete` remain read-only list conveniences handled by the later Console adapter and are not mapped to mutation intents.

Source-list data itself already exists through the current empty-`get` transport and `WorkspaceStateReactor` normalized `sources` list, so UI source pickers do not require a new semantic command.

## 12. STORAGE family

| Intent | Canonical syntax | Mapping | Current/runtime path |
|---|---|---|---|
| `STORAGE_STATUS` | `storage` | STRICT_ADAPTER | current empty `use` list + `WorkspaceStateReactor` active/logical storage projection |
| `STORAGE_USE` | `storage use <name>` | DIRECT | command `use=<name>` through explicit lifecycle + stop-loss guards |
| `STORAGE_CLOSE` | `storage close` | DIRECT | command `close` through Core `User.close(...)` lifecycle path |
| `STORAGE_DROP` | `storage drop <name>` | DIRECT | command `drop=<name>`; canonical parser requires explicit target |
| `STORAGE_REINDEX` | `storage reindex <name>` | DIRECT | command `reindex=<name>`; canonical parser requires explicit target |

Canonical `storage` is not the legacy `used` command. It means available storages plus current/open marker. The current empty-`use` list together with the authoritative `workspace.storage` projection already contains that information.

Legacy optional-target behavior in `drop` / `reindex` is intentionally hidden: canonical grammar requires `<name>` and rejects omission before runtime dispatch.

## 13. SYSTEM / SESSION

| Intent | Canonical syntax | Mapping | Current/runtime path |
|---|---|---|---|
| `ERASE` | `erase` | DIRECT | command `erase` -> existing qualified clear-workspace path; confirmation remains presentation policy |
| `HELP` | `help` | COMMAND_LAYER | generate from `CommandRegistry` metadata; do not delegate to stale `QueryProcessor.processHelp()` vocabulary |
| `QUIT` | `quit` | DIRECT | current quit/logout path, owned safely by `MindLifecycleReactor` / session runtime |

`HELP` is the strongest reason not to preserve the legacy Server help text as authority: the current text still advertises old `use/used`, transaction `create`, and other historical spellings. Canonical help must be generated from the same registry that parses commands.

## 15. Browser transport consequence

The historical Browser currently performs its own command parse/switch and translates words into legacy JSON fields before contacting the Server. Keeping that model would preserve the duplication that `kanger-command` was introduced to eliminate.

Target boundary:

```text
Browser command editor
    -> raw command text
    -> Server
    -> shared kanger-command parser/registry
    -> canonical CommandIntent + arguments
    -> Server runtime adapter
```

Console target:

```text
Console input
    -> shared kanger-command parser/registry
    -> canonical CommandIntent + arguments
    -> local Console runtime adapter
```

The Browser is therefore a command-composition/presentation client, not a second command parser.

The exact wire envelope is intentionally deferred. The semantic requirement is that the Server, not Browser JavaScript, owns canonical parsing for remote clients.

## 16. Preservation rule for Server implementation

The later implementation must not replace qualified Server 0.18 protections wholesale.

Preferred migration strategy:

```text
canonical raw ingress
    -> parse once with kanger-command
    -> for DIRECT intents translate into the existing qualified operation path
    -> for STRICT_ADAPTER intents narrow/project existing data
    -> for NEW_BINDING intents add the smallest Core-facing binding
    -> preserve SessionSerializing / lifecycle / stop-loss / workspace authority
```

A new parser is not justification to bypass existing lifecycle reactors or duplicate Core storage/source logic.

## 17. Remaining review questions

No command vocabulary question remains in this mapping.

Before closing 3.7.0.1, review only these implementation-boundary conclusions:

1. remote Browser/future clients send raw command text and Server owns canonical parsing;
2. the five `NEW_BINDING` intents remain narrow Server bindings over existing Core semantics;
3. `VALUES_ORDER` waits for/remains coupled to removal of persistent Values ordering leakage;
4. canonical help is registry-derived rather than legacy Server help text;
5. existing Server 0.18 lifecycle/stop-loss/workspace chain remains the execution authority under the adapter.

No runtime implementation belongs in this document or in the current 3.7.0.1 design baseline.
