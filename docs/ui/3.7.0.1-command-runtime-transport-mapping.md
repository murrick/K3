# KANGER 3.7.0.1 — Canonical command runtime / transport mapping

Status: **ACCEPTED DESIGN MAPPING / DOCUMENTATION ONLY / CLOSED**

Reference runtime: accepted `release/3.5.2` / `server-0.18`.

This document maps the accepted canonical command intents onto the currently qualified Server/Core execution surface. It changes no runtime behavior.

## 1. Mapping classes

```text
DIRECT
    Server 0.18 already exposes the required runtime operation.

STRICT_ADAPTER
    Required capability exists, but legacy transport is broader or shaped
    differently and must be narrowed/projected.

NEW_BINDING
    Core/Console capability exists, but Server 0.18 has no exact transport
    operation. Add only a narrow Server binding.

PRESENTATION_EXTENSION
    Existing presentation capability is insufficient for the accepted result
    projection contract; extend presentation without changing logical semantics.

COMMAND_LAYER
    Result belongs to kanger-command metadata/registry rather than runtime.
```

## 2. Qualified Server execution authority

Server 0.18 currently executes authenticated requests through:

```text
SessionSerializingReactor
  -> MailBoundaryReactor
    -> WorkspaceStateReactor
      -> ExplicitStorageLifecycleReactor
        -> DestructiveStopLossReactor
          -> MindLifecycleReactor
            -> QueryProcessor
```

The shared command processor must preserve these qualified lifecycle, stop-loss, workspace and session boundaries.

## 3. Client/processor boundary

KANGER Core-language prefixes remain outside ordinary command grammar:

```text
! ? + - =
```

Remote clients do not own a second canonical parser.

```text
Browser / future remote client
    -> raw command text
    -> Server
    -> kanger-command
    -> CommandIntent + arguments
    -> Server runtime adapter
    -> qualified Server/Core execution path
```

Console uses the same processor locally:

```text
Console input
    -> kanger-command
    -> CommandIntent + arguments
    -> local runtime adapter
```

The exact wire envelope carrying raw command text is deferred to implementation.

## 7. VALUES

| Intent | Syntax | Mapping | Existing path / required delta |
|---|---|---|---|
| VALUES | `values` | DIRECT | current Values result projection |
| VALUES_ORDER | `values order <field> [asc|desc] [, <field> [asc|desc]]...` | PRESENTATION_EXTENSION | add invocation-local ordered multi-key SortSpec projection |

Accepted ordering model:

```text
configured DefaultSortSpec
    -> plain `values`

explicit SortSpec from command
    -> current invocation only
```

If no default sort exists, plain `values` uses natural order.

Each explicit key is:

```text
(field, direction)
```

with omitted direction = `asc`; commas separate keys.

The current single-field `ValuesStore.order` / `ascending` mechanism is useful migration evidence for default ordering but is insufficient as the final model because it couples row storage to presentation and cannot express multi-key sorting.

Implementation direction:

1. preserve authoritative Values rows independently of presentation order;
2. introduce ordered `SortSpec` / `SortKey(field,direction)` representation;
3. allow configured default sort policy;
4. apply `values order ...` as a temporary projection without mutating the default or authoritative rowset.

This is presentation functionality, not new KANGER inference semantics.

## 8. SOLUTION

| Intent | Syntax | Mapping | Existing path / required delta |
|---|---|---|---|
| SOLUTIONS | `solutions` | DIRECT | current all-solutions projection |
| SOLUTION_SHOW | `solution <id>` | NEW_BINDING | select current Solution/IRule by runtime ID |
| SOLUTION_TREE | `solution tree <id>` | NEW_BINDING | select by runtime ID and expose causes/provenance |

Solution address is the actual `IRule` runtime ID, never a row ordinal.

`SolutionsStore.get(long)` currently does not provide this lookup; first binding may iterate current solutions and compare `IRule.getId()`. Completing store lookup is optional Core cleanup, not a change in command semantics.

## 9. WHEN

| Intent | Syntax | Mapping | Existing path / required delta |
|---|---|---|---|
| WHEN_STATUS | `when` | DIRECT | current optimized hypotheses projection |
| WHEN_ACCEPT | `when accept <index>` | NEW_BINDING | select zero-based current hypothesis row and delegate to existing Core acceptance path |

Hypotheses have no stable displayed ID. Canonical addressing is row-based and zero-based:

```text
0 .. size-1
```

The Server/UI projection should expose the same `index` field that the command accepts. Historical one-based Console numbering is migration-only behavior and must not become canonical.

## 15. Implementation preservation rule

Preferred later migration:

```text
canonical raw ingress
    -> parse once with kanger-command
    -> DIRECT: translate into existing qualified operation path
    -> STRICT_ADAPTER: narrow/project existing data
    -> NEW_BINDING: add smallest Core-facing binding
    -> PRESENTATION_EXTENSION: add result projection without changing inference semantics
    -> COMMAND_LAYER: answer from command metadata
```

Existing Server 0.18 lifecycle, stop-loss, workspace and session authorities remain in force.

## 16. Accepted closure

The following boundary conclusions are accepted:

1. Browser/future remote clients send raw command text; Server owns canonical parsing.
2. Console and Server consume the same `kanger-command` parser/registry.
3. The five NEW_BINDING intents are narrow bindings over existing Core capability.
4. Solutions are addressed by concrete runtime ID.
5. Hypotheses are addressed by zero-based row index of the current hypothesis rowset.
6. Values retain configurable default sorting and gain invocation-local comma-separated multi-key ordering.
7. Canonical help is registry-derived.
8. Existing qualified Server 0.18 protection chain remains execution authority beneath the adapter.

No runtime implementation belongs in 3.7.0.1.
