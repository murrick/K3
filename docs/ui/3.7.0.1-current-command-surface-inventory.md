# KANGER 3.7.0.1 — Current command-surface inventory

Status: FIRST-PASS INVENTORY / DOCUMENTATION ONLY  
Reference runtime: `release/3.5.2` at `9c8b7dd2c9ef347cea6af6a6faef9cfa48030306`

## Purpose

This document inventories the command and semantic-read surfaces that exist in the accepted 3.5.2 repository before any unification work begins.

It is descriptive, not yet the final grammar.

The inventory deliberately distinguishes three concepts that are currently mixed across implementations:

1. **user command** — an operation the user intentionally composes and executes;
2. **semantic view/read** — a projection used to render current KANGER state;
3. **diagnostic/admin action** — technical introspection or operator behavior that need not belong to the ordinary semantic command language.

## 1. Current implementation layers

### Java Console

`kanger-console/src/org/kanger/Console.java` dispatches primarily on the first character of the entered line.

Top-level command surface in 3.5.2:

```text
Q  quit
H  help
R  rules
B  base / predicates/statements projection
F  functions
L  hypothesis
A  accept hypothesis
V  values log
S  solutions
X  explanation
E  erase workspace
G  get/load source
P  put/save source (and rule-comment editing overload)
C  close database
U  use database
D  drop database
I  pack/reindex database
O  options / diagnostics / tests
T  transaction control
Z  repeat last query
```

KANGER language-leading operators are routed separately through the logical query/compiler path rather than the Console command switch.

The Console also embeds interactive prompts, confirmations and object selection directly in the execution helpers.

### Browser console

The historical Browser command parser recognizes textual words:

```text
used
use
close
drop
reindex
get
put
delete
erase
transaction
create
commit
rollback
help
quit
```

The Browser therefore already differs substantially from the Java Console vocabulary.

### Browser operation authority

`html/operation.js` independently classifies packets as reads or authoritative mutations and recognizes operation names including:

```text
compile
transaction
request
get
put
delete
use
close
drop
reindex
erase
quit
```

This is execution metadata duplicated outside both command parsers.

### Browser workspace authority

`html/workspace.js` independently knows argument domains:

```text
source names:  get, put, delete
storage names: use, drop, reindex
```

It also canonicalizes those names and consumes the post-operation workspace projection.

### Server QueryProcessor

The server has another dispatch vocabulary.

`command` context:

```text
get
put
delete
use
used
close
drop
reindex
erase
ping
help
quit
```

`query` context:

```text
request
compile
results
solutions
hypothesis
rules
predicates
statements
functions
transaction
log
source
```

`history` is a separate transport/application context.

## 3. Important divergence: transaction syntax

The accepted repository already demonstrates why one grammar is needed.

Java Console transaction handling is not the same textual language as Browser transaction handling. The Console routes by first letters inside `T`, while Browser accepts both the compound and shorthand forms:

```text
transaction create
create

transaction commit
commit

transaction rollback
rollback
```

3.7.0 must define one canonical parse result for each operation. Shorthand forms must resolve to the same canonical command rather than separate implementations.

## 4. Important divergence: source lifecycle

The Server and Browser expose source deletion. The Java Console top-level dispatcher does not expose a corresponding source-delete command.

The accepted Server source surface already contains:

```text
get
put
delete
```

while the Java Console uses:

```text
G  load/get
P  save/put
```

and has no matching top-level source-delete command.

This is concrete interface drift, not a hypothetical future risk.

3.7.0 must additionally design:

```text
download
upload
```

with upload defined as atomic semantic ingest rather than raw repository file replacement.

## 5. Important divergence: reindex vs pack

The Java Console exposes the database maintenance operation under `I` and describes it as packing/reindexing. The Browser/Server vocabulary calls it `reindex`.

The unified grammar must decide the canonical user term and any compatibility alias without maintaining two execution paths.

## 6. Views are not automatically commands

The Java Console historically makes semantic inspection look like commands because a terminal has only one interaction surface:

```text
R / B / F / L / V / S / X
```

The Browser naturally renders many of these as persistent semantic regions backed by server reads.

The new command model must therefore avoid the false conclusion that every historical Console letter is necessarily a canonical mutating/user command.

A useful target distinction is:

```text
COMMAND
    explicit user intent that may change or interrogate KANGER state

VIEW READ
    projection needed to display statements/functions/results/etc.

DIAGNOSTIC READ/ACTION
    runtime/operator information and controls

EDITOR/COMPOSITION ACTION
    local interaction such as inserting visible semantic text into command input
```

The same underlying capability may be reachable through more than one presentation without duplicating its semantics.

Possible compatibility aliases such as `create`, `commit`, `rollback`, or `pack` must be resolved by the grammar registry, not by independent interface switches.

## 8. Parser requirements carried forward

The future parser must support:

- case-insensitive command words;
- minimum unique leading prefixes, normally yielding FoxBase-style three/four-character interaction;
- explicit alias registration;
- ambiguity rejection rather than guessing;
- the same parse result in Console, Browser and future interfaces;
- preservation of KANGER language expressions as a distinct logical-language path;
- enough parse metadata for live-link command composition and later completion/help.

## 9. Next inventory work

Before runtime implementation, refine this first pass into a normative registry containing for every command or read:

```text
canonical name
aliases
minimum unique prefix under the complete registry
argument grammar
scope/domain
read vs mutation

whether destructive
whether confirmation is presentation policy or execution contract
canonical result/state projection

current Browser spelling

```

Only after that registry is stable should parser/dispatcher ownership and module placement be implemented.
