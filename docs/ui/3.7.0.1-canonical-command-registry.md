# KANGER 3.7.0.1 — Canonical command registry

Status: **ACCEPTED EXECUTABLE COMMAND-LANGUAGE CONTRACT**

Executable authority: `kanger-command` `CommandRegistry` + `CommandParser`.

This registry consolidates the accepted 3.7.0.1 command-language decisions and documents the executable `CommandRegistry` / `CommandParser` contract.

## 1. Parsing boundary

KANGER logical expressions remain Core language and are not ordinary command words:

```text
! ? + - =
```

Command keywords are case-insensitive and use the minimum unique leading prefix in the relevant grammar position.

Resolution rule:

1. exact full keyword wins;
2. otherwise a unique leading prefix resolves the keyword/family stem;
3. ambiguity is rejected;
4. arguments are interpreted only by the grammar production that owns their position;
5. argument spelling must not select between unrelated command identities.

Arguments preserve their content/case and are validated by the relevant semantic/namespace layer. Lexical and quoting rules are normative in `3.7.0.1-command-lexical-decisions.md`.

Natural top-level aliases are registry metadata and participate in the same top-level minimum-prefix calculation as canonical families. Family spellings are a separate mechanism: `rule/rules` and `predicate/predicates` collapse to one family before ambiguity is counted. Every accepted alias or family spelling normalizes to one canonical intent before execution.

## 2. Canonical command surface

### RULE

```text
rule
rule <id>
rule all
rule produced
rule level <n>
rule tree <id>
rule comment <id>
rule comment <id> <text...>
```

| Intent ID | Canonical syntax | Class | Mutation |
|---|---|---|---:|
| `RULE_STATUS` | `rule` | USER_READ | no |
| `RULE_SHOW` | `rule <id>` | USER_READ | no |
| `RULE_ALL` | `rule all` | USER_READ | no |
| `RULE_PRODUCED` | `rule produced` | USER_READ | no |
| `RULE_LEVEL` | `rule level <n>` | USER_READ | no |
| `RULE_TREE` | `rule tree <id>` | USER_READ | no |
| `RULE_COMMENT_GET` | `rule comment <id>` | USER_READ | no |
| `RULE_COMMENT_SET` | `rule comment <id> <text...>` | USER_MUTATION | yes |

`rule <id>` is the direct object-address form. The intermediate `rule show <id>` design is retired as redundant.

### FUNCTION

`function/functions` are grammatical forms of one family, not independent namespaces.

### BASE

```text
base
base predicates
base predicate <id|name>
base tree <statement-id>

predicate / predicates
predicate / predicates <id|name>
```

| Intent ID | Canonical syntax | Class | Mutation |
|---|---|---|---:|
| `BASE_STATUS` | `base` | USER_READ | no |
| `BASE_PREDICATES` | `base predicates` | USER_READ | no |
| `BASE_PREDICATE` | `base predicate <id|name>` | USER_READ | no |
| `BASE_TREE` | `base tree <statement-id>` | USER_READ | no |

`predicate/predicates` are top-level spellings of one family, not aliases and not competing commands. With no argument they normalize to `base predicates`; with one reference they normalize to `base predicate <id|name>`. Bare `tree` is not a command; tree forms remain qualified by `base`, `rule` or `solution`.

### VALUES

```text
values
values order <field> [asc|desc] [, <field> [asc|desc]]...
```

| Intent ID | Canonical syntax | Class | Mutation |
|---|---|---|---:|
| `VALUES` | `values` | USER_READ | no |
| `VALUES_ORDER` | `values order <field> [asc|desc] [, <field> [asc|desc]]...` | USER_READ | no |

Each sort key is `(field, direction)`; omitted direction means `asc`. Commas separate sort-key pairs and are structural punctuation only for this production.

Plain `values` uses the configured default Values ordering, falling back to natural rowset order when no default exists. `values order ...` is an invocation-local override and must not mutate the configured default.

### SOLUTION

```text
solutions
solution <id>

```

| Intent ID | Canonical syntax | Class | Mutation |
|---|---|---|---:|
| `SOLUTIONS` | `solutions` | USER_READ | no |
| `SOLUTION_SHOW` | `solution <id>` | USER_READ | no |
| `SOLUTION_TREE` | `solution tree <id>` | USER_READ | no |

`solution/solutions` are grammatical forms of one family. `<id>` is the concrete Solution/IRule runtime identity, never a presentation row number.

### WHEN

```text
when
when accept <index>
```

| Intent ID | Canonical syntax | Class | Mutation |
|---|---|---|---:|
| `WHEN_STATUS` | `when` | USER_READ | no |
| `WHEN_ACCEPT` | `when accept <index>` | USER_MUTATION | yes |

Hypotheses have no stable displayed semantic ID. `when` exposes the current hypothesis rowset with zero-based row indexes, and `when accept <index>` addresses that current row position (`0 .. size-1`). No artificial hypothesis identity is introduced.

Historical `list` / `append` are not canonical vocabulary.

### TRANSACTION

```text
transaction
transaction start
transaction commit
transaction rollback
transaction squash
```

| Intent ID | Canonical syntax | Class | Mutation |
|---|---|---|---:|
| `TX_STATUS` | `transaction` | USER_READ | no |
| `TX_START` | `transaction start` | USER_MUTATION | yes |
| `TX_COMMIT` | `transaction commit` | USER_MUTATION | yes |
| `TX_ROLLBACK` | `transaction rollback` | USER_MUTATION | yes |
| `TX_SQUASH` | `transaction squash` | USER_MUTATION | yes |

Top-level aliases are `start`, `commit`, `rollback` and `squash`. `create` is not canonical vocabulary. Within the transaction family, `transaction s` is ambiguous between start and squash; the stable minima are `transaction st` and `transaction sq`.

### SOURCE

Canonical Browser/UI executable forms are exactly:

```text
get <source>
put <source>
delete <source>
```

| Intent ID | Canonical syntax | Class | Mutation | Destructive |
|---|---|---|---:|---:|
| `SOURCE_GET` | `get <source>` | USER_MUTATION | yes | no |
| `SOURCE_PUT` | `put <source>` | USER_MUTATION | yes | no |
| `SOURCE_DELETE` | `delete <source>` | USER_MUTATION | yes | yes |

There is no canonical `source` namespace.

Deferred Console convergence may additionally accept bare `get`, `put`, `delete` as **read-only terminal conveniences** that list available source names and perform no mutation. These are not additional canonical source intents and are not Browser/UI grammar.

Browser-only Source-menu transport actions:

```text
upload
download
```

are not KANGER commands and do not participate in prefix resolution.

### STORAGE

```text
storage
storage use <name>
storage close
storage drop <name>
storage reindex <name>
```

| Intent ID | Canonical syntax | Class | Mutation | Destructive |
|---|---|---|---:|---:|
| `STORAGE_STATUS` | `storage` | USER_READ | no | no |
| `STORAGE_USE` | `storage use <name>` | USER_MUTATION | yes | no |
| `STORAGE_CLOSE` | `storage close` | USER_MUTATION | yes | no |
| `STORAGE_DROP` | `storage drop <name>` | USER_MUTATION | yes | yes |
| `STORAGE_REINDEX` | `storage reindex <name>` | USER_MUTATION | yes | no |

Bare `storage` lists available storages and identifies the current/open storage.

Top-level aliases are `use`, `close`, `drop` and `reindex`. `use` is arity-aware: bare `use` normalizes to storage status, while `use <name>` normalizes to `storage use <name>`.

`use` is intentionally retained. Without it, an arbitrary storage name could collide with `close`, `drop` or `reindex`; `storage use close` must unambiguously mean storage named `close`, while `storage close` means close the current storage.

Historical `used`, `index`, `pack` are not canonical vocabulary. `drop` and `reindex` require an explicit storage name.

### SYSTEM / SESSION

```text
erase
help
quit
```

| Intent ID | Canonical syntax | Class | Mutation | Destructive |
|---|---|---|---:|---:|
| `ERASE` | `erase` | USER_MUTATION | yes | yes |
| `HELP` | `help` | USER_READ | no | no |
| `QUIT` | `quit` | SESSION | yes | no |

Confirmation is presentation policy, not command identity.

`help` is rendered from the same `CommandRegistry` metadata that defines grammar and parsing. Each production carries its semantic help grouping/description metadata; usage text is derived from grammar rather than duplicated in a second hand-maintained command list.

There is no canonical `system`, `settings`, `options`, or generic `diagnostics` namespace.

Bare `c`, `d`, `p`, `r`, `s` and `st` are ambiguous. Exact spellings still win over prefixes; arguments never choose between unrelated command groups. The `use` group is the sole intentional arity overload, selecting status for an empty tail and storage-use for a non-empty tail.

## 5. Lexical contract

The accepted lexical model is deliberately small:

```text
keyword/argument tokens separated by whitespace
+ double-quoted argument when one argument contains whitespace
+ minimum-unique-prefix resolution only in keyword positions
+ free-text remainder for rule comment bodies
+ comma-separated SortKey pairs inside values order only
```

Keywords are case-insensitive; argument content/case is preserved.

Once grammar expects an argument, a word that happens to equal a command keyword is data. Examples:

```text
get delete
storage use close
```

Quoted arguments use double quotes. Inside them only `\"` and `\\` are special. No single-quote or shell-style escape syntax is introduced.

`rule comment <id>` reads; `rule comment <id> <text...>` writes; `rule comment <id> ""` writes an explicitly empty comment.

Source/storage names are namespace objects, not filesystem-path expressions. Legality/canonicalization is validated below the lexer.

The comma used by `values order` is consumed by that production's grammar and does not acquire general command-language meaning.

## 6. Console-local diagnostic outside Browser/UI registry

```text
xplain
xplain <file>
xplain mode on
xplain mode off
```

`xplain` remains Console-local. It may use the same keyword/prefix machinery during Console convergence but does not change the Browser/UI prefix table.

## 8. Command processor ownership

The single owner of canonical command parsing and registry metadata is the accepted sibling module:

```text
kanger-command/
    src/org/kanger/command/...
```

`kanger-command` owns parsing, canonical intents, argument extraction, lexical/quoting behavior, minimum-prefix resolution, canonical command metadata and registry-derived help metadata.

It does **not** execute KANGER operations and must not depend on `IMind`, Console, Server transport, Browser/UI, concrete storage or source filesystem implementation.

The shared processor stops at:

```text
raw command text
    -> canonical intent + arguments
```

Execution is performed by the appropriate Console or Server/runtime dispatcher.

Normative ownership details are recorded in `3.7.0.1-command-processor-ownership.md`. Help metadata/rendering details are recorded in `3.7.0.1-help-command-decisions.md`.
