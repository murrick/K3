# KANGER 3.7.0.1 — Parser conformance cases

Status: **ACCEPTED-DERIVED CONFORMANCE SPEC / DOCUMENTATION ONLY**

Reference runtime: accepted `release/3.5.2`.

This document derives parser test cases from the already accepted canonical registry and lexical rules. It introduces no runtime implementation and no alternate command vocabulary.

## 1. Purpose

The future common command parser must produce the same canonical intent and arguments regardless of whether input came from Console typing, Browser command composition, or another future UI surface.

Conformance boundary:

```text
raw line
  -> Core-language bypass OR command tokenization
  -> keyword/prefix resolution in grammar positions
  -> canonical intent + parsed arguments
  -> later semantic/lifecycle validation
```

These cases test parsing/canonicalization. They do not claim that every semantically addressable object exists at runtime.

## 2. Result notation

Examples use:

```text
OK <INTENT> { arguments... }
REJECT <reason-class>
CORE_LANGUAGE <raw expression>
```

Reason classes are conformance categories, not frozen user-facing error strings:

```text
UNKNOWN_KEYWORD
AMBIGUOUS_PREFIX
INVALID_GRAMMAR
MISSING_ARGUMENT
EXTRA_ARGUMENT
INVALID_ARGUMENT_SHAPE
UNTERMINATED_QUOTE
```

Actual UI/server error wording is a later presentation/protocol concern.

## 3. Core-language bypass

The command processor must not steal KANGER logical language:

| Input | Expected |
|---|---|
| `?father(John,Tom)` | `CORE_LANGUAGE` |
| `!male(John)` | `CORE_LANGUAGE` |
| `+native($x)` | `CORE_LANGUAGE` |
| `-obsolete($x)` | `CORE_LANGUAGE` |
| `=x+y` | `CORE_LANGUAGE` |

The existing Core parser/compiler owns these lines after the initial language/command boundary decision.

## 4. Top-level prefix resolution

Accepted minimum top-level prefixes:

```text
b  -> base
d  -> delete
e  -> erase
f  -> function/functions
g  -> get
h  -> help
p  -> put
q  -> quit
r  -> rule
so -> solution/solutions
st -> storage
t  -> transaction
v  -> values
w  -> when
```

Conformance cases:

| Input | Expected |
|---|---|
| `b` | `OK BASE_STATUS {}` |
| `d foo.k` | `OK SOURCE_DELETE {source:"foo.k"}` |
| `e` | `OK ERASE {}` |
| `f` | `OK FUNCTIONS {}` |
| `g foo.k` | `OK SOURCE_GET {source:"foo.k"}` |
| `h` | `OK HELP {}` |
| `p foo.k` | `OK SOURCE_PUT {source:"foo.k"}` |
| `q` | `OK QUIT {}` |
| `r` | `OK RULE_STATUS {}` |
| `so` | `OK SOLUTIONS {}` |
| `st` | `OK STORAGE_STATUS {}` |
| `t` | `OK TX_STATUS {}` |
| `v` | `OK VALUES {}` |
| `w` | `OK WHEN_STATUS {}` |
| `s` | `REJECT AMBIGUOUS_PREFIX` |
| `z` | `REJECT UNKNOWN_KEYWORD` |

Case is ignored only for keyword resolution:

| Input | Expected |
|---|---|
| `RuLe 17` | `OK RULE_SHOW {id:17}` |
| `ST U Demo` | `OK STORAGE_USE {name:"Demo"}` |

Argument case/content is preserved.

## 5. RULE family

Canonical grammar:

```text
rule
rule <id>
rule all
rule produced
rule level <n>
rule tree <id>
rule comment <id>
rule comment <id> <text...>
```

Positive cases:

| Input | Expected |
|---|---|
| `rule` | `OK RULE_STATUS {}` |
| `rule 17` | `OK RULE_SHOW {id:17}` |
| `r 17` | `OK RULE_SHOW {id:17}` |
| `rule all` | `OK RULE_ALL {}` |
| `r a` | `OK RULE_ALL {}` |
| `rule produced` | `OK RULE_PRODUCED {}` |
| `r p` | `OK RULE_PRODUCED {}` |
| `rule level 2` | `OK RULE_LEVEL {level:2}` |
| `r l 2` | `OK RULE_LEVEL {level:2}` |
| `rule tree 17` | `OK RULE_TREE {id:17}` |
| `r t 17` | `OK RULE_TREE {id:17}` |
| `rule comment 17` | `OK RULE_COMMENT_GET {id:17}` |
| `r c 17` | `OK RULE_COMMENT_GET {id:17}` |
| `rule comment 17 Important rule` | `OK RULE_COMMENT_SET {id:17,text:"Important rule"}` |
| `r c 17 ""` | `OK RULE_COMMENT_SET {id:17,text:""}` |

Rejected cases:

| Input | Expected |
|---|---|
| `rule show 17` | `REJECT INVALID_GRAMMAR` |
| `r s 17` | `REJECT INVALID_GRAMMAR` |
| `rule tree` | `REJECT MISSING_ARGUMENT` |
| `rule comment` | `REJECT MISSING_ARGUMENT` |
| `rule level` | `REJECT MISSING_ARGUMENT` |
| `rule all 17` | `REJECT EXTRA_ARGUMENT` |

`rule <id>` is intentionally accepted as the direct object-address production; no `show` keyword exists in the final RULE grammar.

## 15. Quoting and lexical cases

| Input | Expected |
|---|---|
| `get "my source.k"` | `OK SOURCE_GET {source:"my source.k"}` |
| `storage use "test base"` | `OK STORAGE_USE {name:"test base"}` |
| `get "a\"b.k"` | `OK SOURCE_GET {source:"a\"b.k"}` |
| `get "dir\\name.k"` | `OK SOURCE_GET {source:"dir\\name.k"}` |
| `get "unfinished` | `REJECT UNTERMINATED_QUOTE` |
| `get two names` | `REJECT EXTRA_ARGUMENT` |

The parser does not interpret source/storage names as filesystem navigation. Namespace validation/containment happens below parsing.

## 16. Exact-word precedence and ambiguity

Exact canonical words win before prefix expansion.

Required ambiguity behavior:

```text
s
    -> reject, because solution/storage share top-level `s`

so
    -> solution family

st
    -> storage family
```

Within each family, prefix resolution considers only keywords valid in that grammar position. Argument positions are never prefix-expanded.

## 17. Canonical echo invariant

Any accepted abbreviated form must canonicalize to the same full command identity as its long form.

Examples:

```text
r 17              -> rule 17
r c 17            -> rule comment 17
f s 8             -> function source 8
b p father        -> base predicate father
v o x d           -> values order x desc
so t 42           -> solution tree 42
w a 2             -> when accept 2
t c               -> transaction commit
st u close        -> storage use close
```

Canonical echo/help must never preserve the user's abbreviation as normative vocabulary.

## 18. What conformance does not decide

This matrix deliberately does not decide:

- whether a referenced runtime ID exists;
- whether a storage/source exists;
- authorization and ownership;
- transaction/storage lifecycle preconditions;
- source compile/collision results;
- confirmation UX;
- exact external error text/status codes;
- compatibility aliases;
- parser implementation class/package.

Those belong to later semantic execution, transport, presentation or implementation layers.

## 19. Closure criterion

A future parser implementation conforms to the 3.7.0.1 command contract when:

1. all positive cases above produce the specified canonical intents/arguments;
2. all rejected cases fail before execution;
3. Core-language lines bypass command dispatch unchanged;
4. abbreviation never changes semantic intent;
5. arguments are never reinterpreted as keywords after grammar has entered an argument position;
6. Console-only conveniences, if implemented, remain explicit local projections over the same canonical command model.
