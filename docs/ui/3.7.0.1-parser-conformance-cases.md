# KANGER 3.7.0.1 — Parser conformance cases

Status: **ACCEPTED-DERIVED CONFORMANCE SPEC / DOCUMENTATION ONLY / CLOSED**

Reference runtime: accepted `release/3.5.2`.

This document derives parser test cases from the accepted canonical registry and lexical rules. It introduces no runtime implementation and no alternate command vocabulary.

## 1. Boundary

```text
raw line
  -> Core-language bypass OR command tokenization
  -> keyword/prefix resolution in grammar positions
  -> production-specific argument parsing
  -> canonical intent + arguments
  -> later semantic/lifecycle validation
```

Notation:

```text
OK <INTENT> { arguments... }
REJECT <reason-class>
CORE_LANGUAGE <raw expression>
```

Representative rejection classes:

```text
UNKNOWN_KEYWORD
AMBIGUOUS_PREFIX
INVALID_GRAMMAR
MISSING_ARGUMENT
EXTRA_ARGUMENT
INVALID_ARGUMENT_SHAPE
UNTERMINATED_QUOTE
```

## 7. VALUES

Canonical grammar:

```text
values
values order <field> [asc|desc] [, <field> [asc|desc]]...
```

The parsed argument is an ordered list of sort keys:

```text
SortKey(field, direction)
```

with omitted direction = `ASC`.

Positive cases:

| Input | Expected |
|---|---|
| `values` | `OK VALUES {}` |
| `v` | `OK VALUES {}` |
| `v o x` | `OK VALUES_ORDER {sort:[(x,ASC)]}` |
| `v o x d` | `OK VALUES_ORDER {sort:[(x,DESC)]}` |
| `values order x desc, y asc` | `OK VALUES_ORDER {sort:[(x,DESC),(y,ASC)]}` |
| `values order surname, name, age desc` | `OK VALUES_ORDER {sort:[(surname,ASC),(name,ASC),(age,DESC)]}` |
| `v o x d, y a, z` | `OK VALUES_ORDER {sort:[(x,DESC),(y,ASC),(z,ASC)]}` |

Required rejection cases:

| Input | Expected |
|---|---|
| `values order` | `REJECT MISSING_ARGUMENT` |
| `values order x sideways` | `REJECT INVALID_GRAMMAR` |
| `values order x desc y asc` | `REJECT INVALID_GRAMMAR` |
| `values order x desc,` | `REJECT MISSING_ARGUMENT` |
| `values order , x` | `REJECT INVALID_GRAMMAR` |
| `values reset` | `REJECT INVALID_GRAMMAR` |

The comma is structural only inside this production. It separates SortKey pairs so `asc`/`desc` cannot be confused with a following field name.

Parser output does not decide whether a field exists in the current rowset; that is later result-projection validation.

## 11. SOURCE

Canonical Browser/UI executable grammar:

```text
get <source>

```

| Input | Expected |
|---|---|
| `g foo.k` | `OK SOURCE_GET {source:"foo.k"}` |
| `p foo.k` | `OK SOURCE_PUT {source:"foo.k"}` |
| `d foo.k` | `OK SOURCE_DELETE {source:"foo.k"}` |
| `get delete` | `OK SOURCE_GET {source:"delete"}` |
| `get 123` | `OK SOURCE_GET {source:"123"}` |
| `get "my source.k"` | `OK SOURCE_GET {source:"my source.k"}` |

| `get` | `REJECT MISSING_ARGUMENT` for Browser/UI canonical parser |

Console convergence may treat bare `get`, `put`, `delete` as local read-only list conveniences before canonical mutation dispatch. Named forms still normalize to the canonical intents above.

## 14. Quoting / lexical behavior

| Input | Expected |
|---|---|
| `get "my source.k"` | `OK SOURCE_GET {source:"my source.k"}` |
| `storage use "test base"` | `OK STORAGE_USE {name:"test base"}` |
| `get "a\"b.k"` | `OK SOURCE_GET {source:"a\"b.k"}` |
| `get "dir\\name.k"` | `OK SOURCE_GET {source:"dir\\name.k"}` |
| `get "unfinished` | `REJECT UNTERMINATED_QUOTE` |
| `get two names` | `REJECT EXTRA_ARGUMENT` |

Outside the two accepted quoted escapes (`\"`, `\\`), backslash has no shell-escape role. Source/storage names are namespace objects; filesystem interpretation belongs below the parser.

## 15. Positional argument invariant

Once grammar expects data, keyword-looking text is data:

```text
storage use close
    -> STORAGE_USE {name:"close"}

get delete
    -> SOURCE_GET {source:"delete"}
```

Minimum-prefix expansion applies only in keyword positions.

## 16. Canonical echo invariant

Accepted abbreviations normalize before execution/help echo:

```text
r 17              -> rule 17
r c 17            -> rule comment 17
f s 8             -> function source 8
b p father        -> base predicate father
v o x d, y a      -> values order x desc, y asc
so t 42           -> solution tree 42
w a 0             -> when accept 0
t s               -> transaction start
st u close        -> storage use close
```

Canonical help/echo uses full accepted spelling and never preserves abbreviated command identity as a separate operation.

## 18. Closure

This matrix is normative for future `kanger-command` parser tests.

It closes parser behavior for:

- canonical and abbreviated forms;
- keyword-position prefix resolution;
- direct object IDs;
- zero-based hypothesis indexes;
- comma-separated multi-key Values sorting;
- quoted arguments and rule-comment free tails;
- Browser/UI source arity;
- ambiguity and retired-vocabulary rejection.

Runtime object existence, transaction/storage preconditions and result-field validation are intentionally downstream concerns.
