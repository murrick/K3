# KANGER 3.7.0.1 — Command/UI design baseline

Status: DESIGN BASELINE / DOCUMENTATION ONLY  
Date: 2026-08-07  
Base release: `release/3.5.2`  
Base commit: `9c8b7dd2c9ef347cea6af6a6faef9cfa48030306`  
Integration line: `develop/3.7.0`  
Scoped branch: `ui/3.7.0.1-command-ui-baseline`

## Purpose

This stage establishes the normative interaction and command-language baseline for the next KANGER UI/Console engineering line.

It does **not** redesign KANGER semantics, transaction semantics, storage semantics, source dirty-state semantics, Server 0.18 lifecycle behavior, or the accepted `release/3.5.2` runtime. It introduces no production-code change.

The immediate goal is to preserve the useful character of the existing UI while removing duplicated command semantics across Console, Browser and future interfaces.

## 1. Primary UI geometry is an invariant

The existing KANGER screen organization is retained rather than replaced by a generic dashboard layout.

```text
+-------------------------------------------------------------------+
| LEFT                    CENTER                         RIGHT       |
|                                                                   |
| informational /        command console               optional     |
| semantic KANGER        and command composition       technical    |
| structure                                            panel        |
|                                                      collapsible  |
|                         ------------------------------------------ |
|                         LOG / RESULTS                              |
|                         lower working area                         |
+-------------------------------------------------------------------+
```

Normative interpretation:

- **center** remains the primary command console and command-composition surface;
- **left** remains the main informational / semantic KANGER structure;
- **bottom** remains the principal log and result area;
- **right** may be added as an auxiliary collapsible technical/administrative panel;
- the right panel must not displace the semantic structure or turn the application into a dashboard.

Possible future technical-panel content includes runtime memory/heap, CPU, threads, uptime, session generation/state, active operation and latency, transaction/Mind diagnostics, storage physical diagnostics/WAL/cache/I/O, quotas and limits, product identities, health and readiness. The exact inventory is intentionally deferred.

## 2. Live text remains the primary interaction pattern

The existing UI character is based on live textual links and clickable semantic objects rather than a button-heavy control panel. That interaction style is preserved.

A visual control is primarily a projection of KANGER objects and command language, not an independent action vocabulary.

The redesign must not replace the console-oriented interaction model with conventional dashboard widgets merely for visual modernization.

## 3. Screen-to-command composition invariant

The visible KANGER state is not only output. It is also a palette for composing the next command.

A click on a semantic object or statement:

```text
visible semantic object
        -> textual command-language representation
        -> insertion into command input
        -> user may continue editing/composing
        -> explicit execution only after user approval
```

A click does **not** implicitly execute the resulting command.

Target editing behavior:

- insert at the current caret position;
- if command-input text is selected, the inserted fragment may replace the selection;
- preserve the current partially entered command;
- restore input focus after insertion;
- allow repeated clicks on visible objects to construct a compound command.

Example:

```text
user types:      ? owns(
clicks John:     ? owns(John
clicks Account17:? owns(John,Account17
user finishes:   ? owns(John,Account17);
user executes explicitly
```

The governing interaction principle is:

> **screen -> command composition -> explicit execution**

The mouse assists writing the command. It does not take ownership of the decision to execute it.

This principle also provides a uniform safety boundary for destructive and transactional operations: clicking an object or action projection prepares an operation, while explicit user execution remains separate.

## 4. Two classes of live link

The UI may expose two related kinds of live textual interaction.

### 4.1 Semantic insertion

A statement, value, term, rule, predicate or other semantic object inserts its command-language representation at the current command-line caret.

It does not execute.

### 4.2 Command/action projection

A source, database or other operational object may compose a complete or partial canonical command.

Examples:

```text
click source foo.k  -> compose: get foo.k
click storage demo  -> compose: storage use demo
```

These projections also do not execute automatically by default.

Both classes therefore converge on one interaction surface: the command line.

## 5. One command language across all interfaces

Console, Browser UI and future interfaces must accept the same KANGER command syntax.

The current situation contains duplicated command knowledge in several independent surfaces:

```text
kanger-console Console.java
    -> first-character dispatcher
    -> interactive prompts
    -> Console-specific result text

Browser console.html
    -> independent string parser / switch
    -> independent commandGet/Put/Delete/Use/... functions

Browser operation.js
    -> independent read/mutation classification
    -> independent operation-name classification

Browser workspace.js
    -> independent knowledge of source-name vs storage-name arguments

Server QueryProcessor
    -> independent command/query dispatch
    -> independent command help and result shaping
```

This duplication has already produced interface drift.

The 3.7.0 line therefore adopts **one command language** and one neutral command processor, with presentation/transport adapters around it.

## 6. Canonical syntax, abbreviations and aliases

The command language is case-insensitive in keyword positions.

The normative parsing rule is:

> A command token may be abbreviated to its minimum unambiguous leading prefix in the relevant grammar position.

There is no fixed abbreviation length. Ambiguous abbreviations are rejected rather than guessed.

Aliases, if later retained for migration/usability, must resolve to the **same canonical command and implementation**, not become parallel command paths.

The final vocabulary, direct object forms, storage ambiguity rule and prefix table are normative in:

```text
docs/ui/3.7.0.1-canonical-command-registry.md
```

## 7. Shared command processor ownership

The canonical command language has one neutral owner:

```text
kanger-command/
    src/org/kanger/command/...
```

The module owns parser/registry concerns only:

```text
CommandRegistry
CommandParser
canonical CommandIntent model
parsed arguments/results/errors
minimum-prefix resolution
lexical/quoting rules
canonical echo/help metadata
```

Its boundary is:

```text
raw command text
        -> kanger-command
        -> canonical intent + arguments
        -> execution adapter
```

It does **not** execute KANGER operations and must not depend on `IMind`, Console, Server transport, Browser UI, concrete storage or source-filesystem implementation.

Dependency direction:

```text
kanger-console -> kanger-command
kanger-server  -> kanger-command
future clients -> kanger-command
```

KANGER Core must not depend on `kanger-command`.

The current repository uses sibling source roots rather than a strict Maven multi-module reactor; therefore the accepted later implementation target is the sibling source module `kanger-command/src`, added to the aggregate/root and standalone Server builds. A separate published Maven artifact is not required by this decision.

Normative ownership contract:

```text
docs/ui/3.7.0.1-command-processor-ownership.md
```

## 8. Preserve qualified 3.5.2 browser foundations

The new design should reuse rather than casually discard the qualified Browser foundations established in 3.5.2:

- serialized authoritative mutations;
- generation-aware reads;
- coherent semantic snapshot publication;
- canonical post-operation workspace projection;
- source/storage name canonicalization at the trust boundary;
- typed failure/error taxonomy;
- trusted rendering and containment boundaries;
- parent-owned session authority.

The design task is to replace duplicated historical interface semantics around these foundations, not to regress the protections already qualified in 3.5.2.

## 9. Source `.k` lifecycle extension

Canonical source command operations are:

```text
get <source>
put <source>
delete <source>
```

Browser/UI additionally provides transport actions:

```text
upload
download
```

`upload` / `download` are not KANGER commands.

`download` obtains the actual `.k` source file from the server rather than copying editor text through the clipboard.

`upload` is not a blind filesystem write. Its intended semantics are atomic source ingest:

```text
receive uploaded source bytes/name
        -> create provisional source input
        -> compile/admit in a provisional transaction context
        -> collision / consistency check against current context
        -> reject: rollback/discard provisional state, persist nothing
        -> accept: persist source under the uploaded filename
```

Source deletion remains distinct from storage `drop`.

The historical Mind source dirty marker / `*` remains authoritative existing behavior.

For terminal self-sufficiency, deferred Console convergence preserves bare `get`, `put`, `delete` as read-only source-list conveniences only.

## 10. Retained UI cleanup Heap

The following accepted non-release-blocking items remain in scope for later 3.7.0 stages:

- explicit confirmed server-side session-loss indication and recovery/reconnect UX;
- removal/suppression of empty Statement branches after rollback;
- suppression of empty semantic section headers;
- separation of logical database contents from physical storage diagnostics in normal presentation;
- optional collapsible technical/admin diagnostics panel;
- consistent source upload/download/delete lifecycle;
- convergence of Console, Browser and future interfaces through `kanger-command`.

`erase` semantics are explicitly **not** changed in this design baseline.

## 11. Deliberate exclusions

This stage does not:

- change Core logical semantics;
- change transaction/storage lifecycle semantics;
- change DUMB format or storage topology;
- change Server 0.18 production behavior;
- redesign `erase`;
- replace the historical source dirty mechanism;
- implement `kanger-command` runtime code yet;
- change the primary UI geometry;
- convert the interface into a button-oriented dashboard;
- mix project genesis/history into operational status or recovery documents.

## 12. Closed design contracts and next sequence

The following are now closed in 3.7.0.1:

```text
canonical registry          CLOSED
command vocabulary          CLOSED
lexical/quoting contract    CLOSED
minimum-prefix table        CLOSED
parser conformance matrix   CLOSED
command processor ownership CLOSED
```

The remaining design step before runtime implementation is narrow:

1. map canonical intents onto current Server/runtime operations and transport responses;
2. preserve the accepted boundary into a dedicated command-processor implementation artifact;
3. later execute the separately recorded Java Console flash-back/convergence;
4. adopt the same processor in Server-backed Browser/UI and future clients.

Only after these contracts are stable does runtime implementation begin.

## 13. Qualification boundary

`3.7.0.1` is successful when the design baseline is coherent enough that later implementation cannot accidentally create separate Console, Browser and Server command languages.

At this checkpoint there is intentionally no runtime delta and therefore no production deployment or release decision.
