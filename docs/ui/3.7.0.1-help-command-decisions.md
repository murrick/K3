# KANGER 3.7.0.1 — `help` command decisions

Status: **ACCEPTED DESIGN DECISION / DOCUMENTATION ONLY**

Reference runtime: accepted `release/3.5.2`.

No runtime behavior is changed by this document.

## 1. Authority

Canonical command help is generated from the same `CommandRegistry` metadata that defines and parses the command language.

The registry is therefore the single authority for:

```text
command grammar
canonical intent
help grouping
short description
argument descriptions
presentation order
```

The help renderer must not maintain a second independently written command vocabulary.

## 2. Metadata model

Each canonical command production should expose enough metadata to render useful help without duplicating syntax text manually.

Conceptually:

```text
CommandDefinition
    intent
    grammar
    helpSection
    summary
    argumentDescriptions
    displayOrder
```

`grammar` is authoritative for usage text. A separate hand-maintained `usage` string should not be required when the grammar can render the canonical syntax directly.

Example conceptually:

```text
intent: RULE_TREE
grammar: rule tree <id>
section: RULE
summary: Show compiled structural tree for a rule
arguments:
    id: Rule identifier
```

## 3. Rendering

The canonical renderer groups accepted productions by semantic help section and prints their grammar-derived syntax plus descriptions.

Conceptually:

```text
CommandRegistry
      -> HelpRenderer
      -> group by helpSection
      -> grammar-derived syntax
      -> summary / argument descriptions
```

This allows one registry change to update parsing and help together.

## 4. Current canonical command

The 3.7.0.1 command grammar remains:

```text
help
```

No additional `help <topic>` syntax is introduced by this decision.

The metadata model may support filtered/topic help later without forcing a redesign, but that future grammar must be accepted separately.

## 5. Client use

Registry metadata may also be used by presentation clients for discoverability, semantic command composition, contextual hints, menus or future completion.

That does not make the client a command parser. Canonical parsing remains owned by `kanger-command`.

Accepted authority chain:

```text
registry defines
parser interprets
help describes
UI discovers
```

## 6. Historical help

Historical Console/Server help text remains implementation evidence only. It must not be used as canonical authority because it contains retired or compatibility vocabulary.

The future `help` intent should therefore terminate in the command layer / registry renderer rather than delegate to the legacy `QueryProcessor.processHelp()` or a copied Console help block.

## 7. Design principle

- one grammar authority;
- no manually synchronized second command list;
- descriptions live beside the production they describe;
- parser and help cannot drift by ordinary command addition/removal;
- presentation may consume registry metadata but never redefine command semantics.
