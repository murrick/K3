# KANGER 3.7.0.1 — System/admin command decisions

Status: **ACCEPTED DESIGN DECISION / DOCUMENTATION ONLY**

Reference runtime: accepted `release/3.5.2`.

No runtime behavior is changed by this document.

## 1. Accepted ordinary system/session commands

For the 3.7.0.1 command-language baseline, retain only the ordinary system/session commands with clear operator meaning:

```text
erase
help
quit
```

No additional `system` namespace is introduced.

## 2. `erase`

```text
erase
```

erases the current workspace according to the existing qualified runtime semantics.

The command word is historical, already present across current interfaces, and requires no additional namespace such as `workspace erase` or `system erase`.

Any interactive confirmation is presentation policy and not part of canonical command identity.

## 3. `help`

```text
help
```

remains the canonical help entry point.

Future help content should be derived from accepted command-registry metadata rather than maintained as a second independent command vocabulary.

No broader help grammar is required at this baseline stage.

## 4. `quit`

```text
quit
```

remains the canonical explicit session termination command.

Any confirmation required because of transaction/storage/dirty state is presentation policy layered over the same command identity and does not create a second grammar.

## 5. Historical `options` family is not carried forward

The historical Java Console `options` command is **not** part of the 3.7.0.1 canonical UI command language.

Do not preserve it merely because it once grouped miscellaneous runtime toggles, diagnostics and tests.

Known historical contents are intentionally decomposed or retired:

```text
options order ...
    -> values order <variable> [asc|desc]

options log ...
    -> Console-local xplain mode on|off

options memory
options debug ...
options values ...
options status ...
options diagnostics/snapshot ...
qualification/test invocation
    -> not carried into the ordinary 3.7.0.1 UI command language
```

The absence of a replacement is intentional.

If a concrete diagnostic or operator need reappears later, it must be introduced as an independently justified command, read, panel affordance or developer/operator tool. Do not recreate a generic settings/options bucket in anticipation of hypothetical needs.

## 6. UI/admin boundary

The current UI baseline therefore does not require a general settings/options command family.

Technical information that already has a natural persistent UI projection may remain a presentation concern. Developer qualification/test paths remain developer tooling rather than ordinary user command vocabulary.

The accepted baseline is deliberately minimal:

```text
SYSTEM / SESSION COMMANDS
    erase
    help
    quit

NO CANONICAL
    options
    settings
    diagnostics   # as a generic bucket
```

This does not forbid future narrowly defined diagnostics; it forbids carrying forward an undifferentiated historical container without a demonstrated consumer.

## 7. Console follow-up

The later Console flash-back/convergence must remove the historical `options` family from the canonical command surface while preserving any still-required Console-local behavior through the already accepted specific homes (for example `values order` and `xplain mode`).

This is deferred implementation work and must not interrupt the current 3.7.0.1 UI/design pass.
