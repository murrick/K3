# KANGER 3.7.0.1 — Storage command decisions

Status: **ACCEPTED DESIGN DECISION / DOCUMENTATION ONLY**

Reference runtime: accepted `release/3.5.2`.

No runtime behavior is changed by this document.

## 1. Why `storage` is a real command family

Unlike source-file operations (`get`, `put`, `delete`), storage has a persistent operator-visible context: one storage may be currently selected/open.

Therefore the `storage` namespace expresses real ownership and state rather than decorative grouping.

The accepted semantic hierarchy is:

```text
storage
storage use <name>
storage close
storage drop <name>
storage reindex <name>
```

## 2. Bare `storage`

```text
storage
```

is the read-only storage status/list projection.

It should expose the available storages and identify the currently used/open storage when one exists.

This replaces the need for a separate historical `used` command and avoids overloading argument-less `use` with status/list/select behavior.

## 3. `storage use <name>`

```text
storage use <name>
```

selects/opens the named storage according to the existing qualified storage lifecycle contract.

The storage name is explicit in the canonical command.

## 4. `storage close`

```text
storage close
```

closes the current storage.

No storage name argument is needed because close is intrinsically an operation on the current storage context.

## 5. `storage drop <name>`

```text
storage drop <name>
```

drops the explicitly named physical storage.

The name is required in canonical syntax. Historical behavior that implicitly targets the current storage when the argument is omitted is not retained as canonical grammar.

Because `drop` is destructive, explicit object naming is preferable to context-dependent shorthand.

## 6. `storage reindex <name>`

```text
storage reindex <name>
```

rebuilds/reindexes the explicitly named physical storage.

The name is required in canonical syntax. Historical implicit-current behavior is not retained as canonical grammar.

Historical terms:

```text
index
pack
```

are implementation/legacy vocabulary and are not canonical. The accepted operator word is:

```text
reindex
```

## 7. Historical vocabulary normalization

The accepted mapping is:

```text
used
    -> storage

use <name>
    -> storage use <name>

close
    -> storage close

drop <name>
    -> storage drop <name>

index <name>
pack <name>
reindex <name>
    -> storage reindex <name>
```

Any compatibility aliases are a later parser/migration decision and must map one-to-one to the same canonical operations.

## 8. Complete accepted family

For 3.7.0.1 the storage command family is complete at this level:

```text
storage
storage use <name>
storage close
storage drop <name>
storage reindex <name>
```

The family contains exactly five operator intents:

```text
status/list
use
close
drop
reindex
```

No separate `used`, `index`, or `pack` canonical command is required.

## 9. Console follow-up

The historical Console already implements the underlying storage operations with older top-level vocabulary and context-dependent shorthand.

The deferred Console flash-back must converge those operations onto the accepted storage family and common minimum-unique-prefix parser.

This is deferred implementation work and must not interrupt the current 3.7.0.1 UI/design pass.
