# KANGER 3.7.0.1 — Canonical command registry draft

Status: DESIGN DRAFT / NO RUNTIME AUTHORITY YET  
Reference runtime: `release/3.5.2` at `9c8b7dd2c9ef347cea6af6a6faef9cfa48030306`

## 1. Purpose

This document is the first canonicalization pass over the current Console, Browser and Server command surfaces.

It is intentionally conservative. It attempts to preserve useful historical KANGER interaction before deciding which compatibility spelling may later be deprecated.

No command in this document is a runtime change yet.

## 2. Parsing principles

### 2.1 Case

Command words are case-insensitive.

```text
transaction commit
TRANSACTION COMMIT
Tra Com
```

must resolve identically when the abbreviated tokens are unambiguous.

### 2.2 Minimum unique prefix

A keyword may be abbreviated to its shortest unambiguous leading prefix in the relevant grammar position.

This preserves the historical/FoxBase-style interaction where three or four characters are normally enough without hard-coding an arbitrary length.

The parser must reject ambiguity.

```text
CO      -> COMMIT, if COMMIT is the only CO... keyword in that grammar position
CR      -> CREATE, if CREATE is the only CR... keyword
C       -> reject if CLOSE / COMMIT / CREATE are all valid there
```

Exact full keyword matches take precedence over prefix expansion. This matters for pairs such as `USE` and `USED` if both remain accepted spellings.

### 2.3 Aliases

An alias is syntax only.

Aliases resolve during parsing to the same canonical command ID as the long form and cannot own separate execution semantics.

Example target:

```text
transaction commit
commit
```

both parse as:

```text
TX_COMMIT
```

### 2.4 KANGER logical language remains distinct

Logical expressions beginning with KANGER language operators are not ordinary shell words and must continue into the language compiler/query path.

The command parser must not reinterpret logical syntax as UI commands.

### 2.5 Parsing and execution are separate

```text
text
 -> parse
 -> canonical command + typed arguments
 -> lifecycle/precondition validation
 -> execution
 -> structured result/state projection
 -> presentation
```

Live-link composition enters at the `text` stage and does not bypass parsing or explicit execution.

## 3. Command classes

The registry uses four high-level classes.

```text
USER_READ
    explicit user request to inspect semantic/workspace state

USER_MUTATION
    explicit user operation that may change Mind/workspace/source/storage state

SESSION
    session-level lifecycle operation

DIAGNOSTIC
    technical/runtime/operator inspection or configuration
```

`EDITOR_ACTION` is deliberately not part of the command registry. Caret insertion, history recall and live-link composition are local editor behaviors that create command text but do not execute commands.

## 4. Canonical command families

The names below are first-pass canonical candidates. Compatibility aliases are listed separately.

### 4.1 General

| Canonical ID | Canonical syntax | Class | Mutation | Notes |
|---|---|---|---:|---|
| `HELP` | `help [topic]` | USER_READ | no | Help should ultimately be generated from registry metadata rather than hand-maintained copies. |
| `QUIT` | `quit` | SESSION | yes | Explicit session termination. UI may require presentation confirmation depending on dirty/transaction state. |

### 4.2 Semantic inspection

| Canonical ID | Canonical syntax | Class | Mutation | Current capability mapping |
|---|---|---|---:|---|

| `VIEW_BASE` | `base [selector...]` | USER_READ | no | Console `B`; Server predicates/statements reads; Browser statements view. |
| `VIEW_FUNCTIONS` | `functions [selector...]` | USER_READ | no | Console `F`; Server `query.functions`; Browser functions view. |
| `VIEW_VALUES` | `values` | USER_READ | no | Console `V`; Server `query.results`; Browser results view. |
| `VIEW_SOLUTIONS` | `solutions [selector...]` | USER_READ | no | Console `S`; Server `query.solutions`; Browser solutions view. |

```text
results      -> VIEW_VALUES
hypothesis   -> VIEW_HYPOTHESES
explain      -> VIEW_EXPLANATION
statements   -> VIEW_BASE or a narrower BASE projection
```

These names currently appear in Browser/Server transport or presentation vocabulary. Whether all should be accepted as command-line aliases is still a design decision.

### 4.3 Transaction

| Canonical ID | Canonical syntax | Class | Mutation | Lifecycle meaning |
|---|---|---|---:|---|
| `TX_STATUS` | `transaction` | USER_READ | no | Show current transaction level/state. |
| `TX_START` | `transaction start` | USER_MUTATION | yes | Create child transaction. |
| `TX_COMMIT` | `transaction commit` | USER_MUTATION | yes | Commit child; at root/open storage preserve qualified checkpoint semantics. |
| `TX_ROLLBACK` | `transaction rollback` | USER_MUTATION | yes | Roll back current child transaction. |

Compatibility aliases:

```text
create        -> TX_START       [current Browser spelling]
start         -> TX_START       [candidate convenience alias]
commit        -> TX_COMMIT
rollback      -> TX_ROLLBACK
transaction create -> TX_START  [current Browser compound spelling]
```

The canonical long form currently prefers `transaction start` because that is the historical Java Console help vocabulary. `create` remains a required compatibility spelling at least during migration.

No alias may create a second implementation path.

### 4.4 Source repository

| Canonical ID | Canonical syntax | Class | Mutation | Notes |
|---|---|---|---:|---|
| `SOURCE_GET` | `get [source]` | USER_MUTATION | yes | Loads/compiles selected source into current workspace semantics. Empty argument may request/select available sources. |
| `SOURCE_PUT` | `put [source]` | USER_MUTATION | yes | Persists current authorial source projection. Historical Console `put <n>` comment-edit overload requires separate treatment below. |
| `SOURCE_DELETE` | `delete [source]` | USER_MUTATION | yes | Exists Browser/Server, absent from top-level Java Console. |
| `SOURCE_DOWNLOAD` | `download [source]` | USER_READ | no | New file-transfer surface: obtain actual `.k` file bytes. |
| `SOURCE_UPLOAD` | `upload <source-transfer>` | USER_MUTATION | yes | New atomic semantic ingest; never blind filesystem overwrite. |

Atomic upload contract:

```text
name + bytes
 -> canonicalize/validate source identity
 -> provisional compile/admission in child/provisional Mind
 -> collision/consistency result
 -> reject: rollback/discard, persist nothing
 -> accept: persist exactly under accepted uploaded filename
```

Open issue: the historical Java Console overload:

```text
put <numeric-rule-id>
```

edits rule comments rather than naming a source. This is semantically unrelated to `SOURCE_PUT` and should not survive merely because both historically begin with `P`. It requires a dedicated canonical command or explicit removal decision after usage review.

Candidate future form, not yet accepted:

```text
comment rule <id>
```

### 4.5 Database/storage

| Canonical ID | Canonical syntax | Class | Mutation | Lifecycle notes |
|---|---|---|---:|---|
| `DB_USE` | `use [database]` | USER_MUTATION / contextual read | yes when named | Open/create selected database and perform the qualified workspace-baseline insertion contract when applicable. |
| `DB_USED` | `used` | USER_READ | no | Show current active database/workspace storage state. Whether this survives as a separate command is open. |
| `DB_CLOSE` | `close` | USER_MUTATION | yes | Must retain explicit storage-lifecycle preconditions. |
| `DB_DROP` | `drop [database]` | USER_MUTATION | yes | Destructive physical storage lifecycle operation. |
| `DB_REINDEX` | `reindex [database]` | USER_MUTATION | yes | Current Browser/Server term. |

Compatibility aliases:

```text
index [database] -> DB_REINDEX  [historical Java Console help]
pack  [database] -> DB_REINDEX  [historical implementation terminology]
```

`use` without an argument currently has different presentation behavior depending on context/interface: show current database, list available databases or initiate selection. The registry must eventually define this precisely rather than leaving it to each UI.

### 4.6 Workspace

| Canonical ID | Canonical syntax | Class | Mutation | Notes |
|---|---|---|---:|---|
| `WORKSPACE_ERASE` | `erase` | USER_MUTATION | yes | Existing semantics frozen for 3.7.0 baseline. Do not redesign until historical motivation is recovered. |

### 4.7 Diagnostics/options

The historical Java Console `options` tree contains both user presentation preferences and technical diagnostics. It must not automatically become one undifferentiated shared command family.

Current Console capabilities include:

```text
options order <var> [asc|desc]
options debug [yes|no]
options values [yes|no]
options status [yes|no]
options log [yes|no]
options memory
options diagnostics/snapshot path
qualification/test invocation path
```

First-pass classification:

```text
result ordering / presentation toggles
    -> client/workspace preference candidates

memory / runtime snapshot
    -> DIAGNOSTIC reads, natural candidates for collapsible technical panel

qualification/test invocation
    -> developer/operator surface; not ordinary end-user command language without explicit decision
```

No canonical syntax is frozen for these in this stage.

## 5. Selector grammar retained for semantic reads

The historical Console exposes useful selector concepts that should not be lost even if their parser is replaced.

### RULES

Current concepts:

```text
rules
rules produced
rules all
rules level [n]
rule <id>
rules tree
rule tree <id>
```

Target registry should model selectors structurally rather than first-letter branching:

```text
mode = primary | produced | all
level = optional transaction level
id = optional rule id
tree = boolean
```

The final user syntax may preserve singular/plural forms as aliases if useful.

### BASE

Current concepts:

```text
base
base predicates
base <predicate-name>
base <predicate-id>
base tree
base tree <statement-id-or-predicate>
```

Target structured selector candidates:

```text
predicate = optional name/id
statement_id = optional id
predicates_only = boolean
causes/tree = boolean
```

### FUNCTIONS

Current concepts:

```text
functions
function <id>
functions source
functions source <id>
```

Target selector:

```text
id = optional
include_source = boolean
```

### SOLUTIONS

Current concepts:

```text
solutions
solution <id>
solutions tree
solutions tree <id>
```

Target selector:

```text
id = optional
tree/causes = boolean
```

### XPLAIN

Current Java Console additionally writes explanation output to a local file. This is not automatically the same operation as Browser semantic explanation display.

The future registry should separate:

```text
VIEW_EXPLANATION
EXPORT_EXPLANATION
```

rather than overloading one parser branch with both display and file I/O.

## 6. Top-level prefix design — first calculation

The exact minimum prefix set cannot be frozen until the final accepted keyword/alias registry is closed. Still, the current candidate vocabulary demonstrates the desired behavior.

Examples:

```text
HELP          -> H...      unique among current candidate H words
BASE          -> B...
FUNCTIONS     -> F...
GET           -> G...
PUT           -> P...
QUIT          -> Q...
TRANSACTION   -> T...
VALUES        -> V...
XPLAIN        -> X...

CLOSE         -> CL...     because COMMIT / CREATE aliases may also start with C
COMMIT        -> CO...
CREATE        -> CR...

DELETE        -> DE...
DOWNLOAD      -> DO...
DROP          -> DR...

LIST          -> LI...     if LOG becomes a user keyword
LOG           -> LO...

REINDEX       -> REI...    if RESULTS is accepted as a top-level alias
RESULTS       -> RES...
RULES         -> RU...

UPLOAD        -> UP...
USE           -> exact USE; prefix rules must account for USED
USED          -> USED or other unambiguous form
```

These are illustrations only. The registry generator/parser should compute minimum unique prefixes from the accepted vocabulary rather than hard-code them manually.

## 7. Execution metadata required by the registry

Each executable canonical command should eventually expose at least:

```text
id
canonical words
aliases
argument grammar
class: USER_READ | USER_MUTATION | SESSION | DIAGNOSTIC
scope: LOGICAL | TRANSACTION | SOURCE | STORAGE | WORKSPACE | SESSION | DIAGNOSTIC
mutation: boolean
destructive: boolean
lifecycle preconditions
result/state projection contract
help metadata
current transport mapping
```

Additional metadata may be justified later for completion, authorization, quotas or UI affordances, but must not be invented before a real consumer requires it.

## 8. Presentation confirmation is not command identity

The current Console embeds confirmations inside helpers such as quit/drop/erase. The future design should distinguish:

```text
canonical operation semantics
```

from:

```text
presentation policy asking the human to confirm execution
```

A Browser live link, terminal Console and automated API client may require different confirmation UX while still executing the same canonical command.

This does **not** imply that lifecycle preconditions or server-side authorization move into the UI. Safety-critical validity remains enforced at the execution boundary.

## 9. Live-link mapping into the registry

Live links must compose command-language text or semantic fragments; they do not call execution methods directly.

Examples:

```text
source foo.k
    action projection -> insert/compose `get foo.k`

database demo
    action projection -> insert/compose `use demo`

statement person(John, engineer)
    semantic insertion -> insert statement text at caret

value John
    semantic insertion -> insert `John` at caret
```

The editor then owns caret/selection behavior and the user explicitly executes the resulting text.

This guarantees that mouse interaction and typed interaction converge through the same parser.

## 10. Transport mapping principle

The command language does not require the Browser to send raw text over HTTP forever.

A valid architecture is:

```text
Browser command editor text
 -> shared/canonical parser
 -> command ID + typed arguments
 -> transport adapter
 -> server execution
```

and equivalently:

```text
Java Console text
 -> same parser semantics
 -> command ID + typed arguments
 -> local execution adapter
```

The JSON/HTTP representation is transport, not a second command language.

Current `context=command/query/history` and parameter names therefore become compatibility/protocol mappings to audit, not the normative human grammar.

## 11. Decisions still intentionally open

The following are not frozen by this draft:

1. exact package/module owning parser and registry;
2. whether `VIEW_BASE` should retain the historical word `base` or expose `statements` as a primary synonym;
3. whether `list` remains the primary hypothesis-view command or `hypothesis` becomes canonical;
4. final treatment of historical `put <rule-id>` comment editing;
5. exact semantics of argument-less `use`, `get`, `put`, `delete`, `drop`, `reindex` in non-interactive clients;
6. whether `used` survives or is replaced by a clearer storage-status read;
7. exact canonical spelling `start` vs `create` for transaction creation after compatibility review;
8. whether explanation/log export belongs in ordinary command language or technical tooling;
9. canonical diagnostic/admin command vocabulary;
10. final accepted aliases, after which minimum unique prefixes can be computed exactly.

These are now explicit design questions rather than accidental differences between interfaces.

## 12. Next implementation-independent task

Before touching runtime code, close the open registry questions using three criteria:

```text
historical KANGER interaction worth preserving
semantic clarity of the command language
one-to-one mapping to existing qualified execution contracts
```

Then write parser conformance examples that must produce identical canonical command IDs from Console and Browser input. Only after those examples are accepted should parser/dispatcher code be introduced.
