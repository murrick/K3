# KANGER 3.7.0.1 — Canonical command syntax decisions

Status: ACCEPTED DESIGN BASELINE / NO RUNTIME AUTHORITY YET  
Reference runtime: `release/3.5.2` at `9c8b7dd2c9ef347cea6af6a6faef9cfa48030306`

## 1. Scope

This document records accepted syntax decisions for the unified KANGER Console / Browser / future UI command language.

It does not change Core syntax, KANGER logical operators, runtime execution semantics or production behavior.

## 2. Core-language boundary

The existing KANGER logical-language operators, including `=` and `?`, are outside the UI command-language redesign.

They belong to the KANGER language/compiler/query path and must not be reinterpreted as command-shell syntax or repurposed for options, assignment, selectors or UI metadata.

The UI command parser must hand logical expressions to the existing language path without introducing competing meanings for these tokens.

## 3. Command dialogue, not shell syntax

KANGER uses a command dialogue rather than a Unix-style command shell.

Therefore command syntax should consist of meaningful words and arguments only.

Do not introduce shell artifacts such as:

```text
--all
--tree
--level
-name
/value
```

Prefer natural command phrases:

```text
rules all
rules level 2
rules tree
options memory
```

The grammar itself should express the operation. Extra punctuation must not be required merely to distinguish options.

## 4. Canonical semantic order

The canonical command phrase follows semantic hierarchy:

```text
WHERE -> WHAT TO DO -> WITH WHAT
```

or grammatically:

```text
<group> [<verb>] [<arguments...>]
```

Examples:

```text
storage use demo
storage drop demo
storage reindex demo

source get foo.k
source put foo.k
source delete foo.k
source download foo.k

transaction start
transaction commit
transaction rollback

rule comment 123
```

This ordering is normative for the long canonical form.

It makes command ownership explicit and removes ambiguity caused by historically overloaded top-level verbs.

## 5. Bare group command

A bare command group is an official read-only status/context command.

Examples:

```text
source
storage
transaction
rule
```

The exact projection for each group is defined by that group's registry entry, but the general rule is fixed:

```text
<group>
```

must never mutate state merely because the action word is omitted.

Typical intent:

```text
source
    -> current source context and/or available sources

storage
    -> current storage context and/or available databases

transaction
    -> current transaction level/state
```

This gives the command language a regular way to ask "where am I / what is available here?" without inventing separate status verbs for every subsystem.

## 6. Aliases are usability syntax only

Aliases are allowed only when they improve frequent interactive use.

They are not alternate semantics and they do not own execution paths.

Examples of acceptable convenience aliases:

```text
get foo.k
    -> source get foo.k

put foo.k
    -> source put foo.k

use demo
    -> storage use demo

commit
    -> transaction commit

rollback
    -> transaction rollback
```

Every alias must resolve to exactly one canonical command before execution.

## 7. Alias ambiguity is forbidden

A convenience alias must remain semantically unambiguous for all valid argument values.

The parser must never infer command identity from the lexical type of an argument when the same alias could mean unrelated operations.

The historical overload:

```text
put foo.k
    -> save source

put 123
    -> edit comment of rule 123
```

is rejected as a future canonical design because `123` is also a perfectly valid possible source filename.

The meaning of `put` must not depend on guessing whether its argument "looks numeric".

Accepted direction:

```text
source put 123
```

means source persistence for source name `123`.

Rule-comment editing receives its own semantically explicit command:

```text
rule comment 123
```

No `put` alias for rule comments is planned in the canonical language.

General invariant:

> one alias -> one canonical command, independent of argument spelling.

## 8. Prefix abbreviations

Command words are case-insensitive and may use minimum unique leading prefixes in their grammar position.

Examples, once the final vocabulary makes them unique:

```text
sto use demo
sou get foo.k
tra com
ru com 123
```

The exact minimum length is computed from the accepted vocabulary; there is no fixed "three characters" or "four characters" rule.

Ambiguous prefixes are rejected rather than guessed.

Full exact keywords always remain valid.

## 9. Long form and short form relationship

Canonical long form expresses semantic hierarchy:

```text
storage use demo
source put foo.k
transaction commit
rule comment 123
```

Frequent short forms may exist for usability:

```text
use demo
put foo.k
commit
```

but only when they preserve one-to-one meaning.

The long form is therefore the normative representation for documentation, help metadata, canonical echo, testing and command identity.

The short form is input convenience.

## 10. No implicit execution from UI interaction

This syntax design preserves the accepted interaction invariant:

```text
screen -> command composition -> explicit execution
```

Live links and semantic objects compose or insert command text at the caret.

They do not execute a command directly.

A live storage link may compose:

```text
storage use demo
```

A live source link may compose:

```text
source get foo.k
```

A visible semantic statement/value may insert its KANGER-language text into the partially composed command/query.

Execution remains an explicit user action.

## 11. Consequences for current registry questions

The following design questions are now closed:

1. `=` and `?` are not UI command syntax and are not redesigned here.
2. Unix-style option markers are rejected; use meaningful command words.
3. canonical long-form order is `<group> <verb> <arguments...>`.
4. bare `<group>` is a read-only status/context operation.
5. aliases are usability-only parser mappings.
6. aliases must be one-to-one and independent of argument lexical form.
7. historical `put <rule-id>` overload is not retained as canonical syntax.
8. rule comment editing uses an explicit `rule comment <id>` family command.
9. source name `123` must remain legal and unambiguous under `source put 123` / `put 123` when `put` is the SOURCE_PUT alias.
10. minimum-unique-prefix abbreviation remains the accepted abbreviation mechanism.

## 12. Remaining syntax decisions

Still open for discussion before parser implementation:

- final group vocabulary for semantic views (`base` vs `statements`, `list` vs `hypothesis`, etc.);
- `transaction start` vs `transaction create` as the canonical long spelling;
- canonical source status projection for bare `source`;
- canonical storage status projection for bare `storage`, and whether historical `used` remains only as compatibility syntax;
- canonical singular/plural forms for semantic object groups (`rule/rules`, `solution/solutions`, etc.);
- exact argument grammar and quoting rules for names containing whitespace or reserved words;
- canonical diagnostic/admin group vocabulary for the future collapsible technical panel.

These remaining questions must preserve the accepted principles above.
