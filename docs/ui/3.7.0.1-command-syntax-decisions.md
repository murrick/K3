# KANGER 3.7.0.1 — Canonical command syntax decisions

Status: ACCEPTED DESIGN BASELINE / DOCUMENTATION ONLY / CLOSED  
Reference runtime: `release/3.5.2` at `9c8b7dd2c9ef347cea6af6a6faef9cfa48030306`

## 1. Scope

This document records accepted syntax decisions for the unified KANGER Console / Browser / future UI command language.

It does not change Core syntax, KANGER logical operators, runtime execution semantics or production behavior.

## 2. Core-language boundary

The existing KANGER logical-language operators, including `! ? + - =`, are outside the UI command-language redesign.

They belong to the KANGER language/compiler/query path and must not be reinterpreted as command-shell syntax or repurposed for options, assignment, selectors or UI metadata.

## 3. Command dialogue, not shell syntax

KANGER uses a command dialogue rather than a Unix-style shell.

Command syntax consists of meaningful words and arguments. Do not introduce shell artifacts such as `--all`, `--tree`, environment expansion, globbing or command substitution.

## 4. Canonical semantic order

Where a real semantic family exists, the phrase follows:

```text
WHERE -> WHAT TO DO -> WITH WHAT
```

or:

```text
<group> [<verb-or-selector>] [<arguments...>]
```

Accepted grouped examples:

```text
transaction start
rule comment 123
when accept 0
storage use demo
storage close
storage drop demo
storage reindex demo
```

Source operations remain self-identifying top-level `get`, `put`, `delete`. Browser-only `upload` / `download` are UI transport, not KANGER commands.

Storage remains a grouped family because it owns current selected/open context. `use` remains explicit because storage names may equal `close`, `drop` or `reindex`.

## 5. Bare groups and direct object forms

Read-only bare forms exist where semantically defined:

```text
transaction
rule
when
base
storage
```

Direct object-address forms:

```text
rule <id>
function <id>
solution <id>
```

`rule show <id>` is retired as redundant.

A Solution address is its actual Solution/IRule runtime ID, not a row number.

Hypotheses are different: they do not expose a stable semantic ID. `when` presents a zero-based rowset and `when accept <index>` addresses the current row position.

## 6. Aliases and ambiguity

Aliases, if later enabled, are one-to-one parser conveniences and normalize before execution.

The parser must never infer unrelated command identity from argument lexical type.

Historical overloaded `put 123` is rejected as a rule-comment mechanism. Rule comments are explicit through `rule comment <id>`.

`rule <id>` remains valid because `<id>` is an explicit production inside the RULE family rather than a lexical guess between unrelated operations.

## 7. Minimum unique prefix abbreviation

Keywords are case-insensitive and may use the shortest unambiguous leading prefix in the relevant grammar position.

There is no fixed abbreviation length.

Resolution:

1. exact full keyword wins;
2. otherwise unique leading prefix resolves;
3. ambiguity rejects;
4. arguments are not keyword-expanded.

Canonical help and echo use full spelling.

## 8. Lexical contract

Ordinary tokens are whitespace-separated. Double quotes delimit one argument containing whitespace. Inside double quotes only `\"` and `\\` are special.

Keywords are case-insensitive; argument content/case is preserved.

`rule comment <id> <text...>` consumes the remaining line as free comment text. `rule comment <id> ""` sets an explicitly empty comment.

One production has additional local structural punctuation:

```text
values order <field> [asc|desc] [, <field> [asc|desc]]...
```

A comma separates ordered `(field,direction)` sort-key pairs. This prevents `asc` / `desc` from being confused with a following field name. The comma has no general shell-like meaning outside `values order`.

## 9. Values ordering model

Values ordering has two layers:

```text
configured DefaultSortSpec
    -> plain values

explicit SortSpec
    -> values order ... for this invocation only
```

If no default exists, plain `values` uses natural rowset order.

Example:

```text
values order x desc, y asc, name
```

means ordered keys:

```text
(x, DESC)
(y, ASC)
(name, ASC)
```

Omitted direction defaults to ascending.

The explicit command must not mutate the configured default ordering. The final runtime model should preserve authoritative Values rows independently of presentation sort order and support ordered multi-key `SortSpec` projection.

The default sort policy may remain a persistent/operator presentation setting. Historical single-field `order/ascending` state is migration evidence, not a sufficient final multi-key projection model.

## 10. UI execution invariant

```text
screen -> command composition -> explicit execution
```

Clickable semantic objects compose/insert command text and never execute automatically.

## 11. Shared command processor ownership

One neutral sibling module owns canonical language parsing and metadata:

```text
kanger-command/
    src/org/kanger/command/...
```

It owns:

```text
CommandRegistry
CommandParser
canonical intents
argument extraction
lexical/quoting behavior
minimum-prefix resolution
canonical echo/help metadata
```

It stops at:

```text
raw command text -> canonical intent + arguments
```

It does not execute KANGER operations and KANGER Core does not depend on it.

Consumers:

```text
kanger-console -> kanger-command
kanger-server  -> kanger-command
future clients -> kanger-command
```

## 12. Registry-derived help

Canonical help is generated from the same registry metadata that defines parser productions.

Per production, metadata conceptually includes:

```text
intent
grammar
helpSection
summary
argument descriptions
display order
```

Usage text is rendered from authoritative grammar rather than maintained as a second manual command list.

Accepted authority chain:

```text
registry defines
parser interprets
help describes
UI discovers
```

Current grammar remains simply `help`; topic-filtered help is not added in 3.7.0.1.

## 13. Remote-client boundary

Browser and future remote clients do not own a second canonical parser.

```text
Browser command text
    -> Server
    -> kanger-command
    -> CommandIntent + arguments
    -> Server adapter
    -> qualified Server 0.18 runtime path
```

Console invokes the same processor locally.

The exact wire envelope is deferred to implementation.

## 14. Closed decisions

Closed in 3.7.0.1:

1. Core logical syntax remains outside command syntax.
2. Unix-style shell option syntax is rejected.
3. Semantic family order is used where a real family exists.
4. Group words are not invented for symmetry.
5. Bare forms, where defined, are read-only.
6. Aliases are one-to-one parser conveniences only.
7. Historical overloaded `put <rule-id>` is rejected.
8. Rule comments use `rule comment <id>`.
9. Direct rule lookup uses `rule <id>`.
10. Minimum-unique-prefix abbreviation is normative.
11. Source command language is `get`, `put`, `delete`.
12. Browser `upload` / `download` are transport actions only.
13. Storage grammar is explicit and `storage use` is retained for ambiguity control.
14. Historical `used`, `index`, `pack`, `options` are not canonical vocabulary.
15. Lexical/quoting rules are closed.
16. `values order` uses comma-separated multi-key `(field,direction)` pairs.
17. Plain Values retain configurable default ordering; explicit order is invocation-local.
18. Solutions use actual runtime IDs.
19. Hypotheses use zero-based current-row indexes.
20. Parser conformance is closed.
21. Command processor ownership is closed in `kanger-command`.
22. Remote clients send raw command text and Server owns canonical parsing.
23. Runtime/transport mapping is closed.
24. Canonical help is registry-derived.

## 15. Implementation boundary

No runtime implementation belongs in 3.7.0.1.

The next dedicated implementation artifact may implement the accepted `kanger-command` module, Server raw-command ingress/adapter, narrow missing bindings, Values projection extension, and later Console convergence while preserving the qualified Server 0.18 protection chain.
