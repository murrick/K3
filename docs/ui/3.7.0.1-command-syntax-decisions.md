# KANGER 3.7.0.1 — Canonical command syntax decisions

Status: ACCEPTED DESIGN BASELINE / NO RUNTIME AUTHORITY YET  
Reference runtime: `release/3.5.2` at `9c8b7dd2c9ef347cea6af6a6faef9cfa48030306`

## 1. Scope

This document records accepted syntax decisions for the unified KANGER Console / Browser / future UI command language.

It does not change Core syntax, KANGER logical operators, runtime execution semantics or production behavior.

## 2. Core-language boundary

The existing KANGER logical-language operators, including `=` and `?`, are outside the UI command-language redesign.

They belong to the KANGER language/compiler/query path and must not be reinterpreted as command-shell syntax or repurposed for options, assignment, selectors or UI metadata.

The UI command parser must hand logical expressions to the existing language path without introducing competing meanings for these tokens.

## 3. Command dialogue, not shell syntax

KANGER uses a command dialogue rather than a Unix-style command shell.

Therefore command syntax should consist of meaningful words and arguments only.

Do not introduce shell artifacts such as:

```text
--all
--tree
--level
-name
/value
```

Prefer natural command phrases.

The grammar itself should express the operation. Extra punctuation must not be required merely to distinguish options.

## 4. Canonical semantic order

The canonical command phrase follows semantic hierarchy:

```text
WHERE -> WHAT TO DO -> WITH WHAT
```

or grammatically:

```text
<group> [<verb-or-selector>] [<arguments...>]
```

Examples:

```text
storage use demo
storage drop demo
storage reindex demo

source get foo.k
source put foo.k
source delete foo.k

transaction start
transaction commit
transaction rollback

rule comment 123
```

This ordering is normative for the long canonical form.

It makes command ownership explicit and removes ambiguity caused by historically overloaded top-level verbs.

## 5. Bare group command

A bare command group is an official read-only status/context command when that family defines such a projection.

Examples:

```text
source
storage
transaction
rule
when
base
```

The exact projection for each group is defined by that group's accepted grammar, but omission of an action word must never cause accidental mutation.

Some families intentionally use a contextual singular/plural grammar instead of a bare singular group. For example, `functions` lists UDFs while `function <id>` addresses one UDF; `solutions` lists current solutions while `solution <id>` addresses one solution.

## 6. Aliases are usability syntax only

Aliases are allowed only when they improve frequent interactive use.

They are not alternate semantics and they do not own execution paths.

Examples of acceptable convenience aliases:

```text
get foo.k
    -> source get foo.k

put foo.k
    -> source put foo.k

use demo
    -> storage use demo

commit
    -> transaction commit

rollback
    -> transaction rollback
```

Every alias must resolve to exactly one canonical command before execution.

## 7. Alias ambiguity is forbidden

A convenience alias must remain semantically unambiguous for all valid argument values.

The parser must never infer command identity from the lexical type of an argument when the same alias could mean unrelated operations.

The historical overload:

```text
put foo.k
    -> save source

put 123
    -> edit comment of rule 123
```

is rejected because `123` may also be a valid source name.

Accepted direction:

```text
source put 123
```

means source persistence for source name `123`, while rule-comment editing is explicit:

```text
rule comment 123
```

General invariant:

> one alias -> one canonical command, independent of argument spelling.

## 8. Fixed four-character command-family identifiers

The earlier minimum-unique-prefix proposal is superseded.

Every top-level command family receives one fixed, case-insensitive, four-character registry/dispatcher identifier shared across Browser/UI, Server and the later Console convergence work.

The four-character identifier is a stable machine/dispatcher key for the family. It does not replace the human-readable canonical command word in documentation or composed command text.

Representative mapping:

```text
source        -> SOUR
storage       -> STOR
transaction   -> TRAN
rule          -> RULE
function(s)   -> FUNC
base          -> BASE
values        -> VALU
solution(s)   -> SOLU
when          -> WHEN
xplain        -> XPLA   # Console-local diagnostic family
```

Singular/plural command forms that address the same semantic family intentionally share one family identifier:

```text
functions            -> FUNC
function <id>        -> FUNC

solutions            -> SOLU
solution <id>        -> SOLU
solution tree <id>   -> SOLU
```

The remainder of the grammar determines collection-vs-object intent; a second top-level family ID is not created merely for grammatical number.

Do not compute family identity from a one-letter switch, minimum unique prefix, or argument spelling.

Exact action/selector vocabulary remains the accepted readable grammar (`get`, `put`, `delete`, `tree`, `comment`, `order`, etc.); the four-character rule is specifically the common top-level family identity mechanism.

## 9. Long form and short form relationship

Canonical long form expresses semantic hierarchy:

```text
storage use demo
source put foo.k
transaction commit
rule comment 123
```

Frequent short aliases may exist for usability:

```text
use demo
put foo.k
commit
```

but only when they preserve one-to-one meaning.

The long form remains the normative user-facing representation for documentation, help metadata, canonical echo and conformance cases. Internally, all surfaces normalize it to the same four-character family ID plus the resolved action/selector.

## 10. No implicit execution from UI interaction

This syntax design preserves the accepted interaction invariant:

```text
screen -> command composition -> explicit execution
```

Live links and semantic objects compose or insert command text at the caret.

They do not execute a command directly.

A live storage link may compose:

```text
storage use demo
```

A live source link may compose:

```text
source get foo.k
```

A visible semantic statement/value may insert its KANGER-language text into the partially composed command/query.

Execution remains an explicit user action.

## 11. Consequences for current registry questions

The following design questions are closed:

1. `=` and `?` are Core KANGER syntax, not UI command syntax.
2. Unix-style option markers are rejected; use meaningful command words.
3. canonical long-form order is `<group> <verb-or-selector> <arguments...>`.
4. bare group forms, where defined, are read-only projections.
5. aliases are usability-only parser mappings.
6. aliases must be one-to-one and independent of argument lexical form.
7. historical `put <rule-id>` overload is not retained.
8. rule comments use `rule comment <id>`.
9. source name `123` remains legal and unambiguous under `source put 123` / `put 123` when `put` is the SOURCE_PUT alias.
10. top-level command families use fixed four-character IDs shared by all surfaces.
11. minimum-unique-prefix family resolution is no longer part of the accepted design.

- canonical storage status projection for bare `storage`;
- exact argument grammar and quoting rules for names containing whitespace or reserved words;
- canonical diagnostic/admin vocabulary for the future collapsible technical panel;
- complete mapping of every accepted command family to its fixed four-character ID.
