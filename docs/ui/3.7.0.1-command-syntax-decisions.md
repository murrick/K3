# KANGER 3.7.0.1 — Canonical command syntax decisions

Status: ACCEPTED DESIGN BASELINE / NO RUNTIME AUTHORITY YET  
Reference runtime: `release/3.5.2` at `9c8b7dd2c9ef347cea6af6a6faef9cfa48030306`

## 1. Scope

This document records accepted syntax decisions for the unified KANGER Console / Browser / future UI command language.

It does not change Core syntax, KANGER logical operators, runtime execution semantics or production behavior.

## 2. Core-language boundary

The existing KANGER logical-language operators, including `=` and `?`, are outside the UI command-language redesign.

They belong to the KANGER language/compiler/query path and must not be reinterpreted as command-shell syntax or repurposed for options, assignment, selectors or UI metadata.

The command processor must hand logical expressions to the existing language path without introducing competing meanings for these tokens.

## 3. Command dialogue, not shell syntax

KANGER uses a command dialogue rather than a Unix-style command shell.

Therefore command syntax consists of meaningful words and arguments only. Do not introduce shell artifacts such as `--all`, `--tree`, `-name` or `/value`.

## 4. Canonical semantic order

The canonical command phrase follows semantic hierarchy:

```text
WHERE -> WHAT TO DO -> WITH WHAT
```

or grammatically:

```text
<group> [<verb-or-selector>] [<arguments...>]
```

This is a design principle where an explicit semantic group improves clarity. It is not a requirement to invent a group around an already clear top-level operation.

Accepted grouped examples:

```text
transaction start
transaction commit
transaction rollback

rule comment 123
when accept 2

storage use demo
storage close
storage drop demo
storage reindex demo
```

Source operations remain the self-identifying top-level `get`, `put`, `delete`. Browser-only `upload` / `download` remain UI transport actions under the `Source` menu and are not KANGER commands.

Storage remains a real grouped family because it owns a current selected/open storage context. `use` is retained because storage names are arbitrary and may equal action words such as `close`, `drop` or `reindex`.

## 5. Bare group and direct object forms

A bare command group is an official read-only status/context command when that family defines one:

```text
transaction
rule
when
base
storage
```

Omission of an action word must never cause accidental mutation.

Some families use singular/plural direct object grammar:

```text
functions
function <id>

solutions
solution <id>
```

RULE now follows the same direct object-address principle:

```text
rule <id>
```

The intermediate `rule show <id>` form is retired as redundant.

Do not invent a bare group or intermediate verb merely to make unrelated families visually symmetrical.

## 6. Aliases and ambiguity

Aliases are usability syntax only. Every alias must normalize to exactly one canonical command before execution.

The parser must never infer command identity from argument lexical type when the same spelling could mean unrelated operations.

Historical:

```text
put foo.k
put 123
```

must not select unrelated meanings merely because `123` looks numeric. Rule comments are explicit through `rule comment <id>`.

By contrast, `rule <id>` is a grammar production inside the single RULE family and does not create unrelated-command ambiguity.

## 7. Minimum unique prefix abbreviation

Command keywords are case-insensitive and may use the shortest unambiguous leading prefix in the relevant grammar position.

There is no fixed abbreviation length.

The parser resolves against only the keywords valid at that grammar position:

1. exact full keyword wins;
2. otherwise a unique leading prefix resolves;
3. an ambiguous prefix is rejected;
4. arguments are not keyword-expanded.

Canonical documentation, help and echo use full readable words.

## 8. Lexical contract

Ordinary tokens are whitespace-separated. Double quotes delimit one argument containing whitespace. Inside double quotes only `\"` and `\\` are special.

Keywords are case-insensitive; argument content/case is preserved.

`rule comment <id> <text...>` consumes the remaining line as comment text; `rule comment <id> ""` sets an explicitly empty comment.

No shell flags, single-quote language, environment expansion, globbing or shell command substitution are introduced.

## 9. UI execution invariant

The accepted interaction invariant remains:

```text
screen -> command composition -> explicit execution
```

Clickable semantic objects compose/insert command text and do not execute automatically.

## 10. Shared command processor ownership

The canonical command language is owned by one neutral sibling module:

```text
kanger-command/
    src/org/kanger/command/...
```

The module owns:

```text
registry
parser
canonical intents
argument extraction
lexical/quoting behavior
minimum-prefix resolution
canonical echo/help metadata
```

It does not execute KANGER runtime operations.

The dependency direction is:

```text
kanger-console -> kanger-command
kanger-server  -> kanger-command
future clients -> kanger-command
```

KANGER Core must not depend on `kanger-command`.

Normative details are in `3.7.0.1-command-processor-ownership.md`.

## 11. Closed decisions

The following are closed:

1. Core logical syntax remains outside command syntax.
2. Unix-style option syntax is rejected.
3. Semantic command order is used where a real family exists.
4. Group words are not invented for symmetry.
5. Bare group forms, where defined, are read-only.
6. Aliases are one-to-one parser conveniences only.
7. Historical overloaded `put <rule-id>` is rejected.
8. Rule comments use `rule comment <id>`.
9. Direct rule lookup uses `rule <id>`; `rule show <id>` is retired.
10. Minimum-unique-prefix abbreviation is normative; no fixed abbreviation length exists.
11. Source command language is `get`, `put`, `delete`; `source` is only UI grouping.
12. Browser `upload` / `download` are transport actions, not commands.
13. Storage grammar is `storage`, `storage use <name>`, `storage close`, `storage drop <name>`, `storage reindex <name>`.
14. Bare `storage` replaces historical `used`.
15. Historical `index` / `pack` are not canonical; `reindex` is canonical.
16. `storage drop` and `storage reindex` require an explicit name.
17. `storage use` remains explicit to avoid action/name ambiguity.
18. lexical/quoting rules are closed.
19. parser conformance cases are closed.
20. parser/registry ownership is closed in shared module `kanger-command`.

## 12. Remaining design work

Before runtime implementation, only these design mappings remain:

- map canonical intents onto current Server/runtime operations and transport behavior;
- preserve the separately recorded Console flash-back/convergence boundary and sequence.

No runtime implementation belongs in 3.7.0.1.
