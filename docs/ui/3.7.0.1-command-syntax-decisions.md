# KANGER 3.7.0.1 — Canonical command syntax decisions

Status: ACCEPTED DESIGN BASELINE / NO RUNTIME AUTHORITY YET  
Reference runtime: `release/3.5.2` at `9c8b7dd2c9ef347cea6af6a6faef9cfa48030306`

## 1. Scope

This document records accepted syntax decisions for the unified KANGER Console / Browser / future UI command language.

It does not change Core syntax, KANGER logical operators, runtime execution semantics or production behavior.

## 2. Core-language boundary

The existing KANGER logical-language operators, including `=` and `?`, are outside the UI command-language redesign.

They belong to the KANGER language/compiler/query path and must not be reinterpreted as command-shell syntax or repurposed for options, assignment, selectors or UI metadata.

The UI command parser must hand logical expressions to the existing language path without introducing competing meanings for these tokens.

## 3. Command dialogue, not shell syntax

KANGER uses a command dialogue rather than a Unix-style command shell.

Therefore command syntax should consist of meaningful words and arguments only.

Do not introduce shell artifacts such as:

```text
--all
--tree
--level
-name
/value
```

Prefer natural command phrases.

The grammar itself should express the operation. Extra punctuation must not be required merely to distinguish options.

## 4. Canonical semantic order

The canonical command phrase follows semantic hierarchy:

```text
WHERE -> WHAT TO DO -> WITH WHAT
```

or grammatically:

```text
<group> [<verb-or-selector>] [<arguments...>]
```

This is a design principle for commands where an explicit semantic group improves clarity. It is not a requirement to invent a group word around an already clear historical top-level operation.

Examples already accepted in grouped families include:

```text
transaction start
transaction commit
transaction rollback

rule comment 123

when accept 2
```

Source operations are an explicit accepted exception to mechanical grouping: the canonical command-language surface is the self-identifying top-level `get`, `put`, and `delete`. Browser-only `upload` / `download` remain UI transport actions under the `Source` menu and are not KANGER commands.

Storage grouping remains subject to family-specific review rather than being assumed merely for visual symmetry.

## 5. Bare group command

A bare command group is an official read-only status/context command when that family defines such a projection.

Examples already accepted include:

```text
transaction
rule
when
base
```

Omission of an action word must never cause accidental mutation.

Some families intentionally use a contextual singular/plural grammar instead of a bare singular group. For example, `functions` lists UDFs while `function <id>` addresses one UDF; `solutions` lists current solutions while `solution <id>` addresses one solution.

Do not invent a bare group merely to make unrelated families visually symmetrical.

## 6. Aliases are usability syntax only

Aliases are allowed only when they improve frequent interactive use.

They are not alternate semantics and they do not own execution paths.

Every alias must resolve to exactly one canonical command before execution.

## 7. Alias ambiguity is forbidden

A convenience alias must remain semantically unambiguous for all valid argument values.

The parser must never infer command identity from the lexical type of an argument when the same spelling could mean unrelated operations.

The historical overload:

```text
put foo.k
    -> save source

put 123
    -> edit comment of rule 123
```

is rejected because `123` may also be a valid source name.

Rule-comment editing is explicit:

```text
rule comment 123
```

General invariant:

> one alias/spelling -> one canonical command, independent of argument spelling.

## 8. Minimum unique prefix abbreviation

Command words are case-insensitive and may use the minimum unique leading prefix in the relevant grammar position.

There is no fixed abbreviation length.

Three or four characters will often be convenient in practice, but that is an ergonomic observation rather than a syntax rule.

Examples, once the accepted vocabulary makes them unique:

```text
tra com
ru com 123
solu tree 42
valu ord x desc
```

The parser resolves a token against the words valid in that grammar position:

1. an exact full keyword wins;
2. otherwise a unique leading prefix resolves to that keyword;
3. an ambiguous prefix is rejected;
4. the parser never guesses from arguments or execution context.

The exact minimum-prefix table is derived from the final accepted vocabulary and must not be hard-coded prematurely.

This preserves the historical convenience of short interactive commands without retaining the old one-letter Console dispatcher as a semantic rule.

## 9. Canonical form and abbreviated input

Canonical documentation, help metadata, canonical echo and conformance examples use full readable words:

```text
transaction commit
rule comment 123
solution tree 42
values order x desc
```

Interactive input may abbreviate any keyword under the minimum-unique-prefix rule:

```text
tra com
ru com 123
solu tr 42
valu ord x desc
```

Abbreviation is parser convenience only; it does not create alternate command IDs or implementation paths.

## 10. No implicit execution from UI interaction

This syntax design preserves the accepted interaction invariant:

```text
screen -> command composition -> explicit execution
```

Live links and semantic objects compose or insert command text at the caret.

They do not execute a command directly.

A visible semantic statement/value may insert its KANGER-language text into the partially composed command/query.

Execution remains an explicit user action.

## 11. Consequences for current registry questions

The following design questions are closed:

1. `=` and `?` are Core KANGER syntax, not UI command syntax.
2. Unix-style option markers are rejected; use meaningful command words.
3. semantic order is `WHERE -> WHAT TO DO -> WITH WHAT` where a real command family exists.
4. a group word must not be invented solely for symmetry.
5. bare group forms, where defined, are read-only projections.
6. aliases are usability-only parser mappings.
7. aliases/spellings must be one-to-one and independent of argument lexical form.
8. historical `put <rule-id>` overload is not retained.
9. rule comments use `rule comment <id>`.
10. minimum-unique-prefix abbreviation is the accepted abbreviation mechanism.
11. there is no fixed three-character or four-character abbreviation rule.
12. source command language is exactly `get`, `put`, `delete`; `source` is a UI/menu grouping, not a command namespace.
13. Browser `upload` / `download` are UI transport actions, not KANGER commands and not Console syntax.

## 12. Remaining syntax/design work

- canonical storage vocabulary/status projection;
- exact argument grammar and quoting rules for names containing whitespace or reserved words;
- canonical diagnostic/admin vocabulary for the future collapsible technical panel;
- compute the exact minimum-prefix table only after vocabulary closure.

Console implementation convergence is explicitly deferred to the recorded Console flash-back TODO. The current 3.7.0.1 work remains UI/design baseline work with zero runtime delta.
