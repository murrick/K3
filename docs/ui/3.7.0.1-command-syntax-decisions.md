# KANGER 3.7.0.1 — Canonical command syntax decisions

Status: **ACCEPTED DESIGN BASELINE / NO RUNTIME AUTHORITY YET**  
Reference runtime: `release/3.5.2` at `9c8b7dd2c9ef347cea6af6a6faef9cfa48030306`

## 1. Scope

This document records accepted syntax decisions for the unified KANGER Console / Browser / future UI command language.

It does not change Core syntax, KANGER logical operators, runtime execution semantics or production behavior.

## 2. Core-language boundary

The existing KANGER logical-language operators, including `!`, `?`, `+`, `-`, and `=`, are outside the UI command-language redesign.

They belong to the KANGER language/compiler/query path and must not be reinterpreted as command-shell syntax or repurposed for options, assignment, selectors or UI metadata.

The UI command parser must hand logical expressions to the existing language path without introducing competing meanings for these tokens.

## 3. Command dialogue, not shell syntax

KANGER uses a command dialogue rather than a Unix-style command shell.

Therefore command syntax consists of meaningful words and arguments only.

Do not introduce shell artifacts such as:

```text
--all
--tree
--level
-name
/value
```

The grammar itself expresses the operation. Extra punctuation is not required merely to distinguish options.

## 4. Canonical semantic order

The canonical command phrase follows semantic hierarchy:

```text
WHERE -> WHAT TO DO / WHAT EXACTLY -> WITH WHAT
```

or grammatically:

```text
<group> [<verb-or-selector>] [<arguments...>]
```

This is a design principle where an explicit semantic group expresses real ownership or context. It is not a requirement to invent a group around an already clear operation.

Accepted grouped examples:

```text
transaction start
transaction commit
transaction rollback

rule comment 123
when accept 2

storage use demo
storage close
storage drop demo
storage reindex demo
```

Source operations are the accepted exception to mechanical grouping:

```text
get
put
delete
```

They remain self-identifying top-level operations. Browser-only `upload` / `download` are UI transport actions under the `Source` menu and are not KANGER commands.

Storage is grouped because it owns a real operator-visible context: the current selected/open storage.

## 5. Bare groups and grammatical singular/plural

A bare command group is an official read-only status/context command when that family defines such a projection.

Accepted examples:

```text
transaction
rule
when
base
storage
```

Omission of an action word must never cause accidental mutation.

Some families use grammatical singular/plural forms while remaining one semantic dispatcher family:

```text
functions
function <id>
function source <id>

solutions
solution <id>
solution tree <id>

base predicates
base predicate <id|name>
```

`function/functions`, `solution/solutions`, and `predicate/predicates` are therefore resolved through one family/selector stem. English grammatical number is not a second command namespace.

The grammar production determines the canonical full spelling:

- empty FUNCTION family -> `functions`;
- FUNCTION + object -> `function ...`;
- empty SOLUTION family -> `solutions`;
- SOLUTION + object -> `solution ...`;
- BASE + PREDICATE selector without ref -> `base predicates`;
- BASE + PREDICATE selector with ref -> `base predicate <ref>`.

This keeps the parser deterministic without forcing nearly full plural words merely to distinguish grammatical number.

## 6. Aliases are usability syntax only

Aliases are allowed only when they improve frequent interactive use.

They are not alternate semantics and they do not own execution paths.

Every alias must resolve to exactly one canonical command intent before execution.

Compatibility aliases are not part of the canonical vocabulary or canonical minimum-prefix calculation unless explicitly accepted later.

## 7. Alias ambiguity is forbidden

A convenience alias must remain semantically unambiguous for all valid argument values.

The parser must never infer command identity from the lexical type of an argument when the same spelling could mean unrelated operations.

The historical overload:

```text
put foo.k
    -> save source

put 123
    -> edit comment of rule 123
```

is rejected because `123` may also be a valid source name.

Rule-comment editing is explicit:

```text
rule comment 123
```

General invariant:

> one spelling/alias -> one canonical intent, independent of argument spelling.

## 8. Minimum unique prefix abbreviation

Command words are case-insensitive and may use the minimum unique leading prefix in the relevant grammar position.

There is no fixed abbreviation length. Three or four characters are often comfortable in practice, but that is ergonomic convention, not syntax.

Resolution occurs against the semantic keyword/family stems valid at that grammar position:

1. an exact full canonical word wins;
2. otherwise a unique leading prefix resolves the keyword/family stem;
3. an ambiguous prefix is rejected;
4. argument spelling must not choose between unrelated command intents;
5. singular/plural surface forms of one family do not compete as separate dispatcher words.

The accepted registry now yields these top-level minima:

```text
base                 -> b
delete               -> d
erase                -> e
function/functions   -> f
get                  -> g
help                 -> h
put                  -> p
quit                 -> q
rule                 -> r
solution/solutions   -> so
storage              -> st
transaction          -> t
values               -> v
when                 -> w
```

Only SOLUTION and STORAGE require two characters at top level because both begin with `s`.

Examples:

```text
r c 123
f s 12
b p father
v o x d
so t 42
t c
st r demo
```

The complete selector/action prefix table lives in `3.7.0.1-canonical-command-registry.md` and is derived from the accepted vocabulary, not manually invented per interface.

## 9. Canonical form and abbreviated input

Canonical documentation, help metadata, canonical echo and conformance expectations use full readable words:

```text
transaction commit
rule comment 123
solution tree 42
values order x desc
storage reindex demo
```

Interactive input may use any accepted minimum unique prefix:

```text
t c
r c 123
so t 42
v o x d
st r demo
```

Abbreviation is parser convenience only; it does not create alternate command IDs or implementation paths.

## 10. No implicit execution from UI interaction

This syntax design preserves the interaction invariant:

```text
screen -> command composition -> explicit execution
```

Live links and semantic objects compose or insert command text at the caret.

They do not execute a command directly.

A visible semantic statement/value may insert its KANGER-language text into the partially composed command/query.

Execution remains an explicit user action.

## 11. Closed syntax decisions

The following design questions are closed for 3.7.0.1:

1. `! ? + - =` remain Core KANGER syntax, not UI command syntax.
2. Unix-style option markers are rejected; use meaningful command words.
3. semantic order is `WHERE -> WHAT TO DO / WHAT EXACTLY -> WITH WHAT` where a real family exists.
4. a group word must not be invented solely for symmetry.
5. bare group forms, where defined, are read-only projections.
6. singular/plural forms may share one semantic family/selector stem.
7. aliases are usability-only mappings and cannot own execution paths.
8. argument lexical shape cannot choose between unrelated commands.
9. historical `put <rule-id>` overload is not retained; comments use `rule comment <id>`.
10. minimum-unique-prefix abbreviation is the accepted mechanism; there is no fixed 3/4-character rule.
11. source command language is `get`, `put`, `delete`; `source` is only a UI/menu grouping.
12. Browser `upload` / `download` are transport actions, not KANGER commands or Console syntax.
13. storage grammar is `storage`, `storage use <name>`, `storage close`, `storage drop <name>`, `storage reindex <name>`.
14. bare `storage` replaces historical `used`.
15. historical `index` / `pack` are not canonical; operator vocabulary is `reindex`.
16. `storage drop` and `storage reindex` require explicit storage names.
17. ordinary system/session commands are exactly `erase`, `help`, `quit` at this baseline.
18. historical `options` / generic settings/diagnostics are not carried into the UI command language.
19. the accepted canonical command registry and minimum-prefix table are fixed in `3.7.0.1-canonical-command-registry.md`.

## 12. Remaining implementation-independent work

The semantic vocabulary is closed at this level.

Still required before runtime implementation:

1. lexical/quoting rules for names, file names and free-form comment text;
2. parser conformance cases proving full and abbreviated forms normalize to identical intent IDs;
3. parser/dispatcher ownership and module placement;
4. transport mapping from canonical intents to current Server operations;
5. deferred Java Console flash-back/convergence.

Console implementation convergence remains explicitly deferred. The current 3.7.0.1 work is UI/design baseline work with zero runtime delta.
