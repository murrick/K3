# Рабочий мануал: контексты, DMZ и новая запись

Состояние: структурный этап 493, 1 ноября 2026. Это руководство по уже доступным
операциям Java Console с DUMB2. Полный язык DMZ и включение новой квалификации для
обычного `!…` ещё не завершены. Ограниченный режим может вернуть INCOMPLETE даже
для непротиворечивого знания; это не доказательство ложности.

## Безопасная учебная среда

Примеры выполняй в отдельном тестовом каталоге, а не поверх рабочих контекстов.
Одноразовую Console с отдельными базами и настройками создаёт:

```sh
python3 scripts/run-dmz-manual.py
```

Этот launcher готовит другой, restriction-сценарий: [его описание](dmz-manual-walkthrough.md).
В его одноразовой среде можно закрыть текущий storage и выполнить пример ниже.
Имена `A_GUIDE_489` и `X_GUIDE_489` здесь должны быть новыми. В обычной рабочей Console
не используй уже существующие контексты с такими именами.

## Чем отличаются пути работы

| Команда | Назначение | Запись в X |
| --- | --- | --- |
| `!…;` | Прежний обычный путь Core | Да, при принятии |
| `ctx candidate "!…;"` | Прежняя проверка flat universal candidate | Нет |
| `ctx candidate write "!…;"` | Прежняя явная публикация через flat universal qualifier | Да, при принятии |
| `ctx candidate model write "!…;"` | Новый ограниченный путь с унарными/многоместными моделями и автоматическим базисом | Да, при принятии |
| `ctx dmz …` | Запрос к точно указанным источникам и ограничениям | Не публикует исходное утверждение в X |
| `ctx dmz family`, `ctx dmz branch N` | Просмотр сохранённого семейства/ветви | Нет |

Новый model-путь выбирается ЯВНО. Слово `write` обязательно:
`ctx candidate model "!p(1);"` не является диагностикой и отвергается как неправильная
команда, ничего не записывая. Для исходного утверждения используй кавычки и один `;`.
Два утверждения в одной model-команде не допускаются; одно составное утверждение —
отдельная исходная строка, в пределах поддерживаемой формы.

Старый writer может вернуть INCOMPLETE там, где новый model-writer примет ту же строку.
Это разные механизмы квалификации; успешная диагностика не подменяет публикацию.

## Первый пример: signed-контекст

```text
storage close
storage use A_GUIDE_489
!$u seed(u)&&~blocked(u);
storage close

storage use X_GUIDE_489
!anchor(1);
ctx connect A_GUIDE_489
ctx publish "Учебное подключение"

ctx candidate model write "!@u seed(u)->~blocked(u);"
ctx candidate model write "!@u seed(u)->blocked(u);"
```

Первая model-запись должна дать `MODEL WRITE: PUBLISHED`. Вторая — `MODEL WRITE: REFUTED`:
она противоречит знанию A. Отклонённая строка не должна появиться среди исходных правил X.
`ctx publish` в примере фиксирует подключение с его точной ревизией; сама успешная
model-запись уже выполняет сохранение исходного утверждения. После закрытия и открытия
X должны сохраниться безопасное правило и подключение A. Этот сценарий выполнен
автоматической проверкой через настоящую Console, включая повторное открытие.

## Универсальные правила без начального факта

В новом пустом storage поддерживаемую универсальную строку можно записать первой:

```text
ctx candidate model write "!@u p(u);"
?p(42);
```

Не нужно предварительно добавлять `anchor(1)` только ради обхода. Контекст X существует
как структурный срез независимо от наличия фактов. В базу сохраняется универсальное
правило, а не выдуманный факт `p(0)`; запрос о ещё не упоминавшемся 42 проверяет правило.
Поддерживаемая универсальная импликация `!@u p(u)->q(u);` также может быть неактивной:
из отсутствия исходного p не следует, что надо его придумать.

Это не обещание поддержки произвольной смешанной кванторной или функциональной формулы.
Если форма/обход не поддержаны, результат остаётся INCOMPLETE.

## Несколько универсальных переменных

В новом тестовом storage можно выполнить:

```text
ctx candidate model write "!@u @v p(u)&&q(v)->r(u);"
!p(1);
!q(2);
?r(1);
```

Model-запись должна дать PUBLISHED; после двух обычных фактов запрос должен дать true.
`u` и `v` независимы: правило применяется к `p(1)` и `q(2)`, хотя 1 и 2 различны.
Если в обоих местах стоит одна переменная, она сохраняет одно значение.

Автоматическая модельная проверка обрабатывает переменные по их полным спискам, без
малого потолка три. Проверяются сочетания именованных значений и класса всех остальных
допустимых значений в каждой позиции; равномерные отношения позволяют часть проверок
выполнить без полного перебора. Это не ограничивает `@`
значениями, уже записанными в базе. Перебор расходует бюджет аудита; превышение лимита
даёт INCOMPLETE и не доказывает противоречия.

Поддержка модельной проверки сама по себе не расширяет нативный профиль вывода. Например,
чистая положительная дизъюнкция `!@u @v p(u)||q(v);` пока возвращает INCOMPLETE на нативной
стадии. Смешанные префиксы и произвольные вложенные кванторы здесь не объявляются поддержанными. Учебный пример выше проверяется через настоящую
Console, включая сохранение и повторное открытие исходного правила.

### Три переменные в новом нативном профиле

В отдельном пустом тестовом storage можно выполнить:

```text
ctx candidate model write "!@u @v @w p(u)&&q(v)&&r(w)->s(v);"
!p(1);
!q(2);
!r(3);
?s(2);
```

Model-запись должна дать PUBLISHED, запрос — TRUE. Голова использует значение второй
переменной: 2, при независимых `u=1`, `v=2`, `w=3`. Учебный сценарий выполнен через
настоящую Console с повторным открытием и проверкой сохранённых исходных строк.

Нативный signed-контур теперь обрабатывает произвольные конечные списки аргументов
и универсальных переменных в поддерживаемых Horn-правилах. Требования формы сохраняются:
в условном правиле переменная положительной головы должна встречаться в теле.
Автоматическая положительная проверка теперь поддерживает и многоместные модели;
границы ресурсов могут дать INCOMPLETE уже после завершения нативного вывода.
Старый механизм квалификации `ctx candidate write` этим расширением не переключается.

Частичные тела в разных контекстах могут породить остаточные правила, нуждающиеся
в следующих раундах квалификации. Например, A с `p(1),q(2)` и B с `r(3),~s(2)` приводят
к отказу для правила выше: остаточные продукции связывают проверку. Это не означает,
что любые частные факты A/B автоматически объединяются. При отсутствии нужных продукций
противоположные частные знания могут оставаться независимыми.

## Произвольная арность: что уже обобщено

Количество аргументов предиката и число разных переменных — разные характеристики.
У `p(x,x,7)` три аргумента и одна переменная; повторения `x` обязаны получить одно значение.
Обрабатываются все позиции: константы, переменные, их смеси, повторения и перестановки.
Тип значения сохраняется: строка «7» не подменяется числом 7. Разная арность не становится
одним предикатным кортежем только из-за одинакового имени.

В новом нативном Horn-контуре сняты малые пределы 3 переменные / 8 аргументов.
Это не их повышение до очередного числа: полный список проходит захват, сопоставление,
подстановки, перенос продукции и финальный аудит с учётом позиций в бюджете работы.
Проверенные размеры — до 257 позиций при захвате и до 64 аргументов/разных переменных
в полном нативном выводе. Эти числа описывают тесты, а не новый максимум языка.

Автоматическая model-запись теперь строит и независимо проверяет модели многоместных
предикатов. Для длинных отношений используется общее значение и исключения для кортежей;
конкретные факты и конечные продукции помогают построить компактный кандидат модели.
огромная декартова таблица не выделяется до проверки бюджета. Поиск ограничен: отсутствие
найденной модели остаётся INCOMPLETE. Настоящее отрицательное доказательство выполняется
раньше поиска модели, в том числе для 17-местного правила с 17 переменными.

Ограничения числа строк, ширины клауз, числа свидетельских Origin, глубины и работы остаются
отдельными ограничениями текущего профиля. Снятие предела арности не означает поддержку
любого префикса кванторов, функций или любого числа независимых экзистенциальных свидетелей.
Старый flat-путь и обычная запись не переключены на новый механизм.

## Многоместные модели и запись

В отдельном новом тестовом storage можно записать:

```text
ctx candidate model write "!rel(1,2);"
ctx candidate model write "!~rel(2,1);"
?rel(1,2);
?~rel(2,1);
?rel(3,4);
```

Обе записи принимаются: это разные упорядоченные кортежи одного отношения. Первые два
запроса дают TRUE; третий остаётся WHO KNOWS. Выбранное значение в модели не становится
знанием в Core. Эти операции проверены через публичную запись, повторное открытие базы
и нативные запросы.

В другом пустом тестовом storage запись `!@u @v rel(u,v);` через model-команду принимается,
и после повторного открытия запрос `?rel(42,43);` даёт TRUE. Это следствие сохранённого
универсального правила для всех допустимых значений, включая ранее не упомянутые.
У `!@u rel(u,u);` две позиции связаны одним `u`; правило не утверждает все пары разных значений.
Имя и арность входят в сигнатуру: `rel(1)` и `rel(1,1)` не сливаются.

Проверены универсальные отношения до 64 аргументов, 64 разных константы с `points=64`,
неоднородная истинность кортежей, строковая «7» против числа 7 и коррелированный свидетель
`!$u rel(u,1)&&~rel(1,u);`. Для последнего может понадобиться дополнительное настоящее
значение базиса. Разные свидетельские Origin могут совпадать, если знания это допускают.
Проверенные размеры не являются новыми максимумами арности.

Для длинного кортежа из разных констант увеличь `points` по числу нужных значений, например:
`ctx candidate model write "!wide(1,2,3,4,5);" points=5`. Само увеличение бюджета не выделяет
таблицу такого размера: всё ещё действуют `work`, `basis-work`, `cells` и `candidates`.
Два разных 64-местных положительный/отрицательный кортежа проверены с одним исключением,
без огромной таблицы. Более сложное неоднородное отношение может не поместиться в поиск
и вернуть INCOMPLETE.
Проверяются исходные формулы и **все фактические конечные обязательства** каждого среза;
A/B имеют отдельные модели, а TRUST объединяет все физические источники группы.

Этот путь не объявляет поддержку функций, произвольного чередования кванторов или любого
числа экзистенциальных связок. Старый API с вручную заданным унарным базисом сохраняет свой
ограниченный профиль. Обычная запись `!…` и старый flat writer автоматически не переключены.

## Четыре результата model-записи

| Результат | Что означает | Что делать |
| --- | --- | --- |
| `PUBLISHED` | Исходное утверждение принято и выполнен обычный native-путь публикации | Можно проверить правила и ревизию |
| `REFUTED` | Получено проверенное доказательство противоречия текущей операции | Разобрать исходные знания и причины |
| `INCOMPLETE` | Не удалось закончить квалификацию: форма, базис или предел вычислений | Не считать это ни согласием, ни противоречием |
| `NATIVE_REJECTED` | Обычный native-путь вернул отказ ещё до успешной публикации | Проверить локальный конфликт/нативные условия |

Ошибки владельца, исторический storage, неподдерживающий provider и неверная команда
могут быть показаны как ошибки команды. Это тоже не разрешение на запись. Ошибка после
необратимого сохранения отдельно описывается существующим сообщением о результате
settlement; не следует считать любое исключение доказательством полного отката.

## Как выбирается базис значений

Пользователю не надо перечислять Java-объекты значений. Сначала берутся все реальные
константы исходных строк и конечных обязательств, с сохранением типа: число 7 и строка
`'7'` различны. Сначала проверяется этот минимальный базис. При необходимости добавляются
обычные допустимые числовые значения, не совпадающие с уже собранными.

```text
ctx candidate model write "!$u ~p(u);" points=4 fresh=2
```

Если уже имеется `!$u p(u);`, одного значения для обеих независимых экзистенциальных
строк может не хватить; два значения позволяют построить модель. Это не означает, что
разные свидетели ОБЯЗАНЫ быть различными. Они могут совпадать, если знания это допускают.
Числа модели не публикуются в X как новые факты и не становятся ответами запроса сами по себе.
`@u` по-прежнему охватывает все допустимые значения, а не только конечный список из базы.

Основные параметры:

| Параметр | По умолчанию | Смысл |
| --- | ---: | --- |
| `points` | 4 | Настраиваемый положительный бюджет именованных значений; малого потолка 16 больше нет |
| `fresh` | 2 | Бюджет дополнительных значений, максимум 8; 0 запрещает их добавление |
| `rows` | 64 | Предел захваченных исходных строк |
| `candidates` | 512 | Предел кандидатов исходной модели, максимум 512 |
| `cells` | 16 | Предел клеток истинности исходной модели, максимум 16 |
| `witnesses` | 8 | Предел Source-назначений свидетелей |
| `rounds`, `depth` | 2, 16 | Ограничения соответствующего native-обхода |
| `work`, `audit`, `basis-work` | 64000000 | Раздельные бюджеты стадий/аудита/подготовки базиса |

Это раздельные пределы, а не один общий счётчик времени или работы. Увеличение `points`
может увеличить модель настолько, что она не поместится в `cells` или `candidates`.
Не следует повышать пределы механически: причина INCOMPLETE может быть в форме языка.
Нулевая `fresh` допустима; нулевые work/audit не допускаются. Неизвестные и повторные
параметры отвергаются.

## Подключения, независимость и TRUST

```text
ctx
ctx connect A
ctx connect B
ctx connect C trust own
ctx connect D trust own
ctx version A
ctx switch A current
ctx publish "Зафиксирована топология"
```

A–X и B–X квалифицируются отдельно; противоречие между A и B само по себе допустимо.
C и D в группе `own` образуют совместный логический срез и должны рассматриваться вместе.
Проверка не ограничивается представителем группы: сохраняются все физические источники.
Именованный `current` разрешается в конкретную ревизию в момент переключения, а не
означает постоянное следование за чужим HEAD. Перед изменением рабочих подключений
проверь сохранённые правила и ревизии. `ctx publish` с открытой пользовательской
транзакцией имеет собственную процедуру подтверждения; model-команда не обходит её.

Новая запись заново захватывает актуальное состояние. Равенства ревизии X недостаточно:
инициализация A или подготовленный ребёнок могли измениться. Старый ответ/модель остаются
историей, а не разрешением на последующую запись.

## Запросы, сохранённые ответы и ветви

Для точного синтаксиса доступной сборки используй `help` и старый
[одноразовый walkthrough](dmz-manual-walkthrough.md): он печатает реальные UUID/ревизии
и полные команды текущего запуска. Не копируй UUID из чужого запуска.

```text
ctx dmz <имя>@<ревизия> "?p(1);" from=<источник>@<ревизия>
ctx dmz explain
ctx dmz family
ctx dmz family 10
ctx dmz branch 1
ctx dmz choose 1
ctx opinions
ctx tree 1
ctx values
ctx solves
ctx when
```

`ctx dmz family` показывает сохранённое семейство. С числом выполняется новый обход
с заданным лимитом по сохранённому точному запросу ограничений. `ctx dmz branch N` читает
доказательства сохранённой ветви; `ctx dmz choose N` заново выполняет запрос с выбранной
альтернативой ограничений. Выбор ветви — не принятие гипотезы и не model-публикация.
`ctx values`, `ctx solves`, `ctx when` показывают сохранённые Values, Solutions и Hypotheses;
последняя команда не принимает гипотезы автоматически.

После записи, смены pin или инициализации выполни запрос заново. Сохранённые объяснения
могут относиться к старому снимку. Частичный результат и остановка по лимиту не являются
полным семейством. Общее развитие результатов ветвей и orphan/hypothesis-семантики ещё
открыто; model-writer это не закрывает.

## Для разработчика: основные DB API

| API | Назначение |
| --- | --- |
| `inspectSignedProductionCandidate` | Проверка одного кандидата native signed-механизмом, без публикации |
| `inspectSignedPendingProduction` | Проверка целого реально подготовленного ребёнка, без публикации |
| `inspectSignedModelPendingProduction` | Исходная и конечная модель с явно заданными Java-значениями базиса |
| `inspectAutomaticSignedModelPendingProduction` | То же с автоматическим базисом |
| `writeSignedProductionCandidate` | Прежний явный writer с обязательным прежним full-family барьером |
| `writeSignedModelProductionCandidate` | Новый ограниченный model-writer с явным базисом |
| `writeAutomaticSignedModelCandidate` | Новый ограниченный model-writer с автоматическим базисом |
| `publishSignedModelCandidate` | Provider-отчёт о фактически выполненной автоматической записи; используется командой Console |

В `ContextSignedModelInspection.Limits` и `Automatic` передаются границы вычислений,
а не разрешение на запись. Результаты диагностики исторические. Detached-вызов Core
не подтверждает актуальность живой базы; DB-вызовы проверяют фактического владельца,
подготовленного ребёнка, pins и инициализации до и после работы. Повторно применять
старый receipt для разрешения новой записи нельзя. Положительный `MODELLED_SUPPLIED`
диагностики не является вызовом writer.

Точные сигнатуры и ограничения: [writer](architecture/3.8.0-context-production-signed-model-writer.md),
[автоматический базис и Console](architecture/3.8.0-context-production-automatic-model-authoring.md).

- Автоматическое перенаправление обычного `!…` через новый model-writer.
- Полный язык функций, смешанных кванторов и всех требуемых форм DMZ.
- Полная семантика branch Values/Solutions/Hypotheses и вопрос 3 с orphan-утверждениями.
- Включение нового режима в retained-пользовательские транзакции.
- Полная квалификация глубины/масштаба и окончательная ручная приёмка всего DMZ.

Источник текущего статуса: [оставшаяся работа](architecture/3.8.0-dmz-remaining-work-2026-10-24.md).
Архитектурные доказательства и точные тестовые границы — в ссылках последних структурных
этапов этого документа. Мануал обновляется вместе со значимыми изменениями команд.

## Несколько существовательных параметров — этап 495

В явной команде model write поддержан выбор отдельных значений для каждого
из нескольких параметров одного исходного утверждения, например:

```text
ctx candidate model write "!$u $v p(u)&&~p(v);"
```

Здесь требуются два разных значения из-за положительного и отрицательного
условий. В `!$u $v p(u)&&q(v);` оба параметра могут обозначать одно значение.
Само наличие разных имён не задаёт неравенство. Один параметр сохраняет своё
значение во всех вхождениях и при окончательной проверке. Выбранные значения
не добавляются в базу: конкретное `?p(1);` может оставаться WHO KNOWS.

Текущая граница native capture — до четырёх параметров в одном первичном
существовательном конъюнктивном утверждении. Лимит `witnesses` считает отдельные
выборы по всем проверяемым A–X, B–X и X, а не только количество утверждений.
Значения могут отличаться между независимыми A–X и B–X.

Внутри одного атома пока допустим только один различимый существовательный
параметр, в том числе повторённый: `rel(u,u)` поддержан, а
`!$u $v rel(u,v);` остаётся INCOMPLETE на native-этапе. Это отдельная
незакрытая граница; новая модель её не обходит. Смешанные кванторные префиксы,
функции и более широкие формы всё ещё требуют квалификации.


## Несколько параметров внутри одного атома — этап 496

Предыдущее ограничение этапа 495 на один различимый существовательный параметр
в атоме снято для квалифицированного signed native/model пути:

```text
ctx candidate model write "!$u $v rel(u,v)&&~rel(v,u);"
```

Порядок аргументов и повторения сохраняются: `rel(u,v)`, `rel(v,u)` и
`rel(u,u)` различаются. Два разных параметра могут обозначать одно значение,
если условия этому не противоречат. В данном примере противоположные условия
требуют разных значений. Выбранные значения остаются частью модели; конкретное
`?rel(0,1);` может оставаться WHO KNOWS после повторного открытия базы.

Работают перестановка и проекция параметров в производных правилах, а также
цепочка через независимые контексты с полным сохранением Source-доказательств.
Текущие ограничения capture — четыре параметра в первичной конъюнкции, native
packet rank и остальные бюджеты — сохраняются. Функции и произвольное смешение
кванторов по-прежнему требуют отдельной квалификации. Язык DMZ-запросов и обычный
writer этим этапом автоматически не расширяются.

Поиск модели проверяет обе начальные полярности отношений для каждого текущего
выбора параметров. Это устраняет доказанный пропуск модели в цепочке из трёх
контекстов без увеличения лимитов. Поиск остаётся ограниченным: INCOMPLETE
по-прежнему не означает доказанного противоречия.


## Ранг параметров задаётся бюджетом — этап 497

Пределы capture «четыре параметра», signed-профиля «восемь» и размерности
relational witness/Origin maps «64» убраны. Вместо них используются отдельные
явные бюджеты; значения по умолчанию сохраняют прежнюю нагрузку:

| Параметр | По умолчанию | Что считает |
| --- | ---: | --- |
| `rank` | 8 | Разные Origins в одном signed seed/fact packet и на барьере. |
| `witnesses` | 8 | Выборы исходных параметров по всем интерпретациям X, A–X, B–X. |
| `origins` | 8 | Выборы импортированных Origins по всем интерпретациям. |

```text
ctx candidate model write "!$v0 $v1 $v2 $v3 $v4 $v5 $v6 $v7 $v8 wide(v0,v1,v2,v3,v4,v5,v6,v7,v8);" rank=9 witnesses=9
```

`rank` должен быть положительным; `witnesses` и `origins` могут быть нулевыми.
Увеличение одного лимита не увеличивает остальные. Если в X есть N параметров
и подключены контексты, каждая отдельная интерпретация учитывает свои N выборов;
бюджет `witnesses` может потребоваться больше N. Продукция, зависящая от X и
чужого исходного параметра, требует `origins` в принимающей интерпретации.

Разные Origins могут получить одно значение модели, но при подсчёте native
ранга они остаются разными символическими параметрами. Проверены 5, 9, 17, 65
и 257 параметров; число 257 — размер проверки, а не новый потолок. Все позиции
продолжают учитываться в work/audit бюджетах. Символьные формулы также ограничены
бюджетами обхода и числом клауз; поиск модели остаётся ограниченным.

Заниженный бюджет возвращает INCOMPLETE и ничего не записывает. Доказанный
native-конфликт выявляется до ограничений модельного выбора. Legacy-пути
сохраняют прежний rank8 там, где новый signed request не передан. Обычный writer
не переключён на model write; функции и смешанные кванторы остаются открытыми.


## Причина отказа model write — этап 498

Отчёт `ctx candidate model write` сохраняет текст существующего исключения.
Вместо пустого `null` при превышении бюджета теперь видно, какой этап остановился:

| Упоминание в сообщении | Что проверить |
| --- | --- |
| Native seed rank | Бюджет `rank` для числа разных Origins в пакете. |
| Witness choice | Общий бюджет `witnesses` по всем model cuts. |
| Imported Origin | Бюджет `origins` для принимающих интерпретаций. |
| Basis work | Бюджет `basis-work` подготовки значений. |

Существующий префикс `Runtime error:` может входить в текст причины. Тип
результата определяется строкой `MODEL WRITE`: INCOMPLETE означает остановку
квалификации, REFUTED сопровождается проверенным доказательством конфликта,
NATIVE_REJECTED означает отказ native-компиляции/settlement. Структурированный
API сохраняет поля `phase` и `evidence`. Текст причины помогает выбрать действие;
сам по себе он не заменяет доказательство или новую квалификацию при повторе.

После изменения лимитов команда запускает новую попытку. При отказе исходные
правила и CURRENT сохраняются.


## Прямой конфликт универсальных утверждений — этап 501

Обычная компиляция и проверка текущего контекста теперь отвергают пару
`!@x p(x);` и `!@y ~p(y);`, даже если конкретных значений `p` в базе ещё нет.
Проверка сопоставляет переменные символически, сохраняет повторные позиции
и различает типы значений. Произвольная константа или новый факт не добавляются.
При отказе добавляемое утверждение откатывается; запросы сохраняют прежний путь.

Исправление ограничено прямыми противоположными одиночными утверждениями с
обычными аргументами. Составные запреты и смешанные универсальные/существовательные
кванторы этим не закрыты. Их допуск в DMZ по-прежнему требует отдельной проверки.


## Составные запреты с универсальными посылками — этап 502

Обычная компиляция и проверка текущего контекста теперь отвергают
`!@a @b pair(a,b);` совместно с `!@a ~(pair(a,1)&&pair(a,2));`,
в обоих порядках добавления. Проверяются также запреты, которые замыкаются
несколькими одиночными утверждениями. Общие переменные посылок сохраняют
связь; разные значения не объединяются ради получения конфликта.

При отказе сохраняется полная цепочка: весь запрет, использованные исходные
утверждения и каждый шаг сравнения. Добавляемая операция откатывается целиком.
Перенос такой цепочки как сертификата допуска DMZ требует отдельной проверки.

Исправление охватывает обычные одиночные положительные посылки и запреты без
положительного заключения. Полный вывод по составным правилам, функции и
смешанные универсальные/существовательные кванторы этим не закрыты.
