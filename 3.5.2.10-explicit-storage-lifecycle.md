## Normative invariant

> Transaction lifecycle and physical storage lifecycle do not perform implicit transitions into one another.

Allowed transitions:

```text
CLOSED
    -- use -->
OPEN, level 0

OPEN, level N
    -- commit / rollback -->
OPEN, level N-1

OPEN, level 0
    -- checkpoint / root commit -->
OPEN, level 0 + durable checkpoint

OPEN, level 0
    -- close -->
CLOSED
```

Forbidden transitions:

```text
commit → implicit close
OPEN → use the same database
OPEN → use another database
OPEN, level > 0 → close
checkpoint, level > 0
```

## Core/API ownership

The lifecycle is now owned by `IUser` and implemented by the ordinary Core `User`:

- `IUser.use(IMind, String)` — physical open/create, allowed only from CLOSED;
- `IUser.checkpoint(IMind)` — durable root publication without close;
- `IUser.close(IMind)` — level-zero checkpoint followed by physical close and cleanup.

Server sessions instantiate ordinary `User`. The former `ExplicitLifecycleUser` subclass and server-only `StorageCheckpoint` helper were removed. `ExplicitStorageLifecycleReactor` is now only an earliest protocol adapter: it protects ordering before the historical command processor and translates typed Core exceptions into JSON.

## Durable checkpoint implementation

`User.checkpoint()` intentionally reuses the qualified empty-child root-finalization path. Committing the empty child executes the existing Core sequence:

```text
pack → update → flush
```

without introducing a second publication implementation. Checkpoint does not compact the integrity manifest, close Index/Data, detach storage or clear runtime context. This adapter is now a documented public Core operation rather than a server-private workaround.

## Fix A — commit never closes storage

- nested `commit` transfers the child delta to its parent and decrements the level;
- level-one `commit` transfers the child delta to root and leaves storage open;
- root protocol `commit` invokes the Core durable checkpoint and remains at level zero;
- commit responses are stable protocol results; analyzer output is optional `details` and cannot replace the transaction description;
- `commit` never invokes physical close or storage-context cleanup.

Stable transaction descriptions:

```text
Transaction committed
Transaction rejected
Transaction rolled back
Storage checkpoint completed
```

## Fix B — use requires CLOSED

`User.use()` rejects immediately whenever any database is already open, including the requested database itself. Rejection occurs before target open, integrity validation, protective probe transaction or active-context mutation.

The rejected operation preserves:

- active storage identity;
- active `Mind` identity;
- transaction level;
- source/runtime context;
- target storage bytes and metadata.

An explicit successful `close` is required before any later `use`.

## Fix C — close requires level zero

`User.close()` rejects every active transaction level greater than zero. Rejection does not flush, checkpoint, compact, commit, roll back, clear context or close physical storage. The active transaction remains queryable and must be explicitly committed or rolled back.

At level zero, close performs the Core durable checkpoint, closes physical storage through its normal compaction/close path and clears storage-bound runtime context. Repeated close of an already closed storage is a safe no-op.

## Typed lifecycle errors

The Core exposes stable reasons through `StorageLifecycleException` and `StorageLifecycleErrorCode`, independently of JSON or HTTP:

```text
STORAGE_ALREADY_OPEN
  required_action = EXPLICIT_CLOSE_REQUIRED

ACTIVE_TRANSACTION
  required_action = TRANSACTION_RESOLUTION_REQUIRED

NO_STORAGE_OPEN
```

The server protocol publishes these same codes and required actions without parsing exception text. `NO_ACTIVE_TRANSACTION` remains the distinct transaction-protocol condition and carries legacy compatibility metadata.

## Regression matrix

### Core contract

- server sessions use ordinary `User`, not a lifecycle subclass;
- direct Core use/checkpoint/close obey the same contract as the server path;
- direct repeated use and active-transaction close expose typed exceptions.

### Commit/checkpoint

- root commit does not close storage;
- root commit performs a durable checkpoint;
- repeated root commit is safe;
- root commit without storage returns `NO_STORAGE_OPEN`;
- query and mutation remain available after root commit;
- nested commit descriptions remain stable despite analyzer logs;
- level one to zero commit leaves storage open.

### Use

- same-storage use while open is rejected;
- different-storage use while open is rejected;
- rejection does not open or validate the target;
- active storage, `Mind`, transaction level and source context are unchanged;
- required action is `EXPLICIT_CLOSE_REQUIRED`.

### Close

- level one close is rejected;
- level two-or-greater close is rejected;
- transient rules remain queryable after rejection;
- storage files and active context remain unchanged;
- commit/rollback remain available after rejection;
- required action is `TRANSACTION_RESOLUTION_REQUIRED`.

### Persistence

- commit → explicit close → reopen;
- rollback → explicit close → reopen;
- close → use same database;
- close → use another database;
- nested commit → explicit close → reopen;
- repeated close/reopen cycles;
- reopen integrity validation passes and committed rules remain available.
